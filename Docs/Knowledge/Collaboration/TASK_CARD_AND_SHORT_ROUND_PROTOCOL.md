# 任务卡与短回合排查协议

更新时间：2026-05-19  
适用范围：当前项目里中等复杂度以上、会跨越多个模块或运行时层次的排查、修复与协作任务。  
不适用范围：单文件小修、纯概念讨论、已经明确根因且不需要继续收窄的问题。

## 1. 这份文档解决什么问题

这份文档不解释某个系统当前源码怎么接，也不规定某个系统的运行时真相。

它只回答两件事：

1. 这类任务第一轮应该怎样把问题喂给 AI。
2. 第一轮之后，后续回合怎样继续收窄，避免重新滑回背景补充和自然聊天。

## 2. 当前已经成立的方法边界

当前项目里可以稳定复用的，不是某一次对话中的具体修复点，而是下面四条工作法：

1. 先沿主链收窄，不先围着表象层乱补。
2. 上下文只读最小必要链路，不全仓铺开。
3. 先分清谁持有状态、谁转发、谁消费，再决定动哪一层。
4. 改动完成后立刻切验证，再把经验回灌到知识资产。

## 3. 第一轮默认要写成任务卡

当前这类任务，不建议直接用自然聊天起手。

第一轮至少把下面这些字段钉住：

1. 问题背景
2. 目标
3. 范围
4. 约束
5. 期望产出
6. 验收标准
7. 已知风险
8. 相关知识
9. 相关代码

推荐模板：

```md
任务：
- 用一句话写清这轮要排查或实现什么

问题背景：
- 当前现象
- 已确认事实
- 当前主要怀疑点

目标：
- 这一轮最终要确认什么

范围：
- 只允许看哪些链路/模块/文件

约束：
- 这轮不能动什么
- 不能先走什么补丁路径

期望产出：
- 这一轮先要分析、实现，还是验证

验收标准：
- 什么现象算成功
- 哪些回归必须避免

已知风险：
- 当前最容易误判成什么

相关知识：
- 当前对应系统的 `PROJECT_MAP`
- 当前对应系统的 `DECISIONS`
- 当前对应系统的 `KNOWN_ISSUES`

相关代码：
- 按最小必要链路列出
```

## 4. 后续回合默认走短回合协议

第一轮之后，默认不要继续自由发散。

更稳的顺序是：

1. 分析回合  
   只让 AI 输出事实、判断、未定点、最小改动方案、风险、验证方式。
2. 收窄回合  
   如果出现多个可疑方向，只追一个分歧点，不继续补大段背景。
3. 实施回合  
   只授权最小改动切片，明确哪些文件能动、哪些层不能动。
4. 验证回合  
   代码一改完就切到最小验证清单，不顺手继续扩修。
5. 沉淀回合  
   把现象、误判点、边界决策、验证步骤写回知识资产。

## 5. 默认输出格式也要分层

这类任务里，最容易失控的不是“不会修”，而是把多种目标混在一轮里。

因此默认要求：

1. 分析回合只给分析，不直接改代码。
2. 收窄回合只砍一个分歧点，不再综合重讲。
3. 实施回合只改授权切片，不顺带扩修别层。
4. 验证回合只给验证步骤和失效信号，不继续追加实现。

## 6. 最小必要链路优先于全仓阅读

当前更推荐的做法不是“资料越多越安全”，而是：

1. 先围绕当前现象找主链。
2. 只读取能闭合这个问题的最短代码链和最短知识链。
3. 先确认状态持有者、转发者、消费者分别是谁。

如果这一步没做，后续很容易误把外围表现层当根因，或者把无关模块一起改脏。

## 7. 这类方法应该沉淀到哪里

这份协议本身不替代系统设计文档。

真正落地时，应该拆到：

1. 对应系统的 `PROJECT_MAP`
   记录当前该先看哪条链。
2. 对应系统的 `DECISIONS`
   记录“为什么这类问题当前不优先碰哪一层”。
3. 对应系统的 `KNOWN_ISSUES`
   记录“这个现象最容易被误判成什么”。
4. 后续验证文档
   记录最小验证步骤，而不是只记结论。

## 8. 当前来源与边界

这份协议当前首先从 `Notice/HistoryNotice/AI开发实战案例评估与后续输入策略.md` 提炼而来，但它的适用范围是跨系统协作，不只属于 `AI` 包。

因此它放在 `Docs/Knowledge/Collaboration`，而不是继续留在某个单一系统包里。
