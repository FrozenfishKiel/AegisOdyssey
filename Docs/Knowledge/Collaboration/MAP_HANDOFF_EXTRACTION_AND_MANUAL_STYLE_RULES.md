# 项目MAP交接提炼规则

更新时间：2026-05-19  
适用范围：从 `当前工作进度与项目MAP交接说明-2026-05-12.md` 这类跨系统交接文里提炼长期仍成立的协作规则、阅读入口组织方式、说明书式写法约束。  
不适用范围：把具体某个系统当时的阶段进度直接写成全局现状；替代各系统自己的 `PROJECT_MAP / DECISIONS / KNOWN_ISSUES`。

## 1. 这篇文档解决什么问题

那篇项目 MAP 交接文的价值并不主要在于“2026-05-12 那一轮做到哪”。  
它更重要的长期价值有三类：

1. 跨系统排查时怎样组织“先看什么”。
2. 哪些系统边界属于全项目层面的长期约束。
3. 用户要求的“说明书式文档”到底应该写到什么粒度。

这些内容适合进 `Collaboration`，不适合整篇塞进某一个系统包。

## 2. 从项目 MAP 交接里保留下来的跨系统稳定规则

### 2.1 默认先沿主链收敛，不先围着表象修

跨系统问题默认先回答三件事：

1. 谁持有运行时真相。
2. 谁只负责发起或转发。
3. 谁只负责表现或观察。

如果这三层没分开，后续很容易：

- 把 UI 问题误判成后端状态问题
- 把状态持有者问题误判成节点消费者问题
- 在外围层打补丁把真实边界打乱

### 2.2 “先看哪里”应该被沉淀成系统地图，而不是藏在交接文里

项目 MAP 交接文反复在做一件事：告诉下一位接手者应该先看哪些文档、哪些入口代码。  
这类内容如果长期有效，应该拆回各系统自己的：

- `PROJECT_MAP`
- `DECISIONS`
- `KNOWN_ISSUES`

如果属于跨系统协作方法，则放进 `Collaboration`。  
不应继续让后续接手者反复翻历史交接文找入口。

### 2.3 说明书式文档必须默认回答四类问题

用户对“说明书式文档”的要求，提炼后可以固定成下面四组问题：

1. 在哪里配。
2. 为什么这样配。
3. 不这样配会出现什么现象。
4. 结果不对时，第一步先查哪里。

如果一篇“接入说明 / 验收说明 / 配置说明”没有回答这四组问题，它通常还不算真正可执行的说明书。

### 2.4 阶段交接里的“阅读顺序”不应和系统真相正文混写

项目 MAP 交接文里有大量“下一个 AI 开工前先看什么”的内容。  
这类内容本身有价值，但它描述的是：

- 接手顺序
- 阅读顺序
- 排查顺序

而不是某个系统当前运行时真相。  
所以它应当被拆成：

- 系统内稳定入口，回填 `PROJECT_MAP`
- 协作顺序方法，回填 `Collaboration`

而不是直接混在系统正文里。

## 3. 这篇交接文里可回填到各系统的稳定边界

### 3.1 `HarvestSystem`

长期成立的不是“当时正在做采集”，而是下面这些跨系统边界：

- 采集命中时序应尽量与战斗一样，按动画窗口驱动理解。
- 工具未来既可能采集，也可能攻击，所以输入、状态树、动画时序、命中窗口这些层最好按统一语义组织。

这类内容应分别回填到 `HarvestSystem` 和相关 `StateTreeAI / CombatSystem` 的结构说明里，而不是作为项目阶段口号保留。

### 3.2 `InventoryEquipment`

长期成立的不是“当时正在整理库存右键和快捷栏”，而是：

- 库存组件只提供使用入口。
- 能不能用、怎么用、用了消耗多少，属于物品实例自己决定。
- 不要为了短期方便，把物品语义重新塞回库存层。

这已经是项目级长期边界，应继续作为库存与装备类文档的顶层约束。

### 3.3 `StateTreeAI`

长期成立的不是“当时哪一轮在处理状态树”，而是：

- 如果想把新玩法接进 `StateTree`，应优先参照现有主链的状态持有、事件发起、节点消费方式。
- 不要先把大量玩法专属配置硬塞回某个 `GA` 或外围蓝图，再反过来补状态树。

### 3.4 `InventoryEquipment` 与 `GameplayFramework`

项目 MAP 交接文里关于 `GAS Scope Lock` 的价值，不在“提醒看那篇文”，而在：

- 动态授予能力后立刻依赖“可激活能力列表已刷新”是高风险模式。
- 遇到这类问题，优先先确认 GAS 运行时边界，再决定是保留动态授予，还是改成常驻能力加 `GameplayEvent` 触发。

## 4. 当前适合继续保留在 `Collaboration` 的方法论结论

### 4.1 项目 MAP 交接文适合做“线索导航”，不适合做“现行规格”

这类文档可以保留为：

- 线索总览
- 历史阶段判断
- 接手顺序建议

但不应直接当成：

- 当前系统实现说明
- 当前源码权威事实
- 当前所有包的现行导航入口

### 4.2 交接文提到的“必须先看哪些文档”应尽量被消解掉

理想状态不是继续维护一篇越来越长的“先看什么”总交接。  
更好的状态是：

- 各系统自己的 `PROJECT_MAP` 能回答本系统先看什么。
- `Collaboration` 能回答跨系统怎么接、怎么分回合、怎么写任务卡。
- `HistoryNotice` 只保留原始历史上下文。

## 5. 说明书式文档的最小模板约束

后续如果继续写“接入说明 / 配置说明 / 验收说明”，默认至少应覆盖：

1. 目标：这篇文档要让程序员完成什么。
2. 入口：先看哪些代码或资产。
3. 配置：需要在哪些位置接线。
4. 现象：配置正确时会看到什么。
5. 失败信号：结果不对时先查哪一步。
6. 边界：这篇文档不回答什么。

这套要求本身不属于某一个系统，而属于整个知识库的写作约束。
