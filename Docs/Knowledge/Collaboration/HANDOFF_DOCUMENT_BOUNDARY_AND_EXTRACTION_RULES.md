# 交接文档边界与拆分规则

更新时间：2026-05-19  
适用范围：`Notice/HistoryNotice` 这类历史交接、当前进度、阶段说明、案例评估、避坑清单类文档。  
不适用范围：已经稳定成形的系统设计正文、外部研究笔记原文。

## 1. 交接文档应该放在哪里

完整原文继续留在：

- `Notice/HistoryNotice`

这里保留的是历史语境、阶段判断、接手提示和当时的讨论上下文，不把它直接当现行规格正文。

## 2. 什么不应该整篇进知识库正文

交接文档通常混了四类东西：

1. 当前真实事实
2. 阶段性判断
3. 未来计划
4. 给下一位接手者的提示

知识库正文通常只吃：

1. 稳定事实
2. 少量仍然成立的边界判断

不直接吃：

1. 阶段性口吻
2. 对话提示
3. 已过期计划

## 3. 拆分后应该放到哪里

推荐默认落点：

1. 稳定结构
   放进对应系统的 `PROJECT_MAP`
2. 锁定边界
   放进对应系统的 `DECISIONS`
3. 已过期说法、误判点、混层风险
   放进对应系统的 `KNOWN_ISSUES`
4. 可复用方法、流程、协作协议
   放进 `Docs/Knowledge/Collaboration`
5. 具体验证步骤
   放进后续验证文档

## 4. 判断标准

一句话判断标准是：

“这句话半年后还应该成立吗？”

- 如果大概率成立，适合进知识库正文。
- 如果只对当时那个阶段成立，不适合直接进正文。
- 如果它是在教下一轮怎么接，而不是在描述系统真相，就更适合进 `Collaboration`。

## 5. 当前整理时默认遵守的规则

1. 原文先当线索，不先当事实。
2. 任何涉及“当前已实现”“默认行为”“当前硬条件”的说法，都要核源码。
3. 任何涉及“先看什么”“下一轮怎么接”“后续输入怎么组织”的内容，优先判断是否应该进入 `Collaboration`。
4. 不把交接文、BUG 案例、设计方案、验收说明混成同一篇成品正文。

## 6. 当前这份规则为什么单独建文档

这套规则已经不只影响 `AI` 包，而是会影响后续：

1. `InteractionSystem` 的进度交接与长期避坑清单
2. `CombatSystem` 的验收说明与 UI 子主题交接
3. `SkillSystem` 的遗留 BUG 交接与跨系统衔接文档
4. `HarvestSystem` 的目录规范与阶段交接文档

因此它不应继续散落在单个系统包里，而应进入跨系统方法区。
