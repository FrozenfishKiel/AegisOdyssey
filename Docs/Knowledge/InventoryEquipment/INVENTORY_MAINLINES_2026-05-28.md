# 库存后续开发主流程

这份短文档只收口一件事：
后续库存相关功能，不应该继续散成“每个系统各走一套”，而应该尽量收敛到两条正式主链。

这里说的不是“所有库存问题都必须走同一条链”，而是说不同语义要各自回到正确的正式入口里，不要混写。

相关方案可以一起看：

## 一、给对象发货，走统一入库链

这条链负责解决的是：
“某个外部系统，要把物品正式送进某个对象身上的库存里。”

典型来源包括：
- 拾取
- 制作产物发放
- 采集奖励发放
- 调试 give 指令
- 后续其他奖励或掉落结算

当前正式入口是：
- `UAOInventoryStatics::TryAddInventoryBatchToActor(...)`

它的职责语义是：
1. 外部系统先把结果翻译成 `FAOInventoryReceiveBatch`
2. 统一交给 `TryAddInventoryBatchToActor(...)`
3. 由目标 Actor 身上的库存组件自己决定谁来接收
4. 当前实现里会先尝试 `QuickBar`
5. 前置尝试失败后，再按统一接收入库优先级继续尝试
6. 最终由具体库存组件执行 `TryAddInventoryBatch(...)`

这条链的核心约束是：
新系统如果只是想让对象“获得物品”，就应该优先复用这条链，而不是自己再写一套加物品逻辑。

## 二、打开别的对象库存并交互，走容器会话链

这条链负责解决的是：
“一个角色去打开另一个对象身上的库存，并进行查看、拖拽、交换、取出、放入。”

当前箱子已经在走这条链，后续“角色看角色库存”也应该继续站在这条链上。

当前正式语义是：
1. 交互系统命中目标对象
2. 服务端校验是否允许打开
3. 创建 `UAOContainerInteractionSessionModel`
4. 会话开始观察目标库存
5. 会话快照以当前正式同步方式下发
6. UI 侧通过 `SubmitCurrentInteractableMutation(...)` 修改目标库存

这条链的核心约束是：
如果需求本质是“打开对象库存并交互”，就不要绕开现有容器会话，去额外发明角色专属 UI、角色专属同步、角色专属 RPC。

## 三、别把“入库”和“开别人的库存”混成一件事

这两个语义很容易在讨论里被混掉，但它们不是同一层问题。

### 1. 入库链

关注的是：
- 物品从哪里来
- 最终怎么进入对象身上的某个库存组件

它不关心：
- 有没有打开库存 UI
- 玩家现在是不是正在查看这个对象

### 2. 容器会话链

关注的是：
- 谁在查看谁
- 是否有权限打开
- 观察哪个目标库存
- UI 如何对目标库存做正式 mutation

它不负责：
- 替外部玩法系统发奖励
- 替采集、制作、掉落决定物品来源

## 四、对象内部的库存计算，不一定走上面两条

还有一类逻辑要单独看待：
对象自己对自己库存做内部统计、搜索、消耗、决策使用。

例如：
- 制作系统统计材料并消耗材料
- AI 决策层扫描自己有哪些可用物品
- 装备系统查找某个组件里当前有什么实例

这类逻辑很多时候直接读取或遍历库存组件集合即可，不需要先走“打开容器会话”，也不一定属于“外部发货入库”。

所以更准确的口径是：
- “给对象发货”收口到统一入库链
- “打开对象库存并交互”收口到容器会话链
- “对象内部运行时库存逻辑”按内部语义直接复用库存组件能力

## 五、后续做需求时的判断口径

以后碰到库存需求，先问自己它属于哪一类：

1. 只是要把物品送进某个对象身上
   走统一入库链
2. 是要打开某个对象身上的库存并交互
   走容器会话链
3. 是对象自己对自己库存做运行时判断、消耗或使用
   直接复用库存组件集合与正式物品语义

这条判断口径如果不先锁住，后面最容易出现的问题就是：
- 奖励系统私写一套入库
- 调试指令私写一套入库
- 角色库存交互私写一套角色专属打开逻辑
- 最后同一个项目里出现三四套表面相似、实际语义不同的库存入口

这也是后续库存系统需要尽量避免的方向。
