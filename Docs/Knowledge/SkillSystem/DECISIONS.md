# 技能系统已锁定设计

更新时间：2026-05-19  
适用范围：当前技能系统对象模型、装配边界、输入边界、来源边界的已锁定结论。  
不适用范围：所有具体技能案例的执行细节、所有 UI bug 和阶段性交接细节。

## 1. 当前已经锁定的中心

当前技能系统的中心已经锁定为：

**技能本身是主语，库存、QuickBar、输入、武器系统都只是能力来源或参考机制。**

这意味着后续默认不再允许把旧系统语义直接反灌为技能系统语义。

## 2. 已锁定对象模型

### 2.1 `SkillDefinition` 不是物品

已经锁定：

- `SkillDefinition` 是独立技能静态定义资产
- 它回答“这是什么技能”
- 它不承担来源物品那一层语义

### 2.2 技能来源和技能本体解耦

已经锁定：

- 技能来源主要由来源物品承接
- 来源物品通过 `SkillSource` 语义提供技能
- “哪个物品提供这个技能”和“这个技能是什么”是两层

### 2.3 `SkillInstance` 是运行时身份对象

已经锁定：

- 一个来源对应一个运行时技能实例
- `SkillInstance` 持有定义、来源、等级、品质、装配状态、槽位和冷却身份

### 2.4 技能槽只表达装配关系

已经锁定：

- 技能槽不是真相本体
- 它只表达当前槽装了哪个实例、对哪个输入标签、在 ASC 上授予了什么

## 3. 已锁定装配边界

### 3.1 技能槽是正式装配层

已经锁定：

- 输入绑定的是技能槽，不是技能名
- 当前技能系统通过固定槽位承接主动技能

### 3.2 主动技能槽不等于“拥有的全部技能”

已经锁定：

- 已装配技能集 != 全部拥有技能
- 背包里未装入槽位的技能来源物品，不自动等于运行时已装配技能

### 3.3 技能槽库存适配层只是投影层

已经锁定：

- `SkillSlotInventoryComponent` 是库存语义适配层
- `SkillComponent` 才是技能运行时真相层

这条边界后续不能被打穿。

## 4. 已锁定输入与触发边界

### 4.1 Hero 链用于统一输入桥接

已经锁定：

- 技能系统仍可复用 Hero 输入广播链

### 4.2 AI / StateTree 不再回灌 Hero 输入

已经锁定：

- 直接技能执行链应走 `SkillComponent -> ASC`
- 不应再把 StateTree 技能触发重新广播回 Hero 输入语义层

## 5. 已锁定冷却与长期状态边界

### 5.1 冷却身份从实例层透出

当前头文件已明确：

- `SkillInstance` 提供冷却身份标签读取入口
- 冷却语义不再由槽位承担

### 5.2 槽位变化不应成为刷新冷却的漏洞

历史方案已经明确这一原则，当前代码结构也支持这个方向：

- 槽位负责装配关系
- 冷却和长期状态应跟实例/技能身份走

这一点后续继续整理交接文档时需要再结合 `.cpp` 细补，但方向已经锁定。

## 6. 已锁定执行结构边界

### 6.1 不再用总 `SkillType` 枚举

当前已经锁定：

- 技能执行差异不通过一个总显式类型枚举驱动
- `SkillDefinition` 当前直接挂一个 `ExecutionDefinition`

### 6.2 执行差异通过多态表达

当前已经落地：

- `UAOSkillExecutionDefinition`
- `UAOSkillProjectileExecutionDefinition`
- `UAOSkillAreaSequenceExecutionDefinition`

这说明“执行语义组合”已经进入正式结构，不再只是历史方案想法。

### 6.3 `SkillGameplayAbility` 父类不再默认包办释放语义

当前头文件已明确：

- 父类故意不再内建“播放动画 -> 等事件 -> 开始执行”的统一默认流程

这条边界很关键：

- 动画时序属于具体技能释放语义
- 不应该由父类替所有技能拍板

## 7. 当前第一轮核对后确认的前进量

这轮核对后确认，`SkillSystem` 当前真实结构已经比早期对象化方案更往前一步：

1. 对象模型已经落地
2. 技能槽库存适配层已经落地
3. 技能 Ability 基类已经落地
4. 执行定义多态层已经落地
5. 至少两类执行结构已经落地

所以后续整理技能系统时，不应该再从“要不要这样设计”开始，而应从“当前已落地结构怎么稳定沉淀与扩展”开始。

## 8. 后续整理时必须遵守的规则

1. 不把 QuickBar、武器系统、玩家输入系统写成技能系统本体。
2. 不把 `SkillSlotInventoryComponent` 写成第二个技能系统。
3. 不把总 `SkillType` 重新写回知识库正文。
4. 不把动画时序问题偷塞回技能父类默认模板。
5. 凡是写“当前已经支持什么执行结构”，都必须先核 `ExecutionDefinition` 和 `AbilityBases`。
