# 技能系统已知边界与历史偏差

更新时间：2026-05-19  
适用范围：当前技能系统第一轮深提炼中已确认的边界、仍未展开整理的部分、容易污染知识库的历史混合内容。  
不适用范围：完整运行时 bug 清单。

## 1. 当前这轮记录什么

这份文档当前主要记录两类东西：

1. 历史超长设计文档中哪些内容不能直接整包沉淀成“当前事实”
2. 当前技能系统整理时最容易混淆的边界

## 2. 当前已确认的整理风险

### 2.1 历史文档把“设计方案”“交接说明”“落地进度”“BUG 修复”混在一起

这在 `SkillSystem` 组尤其明显。

当前两篇超长文档内部已经混入：

- 对象模型设计
- 技能槽库存适配交接
- 输入 bug 修复说明
- 编译通过说明
- 战斗系统衔接说明

这些内容价值都高，但不能在第一轮主骨架文档里混写成一篇。

因此当前知识包已经先拆成：

- `PROJECT_MAP`
- `DECISIONS`
- `EXECUTION_SEMANTICS`

剩下的交接/BUG/战斗衔接内容，后续应单独整理。

### 2.2 “当前是否已经完全落地”必须分层判断

历史文档里很多句子写的是“已经拍板”或“已经完成”，但实际需要区分：

- 是设计边界已锁定
- 还是头文件结构已落地
- 还是 `.cpp` 行为已完全稳定
- 还是蓝图/资源链已全部验收

这一轮我们已经确认：

- 对象模型与执行结构骨架已落地
- 但很多交接、UI、状态树、案例细节还未纳入本轮沉淀

### 2.3 不能把“执行结构多态化”又压回成一个总知识枚举

历史文档已经明确反对显式总 `SkillType`，当前代码也已按这个方向落地。

后续知识整理如果再写回：

- “技能系统当前按 Projectile / AOE / Chain / BossSpecial 四大类驱动”

这就属于知识污染。

## 3. 当前最容易误判的边界

### 3.1 把 `SkillSlotInventoryComponent` 当成技能真相层

当前不是。

它只是库存语义适配层。

### 3.2 把 `SkillDefinition` 当成来源物品定义

当前不是。

`SkillDefinition` 是技能静态定义，来源物品仍是另一层。

### 3.3 把技能父类当成统一释放模板

当前也不是。

父类已经明确不再默认接管“播动画 -> 等事件 -> 开始执行”的完整释放语义。

## 4. 当前仍待后续继续整理的高价值内容

以下内容都在历史文档里，但不在本轮主骨架沉淀范围内：

1. 技能槽库存适配层交接与正式使用说明
2. 技能输入映射 / 键位显示 / 长按重复触发的修复说明
3. 火球术与火山喷发案例链路
4. 技能系统与战斗系统正式衔接口径
5. 状态树触发技能槽命令链

这些都适合在后续继续按“每轮深提炼”方式单独整理。

## 5. 当前整理规则

后续往 `Docs/Knowledge/SkillSystem` 继续提炼时，默认遵守：

1. 先把对象层、执行层、交接层、BUG 层拆开。
2. 不把阶段性验收说明直接当成长效知识正文。
3. 任何涉及“当前已落地”的说法，优先核头文件和对应 `.cpp`。
4. 任何涉及“当前案例是否已完成”的说法，必要时单独开案例文档，不挤进主骨架页。
