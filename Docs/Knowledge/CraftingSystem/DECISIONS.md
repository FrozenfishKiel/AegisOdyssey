# 制造系统已锁定设计
更新时间：2026-05-28

这份文档只记录当前已经锁死的设计，不写推测，不写历史残留说法。

相关文档：

- [[Crafting UI Refresh Refactor Plan]]

- [[Crafting System Known Issues]]

## 1. 当前先落角色制造，不把工作台逻辑混进来

当前首版先收角色身上的制造系统。

这不代表未来不能做工作台上下文，而是说这轮已经落地的主链，默认入口仍然是角色自己的 `UAOCraftingComponent`。后续如果扩工作台，也必须建立在当前这条清晰主链之上，而不是把现在的角色制造重新打散。

## 2. 物品身份只认 `ItemId`

当前锁定：

- 物品身份只认 `ItemId`
- 物品总表负责 `ItemId -> ItemDefinition`
- 制造系统不再发明第二套并行物品身份

所以配方里的材料和产物，组织方式都必须围绕 `ItemId`。

## 3. 制造配方现在是角色侧单表

当前锁定：

- `UAOPawnData` 只有一个制造表入口 `CraftingRecipeDataTable`
- 不再有 `CraftingRecipeSourceDataTable`
- 不再有“角色来源表 + 全局配方表”的双表结构

配方能不能做、配方长什么样、排序和解锁怎么判，全部都应从这张角色侧单表读取。

## 4. `AOGameData` 只负责物品总表

当前锁定：

- `AOGameData` 保留 `ItemCatalogDataTable`
- `AOGameData` 不再持有制造配方表
- 制造系统通过它只做物品定义解析，不做配方规则解析

## 5. 材料扫描范围是角色允许参与制造的全部库存

当前锁定：

- 不是只看背包
- 不是只看某一个库存组件
- 当前角色制造需要扫描角色身上允许参与制造的全部库存集合

所以后续文档、测试和代码 review 里，只要提到“材料池”，都应该按这个口径写。

## 6. 制造采用队列制，入队即扣料

当前锁定：

- 制造是队列制
- 成功入队时立即扣料
- 不是完成时再扣
- 不是开始播放时再扣

这代表服务端已经把制造看成正式的消耗行为，而不是 UI 假扣料。

## 7. 当前不支持中途取消

当前锁定：

- 制造队列不支持中途取消
- 因为不支持取消，所以当前不做取消返还链

后续如果要扩这个能力，必须明确新增一条完整的回滚规则，而不是在 UI 上先补一个取消按钮。

## 8. 中断或死亡时，先按清空队列且不返还材料处理

当前锁定：

- 角色异常中断或死亡时，先清空制造队列
- 已扣材料不返还

这是一条当前玩法边界。除非整体规则明确变更，否则不要在局部代码里偷偷改成部分返还。

## 9. 制造完成先尝试统一入库，失败再掉落

当前锁定：

- 制造完成后先走统一库存接收入口
- 如果不能正常进包，再把产物掉到角色脚下
- 当前掉落边界先按“五分钟、可拾取、不做所有权保护”理解

## 10. 制造耗时读取统一加成属性

当前锁定：

- 制造耗时受角色总制造速度加成影响
- 当前属性名是 `CraftingSpeedBonus`
- 最终时长由制造组件解析，不由 UI 或外部临时字段硬算

## 11. 制造 UI 继续通过 MVVM 收口

当前锁定：

- `UMVVM_Crafting` 是制造 UI 的统一 ViewModel
- 选中配方由 ViewModel 维护
- 制造请求通过 ViewModel 发起
- Widget 不应绕开 ViewModel 直接摸底层

## 12. ViewModel 直接观察底层，不要镜像层

当前锁定：

- `UMVVM_Crafting` 直接观察 `UAOCraftingComponent`
- HUD 只做绑定桥
- 不再保留额外快照层、镜像层、中转层

这条改动会影响后续所有制造 UI 扩展，是必须持续守住的边界。

## 13. 联机下制造事实只认服务端，客户端只负责发起和显示

当前锁定：

- 客户端负责发起制造请求、打开菜单、显示反馈和展示自己观察到的制造结果
- 客户端不负责最终裁决这次请求是否成功、何时开始、何时结束、还剩多少次
- 服务端负责真正的制造事实：
  - 是否接受请求
  - 实际可制造数量
  - 队列项何时进入 `Active`
  - `StartServerWorldTimeSeconds`
  - `ExpectedFinishServerWorldTimeSeconds`
  - `RemainingCraftCount`
  - 每完成 1 个时的产物发放与后续推进

所以以后不管是玩家自身制造，还是工作台、熔炉、烹饪锅制造，只要进入正式制造队列，这部分真相都应继续由服务端持有。不要在某个制造源上偷偷改成客户端本地裁决。

## 14. 联机进度条必须使用服务端时间基准，不能混用客户端本地世界时间

当前锁定：

- 制造队列里的 `StartServerWorldTimeSeconds` 和 `ExpectedFinishServerWorldTimeSeconds` 语义上就是服务端权威时间戳
- 客户端可以本地持续刷新 `ProgressBar`
- 但客户端计算正式进度百分比时，必须建立在可对齐的服务端时间基准上
- 不能再把服务端写入的开始/结束时间，和客户端本地 `World->GetTimeSeconds()` 混着算

这条边界是这次 Dedicated Server 远端客户端进度条问题真正收出来的结论。以后如果别的制造对象也复用当前队列 UI，默认也必须遵守这条规则。

## 15. 请求后立即刷新只代表本地反馈更新，不代表权威队列时间已经到位

当前锁定：

- 客户端请求制造后，可以立即刷新本地反馈文案
- 这次立即刷新不代表权威队列时间已经复制到客户端
- 队列里到底有没有正式开始这一批制造，当前批次开始/结束时间是什么，仍然要等服务端队列快照同步回来
- 如果当前客户端还没拿到权威开始/结束时间，正式进度条可以先保持 `0`

这条规则要和上一条连起来理解：客户端可以先表现，但不能先认定时间事实。
