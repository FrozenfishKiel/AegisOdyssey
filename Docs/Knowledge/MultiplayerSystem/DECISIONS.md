# 多人联机系统已锁定设计
更新时间：2026-06-04

这份文档只记录当前已经锁定的判断，不写猜测，不写过程讨论。

相关文档：
- [[Multiplayer System Project Map]]
- [[Multiplayer System Known Issues]]
- [[Multiplayer System Current State 2026-06-04]]

## 1. 首发语境锁定为 Steam PC

当前多人联机讨论的首发场景，已经收敛到：

1. `Steam`
2. `PC-only`
3. 以互联网联机为主

这意味着当前阶段不按主机跨平台联机去设计，也不按超大范围平台无关抽象去设计。

## 2. 当前真正关心的是服务器承载方式，不是单纯 LAN 还是公网

当前锁定的认知边界是：

1. `LAN / Internet` 是网络范围维度
2. `Listen Server / Dedicated Server` 是服务器承载方式维度

所以后续讨论“创建游戏”“加入游戏”“服务器列表”时，不能再把这些概念混成一件事。

## 3. 项目长期形态应当允许两种承载方式并存

当前锁定的产品形态是：

1. 玩家自托管一局，朋友加入
2. 独立服务器托管一局，玩家去连接它

这意味着项目不应被设计成只适合单一联机承载方式。

## 4. 首版目标不是大规模官方服运营

当前锁定的现实边界是：

1. 当前阶段不追求高成本大型官方服务器运营
2. 当前阶段优先低成本、可验证、可演示的多人闭环
3. 工程结构必须预留 Dedicated Server 升级路径

## 5. 首版联机 MVP 优先是互联网下的玩家自托管闭环

当前锁定的首版主路线是：

1. 打包后的正式客户端可进入多人入口
2. 玩家可以创建一局
3. 另一名玩家可以加入这局
4. 两人进入同一张地图并完成基础游玩

这里的主线在技术语义上更接近 `Listen Server`，但产品上不必直接对玩家暴露这个术语。

## 6. Dedicated Server 不是首版运营目标，但必须是工程预留方向

当前锁定的判断是：

1. 第一阶段不强求立刻做正式官方 DS 运营
2. 但项目工程迟早必须补上独立的 `Server Target`
3. Dedicated Server 基线不能一直拖到最后才第一次验证

## 7. 多人系统不应直接散在 Widget 里

当前锁定的系统边界是：

1. Widget 只负责表现和输入响应
2. 项目层需要一层联机协调逻辑
3. 会话与登录底层优先复用 `CommonUser / CommonSession`

换句话说，后面真正落地时应该是：

`多人菜单 -> 项目级联机协调层 -> CommonUser/CommonSession -> GameMode/Experience 世界主链`

## 8. 进入多人对局后继续复用现有 GameMode / Experience 主链

当前锁定的方向是：

1. 不重造一套“多人专用世界初始化框架”
2. 会话成功后进入现有 `AAOGameMode / Experience` 驱动的世界
3. 利用当前已存在的服务端权威玩法同步思路继续往上搭

## 9. 第一阶段最先该动的是工程层，不是大厅 UI

当前锁定的推进顺序是：

1. 先补 `Server Target`
2. 先清理或隔离 Editor-only 构建依赖
3. 先选定最小多人测试地图和最小玩法链
4. 先验证 `DS 启动 + 客户端连接 + 两人进图`

这意味着多人大厅、服务器列表、复杂菜单都不应抢在前面。

## 10. Dedicated Server 的第一轮验证必须先在本地完成

当前锁定的验证路径是：

1. 先本机构建 DS
2. 先本地启动 DS
3. 先本地或局域网验证客户端连接
4. 先确认正式客户端与独立 DS 的最小链路成立

在这一步之前，不应优先去解决云服务器部署问题。
