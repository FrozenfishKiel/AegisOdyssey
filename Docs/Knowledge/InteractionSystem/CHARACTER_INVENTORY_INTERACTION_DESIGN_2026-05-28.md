# 角色库存交互方案

这份方案只讨论一件事：让“角色打开角色身上的库存”正式进入当前项目已有的交互系统与库存系统主链。  
这次不写代码，只锁方案。  
而且这不是要发明一套新的“角色库存系统”，而是要把当前已经被箱子跑通的“对象打开对象库存”能力，正式扩到角色对象上。

这里最重要的一句话先写在最前面：

**角色在这件事里的本质，就是一种可交互容器对象。**

也就是说，后面无论是玩家打开存活 AI 队友库存，还是玩家打开尸体库存，本质都还是：

**交互对象 -> 创建交互会话 -> 观察目标库存 -> 通过正式 mutation 链修改目标库存**

而不是另起一条“角色专用库存 UI / 角色专用同步 / 角色专用 RPC”。

## 这次到底要解决什么问题

当前项目其实已经有“打开别的 Actor 身上库存”的正式样板了，也就是箱子。  
现状不是“架构上做不到”，而是“只把箱子接进去了，角色还没接进去，而且中间残留了一些写死到 Chest / BackPack 的逻辑”。

所以这次真正要解决的是四件事：

1. 让玩家可以通过现有普通交互入口，打开符合条件的角色库存。
2. 让这个行为继续走当前正式的交互会话链，而不是临时直开 UI。
3. 让多人同步继续沿用当前 `InteractionSessionComponent + OwnerOnly Session Snapshot + Mutation` 结构。
4. 在不脱离现有架构的前提下，清理掉当前妨碍“角色即容器”落地的 Chest 专属硬编码。

## 这次方案的边界先锁死

### 1. 正式入口只走现有普通交互选项

这次已经拍板：

- 存活 AI 队友库存的正式入口，走现有交互系统里的普通交互选项。
- 不做单独快捷键入口。
- 不做单独按钮入口。
- debug 指令只是额外测试入口，不和正式入口混用。

这意味着后续实现必须继续站在当前这条主链上：

`Interact Ability -> IInteractableTarget / InteractionOption -> Object-side ExecuteInteraction -> InteractionSessionComponent -> SessionModel -> Session Snapshot -> UI`

而不是在玩家侧自己判断“这是 AI，所以直接弹 AI 库存面板”。

### 2. 不发明新的角色库存系统

这次需求虽然表面是“角色打开角色库存”，但本质没有脱离当前已存在的容器交互架构。  
角色只是从“不可打开的世界对象”变成“可被当作容器打开的世界对象”。

因此这次明确不做：

- 新的“角色库存子系统”
- 新的“角色专用交互会话类型”
- 新的“角色专用库存复制链”
- 新的“角色专用拖拽交换 RPC”

如果后续实现出现这些方向，默认视为脱离方案。

### 3. 不超出现有交互能力边界

这次已经拍板：

- 不额外发明新的距离限制
- 不额外发明新的朝向限制
- 不额外发明新的锁定规则

正式口径就是：

**能被现有普通交互系统扫描到并通过对象侧合法性判断，就能打开。**

因此“活着的 AI 队友是否能开库存”，不由这次方案单独定义一套交互半径或朝向，而是沿用现有交互系统的能力边界。

### 4. 尸体按完整容器交互处理

这次已经拍板：

- 已死亡角色在 Actor 被销毁前，允许打开库存。
- 尸体库存不是“只读查看”。
- 而是按完整容器交互处理。

也就是：

- 可以查看
- 可以拖拽
- 可以交换
- 可以放入
- 可以取出

直到对应角色 / 尸体 Actor 被销毁为止。  
Actor 销毁以后不做额外持久化或虚拟代理补偿，因为那时组件本体已经不存在。

## 正式访问规则

这次方案建议把“角色是否允许被打开库存”收口成目标对象侧访问规则，而不是散落在 UI 层。

当前拍板后的正式规则如下：

### 1. 玩家可查看存活的友方 AI 库存

这是这次需求的核心正式能力。  
前提是该 AI 目标当前可被普通交互系统命中，并通过对象侧合法性判断。

### 2. 玩家不能查看其他玩家库存

这是明确的游戏设计限制。  
这次方案不绕过，不放宽，也不在 UI 层偷开后门。

### 3. 玩家通常不能查看存活敌对角色库存

这里说的是正式游戏规则。  
也就是在 debug 条件未开启时，玩家不能直接查看活着的敌人库存。

### 4. 任意已死亡角色都允许在存续期间被打开库存

这里的“任意”包括：

- 友方
- 敌方
- 其他阵营角色

只要已经死亡，且对应 Actor 还没销毁，就允许把它当作容器目标打开。

### 5. debug 开关开启后，允许突破正式限制

这里的作用只用于开发调试。  
一旦 debug 开关开启，允许玩家查看任意可解析目标角色的库存，包括正常规则下不可查看的存活敌人。

这条调试能力是额外放开的测试入口，不改变正式设计规则。

## 正式架构怎么落

### 1. 继续把目标角色当作可交互容器对象

当前箱子已经证明了“对象打开对象库存”这条链是成立的。  
因此角色侧不应该另发明一套打开方式，而应该具备和箱子相同的正式身份：

- 可参与普通交互扫描
- 可暴露交互选项
- 可在对象侧执行交互
- 可提供库存组件给会话模型观察

这件事的核心不是“角色一定要长得像箱子类”，而是“角色要具备与箱子等价的交互容器语义”。

### 2. 继续复用当前容器会话模型

当前 `UAOContainerInteractionSessionModel` 虽然名字叫 Container，但它的数据形态本质上已经接近通用：

- 记录当前交互对象
- 解析目标对象上的库存组件
- 维护被观察库存快照
- 为 UI 生成统一的可消费数据

因此本次方案的推荐方向不是新增“角色库存会话模型”，而是继续复用当前容器会话模型，让角色库存也作为一种容器会话运行。

这条结论很重要，因为它直接决定了：

- 不需要第二套 OwnerOnly 复制结构
- 不需要第二套客户端会话重建逻辑
- 不需要第二套容器 UI mutation 权限链

### 3. 角色库存打开后，UI 仍然是“自己一侧 + 目标一侧”

这次不建议新做一套“角色库存专用界面”。  
建议继续沿用当前容器交互的 UI 结构，也就是：

- 一侧是玩家自己的库存
- 另一侧是当前目标对象库存

差异只体现在展示信息，不体现在底层系统形态。

也就是说，后面如果目标是角色：

- UI 可以显示角色名
- 可以显示阵营
- 可以显示死亡状态

但这只是“目标对象抬头信息”的展示区别，不能因此把底层交互链拆成两套。

## 多人网络同步怎么定

这次最重要的约束之一，就是**绝不绕开当前正式同步链**。

### 1. 打开请求仍由服务端权威判定

无论是玩家打开 AI 队友库存，还是打开尸体库存，最终都必须由服务端判断是否允许、创建什么会话、同步什么快照。

客户端不能自己本地直接构建一个“角色库存已打开”的假会话。

### 2. 目标库存详情仍然只同步给当前查看者

当前会话快照已经采用 `OwnerOnly` 复制。  
这次方案明确继续沿用这个结构。

因此后续角色库存打开后，也仍然是：

- 世界对象自身状态按正常 Actor / Component 网络模型走
- 当前会话里的库存详情快照，只同步给当前会话拥有者

不允许因为“目标变成角色”就改成把库存详情广播给所有相关客户端。

### 3. 对目标库存的修改继续走当前 mutation 权限链

这点不能退让。  
后续玩家在目标角色库存 UI 里做的：

- 取出
- 放入
- 拖拽交换
- 右键操作

只要语义上属于“修改当前交互对象数据”，都继续走：

- `SubmitCurrentInteractableMutation(...)`
- 当前交互对象 owner 获取
- 排队等待
- 权限就绪后执行

绝不因为“这是角色库存”就再发明一条旁路 RPC。

### 4. 目标角色失效时，会话应当被正式关闭

后续如果目标角色出现下面这些情况：

- Actor 销毁
- 会话条件失效
- 不再允许当前查看者继续访问

应当由服务端关闭当前会话，客户端只消费会话关闭结果。  
不能把这种失效处理留给 UI 自己猜测和补丁兜底。

## 当前已经确认的 Chest 专属残留

这部分非常重要，因为它决定了后续很可能要先改写死逻辑，再继续做角色库存接入。

### 1. 会话关闭时只会向 `AAOChest` 注销观察者

当前 [AOContainerInteractionSessionModel.cpp](D:\UE_Project\AO\AegisOdyssey\AegisOdyssey\Source\AegisOdyssey\Interaction\Session\AOContainerInteractionSessionModel.cpp:41) 里，`DeactivateSession()` 直接：

- `Cast<AAOChest>(InteractableActor)`
- 然后 `Chest->UnregisterObserver(this)`

这意味着当前“观察者解绑”语义仍然写死在 Chest 上。  
如果角色库存也要走容器会话，这里必须抽松。

### 2. 容器访问权限被写成“只允许当前观察者自己的 Backpack”

当前 [AOChest.cpp](D:\UE_Project\AO\AegisOdyssey\AegisOdyssey\Source\AegisOdyssey\Interaction\Containers\AOChest.cpp:141) 里的 `CanInventoryAccessChest(...)`，并不是在判断：

- 这个库存组件是否属于当前合法会话参与者

而是在判断：

- 这个库存组件是不是观察者角色身上的 `UAOBackPackComponent`

这会直接把“对象间正式库存交换”收窄成“箱子 <-> 玩家背包”。

### 3. 无 UI 取物入口被写成“只取到交互者 Backpack”

当前 [AOChest.cpp](D:\UE_Project\AO\AegisOdyssey\AegisOdyssey\Source\AegisOdyssey\Interaction\Containers\AOChest.cpp:213) 的 `TransferItemToInteractorInventory(...)`，默认目标也是 `UAOBackPackComponent`。

这对于箱子样例来说能工作，但它不应继续冒充通用正式入口。

### 4. 双向交换辅助函数仍然是 Chest 中心命名

当前 `TransferChestSlotToInventorySlot(...)` / `TransferInventorySlotToChestSlot(...)` 虽然已经比旧命名清晰，但它们仍然是“Chest 中心”的对象语义。

这不是当前最大阻碍，但如果后续角色库存也走同样链路，这种命名会持续把调用者往“箱子特例”心智上带。

### 5. 当前交互会话复制仍然只认容器会话

这点不是 Chest 专属，但它是现状约束。  
当前 `UAOInteractionSessionComponent` 在复制与客户端重建时，都默认只处理 `UAOContainerInteractionSessionModel`。

对这次方案来说，这不是问题，因为我们本来就推荐继续把角色库存视作容器会话。  
换句话说，这一层当前不需要为了“角色库存”再去抽第二种会话形态。

## 这次方案对后续实现的直接要求

如果后续开始动代码，这次方案要求至少满足下面这些实现方向：

### 1. 先清理妨碍复用的写死逻辑

在把角色库存正式接入前，优先处理：

- `DeactivateSession()` 只认 `AAOChest`
- 容器访问权限只认 `BackPack`
- 无 UI 取物入口只认 `BackPack`

这一步不是额外重构，而是为了避免后面被迫复制一套“角色版箱子逻辑”。

### 2. 角色侧只补正式对象能力，不新开第二套主链

后续角色接入时，重点是补齐：

- 可交互目标身份
- 可提供库存的对象身份
- 对象侧访问规则
- 对象侧观察者维护

而不是在玩家侧写一堆“如果目标是 AI 就特殊打开”的逻辑。

### 3. UI 层只做展示区分，不做架构分叉

目标是角色时，UI 可增加角色信息展示；  
但不能因此让：

- mutation 入口分叉
- 会话复制分叉
- 拖拽交换语义分叉

## 落代码前的前置清理顺序

在正式接角色库存交互之前，先按下面这个顺序处理当前残留的写死逻辑。  
这不是额外扩 scope，而是为了避免后面把 `Chest / BackPack` 特例继续复制到角色库存链里。

### 1. 先做观察者宿主通用化

第一步先处理“谁负责注册 / 注销 / 刷新容器会话观察者”这层。

这一轮要一起改掉两处当前写死：

- `UAOContainerInteractionSessionModel::DeactivateSession()` 只认 `AAOChest`
- `UAOContainerInventoryComponent::BroadCastInventoryChange()` 只认 `AAOChest`

正式口径是：

- 会话关闭时，向“当前交互对象的通用观察者宿主”注销观察者
- 目标库存变化时，由“当前交互对象的通用观察者宿主”刷新观察者

这一步必须最先做，因为如果这层不先抽松，后面角色库存即使能打开，会话关闭与内容刷新也仍然会卡在 Chest 特例上。

### 2. 再做访问权限语义通用化

第二步处理当前 `CanInventoryAccessChest(...)` 只认 `BackPack` 的问题。

这一轮不再按“组件类型是不是 Backpack”判断，而改成按“这个库存组件是否属于当前合法会话参与者”判断。

也就是说，正式语义从：

- `Chest <-> Backpack`

改成：

- `当前被打开的交互对象 <-> 当前合法会话参与者身上的库存组件`

这一步的目标不是立刻发明更复杂的库存策略，而是先把错误的 Backpack 写死去掉，让后续角色库存交互站回会话归属语义上。

### 3. 再处理非 UI 入口

第三步处理 `TransferItemToInteractorInventory(...)` 只把物品送进交互者 `BackPack` 的问题。

这里不建议粗暴删除旧函数，因为它当前是 `BlueprintCallable`，资产侧是否已有依赖还没有核实。  
这一轮的推荐口径是：

- 新增通用正式入口
- 旧 `TransferItemToInteractorInventory(...)` 暂时作为兼容壳保留
- 新功能与后续角色库存逻辑，不再继续依赖这个 `BackPack` 特化入口

这样既能去掉错误默认语义，又不会在未核实蓝图资产引用前直接误伤现有内容。

### 4. 最后顺手收辅助函数命名

第四步再考虑 `TransferChestSlotToInventorySlot(...)` / `TransferInventorySlotToChestSlot(...)` 这种 Chest 中心命名。

这一步优先级不高，原因很明确：

- 它们当前没有 C++ 外部调用点
- 也不是当前角色库存接入的直接阻塞点

所以这里不做“纯为了好看而重命名”的单独动作，而是在前面几步把语义真正抽通以后，再顺手把命名一起收成通用语义。

### 5. 会话复制层这轮不动

第五步不是改，而是明确这轮先不改。

当前 `UAOInteractionSessionComponent` 的复制与客户端重建逻辑，仍然只认 `UAOContainerInteractionSessionModel`。  
对这次需求来说，这一层不是问题，因为本方案本来就要求：

- 角色库存交互继续复用容器会话
- 不新增第二套角色专用会话类型

因此这一轮不为了“看起来更抽象”而提前泛化会话复制结构，避免无意义扩大改动面。

## 这次方案的最终结论

一句话概括：

**这次不是做“角色专用库存系统”，而是让角色正式成为现有交互系统里的可打开容器对象。**

正式入口继续走普通交互。  
存活友方 AI 可开。  
玩家对玩家不可开。  
存活敌人默认不可开，但 debug 可放开。  
死亡角色在 Actor 销毁前按完整容器交互处理。  
多人同步继续复用当前 `InteractionSessionComponent + OwnerOnly Session Snapshot + Mutation` 正式链。  
在真正落角色接入之前，应优先清理当前残留的 Chest / BackPack 写死逻辑，避免后续复制出第二套角色版容器系统。
