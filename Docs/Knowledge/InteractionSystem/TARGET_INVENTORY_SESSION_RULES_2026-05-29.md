# 目标库存会话规则

这份笔记不记录某一次 BUG 的排查过程，只记录这几轮角色库存 / 对象库存交互里已经反复验证过、后面必须继续遵守的核心原则。

它主要回答四件事：

1. 为什么“打开别人的库存并操作”本质上还是容器会话问题。
2. 为什么客户端不能直接改目标库存，必须先走请求与授权。
3. 为什么 UI 不能自己再去拼第二份目标上下文。
4. 后面接工作台库存、交易库存、更多可交互库存时，什么算复用正式路径，什么算重新走偏。

## 一、先锁死一句话：目标库存操作的核心不是 UI，而是会话授权

这几轮真正提炼出来的第一条原则是：

**客户端操作目标库存时，核心链路必须是“客户端发请求 -> 服务端授予当前交互对象的操作资格 -> 等资格到位后再放行正式 mutation”。**

这里的重点不是“先调哪个函数”，而是语义边界：

- 客户端可以表达想操作哪个目标库存、哪个槽位、做什么操作。
- 客户端不能把“我想操作”直接等同于“我已经有权操作”。
- 目标库存的一切正式变更，最终都必须站在当前交互会话已经拿到的权限之上执行。

如果缺了这一步，就会回到曾经那类典型问题：

- 单机看起来能跑。
- listen server 可能不稳定地能跑。
- 真正多客户端时开始出现“第一次能动，后面不能动”。
- 或者直接出现 `No owning connection ... will not be processed` 这种旧链路报错。

所以后面再看类似问题，先不要问“是不是某个格子没刷新”，先问：

**这次目标库存操作，正式执行前有没有真的经过“请求权限、等待权限、权限到位后放行”这一条链。**

## 二、角色库存、箱子库存、工作台库存，本质上都应复用同一类会话路径

第二条原则是：

**“打开对象库存并操作”不是角色特例，也不是箱子特例，而是一类统一问题。**

箱子之所以一直被拿来当对照，不是因为项目只支持箱子，而是因为箱子这条链已经比较成熟：

- 先命中交互对象。
- 由交互对象建立正式会话。
- 会话层托管当前交互目标、权限获取和 mutation 放行。
- UI 只消费这次会话暴露出来的目标库存上下文。

所以角色打开角色库存、角色打开工作台库存、角色打开交易对象库存，后面都应该尽量站在同一类正式路径上理解：

- 不是“每个对象都来一套自己的库存 UI 逻辑”。
- 不是“每多一个对象就多一套特判”。
- 不是“角色库存特殊，交易库存再发明一套，工作台库存再补一套”。

正确理解是：

**箱子只是当前已经跑通的一份成熟样板，不是专用特例。**

如果后面某个新对象接入库存交互时，需要新增一堆：

- `if TargetIsCharacter`
- `if TargetIsWorkbench`
- `if PanelIsTrade`
- `if WidgetIsTargetQuickBar`

那通常就说明不是在复用成熟路径，而是在重新长分叉。

## 三、会话层要统一的是“正式入口”，不是往下给每个子 UI 加补丁

第三条原则是：

**收口应该发生在会话层和正式 mutation 入口，不应该下放到子 UI、子面板、子槽位各自打补丁。**

这条原则背后有两个很重要的判断。

### 1. 会话层应该托管什么

会话层真正该托管的是：

- 当前正在和哪个交互对象建立会话。
- 当前目标侧哪些库存属于这次会话的正式上下文。
- 当前是否已经拿到可执行目标 mutation 的资格。
- 未拿到资格时，哪些请求需要排队等待。
- 资格到位后，如何把这些请求放进正式执行入口。

也就是说，会话层负责的是“正式入口的统一调度”。

### 2. 会话层不该长成什么

会话层不应该长成：

- 每多一个对象就加一堆对象专属字段。
- 每多一个 UI 就加一套面板专属判断。
- 每多一个库存类型就往会话组件里硬编码一个新分支。

同样，子 UI 也不应该长成：

- 每个控件自己判断 self / target。
- 每个格子自己决定该走自用还是目标会话。
- 每个面板自己再去对象身上 `FindComponentByClass` 补第二份上下文。

一旦开始这么做，就说明方案开始从“统一正式入口”退化成“各层自己修自己的洞”。

## 四、UI 只消费会话给出的目标上下文，不能自己再拼第二份事实源

第四条原则是：

**目标侧 UI 的职责是消费会话上下文，不是重建会话上下文。**

这条原则是这几轮里最容易反复走偏的点。

只要是目标库存显示区，无论是：

- 背包
- 快捷栏
- 容器栏
- 未来交易区
- 未来工作台区

它们都不应该自己回答下面这些问题：

- 当前到底在看谁。
- 目标侧哪些库存属于这次会话。
- 哪个库存允许操作，哪个库存只是展示。

这些答案应该先在正式会话上下文里成立，然后 UI 只是消费结果。

否则就会出现典型错位：

- 显示链看起来已经打开的是目标库存。
- 但执行链仍然偷偷落回玩家自身库存语义。
- 或者显示层和 mutation 层各自认的“目标”不是同一个东西。

BUG2 暴露出来的本质就是这个问题：

**目标侧槽位的显示不一定错，但执行语义可能已经串回了玩家自身操作链。**

所以后面排查“目标侧点一下为什么触发自己用物品”时，优先看执行链有没有脱离正式会话上下文，不要先把问题理解成“UI 绑错库存”。

## 五、只要最后又掉回目标组件 RPC，这条链就还没真正统一

第五条原则是：

**目标库存 mutation 如果最后还是让客户端直接去调用目标 Actor 身上的旧组件 RPC，那就说明这条链还没有真正收口到会话方案。**

这一条可以作为很实用的验收口径。

看起来已经“走了会话”的实现，如果最后依然是：

- 客户端直接对目标库存组件发 RPC。
- 客户端直接对目标角色的库存组件发 `WhenItemExchange` / 同类旧入口。
- 只是在前面多包了一层“看起来像会话”的调用。

那本质上仍然是旧语义，只是外面套了个壳。

这类实现短期可能在本地能工作，但它没有真正解决多人权限问题。

所以对目标库存操作来说，真正要复用的是：

- 成熟的请求权限时机。
- 成熟的等待与排队语义。
- 成熟的正式服务端执行入口。

不是只复用“打开 UI”那半条链。

## 六、未来接更多库存对象时，先问这几个问题

后面如果再接工作台、交易、尸体、商店、更多角色对象，可以先用这组问题做自检。

### 1. 这次是在复用正式路径，还是在长特例

先问：

- 这次目标库存操作是不是仍然遵守“请求权限 -> 等权限 -> 放行 mutation”？
- 这次目标上下文是不是仍然由正式会话统一给出？
- UI 是不是只消费会话结果，而没有自己补目标解析？

只要其中有一个答案是否，就要警惕已经开始长分叉。

### 2. 这次改动是否依赖对象名、面板名、控件名硬编码

再问：

- 未来如果再来一千两百万个对象，是不是还要继续补 `if`？
- 未来如果再多一种库存面板，是不是还得再手写一套判断？
- 这次接入新对象，主要是在接正式上下文，还是在复制一套新执行逻辑？

如果答案偏向后者，就不符合当前方案方向。

### 3. 这次改动能不能同时解释单机和多人

最后问：

- 单机能跑，是因为逻辑真的对了，还是因为权限问题被掩盖了？
- 多客户端下，第二个客户端是不是还能通过同一条路径拿到权限并操作？
- 当前实现能不能解释为什么不会再出现 `No owning connection` 这一类旧报错？

如果不能同时解释单机和多人，那就说明这条知识还没落到正式路径上。

## 七、给后续接手者的最短结论

把这几轮的核心压成最短的几句话，就是：

1. 目标库存交互的核心不是“打开了哪个 UI”，而是“当前会话是否正式拿到了目标 mutation 资格”。
2. 箱子链路是成熟样板，不是对象特例；角色、工作台、交易都应尽量复用同类路径。
3. 会话层要统一的是正式入口和授权调度，不是往每个子 UI、子槽位下放补丁。
4. UI 只消费会话给出的目标上下文，不能自己再拼第二份事实源。
5. 只要最后还在让客户端直接调目标库存组件旧 RPC，这条链就还没有真正统一。
