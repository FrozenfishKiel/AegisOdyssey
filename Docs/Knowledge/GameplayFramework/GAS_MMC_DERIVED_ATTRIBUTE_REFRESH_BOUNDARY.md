# GAS MMC 派生属性刷新边界

更新时间：2026-05-20  
适用范围：当前项目里“来源属性集 -> MMC -> 最终战斗属性”这条派生属性链的现状、误判点和后续排查边界。  
不适用范围：所有具体装备资产的配表细节；把某一轮阶段性交接里的修法直接当成当前统一方案。

## 1. 这份文档记录什么

这份文档只回答四件事：

1. 这次所谓“MMC 不计算”到底指的是什么现象。
2. 到目前为止，哪些结论已经确认，哪些只是阶段怀疑。
3. 这轮已经明确不继续走哪些方向。
4. 后续如果继续查，应该先从哪条链排，不要再怎么走偏。

## 2. 当前问题的准确描述

当前问题不能简单写成“MMC 失效”，更不能写成“GAS 不支持这种做法”。

更准确的说法应该是：

**项目里一条基于来源属性集、派生属性 GE 和 `MMC` 的最终属性计算链，在来源属性已经变化的前提下，最终战斗属性没有按预期联动刷新。**

也就是说，现在看到的现象是：

1. 武器或正式装备带来的来源属性值本身可以变化。
2. 这些来源属性并不是直接给角色最终属性，而是要先经过 `MMC`。
3. 但角色最终真正参与战斗和 HUD 展示的那批属性，没有稳定跟着动起来。

## 3. 当前已经确认的事实

### 3.1 角色最终属性仍然在最终属性集上

当前项目这条线的基本设计没有变。

也就是：

1. 角色最终战斗属性仍然在 `UAOCombatAttributeSet` 这一层。
2. 武器和正式装备只负责提供来源属性。
3. `MMC` 负责把角色基础属性、武器来源属性、正式装备来源属性一起折算成最终值。

### 3.2 来源属性集已经拆开了

当前已经确认的来源属性集是：

1. `UAOWeaponAttributeSet`
2. `UAOEquipmentAttributeSet`

它们的职责是“保存动态装备来源属性”，而不是替代角色最终属性集。

### 3.3 `AbilitySet.AttributeSets` 已恢复为有效授予链

当前已经回到：

`PawnData -> AbilitySets -> AbilitySet.AttributeSets`

这条链。

也就是说：

1. `AbilitySet` 里的 `AttributeSets` 不是摆设。
2. 它负责确保这批依赖属性集在当前 ASC 上可用。
3. 不需要也不应该再单独起第二条 `StartupAttributeSets` 旁路。

### 3.4 `AbilitySet.AttributeSets` 的回收语义已经收紧

这一轮已经确认：

1. `AbilitySet.AttributeSets` 只负责“确保属性集可用”。
2. `FAOAbilitySet_GrantedHandles` 只回收 `Ability` 和 `GameplayEffect`。
3. 不再把共享 `AttributeSet` 实例绑进某次授予句柄的对称回收语义里。

这条边界非常重要，因为它直接避免了“多个授予链共享同类 AttributeSet 时，被其中一条回收误删”的问题。

## 4. 当前已经被否掉的方向

### 4.1 不再继续走动态增删 AttributeSet 的运行时拓扑方案

这一轮已经明确回退，不再继续推进：

1. `AcquireDynamicAttributeSet(...)`
2. `ReleaseDynamicAttributeSet(...)`
3. 基于拓扑变化再去统一协调派生属性 GE

原因不是这条路永远理论错误，而是它在当前项目里已经明显开始把问题越做越复杂，而且还没有真正打通派生链。

### 4.2 不再增加第二条属性集配置路径

这一轮也已经明确否掉：

1. `PawnData.StartupAttributeSets`
2. 任何绕开 `AbilitySet.AttributeSets` 的第二条初始化入口

原因很简单：

`AbilitySet` 本来就承担“授予包里需要哪些 Ability / GameplayEffect / AttributeSet”这层职责。

如果再单独起一条配置路径，只会继续制造系统语义分裂。

### 4.3 不再把共享 AttributeSet 当成某次授予链的私有实例

这次已经明确收口：

1. 共享 AttributeSet 可以被多个授予链复用。
2. 既然是共享实例，就不能再用“谁授予谁回收实例”的思路套它。
3. `AbilitySet.AttributeSets` 当前只负责“确保存在”，不负责“对称删除”。

## 5. 当前最需要警惕的几个误判

### 5.1 不要把问题写成“MMC 根本不支持这种派生玩法”

当前不能这么下结论。

因为现在真正没解释清楚的，不是 `MMC` 有没有表达能力，而是：

1. 当前承载它的派生属性 GE 到底有没有稳定工作。
2. 来源属性变化之后，GAS 内部依赖刷新链到底有没有真的被打通。

### 5.2 不要因为不想手动刷新，就重新把动态拓扑方案捡回来

当前也不能这样做。

这条路这轮已经走过，而且已经证明：

1. 它会把业务层、ASC 层和属性集生命周期层重新混在一起。
2. 它会继续放大系统复杂度。
3. 但它并没有真正给当前 MMC 联动问题带来确定解法。

### 5.3 不要把阶段性资产名硬写成框架层事实

这次排查过程中提到过一些阶段性资产名，比如某个具体派生 GE。

后续继续沉淀知识库时，默认不要把这类资产名直接升成框架结论。

原因是：

1. 它们可能是当前角色专用。
2. 它们可能还会被清理或替换。
3. 知识库应该记录“承载派生属性计算的那类 GE”，而不是把某个临时资产名写死成普适机制。

### 5.4 不要把 `GE_CombatDerivedAttributes` 再当成当前有效主链

这次排查里已经明确过：

1. 它没有承担当前真正有效的初始化和派生职责。
2. 它只会给后续阅读者制造“是不是这里还藏了一层逻辑”的误导。

所以当前知识口径里，不再把它当成现行主链的一部分。

## 6. 当前真正未解的缺口

这才是后续继续排查时真正要盯住的地方。

### 6.1 当前承载派生属性的 active GE 到底是哪一个

后续先别抽象空谈，先确认：

1. 当前运行时到底是哪一个 active GE 在给最终属性提供 `MMC` 结果。
2. 它的 handle 能不能稳定拿到。
3. 它的 modifier 到底是不是作用在你正在观察的那批最终属性上。

### 6.2 来源属性变化之后，对应 aggregator 到底有没有真的变脏

这是当前最关键的现实问题之一。

因为现在的表象并不是“来源属性没写进去”，而更像是：

1. 值看起来变了。
2. 但依赖刷新链没有最终推动派生结果更新出来。

所以后续要继续盯：

1. 当前写值路径到底有没有真的进入 GAS 聚合链。
2. 相关 aggregator 在这次写值后有没有变脏。

### 6.3 就算变脏了，为什么最终属性还是没动

如果后续确认 aggregator 已经变脏，那问题就会继续收口到：

1. 承载 `MMC` 的 active GE 有没有收到依赖变化。
2. 它有没有重新计算自己的 modifier magnitude。
3. 重新计算之后，为什么最终聚合结果仍然没反映到 `UAOCombatAttributeSet`。

## 7. 当前推荐的继续排查顺序

如果后续继续接这块，当前推荐顺序是：

1. 先确认当前实际承载派生计算的 active GE。
2. 再确认来源属性变化时，相关属性聚合器有没有真正进入 dirty 链。
3. 再确认这次 dirty 有没有推动 active GE 重新算 modifier。
4. 最后再看是否有旧资产引用、旧 GE、旧初始化路径把结果覆盖掉。

## 8. 当前已落下来的稳定结论

这篇文档最后要保留的，不是某一轮阶段性怀疑，而是下面几条长期有效的边界：

1. 装备和武器来源属性集仍然有价值，但它们不再走运行时动态增删 AttributeSet 的方向。
2. `AbilitySet.AttributeSets` 当前应继续保留为正式授予链的一部分。
3. `AbilitySet.AttributeSets` 只负责“确保可用”，不再承担共享 AttributeSet 的对称回收语义。
4. 当前真正未解的是派生属性刷新链，而不是正式装备五槽系统本身。
5. 后续继续排查时，优先查“派生 GE / 属性聚合链 / dirty 传播”，不要再重新发明一套属性集生命周期方案。
