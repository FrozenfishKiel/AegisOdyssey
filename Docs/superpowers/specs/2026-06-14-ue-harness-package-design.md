# UE Harness 能力包技术方案

更新时间：2026-06-14

## 1. 方案定位

这份方案描述的不是 Unreal Engine 编辑器插件，也不是游戏运行时模块。
它描述的是一套给 `Codex`、`Claude Code` 这类 AI 编码环境使用的 `UE Harness` 能力包，用来把 AI 放进一套可持续的工程系统里工作。

这套方案的最高优先级不是“把多 agent 编排得更复杂”，也不是“让 AI 更听话”，而是确保它不脱离原始文章《Harness与AI游戏开发：为什么马再好，不套上鞍具它也拉不了车》的核心思想：

- `Agent = Model + Harness`
- Harness 不是 prompt，也不是超长提示词
- Harness 是规则、流程、验证、感知、记忆、版本历史和反馈闭环共同组成的工程系统

因此，本方案的重点不是描述某一种具体的 agent 调度框架，而是先定义 Harness 本体，再说明哪些实现策略可以承载它。

## 2. 修正前方案的已确认偏移

和原文、场景化笔记、Harness 入口说明对照后，当前旧稿存在以下偏移：

- 当前方案把 Harness 的重心放到了多 agent 编排、主 agent 与子 agent 分工、写权限和成本优化上。
- 当前方案把 `SubAgent` 写成了方案主体，而不是五个核心组件之一。
- 当前方案对 `MCP` 的定义过弱，更多停留在 adapter、路径和文件约定，没有把“AI 能看到什么项目上下文”提升到顶层。
- 当前方案没有把“版本控制”提升到顶层定义，只在局部作为辅助条件出现。
- 当前方案没有把“开发自循环”作为方案主轴展开，而是被压缩进流程和交付里。
- 当前方案结论把 Harness 收缩成了“统一入口 + 主 agent 单点写权限 + 低成本子 agent 承担旁路任务”的编排系统定义，这和原文主轴不一致。

这份修正版将保留“能力包”这个题目方向，但会把上述偏移收回来。

## 3. Harness 定义

Harness 的定义不是“给 agent 加一点规则”，也不是“做一个更长的系统提示词”。

Harness 的定义是：

> 给 AI Agent 套上一套工程系统，让它的输出稳定、可靠、可追踪，并且能在下一轮任务里继续复用之前的规则、上下文和记忆。

换句话说，Harness 要解决的不是“AI 会不会做单点任务”，而是“AI 能不能被放进一条真正可持续的开发流水线”。

在这一定义里：

- `Model` 是能力来源
- `Harness` 是让能力稳定落地的工程系统

没有 Harness 的模型，哪怕单点能力很强，也容易出现：

- 规则靠人反复提醒
- 上下文只存在聊天记录里
- 做完这轮，下轮重新开始
- 能写代码，但环节之间咬不住

## 4. 原文核心映射

原文主轴可以映射成以下几层：

### 4.1 三个阶段

AI 驱动开发分三个阶段：

1. Prompt 时代  
   规则在人脑里，靠反复写提示词。
2. Context 时代  
   开始喂文档和代码，但上下文仍然是临时的，做完容易忘。
3. Harness 时代  
   规则、流程、验证、记忆和反馈闭环进入工程系统，AI 开始具备长期稳定工作能力。

### 4.2 五个核心组件

Harness 的核心组件是：

- `Rule`
- `Skill`
- `Script`
- `SubAgent`
- `MCP`

而 `Memory` 在原文和场景化解释里与 `MCP` 一起承担“可见性 + 可沉淀”的关键职责，因此在本方案中会单独成章展开。

### 4.3 小团队三步法

原文给小团队的落地路径是：

1. 先做原型，验证核心玩法
2. 接入版本控制
3. 搭开发自循环

本方案面向的是“跨 UE 项目复用”的能力包，因此必须完整保留这三步法。

如果当前落地场景是一个已经持续开发中的 UE 项目，那么文档重点可以放在第 2 步和第 3 步，也就是版本控制、项目可见性和开发自循环上。
但这属于场景适配，不是对原文第一步的删除。

### 4.4 最终目标

Harness 的目标不是一次性把某轮任务做完，而是形成一个不断复用的开发自循环：

1. 读取上下文
2. 执行任务
3. 验证结果
4. 沉淀文档
5. 记录记忆
6. 下一轮继续读取这些沉淀

## 5. Rule

`Rule` 解决的是“AI 在动手之前，应该先知道什么”。

规则的定位不是知识库总目录，也不是大而全手册，而是最关键的硬约束。

根据原文和笔记，Rule 的设计要求应该是：

- 数量少
- 约束硬
- 事前生效
- 不写愿望清单

在 UE 场景下，Rule 可以约束：

- 核心函数和关键属性必须有中文注释
- 改动系统后必须补技术文档
- 改动后必须补冷启动测试文档
- 涉及蓝图交互时必须写清 C++ 类、蓝图父类和编辑器接线位置

但 Rule 不应该承载：

- 完整任务流
- 验证过程细节
- 项目全部背景知识

这些应由其他组件承担。

## 6. Skill / Task Flow

`Skill` 解决的是“AI 接到任务后应该按什么顺序做”。

它不是单条规则，也不是最后验收，而是高频交付动作的固定工作流。

对于 UE 场景，Skill 的本质作用是防止 AI 每次临时拼装自己的做事顺序，导致：

- 有时先写代码
- 有时先改文档
- 有时没有验证
- 有时没有归档

能力包应提供一个统一入口 skill，用来保证任务先进入 Harness，再进入执行。

其主链至少应包含：

1. 读取规则
2. 读取项目上下文
3. 拆解需求
4. 确认影响范围
5. 完成实现
6. 执行验证
7. 补技术文档
8. 补测试文档
9. 沉淀记忆

这里要特别强调：

- Skill 是流程，不是 prompt
- Skill 是可反复执行的稳定顺序，不是某次聊天中的临时安排

## 7. Script / Validation

`Script` 解决的是“做完了没有”。

原文里这一层非常关键，因为它决定 Harness 不会退化成“AI 说做完了，你就信了”的口头协作。

Script 的定位是：

- Rule 负责事前预防
- Script 负责事后验证

在 UE 场景里，第一版 Script 不应该强求全自动。
因为蓝图挂接、编辑器操作、运行时表现、手感验证，本来就不可能全部自动化。

因此第一版的正确方向是：

- 先做检查清单
- 再做可自动化脚本
- 逐步把高频错误编码成自动检查

对于 UE 项目，验证层至少应覆盖：

- 编译结果
- 测试结果
- 关键日志
- 蓝图接线验证点
- 编辑器操作验证点
- 未覆盖项声明

也就是说，验证不是“有没有脚本”这么简单，而是“是否把验证从脑内动作变成了可复查结果”。

## 8. MCP / Project Visibility

这一章必须提升到顶层，因为它是当前旧稿最明显的弱项。

`MCP` 在这里不应被收缩成 adapter 路径说明，也不只是“项目目录在哪里”。
它的核心问题是：

> AI 能看到什么项目上下文？

如果 AI 看不到真实项目上下文，它就只能隔着聊天窗口猜测，哪怕规则写得再完整，也仍然是在盲飞。

结合原文、笔记和 Harness 入口说明，UE 场景里的 `Project Visibility / MCP` 至少应覆盖：

- 代码
- 规则文件
- Skill / Task Flow 文件
- 技术文档
- 测试文档
- 测试结果
- 编译结果
- 运行日志
- 资源与配置
- 蓝图接线信息
- 编辑器操作信息
- 版本历史
- 任务演进记录

其中最关键的是三类：

1. 结构事实  
   AI 知道项目现在长什么样。
2. 运行与验证事实  
   AI 知道这次改动有没有通过验证。
3. 历史事实  
   AI 知道项目为什么会演进成今天这样。

因此，能力包里的 `Project Adapter` 只能算 `MCP / Project Visibility` 的接线层，而不能代替 `MCP` 本体定义。

## 9. Memory

`Memory` 解决的是“这次任务学到的东西，能不能留到下次”。

它不是“顺手写个总结”，也不是聊天记录自动累积，而是稳定存在、下次会再次被读取的项目记忆。

结合原文和笔记，Memory 至少包括：

- 规则文件
- 任务流程文件
- 技术文档模板
- 测试文档模板
- 任务记忆日志
- 历史坑点记录
- 可复用的协作规范

Memory 的关键要求是：

- 能稳定存活
- 能被下次默认读取
- 能把这次踩坑转成下次护栏

Memory 不应和 `Notice` 混淆。

- 进入 `Memory / Knowledge` 的，是稳定可复用的沉淀
- 进入 `Notice` 的，是阶段性交接、临时背景和当前轮次判断

## 10. Version Control

版本控制必须单独成章，因为原文明确把它作为小团队三步法的第二步，而不是附属条件。

原因不是形式主义，而是：

- 没有版本控制，AI 只能看到当前快照
- 有了版本控制，AI 才能理解项目演进历史

对 Harness 来说，版本控制的价值不是“方便回滚”这么简单，而是把项目历史变成 AI 可读取的长期上下文。

因此，能力包对版本控制的要求至少应包含：

- 项目处于版本控制之下
- AI 能读取变更历史或明确任务演进记录
- AI 能把当前任务放回项目历史中理解

如果一个项目完全没有版本控制，也没有清晰的任务演进记录，那么这套 Harness 只能算“有规则的临时协作”，还不算完整闭环。

## 11. Development Self-Loop

开发自循环是原文必须抬到顶层的另一条主轴。

Harness 不是一次性工作流，而是一个飞轮。

原文对小团队的自循环可以概括为：

1. AI 写入结果
2. AI 读取上下文
3. AI 继续开发
4. AI 获取日志和反馈
5. AI 完成验证
6. AI 把新结论沉淀为新的规则、记忆和检查项

在 UE 场景里，可以翻译成更贴近工程的版本：

1. 读取项目上下文和规则
2. 按任务流完成实现
3. 读取编译、测试、日志和编辑器反馈
4. 产出技术文档与测试文档
5. 记录新增规范、坑点和未覆盖项
6. 下一轮默认重新读取这些沉淀

这才是 Harness 最重要的落点。

如果没有这一层，Rule、Skill、Script、MCP、Memory 都会重新退化成零散工具。

## 12. Multi-agent As Execution Strategy

多 agent 这一章必须保留，但它的地位需要明确降级。

它不是 Harness 的定义本体，而是承载 Harness 的一种执行策略。

原文里 `SubAgent` 只是五个核心组件之一，它的作用是：

- 面对复杂任务时提供角色拆分
- 让不同职责视角协同
- 减少单一 agent 只从一个角度完成任务

因此，本方案对多 agent 的定位应当是：

- 可用，但不是唯一方案
- 有价值，但不是顶层定义
- 是执行策略，而不是 Harness 本体

对于 UE 场景，能力包可以提供以下执行策略建议：

- 需求视角
- 设计视角
- 实现视角
- 测试视角
- 归档视角

如果实际平台支持多 agent，那么这些角色可以被并行承载。
如果平台不支持多 agent，也可以由主执行者按这些视角顺序自检。

### 12.1 主 agent / 子 agent 策略

结合当前团队偏好，可以采用以下策略：

- 主 agent 负责代码实现和最终汇总
- 子 agent 负责注释、文档、测试、检查、归档建议
- 主 agent 是唯一代码语义写入者

但这只能写成“推荐执行策略”，不能上升为 Harness 定义本身。

### 12.2 模型分级策略

同样，模型分级属于成本与执行策略，不属于 Harness 本体。

推荐策略可以是：

- 高档模型用于需求判断、架构设计、代码实现和冲突裁决
- `mini`、`5.3` 等低成本模型用于注释、文档、测试步骤和检查任务

这有价值，但不应代替 Rule、Skill、Script、MCP、Memory、Version Control、Development Self-Loop 这些顶层章节。

## 13. Project Adapter

`Project Adapter` 的作用不是定义 Harness，而是把通用 Harness 接到某个具体 UE 项目上。

它至少应回答：

- 本项目 `Knowledge` 在哪里
- 本项目 `Notice` 在哪里
- 哪些规则文件必须先读
- 哪些系统文档必须先读
- 哪些蓝图入口、测试入口、资源路径是项目特有的
- 项目里有哪些额外硬约束

但 adapter 的本质只是接线层：

- 它不能替代 `MCP / Project Visibility`
- 它不能替代版本历史
- 它不能替代 Memory

换句话说，adapter 负责“接入”，不是负责“定义 Harness 本体”。

## 14. Templates / Checklists / Safe Scripts

这部分是能力包的可执行资产层。

根据笔记和 `00-README.md`，一套最小严格版应包含：

- `00-README.md`
- `01-RULES.md`
- `02-TASK_FLOW.md`
- `03-TECH_DOC_TEMPLATE.md`
- `04-TEST_DOC_TEMPLATE.md`
- `05-MEMORY_LOG_TEMPLATE.md`
- `06-ROLE_SPLIT.md`
- `07-DELIVERY_CHECKLIST.md`

这些资产的职责应该清楚分开：

- `README`：总入口
- `RULES`：硬约束
- `TASK_FLOW`：执行顺序
- `TECH_DOC_TEMPLATE`：技术文档结构
- `TEST_DOC_TEMPLATE`：测试文档结构
- `MEMORY_LOG_TEMPLATE`：任务记忆沉淀
- `ROLE_SPLIT`：复杂任务视角拆分
- `DELIVERY_CHECKLIST`：交付检查

这里要再次强调：

- 它们不是文档模板集合本身就等于 Harness
- 它们是 Harness 的可执行承载物

## 15. 验收与降级

这套能力包的验收，不应只看“多 agent 是否编排顺畅”，而应先看是否符合 Harness 本体。

### 15.1 验收标准

这套方案设计达标，至少要满足：

1. 能明确区分 Rule、Skill、Script、SubAgent、MCP、Memory 的职责
2. 能明确把版本控制提升到顶层
3. 能明确把开发自循环提升到顶层
4. 能说明第一步原型验证仍然保留，只是当前场景重点偏后两步
5. 能说明多 agent 只是执行策略之一，不是 Harness 本体
6. 能说明 `MCP` 覆盖的不只是 adapter 路径，而是 AI 的项目可见性
7. 能说明任务完成后如何沉淀成下一轮可复用的规则和记忆

### 15.2 降级策略

如果某些条件暂时不满足，系统可以降级，但必须明确降到哪一层：

- 没有版本控制  
  降级为“有规则的临时协作”
- 项目可见性不足  
  降级为“局部上下文驱动”
- 暂无自动脚本  
  降级为“检查清单 + 手动验证”
- 暂无多 agent  
  降级为“单执行者按多视角自检”

降级不等于放弃 Harness，而是明确知道当前缺的是哪一层鞍具。

## 17. 推荐实施步骤

为了避免一上来就把这套能力包做成“多 agent 编排壳子”或者“超长提示词集合”，实施顺序必须固定。

推荐按下面五步推进：

### Step 1：先搭能力包骨架

先创建能力包的目录结构和文件清单，明确每个文件只负责一件事。

这一阶段只解决两个问题：

- 通用 Harness 本体放在哪里
- 项目接线层、模板层、脚本层各自放在哪里

这一阶段不要提前写复杂 skill，不要先写多 agent 调度细节。

### Step 2：再写 Harness 本体

先把本体层写完整，再谈执行策略。

本阶段优先完成：

- `Harness Definition`
- `Rule`
- `Skill / Task Flow`
- `Script / Validation`
- `MCP / Project Visibility`
- `Memory`
- `Version Control`
- `Development Self-Loop`

这里的目标是先把“鞍具是什么”定义清楚，而不是先优化“骑手怎么分工”。

### Step 3：再写项目接线层

在本体稳定以后，再写 `Project Adapter`。

这一层只负责回答：

- 某个 UE 项目怎么接这套通用 Harness
- 项目里的 `Knowledge`、`Notice`、规则文件、系统文档、蓝图入口、测试入口分别在哪里

这一阶段不应反向修改 Harness 本体定义，只做接线。

### Step 4：再补模板、清单与安全脚本

本阶段把能力包变成真正可执行的工程资产。

优先补齐：

- 规则模板
- 技术文档模板
- 测试文档模板
- 记忆日志模板
- 交付检查清单
- 安全的验证脚本

这一阶段的重点是让验证和沉淀变得可重复，而不是追求一次性全自动。

### Step 5：最后再写入口 Skill 和执行策略

入口 skill 必须最后写。

原因是：

- 如果先写 skill，很容易退化成一层总提示词
- 如果本体、接线层和模板层还没稳定，skill 只能编排空气

因此，入口 skill 和 `Multi-agent As Execution Strategy` 应建立在前四步已经稳定存在的文件之上。

在这一阶段，才去明确：

- 任务如何进入 Harness
- 哪些步骤是强制读取
- 多 agent 如何作为执行策略接入
- 主 agent / 子 agent、模型分级、写权限如何作为策略落地

### 实施纪律

后续按这份方案执行时，默认遵守下面这条顺序纪律：

1. 不跳过 Step 1 和 Step 2 直接写 skill
2. 不把多 agent 策略提前抬成方案本体
3. 不在 `Project Adapter` 里反向定义通用 Harness
4. 不在模板和清单尚未成型前声称 Harness 已经闭环

如果后续某一步发现前一步的定义不稳，应回退修正上一步，而不是继续往后堆实现。

## 18. 结论

推荐把这套 UE Harness 做成一个面向 `Codex / Claude Code` 的跨项目能力包，而不是做成 Unreal Engine 插件，也不是只写成当前项目的一组提示词或模板。

这套能力包的本质不是“让 agent 更听话”，不是“多 agent 编排框架”，也不是“文档模板集合”。

它的本质是：

> 把 AI 放进规则、流程、验证、感知、记忆、版本历史和开发自循环中工作。

只有当这几层同时成立时，AI 才不再是一次性的单点生成器，而会逐步变成一个稳定、可追踪、可复用的工程执行者。

在这个定义里：

- `Rule` 负责事前约束
- `Skill` 负责执行顺序
- `Script` 负责验证完成度
- `MCP` 负责项目可见性
- `Memory` 负责长期沉淀
- `Version Control` 负责历史上下文
- `Development Self-Loop` 负责让这一切不断回流和增强

`SubAgent` 和模型分级只是这些机制的一种承载方式。
它们有用，但不是 Harness 的定义本身。

因此，这套方案真正要构建的不是一次性任务执行器，而是一套能让 AI 在多个 UE 项目里持续接线、持续验证、持续沉淀、持续复用的工程系统。
