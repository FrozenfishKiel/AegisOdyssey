# Aegis Odyssey 异步加载与加载界面设计说明

## 1. 文档目的

这份文档用于统一当前项目里“异步加载 / 加载界面 / 加载进度条”相关系统的理解。

这不是最终实现文档，而是一份用于设计讨论和后续落地的方案草案。

---

## 2. 当前讨论后的核心结论

当前项目并不是没有加载系统框架，而是已经选好了技术路线，但还没有把整个系统真正闭环。

目前缺的不是“有没有加载逻辑”，而是：

1. 什么时候应该进入加载
2. 当前到底在等哪些东西完成
3. 这些等待项如何映射成可显示的进度条和状态文案

一句话概括：

> 现在已经有“加载工作本身”，缺的是“把加载工作转成 UI 可消费的状态”。

结合本次讨论，后续方案必须明确两条核心原则：

1. 加载时机必须是状态驱动，而不是把少数入口写死
2. 进度条必须由一套明确的资源/任务集合驱动，而不是只做表面动画

## 4. 原理解释：加载系统怎么理解

为了后续讨论方便，可以把整个加载系统理解成三层。

### 4.1 第一层：显示判定层

这一层只回答一句话：

> 现在应不应该挡住玩家并显示加载界面？

当前项目里，这层主要由 `CommonLoadingScreen` 负责。

它适合处理的情况包括：

1. `PreLoadMap / PostLoadMap`
2. Travel 中
3. World 尚未 BeginPlay
4. `GameState` 尚未可用
5. 玩家控制器尚未准备好
6. 外部系统主动声明“我还在加载”

这层的职责不是决定进度条是多少，而是决定：

> 加载界面现在要不要继续在屏幕上。

### 4.2 第二层：加载状态层

这一层负责维护：

1. 当前加载阶段
2. 当前进度百分比
3. 当前状态文案
4. 当前调试原因

它是整个系统的数据中枢。

这一层当前还没有在项目里正式成型。

建议未来由以下之一承担：

1. `UAOGameInstance`
2. `UAOGameInstanceSubsystem`

### 4.3 第三层：界面表现层

这一层就是最终看到的加载页面本身，例如：

1. 背景
2. Logo
3. 进度条
4. 阶段文字
5. 动画
6. 提示语

这一层不负责决定“该不该显示”，也不负责决定“进度从哪来”，只负责把状态显示出来。

---

## 5. 这次讨论明确下来的设计原则

这次讨论后，最重要的不是“某两个入口要不要显示加载界面”，而是要把系统规则抽象清楚。

### 5.1 核心原则一：加载时机是状态驱动，不是入口写死

加载时机不应该写死成：

1. 启动游戏时加载
2. 点击开始游戏时加载
3. 读取存档时加载

这些都只是典型例子，不应该成为系统唯一入口。

真正推荐的定义是：

> 只要系统进入“玩家暂时不该看到半成品状态”的阶段，就应该允许进入加载流程。

### 5.2 核心原则二：进度条必须绑定真实任务集合

后续必须整理出一套明确的资源/任务集合。

这套集合的价值不是为了“把所有资源一股脑提前加载”，而是为了回答：

1. 当前到底在等什么
2. 哪些任务完成后才能允许玩家进入
3. 哪些任务值得参与进度统计
4. 哪些内容适合延后流式加载，不应该挡住玩家

如果没有这套集合，进度条最后就会退化成“看起来在动，但没人知道它到底在表示什么”。

## 6. 推荐的整体方案

推荐采用：

> `CommonLoadingScreen` 负责“该不该显示”  
> `AO 自己的 LoadingState / ViewModel` 负责“显示什么、进度多少、当前处于哪个阶段”

这是最适合当前项目现状的方案。

此外，后续整体方案必须满足以下总原则：

1. 该加载的时候就加载，而不是只在固定入口加载
2. 启动游戏、进入主界面、开始新游戏、读取存档，只是典型场景，不应该是唯一场景
3. 任何会让玩家看到“半初始化结果”的过程，都应该允许加载界面接管
4. 进度条应尽量绑定真实任务集合，而不是完全依赖假进度

## 7. 推荐的职责划分

### 7.1 UAOGameInstance 或 UAOGameInstanceSubsystem

职责：

1. 保存全局加载状态
2. 提供统一读取接口给 Widget / ViewModel
3. 接收 AssetManager / ExperienceManager / 读档流程的进度更新
4. 提供调试信息

建议保存的数据：

1. `bShouldKeepLoadingScreen`
2. `CurrentPhase`
3. `CurrentProgress`
4. `CurrentStatusText`
5. `DebugReason`

### 7.2 UAOAssetManager

职责：

1. 负责启动阶段内容加载
2. 计算启动阶段进度
3. 把启动阶段进度推送到全局加载状态

重点：

现有的 `UpdateInitialGameContentLoadPercent()` 就应该成为这条通路的入口。

### 7.3 UAOExperienceManagerComponent

职责：

1. 负责地图进入后的玩法内容准备
2. 维护自身加载阶段
3. 告诉全局系统“现在还没准备完”
4. 尽可能提供阶段进度

建议对外暴露的最少信息：

1. `IsExperienceLoaded()`
2. `GetCurrentLoadPhase()`
3. `GetCurrentLoadProgress()`
4. `GetCurrentLoadDescription()`

它未来不应该只服务于“当前这一条 Experience 入口”，而应该成为“世界进入可玩状态前仍有多少玩法准备工作未完成”的重要状态来源之一。

### 7.4 Loading Widget

职责：

1. 显示背景、Logo、动画
2. 显示进度条
3. 显示阶段文字
4. 显示提示信息

不要承担的职责：

1. 不要自己判断何时隐藏
2. 不要直接访问散落在各个系统里的加载逻辑

## 8. 加载时机的设计原则

这一节专门回答“什么时候开始进入加载”。

### 8.1 不是写死入口，而是看状态

系统不应该写成：

1. 只有启动时加载
2. 只有开始游戏时加载
3. 只有读档时加载

而应该写成：

> 只要玩家即将进入一个尚未准备好的状态，就允许加载界面介入。

### 8.2 典型应触发加载的场景

1. 游戏启动阶段
2. 主界面首次进入时仍有关键内容未准备完
3. 点击开始新游戏
4. 读取存档
5. 地图切换 / Travel
6. 快速旅行
7. 进入大型玩法场景前仍有关键资源未完成
8. 未来任何会暴露“半初始化世界”或“半初始化玩法”的流程

### 8.3 推荐的判断标准

未来建议统一用以下条件判断是否应继续显示加载界面：

1. 世界是否已切换完成
2. 关键玩法资源是否已完成准备
3. 当前存档恢复是否已完成
4. 当前 Experience 是否已完成
5. 关键 GameFeature 是否已激活
6. 玩家是否已经可以安全进入可操作状态

也就是说，系统设计上要从“固定入口驱动”转为“状态条件驱动”。

## 9. 资源集合设计目标

后续必须整理一套适合驱动进度条的资源/任务集合。

这套集合的意义不是为了“把所有资源都提前加载”，而是为了明确：

1. 哪些内容属于进入当前状态前必须完成的准备工作
2. 哪些内容值得被纳入进度统计
3. 哪些内容即使延后流式加载，也不会影响玩家对当前状态的感知

### 9.1 这套集合至少要支持

1. 启动阶段加载集合
2. 进入世界阶段加载集合
3. 读取存档阶段加载集合
4. Experience / GameFeature 阶段加载集合

### 9.2 第一版的最低目标

第一版不要求把所有资源都纳入，但至少要做到：

1. 系统支持注册和统计一组明确的待加载任务
2. 这些任务可以映射到加载阶段文案
3. 这些任务可以参与进度条计算
4. 后续可以继续往集合里扩展，而不用推翻架构

## 10. 进度条怎么设计最合理

这里不建议执着于“绝对真实的连续进度条”，建议采用：

> 真实进度 + 阶段权重进度 的混合方案

原因是 Unreal 某些阶段天然拿不到稳定、连续、可视化的真实百分比。

例如：

1. 地图 Travel 可以知道是否结束，但未必有平滑进度
2. GameFeature 激活更像阶段事件，而不是稳定百分比
3. Actions 执行通常也偏离散

### 10.1 推荐的阶段权重示例

1. 启动资源加载：`0% - 35%`
2. 地图切换 / 世界建立：`35% - 55%`
3. Experience 资源加载：`55% - 80%`
4. GameFeature 激活：`80% - 95%`
5. Action 执行 / 玩家进入前准备：`95% - 100%`

### 10.2 推荐策略

建议采用：

1. 能拿真实句柄进度的地方就用真实进度
2. 拿不到真实进度的地方就用阶段权重进度
3. 最终向 UI 输出统一的 `0.0 - 1.0`

但要注意，阶段权重不等于随便假设，它仍然应该建立在明确的待完成任务之上。

系统至少应该能回答：

1. 当前到底在等什么
2. 哪些任务完成后才能允许玩家进入
3. 哪些进度是真实进度，哪些是阶段换算进度

## 11. 推荐的 V1 实现目标

第一版先不要追求炫酷，而要追求链路打通。

V1 目标：

1. 地图切换时一定能显示加载界面
2. Experience 未完成时，加载界面不要提前消失
3. 界面上有可工作的进度条
4. 界面上有当前阶段文本
5. 系统具备调试信息，能知道卡在哪一步
6. 加载进入逻辑以状态判定为主，而不是只绑死在少数入口
7. 系统支持挂接一批明确的资源/任务集合用于驱动进度

V1 不必强求：

1. 完整美术包装
2. 多背景轮播
3. 高级动效
4. 精细提示语系统

当 V1 跑通后，可以继续做：

3. 地图专属加载样式
4. 小提示语系统
5. 联机连接等待提示

## 13. 当前最值得优先讨论的设计点

后续继续讨论方案时，建议按下面顺序定：

### 13.1 加载界面应该覆盖到哪个时机结束

重点要定的是：

是否要覆盖到 `Experience Loaded` 结束之后才消失。

当前建议：

是，应该覆盖到 Experience 真正完成。

原因：

如果地图进来了，但玩法内容还没准备完，玩家看到的就是“半初始化世界”，体验会很差。

### 13.2 进度条采用真实进度还是阶段权重

当前建议：

混合方案。

即：

1. 启动资产加载尽量用真实进度
2. Experience / GameFeature / Action 阶段用权重进度补齐

### 13.3 全局状态中心放在哪里

当前建议优先级：

1. `UAOGameInstanceSubsystem`
2. `UAOGameInstance`

原因：

`Subsystem` 更适合作为独立模块，职责更清晰，也更方便未来扩展与测试。

### 13.4 第一版是否先用 C++ 基础 Widget 打底

当前建议：

是。

原因：

先验证逻辑链路，比先做美术样式更稳。

### 13.5 第一版资源集合先纳入哪些内容

这是当前非常关键的设计问题。

因为只有先定义出“哪些内容值得纳入加载集合”，后面的真实进度条才有意义。

---

## 14. 对当前项目的判断总结

当前项目的加载系统不是“从零开始”，而是“框架已经选对了，但最后一层胶水没补完”。

已经存在的高价值基础：

1. `CommonLoadingScreen` 已接入
2. `AOAssetManager` 已具备启动加载进度计算骨架
3. `AOExperienceManagerComponent` 已具备玩法内容加载状态机
4. `AOGameMode / AOGameState` 已默认以 Experience 完成作为可进入游戏的重要前提

所以后续工作不应该是推翻重来，而应该是：

1. 建立统一 LoadingState
2. 接通现有进度来源
3. 提供正式 Loading Widget
4. 把 LoadingScreen 的显示时机和 Experience 生命周期真正绑定
5. 把“状态驱动加载”原则正式落实到系统设计中
6. 逐步整理出可驱动进度条的资源/任务集合

## 16. 推荐开发时机与分阶段落地策略

### 16.1 建议现在就开始做，但只做 V1 骨架

不建议等到游戏快做完再写这套系统。

原因：

1. 到那时资源入口会更分散
2. 很多系统会各自形成隐式加载逻辑
3. 很难再统一收束成清晰的加载集合
4. 打包阶段才补加载系统，返工成本会更高

但同样也不建议现在就直接做成最终完整版。

原因：

1. 当前很多玩法系统仍在生长
2. 资源边界和读档恢复边界还没有完全稳定
3. 现在更适合先立框架，而不是一次性把所有集合都做满

因此推荐策略是：

> 现在就开始做，但先做“可扩展的最小闭环骨架”，不要现在就追求最终版。

### 16.2 推荐的阶段节奏

#### 第一阶段：现在做 V1 骨架

目标：

1. 建立统一 LoadingState
2. 接通 `CommonLoadingScreen` 的显示时机
3. 让 `AOAssetManager` 能上报启动加载状态
4. 让 `AOExperienceManagerComponent` 能上报玩法准备状态
5. 提供基础进度条和阶段文案
6. 支持挂接资源集合/任务集合

这一阶段的重点不是“覆盖所有资源”，而是把系统骨架立稳。

#### 第二阶段：中期逐步挂接真实集合

目标：

1. 把真实的 `PawnData` 依赖纳入加载集合
2. 把 `ExperienceDefinition` 的关键软资源列表纳入加载集合
3. 把 `GameFeature` 统计真正接入进度系统
4. 把读档恢复任务正式接入加载流程

这一阶段的重点是：

让“加载进度条表示的内容”越来越真实、越来越可解释。

#### 第三阶段：后期做调优与包装

目标：

1. 调整阶段权重和显示节奏
2. 打磨正式 Loading Widget 的样式与动画
3. 做不同场景或地图的加载界面包装
4. 针对打包版本做专项加载优化

这一阶段的重点不是改架构，而是在稳定骨架之上做体验增强。

### 16.3 不推荐的节奏

以下两种节奏都不推荐：

1. 等游戏快做完再一次性补整套加载系统
2. 现在就把所有资源全集硬塞进第一版加载集合

前者的问题是返工成本高，后者的问题是系统会过早膨胀、难以维护。

### 16.4 当前推荐结论

当前最推荐的落地策略是：

1. 现在启动加载系统开发
2. 第一版只做骨架与最小闭环
3. 后续伴随玩法系统成熟，逐步扩展真实资源集合
4. 最后再做包体阶段的体验优化和美术包装

## 17. 当前协作约束与实施边界

### 17.1 当前协作约束

当前项目仍在持续开发功能，用户明确提到当前正在推进：

1. 技能
2. 采集

因此，加载系统当前阶段必须遵守的首要约束是：

> 不能阻塞现有技能与采集功能的持续开发。

这条约束高于“现在就把加载系统做得更完整”。

### 17.2 当前客观评估

基于现有工程结构，加载系统如果严格限制在 `V1 骨架` 范围内，整体风险评估为：

1. 对现有功能开发影响：低到中风险
2. 对技能/采集主逻辑的直接干扰：可控
3. 对共享数据入口的耦合风险：存在，但可通过范围控制降低

但如果现在就追求：

1. 真实资源全集纳入
2. 完整读档恢复接入
3. 全地图级加载集合整理
4. 对现有数据结构进行大规模重构

则风险会明显上升，并可能干扰技能、采集开发节奏。

### 17.3 当前允许推进的内容

如果后续开始落地，当前阶段允许推进的内容应限制为：

1. 建立统一 `LoadingState` 骨架
2. 接通 `CommonLoadingScreen` 的显示时机
3. 让 `AOAssetManager` 上报启动加载状态
4. 让 `AOExperienceManagerComponent` 上报玩法准备状态
5. 提供基础进度条、阶段文案和开发调试信息
6. 提供“资源集合/任务集合”的挂接结构，但不要求当前一次性填满

### 17.4 当前不应主动推进的内容

为了避免阻塞技能、采集功能开发，当前阶段不应主动推进：

1. 全技能资源全集纳入加载集合
2. 全采集资源全集纳入加载集合
3. 读档恢复完整接入
4. 全地图远端内容全集式纳入
5. 为加载系统目的而重构现有技能/采集资源组织方式
6. 为了追求完整性而大规模修改 `PawnData / GameData / ExperienceDefinition` 的职责边界

### 17.5 当前实施原则

当前阶段的实施原则正式定为：

> 加载系统现在可以开始做，但只能先做不会阻塞技能、采集开发的 V1 骨架。

这意味着：

1. 先立系统骨架
2. 先打通显示与状态汇总
3. 先保留扩展位
4. 不要求当前把技能和采集系统全面接入加载集合
