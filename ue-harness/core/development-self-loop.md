# Development Self-Loop

## 作用

开发自循环是这套 Harness 最终要形成的飞轮。

如果没有这一层，前面的 Rule、Skill、Script、MCP、Memory 都只是在提供零散工具；
只有把它们放进自循环，Harness 才真正成立。

## 核心定义

Harness 的目标不是一次性把任务做完，而是让每次任务都进入下一轮可复用状态。

对 UE 场景而言，这个自循环至少应包含：

1. 读取项目上下文和规则
2. 按任务流推进实现
3. 读取编译、测试、日志和编辑器反馈
4. 产出技术文档与测试文档
5. 记录新增规范、坑点和未覆盖项
6. 在下一轮任务里默认再次读取这些沉淀

## 和原文飞轮的映射

原文的小团队飞轮可以概括为：

- 自动写入
- 自动读取
- 自动开发
- 自动获取日志
- 自动验证
- 自动进化

落到当前能力包里，不要求第一版就实现完全自动化，但要求这条链条在设计上必须完整存在。

也就是说：

- 先允许部分手工
- 但不允许缺位

如果某个环节暂时不能自动化，也必须被定义出来，并在后续逐步升级。

## 最终判定标准

判断这套能力包是不是真的进入自循环，不看它写了多少模板，而看它是否做到：

- 本轮任务产出的规则能影响下一轮
- 本轮任务产出的验证结果能被下一轮读取
- 本轮任务产出的文档能成为下一轮输入
- 本轮任务踩过的坑不会完全丢失

## Direct Execution Lessons

当一次任务暴露出 Harness 自身导致停顿、半迁移、反复解释、或 patch 失败未及时切换策略时，必须把经验回流为下一轮默认行为：

1. 用户明确要求直接执行时，优先完成代码闭环，再报告流程降级。
2. 删除型重构以后必须保留 Deleted Symbol Checklist 和 `rg` 清零证据。
3. 编码、乱码、宏被注释吞掉、patch 上下文失败，必须升级为文件重建策略，而不是继续小补丁。
4. 如果验证工具不可用，记录缺失入口，但不能把它当作已完成代码修改前的停顿理由。
5. 如果本轮发现 skill 规则让 agent 过度停顿，应直接修 skill，而不是只在最终回复里解释。
