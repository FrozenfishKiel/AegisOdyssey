# Rules Template

用途：为某个 UE 项目或子系统生成最小规则文件。规则必须少、硬、可检查，不能写成长提示词。

## 1. Rule Identity

```yaml
project_or_system: "<项目名或系统名>"
owner_scope: "<规则适用范围>"
updated_at: "<YYYY-MM-DD>"
adapter: "<对应 Project Adapter>"
```

## 2. Hard Rules

这些规则默认不能跳过。每条规则都要能在交付前被人或脚本检查。

- `R1`：任务开始前必须读取对应 `Project Adapter` 和相关知识包。
- `R2`：主 agent 是唯一代码写入者；其它执行者只能给注释、文档、检查、测试建议或报告。
- `R3`：核心函数和新增属性必须写中文注释，说明职责、输入、输出或副作用。
- `R4`：涉及蓝图或编辑器接线时，必须写清 C++ 类、蓝图父类、编辑器接线位置和运行时触发入口。
- `R5`：没有新鲜验证证据时，不允许声称编译、测试或交付完成。

## 3. Documentation Rules

每次系统功能交付后，至少补齐：

- 技术文档：设计说明、调用链、源码入口、蓝图/编辑器接线、风险边界。
- 测试文档：冷启动步骤、预期结果、实际结果或未执行原因、未覆盖项。
- 交付说明：本轮改了什么、验证了什么、哪些内容降级为人工检查。

## 4. Validation Rules

验证优先级从硬证据到降级说明：

1. 编译结果或明确的未编译原因。
2. 自动化测试结果或明确的未运行原因。
3. 日志、截图、编辑器现象等辅助证据。
4. 蓝图和编辑器操作的人工验证步骤。

暂时不能自动化的验证不能删除，只能降级为检查清单和人工步骤。

## 5. Memory Rules

任务结束时必须判断产出应进入哪里：

- 半年后仍成立的结构事实、设计边界、系统入口进入 `Knowledge`。
- 阶段性交接、临时判断、历史背景、未完成提醒进入 `Notice`。
- 如果当前项目没有实体 `Notice` 目录，交付中标记为 `Notice candidate`，不要误写成稳定知识。

## 6. Rule Upgrade

如果同类提醒重复出现，应升级：

- 重复 2 次：加入交付检查清单。
- 重复 3 次：考虑升级为硬规则。
- 能被确定性检查：进入安全脚本。
