# 装备系统与动态属性集当前进度交接

这份文档不是知识库设计稿，也不是聊天记录摘要。它只服务一件事：让下一个 AI 在接手这条线的时候，能尽快分清楚我们已经做到了哪里、现在还卡在哪里、下一步应该从哪里继续，而不是重新把已经收过口的东西再讨论一遍。

## 第一章 现在这条线到底在做什么

这条线表面上看是在做装备系统，但现在其实已经清楚地分成了两部分，而且这两部分的重要性不一样。

第一部分是正式装备栏本身，也就是五个长期穿戴槽怎么和库存、UI、授予回收链路接起来。这个部分已经不再是方案草图了，代码、投影、管理器、ViewModel、UI 都已经有了落地实现，最近这一轮也把一个很具体的 UI 问题收了口。

第二部分是装备和武器来源属性怎么稳定进入 GAS 的派生链，也就是来源属性、MMC、派生 GE、最终战斗属性之间的联动为什么还没有完全打通。现在真正没有解决的主问题在这里，不在正式装备五槽本身。

所以后面谁接这条线，第一件事就是先把注意力分开。正式装备栏这部分现在主要是做收边和补细节，不要再把它当成“还没搭起来”的系统。真正还在排查主线上的，是 MMC 派生联动。

---

## 第二章 这些边界已经锁了，不要再改回去

### 正式装备栏和武器系统是两套运行时真相

这一点现在已经很明确。

正式装备栏只处理角色的长期穿戴态，武器继续由 `UAOWeaponManagerComponent` 处理当前激活态。两边可以复用库存实例语义，也可以复用 `AbilitySetsToGrant`，但不共享同一个运行时真相组件。

换句话说，不要再尝试把“当前武器激活状态”和“角色身上长期穿着什么”重新揉回一套组件里。

### 正式装备来源物必须是库存里的真实实例

正式装备栏不是第二套独立容器，它只是库存投影。

放进正式槽里的，必须是库存里的真实 `Instance`，不是抽象定义。装备、替换、卸下，本质都应该尽量复用统一库存交换链，而不是在 UI 或管理器里手写第二套迁移逻辑。

### 正式装备槽固定为五个唯一槽

当前正式装备槽就是这五个：

1. `Helmet`
2. `Armor`
3. `Gloves`
4. `Necklace`
5. `Boots`

每个槽只认自己对应的合法装备类型。武器、消耗品、材料，以及别的非正式装备来源物，都不应该进入正式装备槽。

### 正式装备属性授予统一走 `Definition.AbilitySetsToGrant`

这条也已经收口了。

正式装备不再从 `Fragment` 上单独开一条属性授予入口，和武器一样，统一走 `Definition.AbilitySetsToGrant`。`AOFragment_FormalEquipment` 现在只负责槽类型这一类静态分类职责。

### `AbilitySet.AttributeSets` 现在的语义已经收紧

`AbilitySet.AttributeSets` 现在只负责一件事：确保当前 ASC 上已经有这类 `AttributeSet` 可用。

它不再参与“某次授予链拥有这组 AttributeSet，并在回收时把它删掉”的对称语义。对应地，`FAOAbilitySet_GrantedHandles` 现在只回收 Ability 和 GameplayEffect，不再把共享 AttributeSet 实例绑进句柄回收。

这条边界不要再回退，否则会重新引入“多条授予链共享同类 AttributeSet 时，被某一条先回收误删”的问题。

### 动态来源属性集不再走运行时增删 AttributeSet 那条路

`UAOWeaponAttributeSet` 和 `UAOEquipmentAttributeSet` 这两个来源属性集保留，但不再按“装备时创建、卸下时删除”的思路推进。

已经否掉的方向包括：

1. `AcquireDynamicAttributeSet(...) / ReleaseDynamicAttributeSet(...)`
2. 基于运行时拓扑变化统一协调派生 GE
3. 单独再起一条 `PawnData.StartupAttributeSets` 旁路

后面不要再把这些旧方向捡回来硬补。

## 第三章 这轮正式装备槽 UI 问题已经推进到哪里

这轮不是在继续做正式装备栏的大结构，而是在收一个很具体、也很容易干扰后续判断的问题：正式装备槽的拖放合法性和槽身份显示。

### 之前的问题是什么

问题不是正式装备管理器完全没有合法性判断，而是正式槽 UI 这层没有把这条判断真正接进拖放入口。

结果就是，表面上会出现两个很糟糕的现象：

1. 武器这类本来就不该进正式槽的东西，拖上去看起来也能放。
2. 就算是正式装备，头盔也可能被拖进护甲槽这种错误槽位。

另外还有一个表现层问题：正式装备槽 UI 虽然已经在重建和显示了，但槽控件本身没有稳定暴露“这个槽是谁”的身份信息。也就是说，UI 能拿到“这个槽现在装了什么”，却没有稳定拿到“这个槽本来是头盔槽还是护甲槽”。

### 这轮已经改了什么

这一轮已经把正式装备槽 UI 的入口收了一遍，改动主要落在下面这几处：

1. `Source/AegisOdyssey/UI/Widgets/FormalEquipment/AOFormalEquipmentSlotUI.*`
2. `Source/AegisOdyssey/UI/Widgets/FormalEquipment/AOFormalEquipmentBarUI.cpp`
3. `Source/AegisOdyssey/UI/Widgets/Inventory/AOInventoryUI.*`

改完以后，当前语义应该这样理解。

第一，正式装备槽 UI 自己接入了 `DragOver / Drop` 前置拦截。它现在会先从拖拽操作里还原真实来源库存和来源槽位，再转发给 `CanAcceptSourceItemForFormalSlot(...)` 做统一判断。也就是说，UI 不再是一个什么都先放进来再说的壳子了。

第二，正式装备槽 UI 还是不自己定义业务规则。它只负责把拖拽上下文还原出来，然后转给正式装备管理器判断是否合法。这一点很重要，因为这意味着后面如果装备合法性边界调整，应该优先改管理器或正式装备槽库存组件，而不是在某个 Widget 蓝图里偷偷改一套局部规则。

第三，正式装备栏 UI 现在不再只拿物品快照。每个槽在初始化时，除了会拿到当前 `FAOInventoryEntry` 快照，还会拿到：

1. 槽索引
2. 槽类型
3. 槽显示名

所以蓝图层现在可以直接知道这个槽到底是 `Helmet`、`Armor`、`Gloves`、`Necklace`、`Boots` 里的哪一个。

第四，正式装备栏重建槽位时，不再只信 `FormalEquipmentList.Num()`。现在会按正式装备管理器当前固定的五槽定义去建 UI，再把每个槽当前的物品快照填进去。这样即使某一帧没有装备物，或者快照数组还没完整补齐，UI 也能稳定显示五个有语义的槽，而不是只显示一组“刚好当前有几条快照就建几个格子”的普通列表。

### 这轮之后这块应该怎么理解

正式装备槽的合法性，现在至少有三层：

1. 正式槽 UI 的拖放前置拦截
2. 正式装备管理器的 `CanAcceptSourceItemForFormalSlot(...)`
3. 统一库存交换链里的 `CanAcceptInventoryEntryAtSlot(...)`

所以这块的正确说法不再是“蓝图 OnDrop 没写，所以暂时什么都能进”。现在已经不是这个状态了。

## 第四章 这条线当前已经成立的代码事实

这部分是给下一个 AI 快速建立最小事实集用的，不是让你重新推方案。

### `PawnData -> AbilitySets -> AbilitySet.AttributeSets` 这条链现在是有效的

`AbilitySet` 里的 `AttributeSets` 现在不是摆设，它已经重新回到正式授予链里了。

也就是说：

1. `AbilitySet` 负责一包能力、效果、依赖属性集
2. `PawnData` 继续通过 `AbilitySets` 驱动这条链
3. 不应该再额外起一条 `StartupAttributeSets` 配置旁路

### `UAOAbilitySystem::EnsureSpawnedAttributeSet(...)` 目前保留

它现在只是一个很小的辅助函数。

逻辑很简单：某个 `AbilitySet` 依赖一类 `AttributeSet`，如果 ASC 上已经有，就复用；没有才补挂一次。

它不是第二套配置系统，也不是动态拓扑协调器。

### 正式装备和武器都继续通过 `AbilitySetsToGrant` 授予

这条边界在正式装备和武器两边都已经统一了。

卸下时，GameplayEffect 回收继续保留 stack-aware 语义，但 AttributeSet 实例本身不再随着某一条授予句柄一起删。

### `GE_CombatDerivedAttributes` 不要再当现行主链

这次排查已经确认，这个东西不承载当前真正有效的初始化和派生职责。后续继续读这条线时，不要再围绕它建立新的解释，否则只会把排查带偏。

## 第五章 现在真正没解决的问题是什么

这部分是最容易被说偏的地方。

当前真正没解决的问题，不是“正式装备系统还没做完”，也不是“MMC 根本不支持这种玩法”。真正没解决的是：

**装备和武器的来源属性已经能变化，但这些来源属性还没有稳定驱动角色最终属性的 MMC 派生链联动更新。**

也就是说，现在我们已经知道：

1. 来源属性层已经有了
2. `MMC_CalculateAttack`、`MMC_CalculateDefense` 这类计算器也已经在读来源属性
3. 角色最终战斗属性仍然在 `UAOCombatAttributeSet`

但中间“为什么来源值变了，最终属性没跟着变”这件事，还是没有彻底收死。

所以不要因为这轮刚补了正式槽 UI，就把注意力重新放回“正式装备拖拽是不是主问题”上。它不是。

## 第六章 后面继续排查时最容易走偏的地方

后面谁再接这块，最容易犯三类错误。

第一类，是把问题直接下结论成“MMC 根本不支持这种派生玩法”。现在不能这么说，因为真正还没解释清楚的，不是 MMC 有没有表达能力，而是当前项目里承载它的 active GE、聚合链和 dirty 传播是不是已经真的打通。

第二类，是因为不想手动刷新，就重新把业务层、ASC 层、动态 AttributeSet 生命周期层混成一锅，再回去捡那套运行时拓扑方案。现在不能再走那条路。

第三类，是看到 `AbilitySet.AttributeSets` 恢复执行，就又把它理解成“某次授予链拥有并独占这一组 AttributeSet”。这个理解也是错的。

## 第八章 当前最合理的继续工作顺序

如果后面继续推进，建议按这个顺序来，而不是哪里不顺眼就先修哪里。

第一步，确认当前实际承载派生属性计算的 active GE 到底是哪一个。不要停留在文档名字或历史资产名上，直接确认运行时到底是哪条 active GE 在提供最终属性结果。

第二步，确认来源属性变化之后，对应 aggregator 到底有没有真的变 dirty。现在最关键的不是“值看起来有没有写进去”，而是这次写值有没有真正进入 GAS 聚合链。

第三步，如果 aggregator 已经变 dirty，再继续查为什么最终属性还是没动。这个时候问题就会收口到：

1. active GE 有没有收到依赖变化
2. 它有没有重新计算自己的 modifier magnitude
3. 重新计算之后，为什么结果没有反映到 `UAOCombatAttributeSet`

第四步，最后再查旧资产引用、旧 GE、旧初始化路径有没有覆盖结果。

而不应该做的事包括：

1. 重新发明第三套属性初始化路径
2. 在武器、正式装备、以后别的系统里到处手写重算
3. 再把动态 AttributeSet 生命周期方案捡回来硬补

## 最后一节 这份交接最重要的三句话

第一句，正式装备栏这部分已经不是纯方案了，尤其是正式槽合法性和槽身份显示这块，这轮已经往现行实现上收过一遍，不要再从“是不是应该另起一套 UI/判定”开始讨论。

第二句，`AbilitySet.AttributeSets` 现在已经恢复成有效授予链，但它只负责“确保属性集到位”，不是“某次授予链独占并回收这组属性集”。

第三句，这条线现在真正卡住的还是 MMC 派生联动，不是正式装备拖拽本身，也不是五槽系统本身。后续继续推进时，注意力应该集中在：

**来源属性是怎么进入 GAS 聚合链的，以及派生属性 GE 为什么没有稳定吃到这次变化。**
