# 消耗品、统一库存接收与获取物品通知方案

更新日期：2026-05-13

---

## 1. 这份文档现在负责什么

这份文档不再只讲“消耗品右键使用”。

从现在开始，它统一负责三条已经正式接上的链路：

1. 物品在库存里的主动使用链。
2. 库存 UI 的统一右键上下文菜单链。
3. 物品真正进入玩家背包后的统一 UI 通知链。

这里说的“获取物品通知”不是采集专属功能，也不是拾取专属功能。
它的正式语义是：

**只要某个结果最终真正进入了玩家背包，就应该有资格进入统一的“获得物品通知”链。**

这意味着它天然覆盖：

1. 采集奖励入包。
2. 地面拾取入包。
3. 后续制作产物入包。
4. 任何未来只要走正式统一入包链的系统。

## 2. 已确认的设计边界

### 2.1 不按来源系统各写一套通知

已经明确不接受下面这种写法：

1. `GA_Harvest` 成功后自己直接弹一条采集通知。
2. `PickUpable` 成功后自己再弹一条拾取通知。
3. 后面制作系统再抄一遍通知逻辑。

原因很简单：

1. 这样会让“通知语义”分散在多个系统里。
2. 以后每加一个入包来源，都要重复补一次 UI 逻辑。
3. 很容易出现有的来源会通知、有的来源忘了通知。

所以当前正式口径是：

**通知跟着“统一入包成功”走，不跟着“来源玩法名字”走。**

### 2.2 只对“真正进入玩家背包”的结果发通知

这条边界非常重要。

不是所有库存变化都应该弹“获得物品”提示。

当前明确：

1. 玩家背包接收到物品，可以通知。
2. 世界容器自身库存变化，不该通知玩家“获得物品”。
3. 快捷栏、技能槽、装备槽这类投影型或中间型库存，不该冒充“获得物品”。

所以这套通知当前只在真正代表玩家主背包接收结果的组件上开启。

### 2.3 通知是库存真相的后续表现，不反向驱动库存

通知链只能消费“已经成功入包”的结果。

不能反过来：

1. 先弹通知，再猜测库存应该已经有了。
2. 根据 Widget 是否播出来，反推这次入包是否成功。
3. 把 UI 行为塞回库存系统当成结算条件。

当前正式方向是：

**库存先成为真相，通知只是这个真相的一个标准化表现出口。**

### 2.4 先保持 HUD 聚合根可用，但不要把通知逻辑再写散

当前工程里 `UMVVM_HUD` 仍然是 HUD 总入口和聚合根。

所以这次通知先挂到：

1. `UAOHUDViewModelComponent`
2. `UMVVM_HUD`
3. `UAOMainUI`

这条现有主链上。

但这不代表后续可以随便把各种原始字段继续堆回 `UMVVM_HUD`。

当前只是在不引入第二套杂乱链路的前提下，先把“统一获取物品通知”正式接通。

## 3. 当前已经落地的真实实现

### 3.1 统一库存接收入口仍然是主收口

当前统一入包主入口仍然是：

1. `Source/AegisOdyssey/Inventory/AOInventoryStatics.h`
2. `Source/AegisOdyssey/Inventory/AOInventoryStatics.cpp`

最关键的入口函数是：

1. `UAOInventoryStatics::CanActorFullyAcceptInventoryBatch(...)`
2. `UAOInventoryStatics::TryAddInventoryBatchToActor(...)`

当前正式语义：

1. 外部系统先把奖励翻译成 `FAOInventoryReceiveBatch`。
2. 再统一交给库存系统处理。
3. 不允许外部系统偷偷绕过这条链直接改背包。

已经确认走这条链的现有系统至少包括：

1. 采集。
2. 拾取。

所以“获取物品通知”挂在这条统一入包链周边是正确的。

### 3.2 获取物品通知的世界消息层已经落地

当前新增的消息层文件：

1. `Source/AegisOdyssey/Inventory/AOInventoryAcquisitionMessage.h`
2. `Source/AegisOdyssey/Inventory/AOInventoryMessageSubsystem.h`
3. `Source/AegisOdyssey/Inventory/AOInventoryMessageSubsystem.cpp`

各自职责：

1. `FAOInventoryAcquisitionMessage`
   - 描述一条已经成功进入库存的物品结果。
   - 只包含接收者、物品定义、数量这些库存真相字段。

2. `UAOInventoryMessageSubsystem`
   - 作为世界级消息子系统广播“已经成功入包”的结果。
   - 不参与采集、拾取、制作这些来源系统的业务决策。
   - 不参与 UI 表现设计。

当前正式边界：

**这个子系统只广播结果，不解释 UI。**

### 3.3 获取物品通知的真实广播点已经落地

当前真实广播点在：

1. `Source/AegisOdyssey/Inventory/AOInventoryComponent.h`
2. `Source/AegisOdyssey/Inventory/AOInventoryComponent.cpp`

新增的关键职责有：

1. 从 `FAOInventoryReceiveBatch` 构建通知消息。
2. 在统一入包成功后分发通知消息。
3. 联机下把成功结果同步到本地客户端再播通知。

当前正式口径：

1. 通知是在“入包成功之后”发。
2. 不是在来源系统里发。
3. 不是在“准备入包”时预发。

### 3.4 当前只有背包组件会正式对外发获取物品通知

当前开关在：

1. `Source/AegisOdyssey/Inventory/AOBackPackComponent.h`

当前做法是：

1. `UAOInventoryComponent` 默认不发获取物品通知。
2. `UAOBackPackComponent` 显式重写 `ShouldBroadcastInventoryAcquisitionNotifications()` 返回 `true`。

这条边界的含义是：

1. 通知只认“真正进了玩家背包”。
2. 容器库存、快捷栏库存、其他中间库存不会乱弹提示。

### 3.5 HUD 侧桥接已经落地

当前桥接文件：

1. `Source/AegisOdyssey/UI/AOHUDViewModelComponent.h`
2. `Source/AegisOdyssey/UI/AOHUDViewModelComponent.cpp`

当前职责：

1. 订阅 `UAOInventoryMessageSubsystem`。
2. 把世界级库存消息转换成 HUD 可直接消费的本地通知数据。
3. 只把和本地玩家相关的通知继续送进 HUD。

也就是说：

1. 世界里别的玩家入包，不该进你本地 HUD。
2. 本地玩家自己入包，才进入你的通知队列。

### 3.6 HUD 可消费通知数据已经落地

当前图标来源：

1. 物品定义上的 `UAOFragment_InventoryIcon`

这意味着：

1. 你的通知 UI 不需要再自己回头查物品图标。
2. 也不需要再自己从物品定义里现组显示名。

## 4. 这套获取物品通知到底怎么用

下面不是抽象说明，是当前程序员和 UI 使用时的正式操作步骤。

### 4.1 如果你只是想让现有采集、拾取自动弹通知

当前不需要再额外配任何“采集通知开关”或“拾取通知开关”。

你只要保证：

1. 奖励最终走 `UAOInventoryStatics::TryAddInventoryBatchToActor(...)`。
2. 接收容器最终是玩家背包组件。
3. 物品定义本身有合法的显示名。
4. 如果你想显示图标，物品定义上挂了 `UAOFragment_InventoryIcon`。

满足这四条后：

1. 采集成功入包会自动进通知队列。
2. 拾取成功入包也会自动进通知队列。

你不需要在采集系统或拾取系统里再写一行额外的“弹通知”代码。

### 4.2 如果你是 UI 蓝图，要怎么拿这批通知

当前最直接的入口就是：

1. `UAOMainUI::ConsumePendingInventoryAcquisition()`

蓝图使用顺序：

1. 拿到 `AOMainUI`。
2. 调 `ConsumePendingInventoryAcquisition()`。
3. 返回的是一批 `FAOInventoryAcquisitionViewData`。
4. 逐条创建你的提示条 Widget。

每条数据你最关心的字段通常是：

1. `DisplayName`
2. `Count`
3. `IconBrush`
4. `bHasValidIcon`

当前最推荐的蓝图消费方式：

1. 在主 HUD 或提示管理 Widget 里统一轮询/统一消费。
2. 消费后立刻生成一批瞬时提示。
3. 不要让多个 Widget 同时各自去 `Consume` 同一份队列。

原因：

1. `Consume` 的语义就是“一次性取走并清空”。
2. 如果多个地方同时消费，很容易丢消息。

### 4.3 如果你不想用 `AOMainUI` 的便捷入口，要怎么接

也可以直接从 `UMVVM_HUD` 上拿。

你可以选两种方式：

1. 事件驱动：
   - 订阅 `OnInventoryAcquisitionReceived`
   - 每来一条就播一次提示

2. 队列驱动：
   - 调 `ConsumePendingInventoryAcquisitionList()`
   - 一次吃掉当前积累的一批

当前建议：

1. 做单条即时 toast，用事件驱动更直接。
2. 做批量列表或统一提示管理，用队列驱动更稳。

### 4.4 如果你想让某个新系统也接入通知，该怎么做

假设后面你做“制作完成直接进背包”。

正确做法不是：

1. 制作系统自己手写一条 HUD 通知。

正确做法是：

1. 先把制作结果翻译成 `FAOInventoryReceiveBatch`。
2. 调 `UAOInventoryStatics::TryAddInventoryBatchToActor(...)`。
3. 让结果真正进入玩家背包。
4. 通知链自然就会跟着成功入包一起触发。

也就是说：

**以后新系统要接入获取物品通知，接的是统一入包链，不是接 HUD。**

### 4.5 如果你想控制显示图标，要去哪里配

当前图标来源不是通知系统自己配的。

你要去物品定义里配：

1. 物品 `ItemDefinition`
2. 挂 `UAOFragment_InventoryIcon`
3. 在 `Brush` 里填正式图标

如果这里没配：

1. 通知仍然会有名字和数量。
2. 但 `bHasValidIcon` 会是 `false`。
3. UI 应该自行走“无图标样式”。

### 4.6 如果你想控制显示名字，要去哪里配

当前显示名来源是：

1. `UAOInventoryItemDefinition::DisplayName`

所以你要改名字，不是改通知链代码，而是改物品定义本身。

### 4.7 如果你问“为什么我拿到物品了但没通知”，先查哪几步

按这个顺序查：

1. 这次结果是不是走了 `UAOInventoryStatics::TryAddInventoryBatchToActor(...)`。
2. 接收结果的库存组件是不是 `UAOBackPackComponent`。
3. 这次入包是不是实际成功了，而不是被满包拦下。
4. 本地 HUD 是否已经正常持有 `UAOHUDViewModelComponent` 和 `UMVVM_HUD`。
5. 你的 UI 是否真的调用了 `ConsumePendingInventoryAcquisition()` 或订阅了 `OnInventoryAcquisitionReceived`。
6. 物品定义是否至少有 `DisplayName`。
7. 如果是图标没显示，再看 `UAOFragment_InventoryIcon` 是否配置。

### 4.8 如果你问“为什么容器里收了东西却不弹通知”

这是当前设计的故意行为，不是 Bug。

因为当前正式语义是：

1. 只有玩家真正获得物品，才弹“获得物品通知”。
2. 世界容器自己库存变化，不冒充玩家获得。

### 4.9 如果你问“为什么快捷栏或技能槽变化不弹通知”

当前也是故意行为。

因为这些更偏向：

1. 背包投影。
2. 装备投影。
3. 使用视图。

它们不是“玩家刚获得一件新物品”的主真相来源。

## 5. 当前程序员验收口径

### 5.1 成功标准

当前这一版通过标准是：

1. 采集成功入包后，本地玩家 HUD 能收到通知。
2. 拾取成功入包后，本地玩家 HUD 也能收到通知。
3. 容器库存变化不会误弹玩家获得提示。
4. 同一轮入包批次里的每种物品，会形成稳定的通知数据。
5. UI 能直接读到名字、数量、图标刷子。
6. 单机与联机客户端都能走通。

### 5.2 当前推荐手工验证步骤

#### A. 采集通知验证

1. 进入测试关卡。
2. 装备合法采集工具。
3. 对准可采节点完成一次成功采集。
4. 确认奖励真正进了背包。
5. 立刻确认本地 HUD 提示出现。
6. 提示内容至少要能看见名字和数量。
7. 如果物品配了图标，再确认图标一起出现。

#### B. 拾取通知验证

1. 在场景里放一个合法拾取物。
2. 让玩家拾取。
3. 确认物品真正进入背包。
4. 确认 HUD 同样出现“获得物品”提示。

#### C. 容器误报验证

1. 打开一个箱子或其他容器。
2. 让容器自身库存发生变化。
3. 确认本地 HUD 不会误弹“获得物品”。

#### D. 满包失败验证

1. 先把背包装满到无法完整接收这次奖励。
2. 再做一次采集或拾取。
3. 确认这次没有真正入包。
4. 确认不会误弹成功获得提示。

## 9. 库存右键弹出菜单手工测试方案

这一节只写测试，不写设计结论。读法按“第一次接手项目、第一次进这个功能”来写，你照着做就能把当前实现的右键链路走一遍。

### 9.1 先确认你在测什么

这轮只测库存右键菜单，不测采集通知，也不测拾取通知。当前实现里，右键入口已经统一到库存 UI，菜单动作由 ViewModel 驱动，真正“使用”时再分流到对应库存链路。

你只需要先记住三件事：

1. 背包右键是最短主链，适合当第一组。
2. 容器右键会走 interaction session mutation，不是本地直接改。
3. 正式装备槽不是普通库存语义，右键结果是“卸下”。

### 9.2 测试前置条件

正式开始前，先把这些条件准备好，不然很容易把“样本不对”误判成“右键菜单坏了”。

#### 9.2.1 需要准备的样本

最好同时准备四类：

1. 背包里的可用物品。
2. 背包里的不可用物品。
3. 容器库存里的可用物品。
4. 已经穿在正式装备槽里的正式装备。

最低配也至少要有这三类：

1. 背包里的可用物品。
2. 容器里的可用物品。
3. 正式装备槽里的装备。

#### 9.2.2 需要先打开的界面

开始前先确认这三个界面都能打开：

1. 角色自己的库存界面。
2. 一个已经接好的容器界面，比如箱子或柜子。
3. 带正式装备槽的界面区域。

#### 9.2.3 开始前先确认的几件小事

1. 背包里确实有东西，不是在测空槽。
2. 容器里确实有东西，不是在测空容器。
3. 正式装备槽里确实已经穿了装备，不是装备还躺在背包里。
4. 角色当前能正常操作鼠标和键盘，不是被别的 UI 焦点卡住。

#### 9.2.4 显示与定位调试前，先确认最小必需绑定

这一轮如果你测的是“菜单明明创建了却看不见”“动作区不出按钮”“定位总觉得不对”，不要一上来先怀疑业务逻辑。先把最小必需绑定过一遍。

主菜单 Widget 这层，先按下面这个口径理解：

1. `ActionListContainer` 是最关键的最小绑定，没有它，动作项子 Widget 没地方挂，菜单很容易变成“只有壳子没有动作区”。
2. `ItemNameText`、`ItemInfoText`、`ItemIconImage` 不是显示链必需，但如果你要验证头部信息，就必须在蓝图里给到这些绑定位。
3. `CloseButton` 是可选的，不是菜单能不能显示的前提。
4. `RootBorder` 现在也不是“必须挂在 `CanvasPanel` 下”的硬前提了。它更偏向于提供整体背景、点击内外判断和更稳定的期望尺寸。

动作项子 Widget 这层，先记住一条：

1. `ActionButton` 是最小必需绑定。没有它，动作项就算被创建出来，也没有正常点击入口。

2. 能在当前菜单 Widget 上改到 `MenuAnchorOffset` 和 `ViewportEdgePadding`。
3. 准备两个测试位置：一个在屏幕中部，一个靠近右边缘或下边缘。

入口：

1. 进入游戏。
2. 打开角色自己的库存界面。
3. 先在屏幕中部找一个有效物品槽。

操作步骤：

1. 用当前默认参数先右键一次，记住菜单相对鼠标的大致距离。
2. 只调大 `MenuAnchorOffset.X`，再次右键。
3. 看菜单是否明显离鼠标更远一些，但仍保持在鼠标右边。
4. 再把 `MenuAnchorOffset.X` 调小，甚至接近零，再次右键。
5. 看菜单是否更贴近鼠标。

9. 看菜单是否会因为边缘夹取而自动往上收一点。
10. 如果你在调试器里跟代码，确认最终位置在 `ResolveMenuCanvasPosition()` 里经过了 `ViewportEdgePadding` 相关的 `Clamp`。

预期现象：

1. `MenuAnchorOffset` 改动后，菜单与鼠标之间的相对距离会立刻跟着变化。
2. `ViewportEdgePadding` 生效时，菜单不会贴边压死，也不会直接跑出可视区域。

如果不对，先查哪里：

1. 先查 `Source/AegisOdyssey/UI/Widgets/Inventory/AOInventoryItemContextMenuWidget.h` 里 `MenuAnchorOffset` 和 `ViewportEdgePadding` 是否真的暴露给调参侧。
2. 再查 `Source/AegisOdyssey/UI/Widgets/Inventory/AOInventoryItemContextMenuWidget.cpp` 里的 `ResolveMenuCanvasPosition()` 是否真的把这两个参数用于最终定位。
3. 如果靠边仍然出屏，再查 `PlayerScreenGeometry.GetLocalSize()` 和最终 `Clamp` 上下界是不是按当前视口算出来的。

### 9.6 快速验收口径

你如果只想最后快速收口，就按这几条看：

1. `InventoryItemContextMenuClass` 和 `ActionEntryWidgetClass` 都已经显式接好，菜单与动作项都能正常创建。
2. 右键菜单唯一入口已经是 `SourceInventory->GetOrCreateContextMenuViewModel(...)`，不再从 `UMVVM_InventoryMenu` 取菜单来源。
3. `InventoryComponent` 现在只负责持有自己的 `ContextMenuViewModel`，不再做统一宿主解析。
4. 不同 `SourceInventory` 打开菜单时，会直接命中各自组件上的菜单 ViewModel，而不是共享某个额外解析出来的统一宿主。
5. 菜单显示链已经是“先注入 ViewModel 并刷新，再加入视口”，第一次打开时不会因为刷新时机太早而拿到旧尺寸。
6. 主菜单最小必需绑定至少保证 `ActionListContainer` 存在；动作项最小必需绑定至少保证 `ActionButton` 存在。
7. `RootBorder` 不再依赖必须挂在 `CanvasPanel` 下才能正常显示或定位。
8. 菜单定位已经走 `screen space -> player screen local space` 的转换，不会因为坐标空间错用而明明加入 viewport 却肉眼看不到。
9. 背包可用物品右键会出现“使用”，点完能真正生效。
10. 背包不可用物品右键不会误出现“使用”。
11. 菜单能通过点外部和 `Escape` 正常关闭。
12. 容器库存右键“使用”会走 interaction session mutation 链。
13. 正式装备槽右键出现的是“卸下”，不是普通“使用”。
14. 正式装备卸下后回到 `BackPack`。
15. 菜单头部图标能跟着物品定义里的图标配置正确显示。
16. 连续打开同一个右键菜单时，标题、数量、图标不会串到上一次打开的物品。
17. 菜单关闭后再次打开，动作项不会越积越多，旧动作状态也不会残留。
18. 反复切换不同物品时，头部展示和动作项都能跟着当前物品刷新，而不是沿用旧实例内容。
19. 如果能观察实例层面表现，菜单应是复用同一个 `AOInventoryUI` 缓存实例；动作区则应表现为“主菜单 Widget 复用 + 动作项子 Widget 重新分发动作项 ViewModel”的结构，而不是 C++ 手写样式按钮。

### 9.7 这一轮最容易误判的地方

最后把最常见的几种误判也记一下。测偏了，结论会整组跟着偏。

1. 菜单里有没有“使用”，先看实例的 `CanUseFromInventory(...)`，不要先怀疑 UI 配表。
2. 容器里的“使用”和背包里的“使用”表面一样，后端入口不一样，这一条别漏看。
3. 正式装备槽和普通库存槽都能右键，不代表它们是同一套语义。
4. 右键空槽本来就不应该弹出有效菜单，这不是这轮要报的问题。
5. 快捷栏和技能栏测的是“上下文有没有恢复对”，不是单纯测有没有按钮。
6. 这轮动作区已经改成“动作项 ViewModel + 动作项子 Widget”链路了，所以如果你看到动作不对，别再按旧思路去找 `RebuildActionButtons()` 这类已经下线的入口。
7. `UMVVM_InventoryMenu` 现在已经不是右键菜单来源；如果你还在那边找 `ContextMenuViewModel`，方向已经错了。
8. 如果你还在按“统一宿主”“BackPack 共享一份菜单 ViewModel”的旧思路测，这轮很容易把本来正确的 `SourceInventory` 自持有行为误判成串线或丢上下文。
9. 如果你故意不配 `InventoryItemContextMenuClass` 或 `ActionEntryWidgetClass`，菜单起不来，优先视为宿主接线没配好，不要再假设有默认路径自动回退。
10. 如果你在调试器里看到 `SetContextMenuViewModel(...)` 和 `InitializeForInventorySlot()` 都进了，但屏幕上没看到菜单，不要立刻断言“菜单没创建”；更常见的真因是定位坐标空间错了，或者蓝图最小绑定没接好。
11. 如果菜单蓝图层级改过，不要再拿“`RootBorder` 必须直接挂在 `CanvasPanel` 下”当成默认前提；当前实现已经不再依赖这条旧约束。
12. 如果菜单外壳能出来但动作区空白，先查 `ActionListContainer` 和 `ActionEntryWidgetClass`；如果动作项出现了但点不动，先查 `ActionButton`。这两类问题很容易被误判成 ViewModel 或定位故障。
