## 一句话先说结论

当前这套武器攻击表现系统，结构主线没变，但刀光轨迹这部分的实际落地路径已经从“高级 History Ribbon 方案”回退到了“更朴素、可先验证链路”的试验实现。  
另外，近战普攻“扫到了但不出伤”的历史病根也已经确认，不是 Niagara，也不是 GC，而是旧逻辑错误把 `bIsBroken` 当成了伤害总开关。

## 当前已经确认的工程事实

### 1. 统一入口思路没有变

这条主线仍然成立，而且应该继续坚持：

1. 武器只提供默认攻击表现入口
2. `AttackEffectProfile` 负责编排“什么时机触发什么 `CueTag`”
3. `GameplayCue` 负责真正落地 Niagara、音效等表现
4. 运行时如果要拿武器本体、组件、socket，一律从 `WeaponInstance` 往下取

这部分结构边界没有推翻，后面接手的人不要因为刀光实现策略调整，就把整条链又打散回 Ability 里手写。

## 这轮已经修掉的历史问题

### 2. 近战普攻“命中了但不出伤”的病根已经定位

这件事现在可以明确写死：

- 问题只在近战普攻上出现过
- 表现是“扫描命中了，但没掉伤害”
- 后来通过测试现象确认，它和破韧提示出现的时机强相关

最后定位到的根因是：  
旧逻辑错误把 `bIsBroken` 当成了某种“后续不再结算伤害”的总开关。

这条设计本身就是错的：

- 破韧不等于无敌
- 破韧更不等于命中无效
- 真正合理的结果反而应该是破韧后更鼓励追击，而不是吞伤害

当前源码已经改到正确方向。  
正式伤害入口 `ApplyDamageToTarget(...)` 不再因为 `bIsBroken` 提前返回：

- [AOCharacterCombatManagerComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOCharacterCombatManagerComponent.cpp:62)

要注意的是，`bIsBroken` 这个状态本身没有被完全删掉。  
它仍然会用于部分反应和受控逻辑，比如：

- [AOCharacterCombatManagerComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOCharacterCombatManagerComponent.cpp:418)

这层语义是“避免某些反应重复触发”，不是“禁止后续掉血”。

### 3. `DamageImmunity` 不是这次要删的对象

这次顺手还要给下一个 AI 讲清楚一个很容易混掉的点。

当前项目里确实还有 `Gameplay.DamageImmunity` 这条正式规则：

- [AOHealthAttributeSet.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Attributes/Core/AOHealthAttributeSet.cpp:18)
- [AOHealthAttributeSet.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Attributes/Core/AOHealthAttributeSet.cpp:62)
- [AOCharacterCombatManagerComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOCharacterCombatManagerComponent.cpp:148)
- [AOCharacterCombatManagerComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOCharacterCombatManagerComponent.cpp:152)

但这条和 `bIsBroken` 不是一回事。

当前应该这样理解：

- `bIsBroken` 是之前被误用成了错误前置条件，现在已经明确属于历史病根
- `DamageImmunity` 是正式无伤窗口语义，目前不该顺手删

后面如果再遇到“命中了但不掉血”，第一件事不是继续怀疑破韧，而是先区分：

1. 是不是又有别的错误前置判断挡住了正式伤害入口
2. 还是目标确实挂着 `Gameplay.DamageImmunity`

## 刀光轨迹这轮到底做到了哪一步

### 4. 动画窗口语义已经正式拆开

这点很关键，因为旧文里不是这么写的。

当前已经明确拆成两个窗口：

1. `AOAttackEffectWindow`
   - 只保留武器判定窗口 / 给拥有者加减标签这层语义
   - 不再负责刀光 Begin / End 派发
   - 源码见 [AOAttackEffectWindow.h](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Animation/NotifyState/AOAttackEffectWindow.h:11)
2. `AOAttackTrailWindow`
   - 新增的专用刀光显示窗口
   - 只负责 `CombatWindowBegin / CombatWindowEnd`
   - 源码见 [AOAttackTrailWindow.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Animation/NotifyState/AOAttackTrailWindow.cpp:55)
   - 源码见 [AOAttackTrailWindow.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Animation/NotifyState/AOAttackTrailWindow.cpp:78)

当时这么拆，不是为了形式好看，而是因为已经确认了一件事：

- 武器判定窗口通常很短
- 刀光显示窗口为了观感往往应该更长
- 这两者如果继续绑死在一个 `AnimNotifyState` 上，表现会天然生硬

所以这轮之后，后面接手的人不要再默认“武器判定窗口 == 刀光显示窗口”。

### 5. `AOAttackTrailWindow` 当前做的事非常明确

当前 `AOAttackTrailWindow` 本身不算复杂，它主要做这几步：

1. 只在服务端工作
2. 找当前角色
3. 找当前角色的 ASC
4. 从当前武器管理器里取 `WeaponInstance`
5. 组 `FGameplayCueParameters`
6. 在 Begin / End 时分别派发 `CombatWindowBegin / CombatWindowEnd`

源码入口：

- [AOAttackTrailWindow.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Animation/NotifyState/AOAttackTrailWindow.cpp:13)
- [AOAttackTrailWindow.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Animation/NotifyState/AOAttackTrailWindow.cpp:55)
- [AOAttackTrailWindow.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Animation/NotifyState/AOAttackTrailWindow.cpp:78)

这里最重要的一点是：  
它会尽量把当前 `WeaponInstance` 塞进 `CueParameters.SourceObject`，这样后面的 GC 才能顺着运行时武器实例继续往下找组件和 socket。

### 6. `WeaponTrail` 当前不是最终版，而是试验版

这点必须讲得非常直白。

当前 [AOCombatGameplayCueNotify_WeaponTrail.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Combat/Cue/AOCombatGameplayCueNotify_WeaponTrail.cpp:65) 不是之前讨论的那种完整“历史轨迹重建 + Ribbon 连续消费”的最终解。

它现在更接近一条朴素的试验路径：

1. 从 `WeaponInstance` 解出对应的武器组件
2. 用开始 socket、结束 socket 算当前线段
3. 取中点作为生成中心
4. 取起终点方向作为朝向
5. 用 `SpawnSystemAttached(...)` 直接挂 Niagara

关键源码：

- [AOCombatGameplayCueNotify_WeaponTrail.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Combat/Cue/AOCombatGameplayCueNotify_WeaponTrail.cpp:97)

并且要注意，后面原本那套更重的持续更新逻辑，当前已经刻意收掉了：

- [AOCombatGameplayCueNotify_WeaponTrail.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Combat/Cue/AOCombatGameplayCueNotify_WeaponTrail.cpp:215)

也就是现在这版不是“每帧把 `TrailStart / TrailEnd / Width / Direction` 稳定推给 Niagara”的成熟路径，  
而是先围绕 `SpawnSystemAttached(...)` 这条最容易验证链路的方案落地。

### 7. 为什么会回退到这条更朴素的路

不是因为前面的高级方案理论上错了，而是因为它对当前资源接线和 Niagara 配置门槛太高了。

之前讨论过的方向包括：

- `History Ribbon`
- 连续历史样本数组
- Scratch 读数组
- 更复杂的 Niagara 用户参数消费

这些方向不是没有价值，但当前工程状态下有两个现实问题：

1. 接线复杂，容易把问题从“代码链路”变成“资源作者配置细节”
2. 用户当前最需要的是先验证这条链到底通不通，而不是先上最高难度制作流程

所以这轮的现实选择是：

- 先保住统一链路
- 先让刀光能通过单独窗口被 GC 驱动起来
- 先用更朴素的方式验证运行时 `WeaponInstance -> 组件 -> socket -> Niagara` 这条线

这不是理论退化，而是工程上先收口。

## 奶瓜这轮的问题，现在该怎么定性

### 8. 观感问题不再主要归咎于 C++

这轮后半段有个很重要的结论，后面接手的人必须知道。

当时刀光“看着卡、看着僵、出来和消失很生硬”，一开始很容易以为都是轨迹几何计算的问题。  
但实际往后测，已经基本分清楚了：

1. 有一部分是窗口太短导致的节奏问题
2. 但很多“像视频硬切一样突然出现 / 突然消失”的感觉，本质是 Niagara / 材质层的表现问题
3. 奶瓜那边最后已经自行把这层内容侧问题先修住了，所以当前先按“效果问题暂时解决”处理

也就是说，后续不要一看到“观感不顺”就本能回头改 `WeaponTrail` C++。  
先分清楚是：

- 运行时链路没打通
- 还是效果资源本身淡入淡出、宽度收缩、尾部收束没做好

## 下一步如果还要继续推进，应该怎么想

### 11. 现阶段最重要的边界

后续如果继续做刀光，不要把这几条边界搞乱：

1. `AttackEffectProfile` 继续只管触发语义编排，不要回头塞具体轨迹实现细节
2. `WeaponTrail` 继续只管表现承接，不要反过来决定战斗真值
3. 武器相关运行时信息继续从 `WeaponInstance` 往下拿，不要重新写死到静态定义或角色本体 socket 上
4. 武器判定窗口和刀光显示窗口保持分离，不要图省事重新绑回一个 `NotifyState`

### 12. 如果后面还要升级视觉效果，方向也别再摇摆

当前更合理的理解是：

- 这轮已经把“统一链路 + 独立刀光窗口 + 运行时武器实例解析”这部分先落住了
- 更高级的连续 Ribbon 轨迹，仍然可以作为后续研究方向
- 但那是下一阶段的表现升级，不是当前这版事实

换句话说，后续如果还要继续做得更像官方那种丝滑轨迹，应该把它当成“下一层视觉升级工程”，而不是“当前这版还没写完所以必须立刻补齐”。
