- `Source\AegisOdyssey\SkillSystem\Core\AOSkillGameplayAbility.h`

这部分语义现在明确下放给具体技能自己决定。

### 2. 火山喷发已经从“Ability 自己一直拖着不结束”改成“动画起手 + runtime 接管”

核心文件：

- `Source\AegisOdyssey\SkillSystem\Abilities\AOSkillAbility_VolcanoBurst.h`
- `Source\AegisOdyssey\SkillSystem\Abilities\AOSkillAbility_VolcanoBurst.cpp`

- `Source\AegisOdyssey\SkillSystem\Execution\Runtime\AOSkillAreaSequenceRuntime_VolcanoBurst.cpp`

当前火山喷发已经明确成下面这条链：

1. Ability 激活
2. 播放起手蒙太奇
3. 等待 `StartSequenceEventTag`
4. 到事件点后生成独立 runtime actor
5. 后续喷发波次、落点结算、生命周期清理由 runtime actor 接管
6. Ability 在完成 handoff 后收口，而不是陪 runtime 活到最后

这个改动的本质意义是：

- 不让长生命周期区域技能继续阻塞玩家的后续技能和移动体验

- 起手施法阶段可以隐藏武器
- Ability 结束时恢复武器
- 支持后摇移动脱手

关键点是：

- 它不是靠固定 `SequenceStartDelay` 启动
- `SequenceStartDelay` 这套旧语义已经不该再加回来

## 五、目前技能链真正已经打通到哪一层

当前可以把技能链理解成这条主路径：

1. 玩家或 AI 触发技能 Ability
2. Ability 通过动画/事件决定正式执行点
3. 技能生成自己的 runtime actor 或 projectile
4. runtime actor 或 projectile 负责自己的命中检测与生命周期
5. 命中结果再回送到 Skill Ability 既有尾链
6. Skill Ability 再复用现有战斗效果应用主链

这个“运行时对象把命中结果送回 Ability”的设计非常关键。

它意味着：

- 技能运行时对象不应该自己偷偷再发明一套伤害系统
- 技能运行时对象也不应该自己偷偷再发明一套独立的战斗结算真相

后续新增技能也应尽量沿着这个结构走。

### 5. 当前阶段已经拍板的战斗系统正式口径

这一节不是“以后再讨论”，而是当前接手时就应该直接遵守的正式口径。

#### 5.1 资源与状态语义

- `Stamina` 是**韧性条**
- `Vigor` 是**体力条**

当前正式定义为：

- 韧性条会在**任何受击**时按一定比例扣除
- 格挡成功时，韧性条仍然会扣，但会**少扣一点**
- 韧性条清空后，角色进入**破韧状态**
- 破韧期间角色**不能移动，也不能做任何动作**
- 破韧持续一段时间后，韧性条**直接回满**
- 体力条用于奔跑、翻滚、格挡等动作消耗
- 体力条会缓慢恢复

额外边界：

- 这套韧性条**不做成只狼那种呼吸式持续对抗条**
- 翻滚后续要正式补上体力消耗，不再长期遗漏

#### 5.2 防御判定优先级

命中进入战斗系统后的优先级，当前正式按下面这条链理解：

1. 先判定是否命中无敌帧
2. 再判定是否命中弹反窗口
3. 再判定是否命中格挡窗口
4. 最后才进入正常受击与正常伤害结算

也就是说：

- 无敌帧成立时，直接视为**没打到**
- 完全格挡成立时，进入**防御成立**结果，而不是普通受击
- 弹反成立时，优先走弹反结果，不再落回普通格挡结果

#### 5.3 无敌帧、格挡、弹反的第一版口径

- 翻滚无敌帧成立时，正式语义是**直接视为没打到**
- 完全格挡与部分减伤格挡都要支持
- 格挡会消耗资源，而且 `Stamina` 与 `Vigor` 都会按设计参与
- 弹反成功时会**大幅扣除攻击方韧性条**
- 在攻击方还没被打到破韧之前，弹反成功也要：
  - 打断攻击
  - 让攻击方进入被弹反反馈
- 一旦韧性条被打空，就进入正式破韧状态

#### 5.4 多段命中的正式方向

当前已经明确，不能继续用“同一次攻击永远只命中一次”的窄逻辑覆盖全部攻击。

第一版正式方向应至少支持下面四类命中策略：

1. 单次命中：一次攻击激活期间，同目标只结算一次
2. 分段命中：一招内有多个独立命中窗，每个命中窗各自允许结算一次
3. 间隔重复命中：同目标可重复命中，但必须满足最小时间间隔
4. 周期持续命中：区域内停留目标按固定周期重复结算

后续普攻、技能、投射体、AOE，不应再各自偷偷维护一套重复命中语义。

#### 5.5 统一攻击来源与上下文最小集

当前已经拍板，第一版不要一上来堆太多来源字段，但至少要统一收口到这几个：

- `AttackTag`
- `SkillTag`（有技能来源时再带）
- `WeaponTag`（有武器来源时再带）

同时建议优先放进战斗上下文的字段包括：

- `Critical`
- `Blocked`
- `Parried`
- `HitInvulnerability`
- `HitResult`
- `DamageType`

原则是：

- 先放**真正影响结算解释权**的字段
- 不影响正式结算的来源信息，先不急着无限扩字段

#### 5.6 友伤与阵营的当前边界

当前阶段不是“不做友伤”，而是：

- **当前单人 PVE 测试阶段先不正式展开友伤规则**
- 但命中最终必须留有一个**统一敌我/阵营判定收束点**

这样后续真正补玩家/敌军/友军/阵营关系时，不会严重冲击现有战斗主链。

#### 5.7 UI、消息与提示字的正式口径

这一条已经明确为硬规则：

- **UI 只订阅战斗系统产出的最终消息**
- **UI 不允许自己猜是不是暴击、是不是格挡、是不是无敌**

第一版消息化后，至少应支持区分：

- 普通伤害
- 暴击
- 弹反
- 免疫 / miss 语义
- 受击反馈相关上下文

但当前又明确规定：

- **完全格挡不跳字**
- **无敌帧命中失败不跳字**

也就是说，“没有提示字”本身也是正式设计结果，不是漏做。

#### 5.8 第一版反馈层的最低验收口径

第一版不是大而全的重演出版本，但必须至少形成最小闭环：

- 正常受击时，有基础受击反馈
- 格挡成功时，有基础防御反馈
- 弹反成功时，攻击方被中断并出现明显被弹反反馈
- 这些反馈应统一建立在战斗真相、消息层与 `GameplayCue` 之上

不要把反馈重新散写回各个攻击实现里硬编码。

## 八、下一阶段建议的正式工作顺序

下面这个顺序是给下一个 AI 的建议，不是死规矩，但强烈建议按这个顺序做。

### 第 1 步：先统一“所有攻击命中 -> 战斗结算”数据语义

目标：

- 搞清楚所有攻击命中后，到底往 `GameplayEffectSpec` 里带什么
- 搞清楚技能伤害、普攻伤害、未来格挡/弹反修正，最终如何统一进入 `ExecCal_Damage`

重点文件：

- `Source\AegisOdyssey\SkillSystem\Core\AOSkillGameplayAbility.cpp`
- `Source\AegisOdyssey\SkillSystem\Execution\Runtime\AOSkillProjectile_Fireball.cpp`
- `Source\AegisOdyssey\SkillSystem\Execution\Runtime\AOSkillAreaSequenceRuntime_VolcanoBurst.cpp`
- `Source\AegisOdyssey\ExecCal\ExecCal_Damage.cpp`
- `Source\AegisOdyssey\AbilitySystem\Attributes\AOHealthAttributeSet.cpp`

要解决的问题：

- 所有攻击命中后怎么区分到底是哪种攻击造成的
- 攻击标签、技能标签、武器标签、伤害类型怎么进入 EffectSpec / Context
- 将来弹反、格挡、无敌帧，应该在哪一层拦截和修正

### 第 2 步：先补战斗 Context，而不是先急着做 UI 飘字

目标：

- 把真正影响伤害解释权的语义放进 `FAOGameplayEffectContext`

建议优先考虑补进去的字段：

- `bWasBlocked`
- `bWasParried`
- `bHitInvulnerability`
- `SourceAttackTag`
- `SourceSkillTag`
- `SourceWeaponTag`
- `DamageType`

理由很简单：

- 如果没有统一上下文，后面暴击字、弹反字、伤害字、受击反馈只能到处靠猜

### 第 3 步：先统一多段命中与持续命中策略

目标：

- 不再让普攻、技能、投射体、AOE 各自维护一套“是否重复命中”的窄逻辑
- 先把单次命中、分段命中、间隔重复命中、周期持续命中收成统一策略

这一层如果不先收，后面翻滚、格挡、弹反都很容易在重复结算与重复反馈上继续乱掉。

### 第 4 步：翻滚无敌帧正式收口

目标：

- 不要只让翻滚“动作看起来像翻滚”
- 要让翻滚在战斗链上正式拥有无敌窗口语义

推荐方向：

1. 用蒙太奇 `NotifyState` 或战斗窗口标签定义无敌帧窗口
2. 在窗口期间给角色加一个正式可判定的标签或 GE
3. 伤害执行前检查该语义并做免疫或特殊反馈

可直接复用的现有点：

- `AOAnimNotifyState_SendGameplayEventWindow`
- `GA_Roll`
- `TAG_Gameplay_DamageImmunity`

正式结果口径：

- 无敌帧成立时直接视为没打到
- 不掉血
- 不跳字
- 但命中主链里仍然要留下可追溯的“无敌帧拦截结果”

### 第 5 步：格挡与弹反正式收口

目标：

- 不只停留在 `GA_Block` 播动画和挂标签
- 要把“成功格挡”和“成功弹反”真正接入伤害主链和受击主链

建议拆成两个层面：

- 防御成立：减伤、抵消、消耗 `Vigor` 与 `Stamina`、播放防御反馈
- 弹反成立：中断对方、大幅扣除对方韧性、给攻击方施加被弹反馈、触发专门表现

优先看的文件：

- `Source\AegisOdyssey\AbilitySystem\Abilities\Attack\Combat\GA_Block.cpp`
- `Source\AegisOdyssey\StateTree\Tasks\STT_PlayBlockAnimation.cpp`
- `Source\AegisOdyssey\AbilitySystem\Attributes\AOHealthAttributeSet.cpp`

### 第 6 步：伤害显示、暴击显示、受击反馈正式消息化

目标：

- 把当前半成品的伤害广播链真正打通

优先落点：

- `FAOVerbMessage`
- `TAG_AO_Damage_Message`
- `UAOHealthAttributeSet::PostGameplayEffectExecute`

建议方向：

1. 正式启用伤害消息广播
2. 广播内容至少要带：伤害数值、是否暴击、来源、目标、上下文标签
3. UI 或表现层只订阅消息，不自己猜结算

这一步完成后，才适合正式做：

- 普通伤害数字
- 暴击伤害数字
- 格挡/弹反提示字
- 命中反馈和屏幕反馈

但这里要注意当前已经拍板的两个例外：

- 完全格挡不跳字
- 无敌帧命中失败不跳字

### 第 7 步：技能受击反馈与防御反馈表现接 GameplayCue / 消息层

目标：

- 让“命中”和“数值”不是只有结算，没有反馈

后续比较合理的分层是：

- 伤害真相：`GameplayEffect / AttributeSet / EffectContext`
- 表现真相：`GameplayCue`
- UI 数字真相：消息系统 / ViewModel / Widget

不要把这些全塞回技能 runtime actor 里硬写。

## 十、下一阶段不要再走的歪路

### 1. 不要让技能 runtime actor 自己演化成第二套战斗系统

它们应该负责：

- 生命周期
- 命中检测
- 局部表现触发

它们不应该长期负责：

- 自己独立算一整套伤害真相
- 自己独立维护受击真相
- 自己独立维护 UI 真相

### 2. 不要把战斗表现和伤害真相混成一层

后续一定要尽量分清：

- 数值真相
- 网络真相
- 特效真相
- UI 真相

### 3. 不要在多个地方各自偷偷判断“是不是暴击/是不是格挡/是不是无敌”

后续必须努力收口到统一上下文，否则：

- 飘字和实际伤害可能不一致
- 客户端和服务端可能不一致
- 技能和普攻可能各自维护一套判定

### 4. 不要重新把 SequenceStartDelay 这种旧语义捡回来

火山喷发和火球术这一轮最重要的改进之一，就是：

- **用动画事件控制正式执行时序**

这条方向不要再倒退。

## 十一、可以直接作为下一阶段目标的一个简化方案

如果下一个 AI 要快速开始工作，我建议直接按这个最小顺序推进：

1. 先把所有攻击命中统一写进 EffectContext / EffectSpec
2. 再补 `Blocked / Parried / Invulnerable / Critical / AttackTag / DamageType` 这些战斗上下文字段
3. 再统一多段命中、重复命中、持续命中的正式策略
4. 再让 `AOHealthAttributeSet` 成为正式伤害广播总入口
5. 再补翻滚无敌帧、格挡、弹反这三类正式结算
6. 最后再把伤害数字、暴击数字、命中反馈、受击反馈接到消息层与 Cue 层

这个顺序的好处是：

- 不会一上来就把 UI 做死
- 不会一上来就把技能和战斗耦得更乱
- 能先把“真相层”收干净，再做表现层

当前项目已经不是“还在搭技能系统骨架”的阶段了。

- **技能释放链已经基本成型**
- **火山喷发和火球术已经有了可复用的正式写法**
- **GameplayCue 接入已经开始收口**
- **下一阶段最关键的工作，是把技能命中正式接入战斗系统，把伤害、暴击、防御、弹反、无敌帧、受击反馈、伤害显示统一成一条可信主链**
- **下一阶段最关键的工作，是把所有攻击命中正式接入战斗系统，把伤害、暴击、防御、弹反、无敌帧、韧性、体力、受击反馈、伤害显示统一成一条可信主链**

接手时不要再从“怎么再做一个技能”开始想，应该从：

- **所有攻击命中之后，战斗真相怎么统一**

这个问题开始想。
