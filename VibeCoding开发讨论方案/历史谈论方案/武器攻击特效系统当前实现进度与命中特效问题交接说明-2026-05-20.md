## 第二章 这轮工作到底做到哪了

这一轮工作的核心，不是“给武器多挂几个特效字段”，而是把武器攻击表现从零散写法收成一条统一路径。

现在已经明确的主线是：

1. 武器定义层只负责给出默认的 `AttackEffectProfile` 入口。
2. `AttackEffectProfile` 只负责编排“什么时候触发哪些 GameplayCue”。
3. Combat 专用 GameplayCue 负责真正把表现落到 Niagara、音效这些资源上。
4. 运行时如果表现要和当前武器实例强绑定，不再直接硬引用某个具体武器蓝图对象，而是统一从 `WeaponInstance` 往下拿。

这条主线已经不只是停留在文档里，关键代码都已经进工程了。

## 第三章 这轮已经落地的关键实现

### 3.1 Combat GC 已经支持“单个 GC 内部分组分流”

这次新增了一个专门的 Combat 瞬时 GameplayCue：

- [AOCombatGameplayCueNotify_Burst.h](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Combat/Cue/AOCombatGameplayCueNotify_Burst.h)
- [AOCombatGameplayCueNotify_Burst.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Combat/Cue/AOCombatGameplayCueNotify_Burst.cpp)

这层现在已经支持：

1. 一个 GC 内部挂多组效果。
2. 每组效果可以根据战斗上下文继续分流。
3. 每组效果下面可以继续挂多个 Niagara / 音效动作。

当前支持的过滤条件包括：

- `RequiredSourceTags`
- `RequiredTargetTags`
- `RequiredAttackTags`
- `RequiredSkillTags`
- `RequiredWeaponTags`
- `RequiredDamageTypeTags`
- `CriticalRequirement`
- `BlockedRequirement`
- `ParriedRequirement`
- `HitInvulnerabilityRequirement`

这件事的意义很明确：`Profile` 不再负责长成一个越来越重的条件编辑器，它只负责决定“这次触发哪个 GC”；更细的普通命中、暴击命中、不同武器类型命中、不同伤害类型命中，继续留在同一个 Combat GC 内部分流。

这一步很重要。没有这一步，GC 内部分组虽然能写条件，但碰到格挡、弹反、破韧这类正式结果时，看不到完整战斗真相，分流能力会断一截。

## 第四章 这轮已经明确守住的边界

这些边界已经讨论过，而且这轮实现也是照这个边界收的。下一个 AI 接手时，不要轻易再把它们改回去。

### 4.1 `Profile` 不是万能配置表

`UAOAttackEffectProfile` 现在只承载：

- 触发语义
- `CueTag` 分发

它不直接承载：

- Niagara 资源编排细节
- 音效资源编排细节
- 战斗真相判断

### 4.2 Combat 表现统一走 GameplayCue，不再混两套入口

这一版的原则已经定死了：

**攻击表现编排层只编排 GameplayCue。**

不要一部分地方手动 `Spawn Niagara`，另一部分地方又走 `ExecuteGameplayCue`。那样后面不仅维护乱，联机同步和排查也会一起乱掉。

### 4.3 武器相关特效不要直接绑定具体蓝图对象

后续如果要做刀光、武器发光、附魔常驻表现、武器特定 socket 持续挂件，统一按这条路径走：

- 当前角色
- 当前武器管理器
- 当前 `WeaponInstance`
- 当前运行时生成的武器 Actor / 组件
- 对应 socket

不要再走“配置里硬拖一个具体武器蓝图对象”的老路。

### 4.4 这轮只收战斗相关模块，不扩散到无关系统

本轮改动真正涉及的模块范围很窄，主要是：

- `Combat/Cue`
- `Combat/Effects`
- `Character/CombatManager`
- `Equipment/Weapons`
- `AbilitySystem/Attributes/Core`

不要顺手把 UI、技能系统别的分支、装备栏别的职责、角色别的输入逻辑一起卷进来。

## 第五章 当前还没有彻底解决的问题

### 5.1 现象：有时候命中并且出伤害了，但没有命中特效

这是现在还没闭环的问题，而且已经不是“偶尔看错”的级别。

当前用户反馈很明确：

1. 武器命中后，有时候目标明确掉血。
2. 但是同一次命中对应的命中特效没有出现。
3. 当前只配置了普通伤害和暴击两种基础命中特效。

也就是说，这里不是“特殊结果没配特效”，而是最基础的命中特效偶发丢失。

### 5.2 目前已经缩小到什么范围

当前已经能比较确定地排除一部分旧怀疑：

1. 这不是之前那种“命中没进正式伤害链”的问题。
2. 现在讨论的是“已经进了正式伤害链，目标已经掉血，但命中特效偶发没出来”。
3. 这也不是武器 socket 搜索不全导致的刀光挂点问题，那是另一条链。

范围现在已经缩到命中后的表现链后半段，也就是：

1. `AOHealthAttributeSet` 掉血后构造 `CueParameters`
2. 基础 `GameplayCue.Combat.Hit`
3. `AttackEffectProfileRuntime::DispatchTrigger(..., HitConfirmed, ...)`
4. Combat GC 内部分组匹配
5. 最终实际播放位置和资源可见性

### 5.3 目前已经确认过但还没钉死根因的几个判断

#### 第一条：只要正式掉血成立，`HitConfirmed` 理论上应该已经被尝试触发

这是当前代码里的明确事实。

在 [AOHealthAttributeSet.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Attributes/Core/AOHealthAttributeSet.cpp) 里，正式掉血分支发生后，会继续做两件事：

1. `TargetASC->ExecuteGameplayCue(CombatResultMessage.CueTag, CueParameters);`
2. `FAOAttackEffectProfileRuntime::DispatchTrigger(..., HitConfirmed, ...)`

所以“有伤害”不等于“一定看得到特效”，但至少说明：

**后半段表现链理论上已经被尝试走到了。**

#### 第二条：当前真正可疑的，不再是伤害结算，而是表现层分流和分发

当前比较像根因的区域只剩这些：

1. `SourceObject` 到 `AttackEffectProfile` 的解析链有没有偶发拿不到东西。
2. 这次命中特效到底没走到基础 Hit GC，还是没走到 `HitConfirmed` 分发出去的额外 GC。
3. GC 走到了，但内部 `EffectGroup` 匹配失败了。
4. GC 和分组都走到了，但 HitResult 不完整，导致落点退回 Actor 原点或模型内部，看起来像没播。

#### 第三条：标签语义本身还需要继续定边界

围绕 GC 分组过滤条件，这轮已经先讨论清楚了一部分，但没有彻底形成最终规则。

目前的阶段性理解如下。

##### `AttackTag / SkillTag / WeaponTag`

这三类更像“单值语义身份”。

它们的价值是：

- 区分攻击段
- 区分技能来源
- 区分武器类型

但它们未必每次都稳定完整，所以它们到底应该算“硬前提”，还是“有值才参与分流”，现在还没有最终拍板。

##### `Critical / Blocked / Parried / HitInvulnerability`

这四类更像“正式战斗结果真相”。

当前代码里它们是三态判断：

- `Ignore`
- `MustBeTrue`
- `MustBeFalse`

这套语义本身没问题，但当前实现还有一个细节要记住：

如果 `EffectContext` 没带到，当前代码会把实际值当成 `false` 参与判断。  
这意味着：

- `MustBeTrue` 会失败
- `MustBeFalse` 会通过

所以它现在是“偏实现层的严格”，还不是完全对称语义上的严格。

##### `SourceTags / TargetTags / DamageTypeTags`

这三类当前实现全都是 **AND** 语义，不是 OR。

代码逻辑是：

- `RequiredTags.IsEmpty() || ActualTags.HasAllExact(RequiredTags)`

也就是说，只要在某一组里填了多个标签，这组就要求实际标签集合同时拥有全部这些标签。

这里目前还没定死两件事：

1. 未来要不要为其中某些条件提供更宽松的 OR 语义。
2. 哪些条件适合做基础命中特效过滤，哪些只能做进阶分流条件。

### 5.4 关于 `SourceTags` 的这次讨论，当前停在哪

用户这轮明确提到过一个很重要的现象：

- 当前 GC 配的是 `SourceTags`
- 配的是 `State.Equip.Sword`
- 用户认为这个标签稳定存在于角色身上
- 但普通攻击命中特效仍然偶发不触发，只出伤害

这条信息很关键，因为它意味着两种可能：

1. 用户看到的“角色身上有这个标签”，并不等于这次 `CapturedSourceTags` 里真的稳定有这个 tag。
2. 这次偶发没特效的根因不在 `SourceTags` 本身，而在更后面的 Profile 解析、GC 分发或落点可见性。

目前还没有最终证据能把这两种可能彻底区分开，所以这块只能算“高可疑区域”，还不能当成结论。

## 第六章 当前还没钉死的真相，下一位 AI 先确认什么

现在最忌讳的不是“改少了”，而是没钉死真相就开始盲改。

下一个 AI 接手后，先确认下面这几件事，再决定要不要改逻辑。

### 6.1 先确认没特效那次，走没走到 `HitConfirmed`

要先分清：

1. 没播的是基础 `GameplayCue.Combat.Hit`
2. 还是 `AttackEffectProfile -> HitConfirmed` 分发出去的那只额外 Combat GC

这两条链如果不先拆开，后面所有排查都会混在一起。

### 6.2 先确认没特效那次，`SourceObject -> Profile` 解析有没有丢

重点看：

- `CueParameters.SourceObject`
- `ResolveProfileFromSourceObject(...)`
- 实际有没有拿到当前武器正在使用的 `AttackEffectProfile`

如果这层没拿到 Profile，伤害照样可以成立，但额外命中特效链会断。

### 6.3 先确认没特效那次，GC 分组到底为什么没过

当前最值得加的不是一堆泛日志，而是最小、能定位分组过滤原因的日志。

建议直接打印：

1. 每次 `HitConfirmed` 分发命中了几个条目。
2. 每次 Combat GC 执行时，当前 `EffectContext` 里到底带了什么：
   - `AttackTag`
   - `SkillTag`
   - `WeaponTag`
   - `DamageTypeTags`
   - `bIsCritical`
3. 每个 `EffectGroup` 为什么失败：
   - 是 `SourceTags` 不过
   - 还是 `CriticalRequirement` 不过
   - 还是别的条件不过

### 6.4 先确认没特效那次，HitResult 和播放落点是不是有问题

如果这次其实已经走到 GC，只是 `HitResult` 没带完整，或者 ImpactPoint / ImpactNormal 异常，那么特效可能已经播了，只是播在不容易看见的位置。

所以还要确认：

1. `CueParameters.Location`
2. `CueParameters.Normal`
3. 当前选用的 Niagara / 音效资源是不是确实在那个位置可见

## 第七章 下一位 AI 不要急着动的地方

以下几个方向，在真相没钉死前，不要直接开始大改。

### 7.1 不要直接把所有过滤条件都删掉

现在虽然暴露出了“有伤害但没特效”的问题，但这不等于所有分流条件都不该存在。

否则后面剑、枪、火伤、冰伤、格挡、暴击这些表现层细分能力会一起被抹掉。

### 7.2 不要直接把所有条件都改成“缺失就放过”

这条只对一部分条件有讨论空间，比如：

- `AttackTag`
- `SkillTag`
- `WeaponTag`

但对于：

- `DamageTypeTags`
- `SourceTags`
- `TargetTags`
- `Critical / Blocked / Parried / HitInvulnerability`

不能想当然一刀切。

不然很容易出现：

- 配了火伤特效，普通物理伤害也播
- 配了剑命中组和枪命中组，结果 `WeaponTag` 缺失时两组都一起放行

### 7.3 不要把基础命中特效和进阶分流特效混成一层职责

现在已经越来越像的一个判断是：

1. 基础命中特效应该极其稳定，目标是“只要正式造成伤害，就一定有一个能看见的命中反馈”。
2. 进阶分流特效才去看武器类型、攻击段、伤害类型、附魔状态这些更细条件。

但这个判断还没有真正落成代码规则，所以先别急着重构整套条件系统。

### 这一轮测试前，先把职责区分看清楚

这一轮最容易接错线的地方，不是资源没配，而是把两个窗口语义混了。

#### `AOCombatWindow` 现在只管什么

`AOCombatWindow` 继续只管“普攻衔接下一段”的战斗窗口语义。

也就是说，它现在不是刀光窗口，也不是武器判定窗口。  
如果你把刀光 Begin/End 还挂回这层，后面测试时会把“连段窗口”和“武器表现窗口”重新混在一起。

#### `AOAttackEffectWindow` 现在只管什么

`AOAttackEffectWindow` 继承自 `AOGiveOwnerTagWindow`，保留“给拥有者加/删窗口标签”的能力，同时把武器攻击表现的 Begin/End GameplayCue 分发挂在这里。

测试时要记住：

1. 普攻衔接窗口继续看 `AOCombatWindow`。
2. 武器判定和刀光窗口改看 `AOAttackEffectWindow`。
3. 这两个窗口现在不是父子职责，也不要再当成同一个窗口来配。

### 这轮刀光测试必须知道的三个 CueTag

测试武器攻击表现时，最容易混的其实不是 GC 资产，而是 Tag 语义。

#### `GameplayCue.Combat.Hit`

这是基础战斗结果 Cue。  
它来自正式命中结果层，本来就用于通用受击表现，不等于这轮新加的武器攻击表现链。

#### `GameplayCue.Combat.AttackEffects.WeaponSwingLoop`

这是本轮新增的“武器挥舞持续表现”专用 Tag。  
用途是接 `CombatWindowBegin / CombatWindowEnd` 这对 Begin/End 生命周期，典型就是刀光、拖尾、挥舞期间武器发光。

它应该配到 `AOCombatGameplayCueNotify_WeaponTrail` 这类持续型轨迹 GC 资产上，而不是继续复用瞬时 Burst。

这里要单独提醒一句：  
旧的 `AOCombatGameplayCueNotify_WeaponLoop` 已经删除。  
现在这条线正式改成 `AOCombatGameplayCueNotify_WeaponTrail`，按 GC 资产 `AOCombatGameplayCueNotify_WeaponTrail` 自己持有的多条轨迹通道配置，持续更新来自当前 `WeaponInstance` 的武器组件起点/终点 socket 世界坐标。  
后面如果有人还按 `WeaponLoop` 去查 GC 资产父类、程序员入口或测试断点，方向就是错的。

#### `GameplayCue.Combat.AttackEffects.WeaponHitBurst`

这是本轮新增的“武器命中瞬时表现”专用 Tag。  
用途是接 `HitConfirmed`，典型就是打中那一瞬间的火花、碰撞爆点、命中音效。

它应该配到 `AOCombatGameplayCueNotify_Burst` 这类瞬时型 GC 资产上。

### 刀光测试前，先把 GameplayCue 链路按这个顺序过一遍

#### 挥舞持续表现链

1. 动画上的武器判定窗口进入 `AOAttackEffectWindow::NotifyBegin`。
2. 这层在服务端构造 `CueParameters`，并把当前 `WeaponInstance` 塞进 `SourceObject`。
3. `FAOAttackEffectProfileRuntime::ResolveProfileFromActor(...)` 从当前角色的当前武器解析生效中的 `AttackEffectProfile`。
4. `DispatchTrigger(..., CombatWindowBegin, ...)` 对条目里的 `CueTag` 执行 `AddGameplayCue`。
5. 如果 Tag 是 `GameplayCue.Combat.AttackEffects.WeaponSwingLoop`，对应的持续型 GC 才会开始挂刀光。

结束时同理：

1. `AOAttackEffectWindow::NotifyEnd`
2. `DispatchTrigger(..., CombatWindowEnd, ...)`
3. 对同一个 `GameplayCue.Combat.AttackEffects.WeaponSwingLoop` 执行 `RemoveGameplayCue`

#### 命中瞬时表现链

1. 正式伤害结果成立。
2. `AOHealthAttributeSet` 先执行基础结果 `GameplayCue.Combat.Hit`。
3. 然后通过 `DispatchTrigger(..., HitConfirmed, ...)` 继续往武器攻击表现层分发。
4. 如果 Profile 里配了 `GameplayCue.Combat.AttackEffects.WeaponHitBurst`，这一步会走 `ExecuteGameplayCue`。
5. 对应的瞬时型 Burst GC 决定最终播放哪组命中爆点。

### 刀光最小测试导航

如果你这轮只是想确认“刀光这条新链到底通没通”，先别做复杂效果，直接按下面最小步骤。

1. 做一个以 `AOCombatGameplayCueNotify_WeaponTrail` 为承接类的刀光 GC，Tag 用 `GameplayCue.Combat.AttackEffects.WeaponSwingLoop`。
2. 做一个以 `AOCombatGameplayCueNotify_Burst` 为承接类的命中 GC，Tag 用 `GameplayCue.Combat.AttackEffects.WeaponHitBurst`。
3. 在 `AttackEffectProfile` 里至少配三条：
   - `CombatWindowBegin -> GameplayCue.Combat.AttackEffects.WeaponSwingLoop`
   - `CombatWindowEnd -> GameplayCue.Combat.AttackEffects.WeaponSwingLoop`
   - `HitConfirmed -> GameplayCue.Combat.AttackEffects.WeaponHitBurst`
4. 武器定义继续只挂 `DefaultAttackEffectProfile`，不要再把 trail 通道细节写回 `WeaponDefinition`。
5. `AOCombatGameplayCueNotify_WeaponTrail` 这个 GC 资产里至少先配一条最小可验证通道；trail 通道配置现在归这个 GC 资产自己持有，重点检查：
   - `NiagaraSystem`
   - `StartSocketName`
   - `EndSocketName`
   - `StartPointVariableName`
   - `EndPointVariableName`
   - `bEnabled`
6. 运行时 socket 解析要按“`WeaponInstance` -> 运行时生成的武器 Actor / 组件 -> 对应 socket”这条线检查，不要再按静态 `WeaponDefinition` 资源去理解挂点来源。
7. 动画里真正负责武器判定的 NotifyState，改成你自己的 `AOAttackEffectWindow` 蓝图子类；不要拿 `AOCombatWindow` 去测刀光。
8. 先空挥测刀光开关，再打目标测命中爆点。

这轮最小测试的结论要理解准确：  
它证明的是 `AOAttackEffectWindow -> WeaponSwingLoop / WeaponHitBurst` 这条攻击表现链已经能工作，  
不等于“最终那种真正跟刀刃挥舞弧线走的刀光轨迹已经完成”。

如果后续要把这条线升级成正式刀光资源，优先方向定成 `Niagara + Ribbon Renderer`。  
这次拿 `Beam` 做出来的东西，只应该被当成链路调试版：它负责帮你确认 Begin/End、GC 生命周期、运行时 socket 解析和 Niagara 参数更新都通了，不负责代表最终刀光观感。

如果空挥没有刀光，但命中时有爆点，优先怀疑的是：

1. 动画上还没换成 `AOAttackEffectWindow`
2. `WeaponSwingLoop` 对应的 GC 还是瞬时类，不是持续类
3. Begin/End 配的不是同一个 `CueTag`
4. `AOCombatGameplayCueNotify_WeaponTrail` 这个 GC 资产里根本没配轨迹通道，或者条目被关掉了
5. `StartSocketName` / `EndSocketName` 填的是旧 socket 名，运行时从 `WeaponInstance` 找到的武器组件上根本解析不到
6. Niagara 用户参数名和 `StartPointVariableName` / `EndPointVariableName` 对不上，导致轨迹组件虽然生成了，但没有吃到位置更新

### 这轮方案在刀光方向上的下一步应该是什么

这一点这轮已经讨论清楚了，后面接手的人不要再来回摇摆。

按当前项目结构：

- 武器是运行时生成的独立对象
- 真正的轨迹点更自然地落在武器自己的 Mesh / socket 上
- 后面还可能有多刃、多翼、多条表现通道

所以动画 `Trail` 不是当前结构下最顺手的主路线。  
更适合后续继续收的方向是：

1. 保留 `AOAttackEffectWindow`
2. 保留 `AttackEffectProfile`
3. 保留 `WeaponSwingLoop / WeaponHitBurst` 的语义分工
4. 把 `WeaponSwingLoop` 背后的承接层正式落成“多通道、多 socket 的武器轨迹系统”

这里的关键不是“只有刀根刀尖两个点”，而是：

- 一把武器可以有多个单点挂接
- 也可以有多组轨迹点对
- 这些点不该平铺成一坨，而应该按不同轨迹通道组织
