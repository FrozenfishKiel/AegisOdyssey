# 正式装备栏系统使用与落地说明

更新时间：2026-05-16

## 第一章 先说清楚，这份文档现在到底是给谁看的

这份文档不再写成“只适合写代码的人看的交接备忘录”，而是改成一份真正能拿来操作的说明书。

它现在主要解决三个问题：

1. 你现在要新建一件正式装备，到底该配哪些东西。
2. 你现在要把正式装备放进角色身上，到底应该走哪条链。
3. 你现在要把正式装备栏接到 UI 上，到底该在哪些地方挂蓝图、怎么拖、怎么右键卸下。

也就是说，这份文档不是单纯介绍“我写了哪些类”，而是要回答：

**你拿到当前工程后，怎么从零开始做出一件能被角色装备的正式装备。**

如果一份文档让你看完之后还不知道“第一步该点哪里”，那它就没有完成任务。这次重写就是为了解决这个问题。

## 第二章 先建立最重要的整体认知，不然后面每一步都会看偏

正式装备栏这套系统，当前不是一个“新发明的独立物品系统”，它本质上还是库存系统的一部分。

只是这次在库存系统里面，额外加了一个专门服务角色长期穿戴的容器和运行时真相层。

你先把这四句话记住，后面很多行为就会顺下来。

第一，正式装备来源物是库存里的真实物品实例。  
不是临时复制品，不是纯展示对象，也不是装备时再动态复制出来的影子物。

第二，正式装备栏本身也是库存语义。  
它不是“背包 UI 外面额外挂的一层图片框”，而是一个真正能接收库存交换的容器。

第三，正式装备栏和武器链是两套系统。  
武器继续走 `QuickBar + WeaponManager`，正式装备栏只管头盔、盔甲、手部、项链、鞋子这五个长期穿戴槽。

第四，正式装备的属性授予现在已经和武器统一了。  
不再走 `Fragment` 里单独配置 `GrantedAttributeEffects` 的路线，而是统一走：

`EquipmentDefinition -> AbilitySetsToGrant -> GiveToAbilitySystem / TakeFromAbilitySystem`

这一条链。

这四句话就是当前正式装备栏的根。后面不管你是在创建装备、配属性、接 UI，还是排查“为什么装备后没生效”，都要回到这四个认知上来。

## 第三章 这套系统里，几个核心类分别是干什么的

先不要急着进编辑器点蓝图。先把当前代码里几层东西的职责分清楚，不然后面你会一直分不清“我现在应该改 Definition、Fragment、还是 Widget”。

### 3.1 正式装备定义层

正式装备定义现在走的是：

`UAOFormalEquipmentDefinition`

它继承自：

`UAOEquipmentDefinition`

这一层是“装备的静态配置层”。你可以把它理解成“这件正式装备天生是什么，它能给角色什么”。

它当前负责两件事：

1. 通过 `AOFragment_FormalEquipment` 声明自己属于哪个正式装备槽类型。
2. 通过父类 `AbilitySetsToGrant` 配置装备后要授予哪些 GameplayEffect / Ability / AttributeSet。

这里最关键的变化一定要记住：

**正式装备属性不再配在 Fragment 里，而是配在 Definition 的 `AbilitySetsToGrant` 里。**

这就是你刚刚专门指出来要统一到武器方式的那条结构。

### 3.2 正式装备实例层

正式装备实例走的是：

`UAOFormalEquipmentInstance`

它继承自：

`UAOEquipmentInstance`

这一层不是拿来配数据的，而是运行时真实存在的那件装备实例。  
库存里真正被拖来拖去的，是它。  
正式装备槽里真正被放进去的，也是它。

所以以后你看到“角色装备了一件头盔”，本质上是：

**某个 `UAOFormalEquipmentInstance` 从一个库存容器移动到了正式装备槽容器。**

### 3.3 正式装备运行时真相组件

正式装备运行时真相现在走的是：

`UAOFormalEquipmentManagerComponent`

这是这套系统最核心的一层。它不是 UI，它也不是一个简单的辅助函数集合，它是真正持有“角色现在穿了什么”的地方。

它当前负责：

1. 维护五个正式装备槽当前各自装备了什么实例。
2. 判断某个来源物能不能进入某个正式装备槽。
3. 在槽位内容变化时，为这件正式装备授予或回收 `AbilitySet`。
4. 提供装备和卸下的运行时入口。

如果你后面遇到“为什么这个头盔拖不进去”“为什么鞋子进了错误槽”“为什么卸下之后属性没掉”，最终都要看它。

### 3.4 正式装备槽库存投影层

正式装备槽库存投影走的是：

`UAOFormalEquipmentSlotInventoryComponent`

这层的意义非常重要，但也最容易被误解。

它不是“角色最终到底装备了什么”的真相持有者。  
它只是把正式装备栏当前五个槽位，投影成一个标准库存容器，这样项目现有的库存交换链、拖拽链、右键菜单链都能直接复用。

你可以把它理解成：

“为了让正式装备栏也能像背包格子、技能槽一样参与库存交换，专门加的一层库存外壳。”

### 3.5 正式装备 UI 层

当前这次已经补上的 UI 基类主要是：

1. `UAOFormalEquipmentBarUI`
2. `UAOFormalEquipmentSlotUI`
3. `UMVVM_InventoryMenu` 里的 `FormalEquipmentList`

这三者的关系是：

- `UAOFormalEquipmentBarUI` 负责整条正式装备栏
- `UAOFormalEquipmentSlotUI` 负责单个正式装备槽
- `FormalEquipmentList` 负责给表现层下发当前五个槽位的快照

也就是说，现在正式装备 UI 不是直接扒运行时容器来拼图，而是已经走了 ViewModel。

## 第四章 当前这套正式装备系统，你真正操作时要经过哪条主链

这一章非常重要。你现在之所以看半天看不明白，本质上不是类太多，而是文档之前没有把“操作链”讲成一句能记住的话。

你现在只需要先记住下面这条主链：

**创建装备定义 -> 创建正式装备物品实例 -> 把它放进角色库存 -> 从库存拖进正式装备槽 -> 正式装备槽库存投影变化 -> 正式装备管理器同步运行时真相 -> AbilitySet 授予到 ASC**

如果是卸下，就是反过来：

**在正式装备槽右键卸下 -> 正式装备管理器把实例退回角色库存 -> 正式装备槽投影变化 -> 正式装备管理器回收这件装备的 AbilitySet 句柄**

这就是整个系统真正的工作链。

后面你无论配蓝图还是测逻辑，都可以把当前操作点强行定位到这条链上的某一段。这样就不会再出现“我现在到底是在配 UI 还是在配属性还是在配运行时真相”这种混乱。

## 第五章 现在如果你要新建一件正式装备，第一步该怎么做

这一章开始不讲抽象结构，直接讲实际操作。

### 5.1 先想清楚，你创建的到底是什么类型的正式装备

当前正式装备槽只有五种：

1. 头盔
2. 盔甲
3. 手部
4. 项链
5. 鞋子

所以你在创建正式装备之前，先回答一个问题：

**这件东西到底属于哪一个唯一正式槽。**

这一点必须先定死。  
因为后面 `Fragment` 要配槽类型，UI 也要靠这个槽类型判断它能不能拖进对应槽。

比如你现在要做一件“新手皮头盔”，那它从创建开始就应该被当成“头盔”，而不是先做一个模糊的“装备物品”，等后面再猜它进哪个槽。

### 5.2 创建正式装备 Definition 资产

你要创建的，不是一个普通消耗品 Definition，也不是武器 Definition，而是正式装备自己的 Definition。

也就是说，这件正式装备的数据资产最终应该是：

`UAOFormalEquipmentDefinition`

如果你在编辑器里现在还没有对应的蓝图资产模板，那你的目标依然要对齐到这个类。

这一层至少要配三类东西：

1. 物品的基本显示信息
2. 正式装备槽类型
3. 装备后要授予的 AbilitySet

### 5.3 配置物品基本显示信息

这一层沿用项目原来的物品定义做法。  
也就是说，正式装备虽然是正式装备，但它首先还是一个库存物品。

你至少要保证这件正式装备有：

1. 名字
2. 图标
3. 对应的实例类型

名字和图标后面不仅背包要显示，正式装备槽也会直接拿它来显示。

所以如果你现在创建了一件正式装备，但是背包里没图标、装备槽里也没图标，那第一反应不是去查正式装备管理器，而是先看这件 Definition 的图标相关 Fragment 有没有配好。

### 5.4 配置 FormalEquipment Fragment

正式装备 Definition 现在仍然需要带：

`AOFragment_FormalEquipment`

但这个 Fragment 现在已经被收口了。  
它不再负责配属性授予。  
它现在只负责一件事：

**声明这件正式装备属于哪个唯一正式槽。**

所以你在这个 Fragment 里当前要配的重点只有：

`FormalSlotType`

如果这是一件头盔，就配 `Helmet`。  
如果这是一件项链，就配 `Necklace`。

不要再在这里找“属性 GE 配置入口”了，因为那条路已经被删掉了。

### 5.5 配置 AbilitySetsToGrant

这一步就是这次最重要的结构统一点。

正式装备的属性授予现在应该像武器一样，配在：

`UAOEquipmentDefinition::AbilitySetsToGrant`

也就是说，你要为这件正式装备准备一个 `UAOAbilitySet`，然后把它挂到这件正式装备 Definition 的 `AbilitySetsToGrant` 数组里。

这一步不要理解成“只是把配置位置换了个地方”。  
它的真正意义是：

1. 正式装备和武器统一使用同一套授权机制
2. 授予结果统一记录在 `FAOAbilitySet_GrantedHandles`
3. 卸下时统一通过 `TakeFromAbilitySystem(...)` 回收
4. 后续如果一件正式装备不止给属性，还给 Ability 或 AttributeSet，也能沿用同一条结构

这比单独在 Fragment 里手动配一堆 GE，然后正式装备管理器自己去 `ApplyGameplayEffectToSelf` 要稳定得多。

## 第六章 AbilitySet 现在到底该怎么配，别再抽象说“走 GameplayEffect”

前面虽然说了正式装备属性走 `AbilitySetsToGrant`，但如果不把 AbilitySet 该怎么配讲清楚，这句话还是等于没落地。

### 6.1 先理解 AbilitySet 在这件事里的角色

`UAOAbilitySet` 不是“只给技能用的东西”。  
在你这个项目里，它本来就承担三类授予：

1. GameplayAbility
2. GameplayEffect
3. AttributeSet

所以正式装备要给角色加攻击、防御、暴击率、抗性，本质上最常用的就是：

**在 AbilitySet 里配置 `GrantedGameplayEffects`**

这才是当前正确口径。

### 6.2 一件正式装备最常见的配置方式

比如你要做一件“皮头盔”，它给角色：

1. 防御力 +10
2. 总抗性 +5

那么当前推荐配置是：

1. 创建一个专门给这件头盔用的 `AbilitySet`
2. 在这个 `AbilitySet` 的 `GrantedGameplayEffects` 里配置一个或多个 GE
3. 这些 GE 去改的是“装备贡献属性”，而不是直接乱改最终战斗值
4. 再把这个 `AbilitySet` 挂到这件头盔 Definition 的 `AbilitySetsToGrant`

这样当头盔被装备进正式装备槽后，正式装备管理器就会遍历这件 Definition 的 `AbilitySetsToGrant`，统一调用：

`AbilitySet->GiveToAbilitySystem(...)`

当头盔被卸下时，再统一调用：

`GrantedHandles.TakeFromAbilitySystem(...)`

### 6.3 GE 里应该改什么属性

当前第一版正式装备系统，建议优先落这几项装备贡献属性：

1. `EquipmentAttack`
2. `EquipmentCritChance`
3. `EquipmentDefense`
4. `EquipmentResistance`

这里的重点不是具体字段名要不要之后再微调，而是设计口径一定要稳：

**正式装备优先改“装备贡献输入项”，不要直接改最终战斗结算结果。**

比如头盔加防御，你就让它去改 `EquipmentDefense`。  
项链加暴击率，你就让它去改 `EquipmentCritChance`。

这样后面无论是 `MMC` 还是派生 GE，都还能继续统一聚合。

### 6.4 为什么不要再回去手配 Fragment 里的 GE

这一点这里再强调一次，因为这就是你刚才指出的问题根源。

如果正式装备还继续走：

`Fragment -> GrantedAttributeEffects -> Manager 手动 ApplyGameplayEffect`

那它和武器就是两条不同的授权结构。

两条结构都能跑，不等于这是对的。  
真正的问题在于：

1. 配置口径不统一
2. 句柄回收口径不统一
3. 后续别人看代码会越来越分不清“装备授予到底应该配在哪里”

所以现在正式装备已经被收回到武器同一条链上了，后面就不要再把属性授予往 Fragment 里塞回去。

## 第七章 配完 Definition 之后，怎么让它真的变成库存里的装备

很多人看完代码会卡在这里：Definition 配完了，然后呢？为什么还是没法装备？

答案很简单，因为 Definition 只是配置，不是角色库存里那件真实存在的装备实例。

### 7.1 先记住一个关键区别

Definition 是“这件东西是什么”。  
Instance 是“这件东西现在真的存在于角色库存里”。

正式装备系统真正拿来移动、拖拽、装备的，是：

`UAOFormalEquipmentInstance`

而不是 Definition 本身。

### 7.2 正式装备 Instance 现在是怎么被决定的

当前 `UAOFormalEquipmentDefinition` 已经覆写了：

`GetPreferredInstanceType()`

它默认会优先返回：

`UAOFormalEquipmentInstance`

这意味着，只要你这件 Definition 走的是正式装备 Definition，并且没故意改成别的实例类型，那么它进入库存时，最终就会解析成正式装备实例。

这件事很重要，因为后面正式装备管理器在判断合法性时，第一步就会检查：

“这是不是一个正式装备实例”

如果你资产配错，最后入库的不是 `UAOFormalEquipmentInstance`，那么它根本进不了正式装备槽。

### 7.3 实际测试时怎么把它放进角色库存

这一步你可以按你当前项目已有的入库方式来。

无论你是：

1. 通过测试逻辑直接加进背包
2. 通过掉落物拾取进入背包
3. 通过调试命令临时发进背包

真正的验收点都不是“Definition 资产存在了”，而是：

**角色背包里现在真的出现了一件正式装备实例。**

你至少要先确认：

1. 这件装备能正常出现在背包格子里
2. 有名字
3. 有图标
4. 右键时能走物品交互链

如果这一步都没过，那就先不要测正式装备槽。  
因为后面所有装备操作，前提都是“库存里已经有一件真实正式装备实例”。

## 第八章 现在真正开始装备，这件装备是怎么进角色身上的

这一章就是你最关心的“从创建装备到装备到角色”里，真正的后半段。

### 8.1 先说结论：正式装备不是直接绑到角色身上，而是先进正式装备槽容器

这里很容易理解错。

正式装备“装备到角色”这件事，在当前系统里不是：

“把一个变量直接写到角色对象上”

而是：

“把这件正式装备实例，从它当前的来源库存，移动到正式装备槽库存投影里”

一旦这件实例进入了正式装备槽库存投影，正式装备管理器就会同步运行时真相，并授予对应的 AbilitySet。

所以“装备到角色”这件事，当前真正落地的语义是：

**进入正式装备槽容器。**

### 8.2 角色身上当前有哪些相关组件

当前角色已经有这两个正式装备相关组件：

1. `UAOFormalEquipmentManagerComponent`
2. `UAOFormalEquipmentSlotInventoryComponent`

简单理解就是：

- `FormalEquipmentManager` 管“角色现在正式穿了什么，以及授予了什么”
- `FormalEquipmentSlotInventoryComponent` 管“正式装备栏这个库存外壳”

所以你后面不管是右键使用、拖拽装备、右键卸下，最后都绕不开这两个组件。

### 8.3 右键使用一件正式装备时，当前走哪条链

如果你现在在背包里右键一件正式装备，当前系统的意图是：

1. 这件物品先被识别为正式装备实例
2. 它的 Definition 告诉系统它属于哪个正式装备槽类型
3. 正式装备管理器找到那个唯一槽
4. 再走统一库存交换链，把这件正式装备实例送进那个槽

也就是说，右键使用本质上不是“直接写装备状态”，而是“根据槽类型发起一次正式装备请求”。

### 8.4 拖拽一件正式装备进正式装备槽时，当前走哪条链

拖拽时，正确路径是：

1. 你在背包里拖起一个真实槽位
2. 拖拽负载里应该带着来源容器和来源槽索引
3. 正式装备槽控件先问正式装备管理器：这个来源物能不能进我这个槽
4. 如果能，就调用统一交换入口
5. 来源槽和目标正式装备槽发生库存交换
6. 正式装备槽库存投影变化
7. 正式装备管理器同步运行时真相
8. AbilitySet 被授予给角色 ASC

所以这条链里，真正做“装备”这件事的不是 UI，不是蓝图动画，不是某个菜单按钮，而是：

**库存交换成功后，正式装备管理器对正式装备槽投影变化作出的同步响应。**

## 第九章 当前正式装备槽为什么只能放对的东西，错误东西为什么进不去

这里你最好顺便看明白，不然以后看到“拖不进去”会误以为是 UI 坏了。

### 9.1 每个正式装备槽现在都是唯一槽

当前正式装备槽固定五个，而且每个槽只有唯一合法类型：

1. 头盔槽只认 `Helmet`
2. 盔甲槽只认 `Armor`
3. 手部槽只认 `Gloves`
4. 项链槽只认 `Necklace`
5. 鞋子槽只认 `Boots`

### 9.2 合法性判断不是 UI 自己猜的

这一点很关键。

正式装备槽 UI 并不是自己写一堆：

`if 这个名字看起来像头盔`

之类的逻辑。

它现在真正的判断入口是：

`UAOFormalEquipmentManagerComponent::CanAcceptSourceItemForFormalSlot(...)`

它至少会检查：

1. 目标槽索引是不是有效
2. 这个来源物是不是正式装备实例
3. 它的 Definition 是不是正式装备 Definition
4. 它的 `FormalSlotType` 和目标槽类型是否一致

只有全通过，才允许这件东西进入这个槽。

### 9.3 为什么武器和消耗品进不去

因为从运行时真相组件的角度看，它们根本不是“正式装备实例”。

所以现在武器不进正式装备槽，不是因为 UI 画得不让进，而是因为后端合法性判断本来就不认它。

这才是稳的。

---

## 第十章 如果槽里已经有装备了，再放一件进去会发生什么

这是当前正式装备系统里最容易被忽略，但又最重要的一条行为语义。

### 10.1 当前允许替换

如果某个正式装备槽已经有装备了，而你又把同类型正式装备放进去，当前系统是允许替换的。

比如：

1. 头盔槽里已经有头盔 A
2. 你再把头盔 B 拖进头盔槽

当前结果不是失败，而是：

**执行替换**

### 10.2 当前替换为什么能成立

因为整个正式装备栏复用了统一库存交换主链：

`UAOInventoryComponent::ExecuteExchangeRequest(...)`

这条交换主链会在真正交换前做两次判断：

1. 目标槽能不能接受来源物
2. 如果目标槽原本就有东西，来源槽能不能接受被换下来的目标物

正是这第二步，保证了旧装备可以回流。

### 10.3 当前替换后的回流规则

你前面已经明确拍板过：

**旧装备优先回发起替换的来源槽位。**

所以当前理想语义不是“旧装备随便丢回背包某个空位”，而是：

1. 你从哪个库存格拖来新装备
2. 旧装备就尽量回到那个位置

这一点之所以重要，是因为它让替换结果非常稳定，也更符合玩家直觉。

---

## 第十一章 现在如果你要卸下正式装备，具体怎么做

这一章也必须讲细，因为卸下和装备是同等重要的一条链。

### 11.1 当前正式装备槽右键菜单已经接了“卸下”

当前正式装备单槽 UI：

`UAOFormalEquipmentSlotUI`

已经把右键菜单改成了正式装备语义。  
也就是说，正式装备槽上的右键菜单不是普通库存 Use 菜单，而是会优先给：

`卸下`

这条动作。

### 11.2 右键卸下时，当前走哪条链

当前链路是：

1. 你在正式装备槽右键
2. 正式装备槽 UI 识别当前槽位索引
3. UI 不自己直接改槽
4. UI 调正式装备管理器的 `RequestUnequipFormalSlot(...)`
5. 正式装备管理器把这件装备从正式装备槽容器交换回角色库存主接收容器
6. 正式装备槽投影变化
7. 正式装备管理器回收这件装备的 AbilitySet 句柄

### 11.3 当前卸下时回到哪里

这里要注意，当前这版“右键卸下”的首版规则和“替换时旧装备回到来源槽”不是同一条。

当前右键卸下走的是：

**退回角色库存主接收容器**

具体来说，当前实现优先回：

`UAOBackPackComponent`

如果背包找不到空位，则卸下失败，这件装备仍然留在正式装备槽里。

这条规则你现在测试右键菜单时一定要记住，不然你会把“为什么没回原历史来源槽”误判成 Bug。  
当前它就是这么设计的。

## 第十二章 UI 这次到底怎么接，你现在在蓝图里应该做什么

前面已经把运行时链讲清楚了，这一章开始讲你在 UMG / 蓝图里到底要怎么落。

### 12.1 先明确，当前 C++ 已经给了你什么

现在 C++ 已经补了这些基础层：

1. `UAOFormalEquipmentBarUI`
2. `UAOFormalEquipmentSlotUI`
3. `UMVVM_InventoryMenu::FormalEquipmentList`

也就是说，当前不是“正式装备栏 UI 完全没写”，而是：

**C++ 基类和 ViewModel 桥已经有了，但真正显示出来还需要你把蓝图外壳挂上。**

### 12.2 你至少需要两个蓝图 Widget

现在要把正式装备栏真正做出来，最少建议有两个蓝图外壳：

1. `WBP_FormalEquipmentBar`
2. `WBP_FormalEquipmentSlot`

这两个蓝图的父类要分别对齐：

1. `UAOFormalEquipmentBarUI`
2. `UAOFormalEquipmentSlotUI`

如果父类没选对，后面那些正式装备槽接口、右键卸下接口、ViewModel 刷新链你就全拿不到。

### 12.3 正式装备栏整体 Widget 要怎么建

在 `WBP_FormalEquipmentBar` 里，当前重点不是先摆美术，而是先把容器接正确。

你至少要有一个能绑定到：

`FormalEquipmentSlotContainer`

的面板控件。

这个面板的作用就是承载五个正式装备槽子控件。  
C++ 侧 `UAOFormalEquipmentBarUI::RefreshFormalEquipmentBar()` 会在运行时清空它，再按 `FormalEquipmentList` 的五个槽位快照重新创建五个 `UAOFormalEquipmentSlotUI` 子控件。

所以这一步你在蓝图里最重要的不是“先画五个固定格子”，而是：

**给正式装备栏一个真实的槽控件容器，让 C++ 能往里面动态加五个子槽。**

### 12.4 正式装备单槽 Widget 要怎么建

在 `WBP_FormalEquipmentSlot` 里，当前建议至少准备下面这些可绑定控件：

1. 图标控件，对应 `ItemIcon`
2. 槽位名字文本，对应 `SlotNameText`
3. 当前装备名字文本，对应 `ItemNameText`

这样当前单槽就能显示三件事情：

1. 这是头盔槽还是项链槽
2. 当前槽里有没有装备
3. 如果有装备，当前显示什么图标、什么名字

### 12.5 当前 ViewModel 是怎么喂到 UI 的

当前正式装备栏复用的是：

`UMVVM_InventoryMenu`

里的：

`FormalEquipmentList`

这意味着：

1. `UAOFormalEquipmentSlotInventoryComponent` 会把正式装备槽库存投影写进 `FormalEquipmentViewModel`
2. `UAOFormalEquipmentBarUI` 会从这个 ViewModel 读 `FormalEquipmentList`
3. `FormalEquipmentList` 一变化，正式装备栏就会重建五个槽位表现

所以现在正式装备 UI 的数据来源，不是你自己在蓝图里手搓一份数组，而是：

**正式装备槽库存投影组件发到 ViewModel 的五槽快照**

## 第十三章 正式装备槽拖拽到底要怎么接，不要再只说“支持拖拽”

这一章就是把“拖入装备槽”真正落成操作说明。

### 13.1 拖拽的起点是什么

拖拽起点不是“拖了一张图标”，也不是“拖了一个 Definition 名字”。  
真正的拖拽起点应该始终是：

1. 某个来源库存容器
2. 某个来源槽位索引

因为正式装备系统最重要的前提就是：

**来源物是库存里的真实物品实例。**

所以你拖出去的，不应该只是展示数据，而应该能最终反查到：

“这是哪个容器的哪个真实物品实例”

### 13.2 正式装备槽在悬停阶段应该做什么

当玩家把背包里的东西拖到正式装备槽上方时，正式装备槽首先要做的是合法性查询，而不是直接装备。

当前 `UAOFormalEquipmentSlotUI` 已经有这类入口：

1. `CanAcceptDraggedSourceSlotForThisFormalSlot(...)`
2. `CanAcceptDraggedItemForThisFormalSlot(...)`

它们最终会把判断收口到：

`UAOFormalEquipmentManagerComponent::CanAcceptSourceItemForFormalSlot(...)`

所以你蓝图里如果要做：

1. 合法悬停高亮
2. 非法悬停红框
3. “这个槽不能放这个物品”的视觉反馈

都应该基于这些接口的 true / false 结果去做，而不是自己在蓝图里再写一套槽位类型判断。

### 13.3 真正落下时应该怎么做

正式落下时，不要自己直接改 UI 图标，也不要手动清空背包格子。

正确做法是：

1. 从拖拽负载里取来源容器
2. 取来源槽位索引
3. 调正式装备槽控件的：

`RequestEquipDraggedSourceSlotToThisFormalSlot(...)`

这个函数内部最终会走：

`RequestExchangeBetweenInventories(...)`

再回到统一库存交换主链：

`UAOInventoryComponent::ExecuteExchangeRequest(...)`

也就是说，拖拽落点真正应该做的是：

**发起库存交换请求**

不是自己在蓝图里模拟装备成功结果。

### 13.4 为什么这条拖拽链能自动支持替换

因为统一库存交换主链本来就支持“来源格和目标格都有东西时的交换语义”。

所以当你把头盔 B 拖进已经有头盔 A 的头盔槽时，后端不是复制一份，而是：

1. 确认头盔槽能接受头盔 B
2. 确认头盔 B 当前来源槽也能接受被换下来的头盔 A
3. 然后完成真正的交换

所以只要前置合法性判断没写错，你不用再额外手写一套“替换时旧装备回去”的私有逻辑。

## 第十四章 现在你如果从零开始做，一步一步应该怎么操作

前面已经把各层原理讲明白了，这一章直接给你一个从零开始的实际操作顺序。

你如果现在要在工程里真正做出一件可以装备的正式装备，建议严格按这个顺序来。

### 第一步，先创建正式装备 Definition

先别碰 UI，也别碰角色面板。

先把装备定义资产建出来，保证它是正式装备 Definition，而不是普通物品或武器 Definition。

这一步的验收点只有一个：

**这件物品从定义层已经明确是正式装备。**

### 第二步，给 Definition 挂 FormalEquipment Fragment

然后给这件 Definition 配：

`AOFragment_FormalEquipment`

把 `FormalSlotType` 配成唯一正确槽位。

这一步的验收点是：

**系统已经知道这件东西到底是头盔、盔甲、手部、项链还是鞋子。**

### 第三步，创建 AbilitySet 并挂到 AbilitySetsToGrant

然后给这件正式装备准备一个 AbilitySet。

在这个 AbilitySet 里把你要给角色的属性 GE 配好，再把这个 AbilitySet 挂到这件正式装备 Definition 的：

`AbilitySetsToGrant`

这一步的验收点是：

**这件正式装备“装备后该授予什么”已经有了统一来源。**

### 第四步，把这件正式装备发进角色背包

然后用当前项目已有的入库方式，把这件正式装备放进角色背包。

先不要急着测装备。  
先确认背包里已经真实出现这件东西：

1. 有图标
2. 有名字
3. 是正式装备实例

这一步的验收点是：

**角色库存里已经有一件真实正式装备实例。**

### 第五步，先用右键使用测一遍自动装备

如果你当前想先绕开 UI 拖拽细节，最稳的第一轮测试方式不是拖拽，而是先右键使用。

因为右键使用会直接走“根据 FormalSlotType 路由到正式装备槽”的链。

如果这一步能成功，至少说明：

1. Definition 没配错
2. Instance 类型没配错
3. 正式装备管理器能识别它属于哪个槽
4. 正式装备槽库存投影和运行时真相同步链大致是通的

### 第六步，再接正式装备栏 UI

右键使用跑通后，再去接 UI。

先做：

1. `WBP_FormalEquipmentBar`
2. `WBP_FormalEquipmentSlot`

让五个槽显示出来，让它们能显示空槽态和当前装备态。

### 第七步，最后接拖拽落点

等正式装备栏能显示、能刷新、能看到已装备结果了，再把拖拽落点接上。

这一顺序非常重要。  
因为如果你一开始就同时测“资产定义 + 运行时真相 + ViewModel + 拖拽蓝图”，最后出了问题你几乎不可能快速定位。

## 第十五章 你现在最容易踩的几个坑

这章不长，但很有必要。

### 15.1 把属性 GE 继续配在 Fragment 里

这个坑现在已经不该再踩了。

正式装备属性授予已经统一回：

`AbilitySetsToGrant`

如果你后面又往 Fragment 里找属性授予入口，或者又临时给它加回去，这套结构就又会开始分裂。

### 15.2 资产是正式装备 Definition，但实例类型不是正式装备实例

这会导致表面上看起来像正式装备，实际上进不了正式装备槽。

所以你一旦发现：

“背包里有这件东西，但正式装备槽完全不认它”

第一反应要先查：

**它最终进库存的实例类型是不是 `UAOFormalEquipmentInstance`**

### 15.3 UI 看起来装备了，但库存里原物还在

这说明你八成没有真正走统一库存交换主链，而是在某个蓝图里自己改了展示状态。

当前正确行为必须是：

1. 正式装备槽里出现了这件实例
2. 原库存格不再持有这件实例

如果两个地方同时都有，那就是严重错误。

### 15.4 非法物能进正式装备槽

这说明你不是在复用正式装备管理器的合法性判断，而是某一层 UI 自己放行了。

当前正确口径是：

**合法性必须在运行时真相组件收口，UI 只查询结果。**

### 15.5 右键卸下后属性没掉

如果出现这个问题，优先查的是：

1. 这件正式装备到底有没有通过 `AbilitySet` 成功授予
2. `GrantedHandles` 有没有被记录到对应槽位
3. 卸下时有没有真的走 `TakeFromAbilitySystem(...)`

这类问题现在不要再去查旧的 `AppliedEffectHandles`，因为那条旧结构已经被收掉了。

## 第十六章 现在这份文档最后给你一个真正可执行的检查清单

如果你今天就要开始自己动手，不想再来回翻全文，那就按这个顺序做。

### 16.1 创建一件正式装备

1. 新建正式装备 Definition
2. 配名字和图标
3. 挂 `AOFragment_FormalEquipment`
4. 配 `FormalSlotType`
5. 创建 AbilitySet
6. 在 AbilitySet 里配置正式装备要授予的 GE
7. 把 AbilitySet 挂到 Definition 的 `AbilitySetsToGrant`

做到这里，才算“定义层完成”。

### 16.2 让它进入角色库存

1. 用现有入库方式把这件装备放进角色背包
2. 确认背包里出现这件装备
3. 确认图标和名字都正常
4. 确认它最终是正式装备实例

做到这里，才算“来源物完成”。

### 16.3 让它装备到角色身上

1. 先右键使用测一遍自动装备
2. 再把正式装备栏 Widget 挂到角色面板或库存界面
3. 确认五个正式装备槽能显示出来
4. 确认已装备结果能反映到正式装备槽 UI
5. 再接拖拽
6. 用拖拽把背包正式装备拖进正确槽
7. 验证错误槽位不能接受错误物品

做到这里，才算“装备链完成”。

### 16.4 验证卸下

1. 在正式装备槽右键
2. 选择卸下
3. 确认这件装备回到角色库存主接收容器
4. 确认正式装备槽清空
5. 确认对应 AbilitySet 已经回收

做到这里，才算“卸下链完成”。

## 第十七章 最后一句收束

现在这套正式装备系统，你可以把它理解成这样一句话：

**先把正式装备做成真实库存物品，再通过正式装备槽这个库存外壳把它送进角色长期穿戴位，最后由正式装备管理器统一把 Definition 里的 AbilitySet 授予给角色。**

如果你后面操作时迷路了，就回来看这句话，然后问自己：

“我现在卡住的，是定义层、实例层、库存层、正式装备槽层、运行时真相层，还是 UI 层？”

只要你能把问题定位到这五层里的某一层，这套系统就不会再显得乱。
