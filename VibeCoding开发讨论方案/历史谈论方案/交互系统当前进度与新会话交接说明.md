# 交互系统当前进度与新会话交接说明

更新日期：2026-05-04

这份文档写给下一位接手本项目的 AI。目标不是复读聊天记录，而是让接手者在最短时间内弄清楚三件事：

1. 这个项目当前在做什么。
2. 我们已经踩过哪些坑，哪些方向已经被明确否定。
3. 现在代码处于什么状态，下一步应该从哪里继续，而不再把项目带回“拆东墙补西墙”的循环。

---

## 一、当前阶段的核心目标

当前主线不是 AI 决策，不是新功能发散，而是把“统一交互 + 会话层 + 容器 UI + 联机权限”这一整条链真正打通，并且保持可复用、可扩展、可维护。

这里的“容器”目前以箱子为第一个落地对象，但设计目标从一开始就不是只服务箱子。后续同一套思路应能够服务于：

- 箱子
- 工作台
- 铁砧
- 商店
- AI 可交互对象
- 其他任何需要“打开 UI 或修改对象数据”的世界对象

因此，整个系统绝不能围绕“箱子专用判断”去写。

---

## 二、用户已经明确确认过的架构原则

这些不是建议，而是当前项目的硬约束。下一位 AI 接手时必须先接受这些约束，再动代码。

### 1. 不要写类型专用分支

用户已经多次明确否定以下方向：

- 单独判断“这是不是箱子”
- 单独判断“这是不是交互 GA”
- 为每个对象类型分别写一套交互入口
- 未来对象变多后继续靠 `if/else` 扩写

用户对“扩展性”的定义不是“以后再加判断”，而是“现在就写成可复用框架”。

### 2. 不要为了止血而制造额外状态

用户非常反感这种做法：

- 为了解决眼前问题，额外加一堆布尔状态
- 写临时锁、临时门闩、临时辅助函数来掩盖根因
- 用“回避根本问题”的方式让表面现象消失

典型被否定的风格包括：

- `IsUnifiedInteractAbility`
- `ShouldUseUnifiedInteractRouting`
- `SinglePressDispatchedSpecHandles`
- `bIsWaitingForCurrentInteractableMutationAuthority`
- 各种“是不是当前容器”“是不是当前交互对象”的专门判断链

原则很简单：

- 先把链路收回最小核心
- 只保留真正必要的状态
- 不要为了一个对象、一个现象、一个 Bug 写死整条框架

### 3. 会话层存在的意义，是解决“当前谁在与对象交互”

会话层不是展示层，不是数据层，也不是对象类型分发器。会话层存在的意义主要有三件事：

- 标记当前玩家正在交互哪个对象
- 管理该玩家当前打开的交互会话模型
- 在需要修改对象数据前，协调“谁当前有权限动这个对象”

### 4. UI 不是只读层

用户很明确：

- UI 不只是显示数据
- UI 会主动发起拖拽、交换、整理、删除等数据修改行为
- 因此 UI -> 会话层 -> 数据层 这条反向操作链必须成立

### 5. 分层必须守住边界

用户非常在意这一点：

- 数据层的问题，不要跑去 UI 层硬补
- UI 层的问题，不要通过重置底层数据来掩盖
- 会话层的问题，要在会话层解决

之前已经明确踩坑过一次：曾尝试通过“初始化/重置容器数据”来弥补 UI 不刷新的问题，这被明确否定，原因是这属于越层操作，而且会污染真实数据。

## 三、当前这轮工作已经实际解决了什么

截至 2026-05-04，这一轮工作已经把下面几类问题收掉了。

### 1. 箱子 UI 打开/关闭的基本链路已经恢复正常

之前出现过：

- 第一次打开箱子后可以显示 UI
- 关闭后再次交互无法重新打开
- 同时会连带影响拾取或其他交互

这类问题本质上和之前那批“统一交互接管输入”的补丁式改动有关。后续已经做过一轮清理，移除了大量把输入路由写乱的逻辑。

### 2. 箱子格子不显示的问题已经定位并解决

这部分曾经混在两类问题里：

- 一类是蓝图配置问题
- 一类是会话层到 UI 的数据对接问题

实际排查结果如下：

- `ContainerSlotClass` 没配置时，UI 当然不会生成格子
- 但除了配置问题之外，我们也确实排查过“会话层数据到 UI 的时机和绑定链是否正确”
- 后续已经把“遍历 UI 树找容器 UI”这种做法否掉，收回到会话模型和交互 Session 组件自己的链路上

### 3. 客户端看不到箱子格子的问题已经解决

这部分的真实问题不是“箱子没初始化”，而是“客户端会话模型拿到容器数据的时机与同步链路不稳定”。后续围绕 `ReplicatedSessionState`、客户端会话模型重建、UI 绑定刷新这条链做过修复。

### 4. 客户端从箱子格子拖动物品失败的问题已经解决

用户曾定位到一个很关键的现象：

- 客户端上 `ObservedSlots` 里能拿到槽位
- 但槽位中的 `Instance` 为空
- 蓝图 `OnMouseButtonDown` 会因为 `Instance` 为空直接判定“这个格子不可拖动”

这个问题说明会话/UI 观察结构与底层容器数据之间有映射差。后续已经按用户要求把这个链路补通，让客户端能正确拿到拖拽所需的数据，而不是退化成只靠 `ItemDefClass` 勉强判断。

### 5. 背包与箱子之间的数据交换现在已经能正常跑通

包括：

- 单机
- 服务器
- 客户端联机

目前运行结果已经被用户确认“运行完美”。

## 四、这轮工作中最重要的一次问题收敛

这轮后半段最关键的问题，不是“箱子格子显示不显示”，而是联机环境下修改对象数据的权限问题。

用户在实际联机测试中看到过这个警告：

`LogNet: Warning: UNetDriver::ProcessRemoteFunction: No owning connection for actor BP_Chest... Function WhenItemExchange will not be processed.`

这个警告的含义非常明确：

- 客户端试图通过箱子侧的库存组件发起一个 Server RPC
- 但此时该对象并不归这个客户端拥有
- 所以 RPC 被网络层直接拒绝

这也是为什么之前会出现这些现象：

- 背包放入箱子第一次失败，第二次成功
- 重开箱子后第一次拖拽又失败
- 某个方向能拖，反方向不能拖
- 服务器和单机正常，客户端异常

本质都在于：

- 操作发起时，真正的 Actor Owner 还没同步到当前客户端
- 但更早的一层逻辑已经误以为“可以执行修改操作了”

## 五、这次最终落地的最小权限方案

用户最终确认并接受的核心思路非常简单：

1. 只要当前操作要修改正在交互对象的数据，就先请求该对象的 Owner。
2. 如果此时 Owner 还没真正到当前玩家手上，就不要立刻执行真正的数据修改。
3. 等真实 Owner 到手，再执行之前挂起的操作。

用户不接受的，是围绕这个思路继续加很多额外状态、类型判断、补丁函数。

因此这次最终收口后的实现，特征是：

- 只保留“待执行修改操作队列”
- 不再保留额外等待布尔
- 不再保留“当前交互对象是不是容器”“这次修改是否触及当前交互对象”的专门判断
- 不再依赖“会话复制出来的 owner 状态”作为权限已到的判据

### 当前关键代码位置

#### 1. 会话组件

文件：

- [AOInteractionSessionComponent.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Interaction/AOInteractionSessionComponent.cpp)
- [AOInteractionSessionComponent.h](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Interaction/AOInteractionSessionComponent.h)

当前关键行为：

- `RequestAcquireCurrentInteractableOwner()`：
  向服务器申请把当前交互对象的 Owner 切到当前玩家
- `ExecuteOrQueueCurrentInteractableMutation(...)`：
  如果当前有真实权限，立即执行；否则把操作塞进 `PendingCurrentInteractableMutations`
- `HasCurrentInteractableMutationAuthority()`：
  现在只认 `InteractableActor->GetOwner() == SessionOwnerActor`
- `FlushPendingCurrentInteractableMutationsIfReady()`：
  如果待执行队列不为空，并且真实 Owner 已经到当前玩家，就把挂起操作放出去执行
- `TickComponent(...)`：
  每帧尝试一次 `FlushPendingCurrentInteractableMutationsIfReady()`，避免“会话复制状态先到，但 Actor Owner 还没到”的时序半拍问题

#### 2. UI 发起统一库存交换请求

文件：

- [AOInventoryUI.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/Widgets/Inventory/AOInventoryUI.cpp)

当前关键行为：

- `RequestExchangeBetweenInventories(...)`
  不再直接执行交换，而是统一走 `ExecuteOrQueueCurrentInteractableMutation(...)`
- 真正挂起的是一个 `TFunction<void()>`
- 这个 `TFunction` 最终会执行 `UAOInventoryComponent::ExecuteExchangeRequest(...)`

#### 3. 底层库存交换仍然保持统一入口

文件：

- [AOInventoryComponent.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Inventory/AOInventoryComponent.cpp)
- [AOInventoryComponent.h](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Inventory/AOInventoryComponent.h)

当前关键行为：

- `ExecuteExchangeRequest(SourceInventory, SourceIndex, TargetInventory, TargetIndex)`
  仍然是统一四参数入口
- 目前它内部仍然调用
  `SourceInventory->WhenItemExchange(TargetInventory, SourceIndex, TargetIndex);`
- `WhenItemExchange` 依然是 `Server, Reliable` RPC

这一点非常重要，因为它意味着：

- 当前“统一四参数交换接口”还保留着
- 但真正发起 RPC 的载体，仍然是 `SourceInventory`

这就是当前系统已经跑通，但未来仍然可能继续演化的关键点之一。

## 六、当前代码为什么能跑通

当前能跑通，不是因为“RPC 发起载体问题已经从架构上彻底消失”，而是因为这次最小方案解决了此前最致命的一点：

- 以前是还没真正拿到对象 Owner，就提前执行了交换动作
- 现在变成了：只有真实 Owner 到位后，挂起的交换动作才会被放行

也就是说，当前系统成立的直接原因是：

- 权限申请
- 等待真实 Owner 到位
- 再执行底层 RPC

这条链终于按正确顺序发生了。

## 七、这轮明确踩过、并且已经被否定的错误方向

这一节非常重要。下一位 AI 不要再重走这些路。

### 1. 不要再做“围绕箱子专门判断”的修复

例如：

- `IsUnifiedInteractAbility`
- `ShouldUseUnifiedInteractRouting`
- 针对箱子、工作台、AI 各写一套判定

这些方向已经被明确否定，原因是它们没有框架价值，只会把项目带回屎山。

### 2. 不要再通过遍历 UI 树去找当前容器 UI

用户已经明确指出：

- `Layout` 本身只负责把 UI push 到玩家屏幕
- 真正的“当前打开了哪个交互 UI”应围绕会话模型和交互 Session 组件来理解
- 通过遍历 UI 树找某个类型 UI，本质上仍然是在写硬编码分支

### 3. 不要通过重置或重新初始化数据层来掩盖 UI 问题

这在之前已经被明确批评过一次。原因是：

- 根因是控制层/会话层/同步时机问题
- 不是数据层真的坏了
- 用“格式化数据”去掩盖视图刷新问题，会在项目规模扩大后变成灾难

### 4. 不要再加额外的等待布尔或状态机补丁

这次已经删掉过一批相关状态，下一位 AI 不要为了新现象再把这些东西加回来。

### 5. 不要把“增删改查”拆成一堆类型专用转发函数

用户已经明确指出：

- 交换不是唯一数据修改行为
- 后面还会有删除、增加、丢弃、整理等操作
- 本质都是“修改当前交互对象的数据”

因此正确方向应始终围绕“修改前先拿权限，权限到手再执行统一操作入口”，而不是围绕某一个具体动作发散出一堆专门函数。

## 八、当前仍需保持警惕的潜在风险

虽然当前运行已经恢复正常，但下面这些点仍然是后续继续演进时必须小心的地方。

### 1. 当前底层库存交换的 RPC 发起载体仍然是 `SourceInventory`

这意味着：

- 如果未来有新的跨容器操作形态
- 或者不再是简单的“源 -> 目标”交换
- 那么 `WhenItemExchange` 这个网络入口是否仍然适合挂在库存组件上，需要重新评估

但注意：

- 现在不要急着重构这一层
- 因为当前问题已经收掉，用户也已经确认运行正常
- 下一位 AI 不应该在没有新证据前主动扩写

### 2. 当前 `TickComponent` 的作用非常单纯，不要把它膨胀成复杂状态机

现在这个 Tick 只是为了做一件事：

- pending 队列存在时，持续尝试 `FlushPendingCurrentInteractableMutationsIfReady()`

如果后续又在这里加各种“状态判断”“超时逻辑”“对象类型分流”，很容易再次变成补丁中心。

### 3. 会话层依然应该只负责当前交互对象

不要让会话层逐渐长成：

- 全局 UI 树检索器
- 任意对象类型路由器
- 数据层特判中心

否则以后继续扩功能时，复杂度会急速上升。
