## 四、当前已经明确并落地的设计结构

这一部分很重要，新 AI 必须先理解，不要再误判结构。

### 1. 技能对象模型

当前正式采用的是这套分层：

- `SkillDefinition (DataAsset)`
  - 负责“这是什么技能”。
  - 定义技能名、描述、图标、技能 AbilityClass 等静态语义。

- `SourceItemDefinition (物品定义 / Definition)`
  - 负责“哪个物品会提供哪个技能”。
  - 通过 `AOFragment_SkillSource` 这类碎片把物品和技能定义关联起来。

- `SourceItemInstance`
  - 负责运行时的技能来源锚点。
  - 技能不是凭空存在，而是挂在某个具体物品实例来源上。

- `SkillInstance`
  - 负责运行时技能状态。
  - 例如当前来源物品、当前装配槽位、技能等级、品质等运行时信息。

- `SkillComponent`
  - 负责角色身上的技能运行时真相。
  - 它回答的是：
    - 当前角色有哪些技能实例。
    - 哪些技能被装到了哪些槽位。
    - 某个槽位应该授予什么 Ability。
    - 冷却怎么查。

- `SkillSlotInventoryComponent`
  - 负责把技能槽“伪装成一个可参与现有库存交换主链的库存容器”。
  - 它不是技能系统真相，只是一个投影适配层。
  - 这样做的目的是复用现有库存 / 背包 / 箱子 / 快捷栏的统一交换逻辑，而不是重写一套专门的技能拖拽系统。

### 2. 当前最重要的职责边界

- `HeroComponent`
  - 只负责发送输入广播和桥接到底层输入系统 / ASC。
  - 不应该在这里写技能槽业务判断。

- `SkillComponent`
  - 负责订阅 Hero 输入，然后自己决定这次输入是否属于技能槽语义。
  - 也负责技能槽输入标签、技能槽位、技能实例之间的关联。

- `StateTree`
  - 当前目标语义是：
    - 玩家输入先进入状态树判定。
    - 再由状态树命中对应技能槽语义。
  - 但这一块当前还没有完全收干净，下面会单独说。

- `SkillSlotInventoryComponent`
  - 只负责库存投影和交换准入。
  - 不负责技能真相。

- `HUD Skill UI`
  - 尽量只读源数据，不自己维护多份真相。
  - 用户此前非常强调这一点，所以后续接手时不要再引入额外快照缓存数组、额外映射表、额外镜像状态。

## 七、当前没有解决的两个核心 BUG

这部分是新 AI 必须优先处理的事情。

### BUG 1：技能输入进入状态树后，按住期间仍然会重复激活

#### 1. 当前现象

- 玩家按下某个技能键后，状态树输入侧会重复被激活。
- 玩家长按该技能键时，这种重复现象更明显。
- 用户的测试技能很简单，只是激活后打印 `Hello` 并立即结束，但按住时仍会持续刷屏。
- 后来观察到一个更精确的现象：
  - **能力本身不一定每帧重复真正激活。**
  - **但状态树那一层仍然在不断重复吃输入。**

这意味着问题的重点不一定只在 GAS Ability 激活上，更可能在：

- Hero 输入广播链。
- InputBuffer 重放链。
- StateTree 事件转发链。
- 这几层之间对 `Trigger / Start / Release` 的定义没有收成一套。

#### 2. 用户明确要求的正确语义

用户要的不是简单“别触发太多次”，而是明确的输入语义：

- 同一次按住期间：
  - 只允许第一次 `Trigger` 被当成一次有效按下。
- 在收到对应 `Release` 之前：
  - 不允许下一次 `Trigger` 再次进入。
- 收到 `Release` 之后：
  - 才允许下一次新的按下重新进入。

换句话说，用户要的是：

- **按住周期去重**
- 而不是简单删除某条输入链或粗暴禁用某个回调。

#### 3. 这次会话里已经做过但仍不足的处理

本轮已经做过这些改动：

- 在 `UAOStateTreeComponentBase` 里新增了 `ShouldForwardStateTreeInputEvent(...)`。
- 用 `ObservedPressedInputTags` 记录“同一按住周期里已经放行过的输入标签”。
- 当前逻辑是：
  - `Trigger` 第一次放行，后续同标签 `Trigger` 拦住。
  - `Release` 到来后移除标签，允许下一次再进。

相关文件：

- `Source\AegisOdyssey\StateTree\AOStateTreeComponentBase.h`
- `Source\AegisOdyssey\StateTree\AOStateTreeComponentBase.cpp`
- `Source\AegisOdyssey\StateTree\CombatStateTree\AOCombatStateTree.cpp`

并且这次还做了一次减法：

- 不再把这个“按住去重闸门”绑定到 `StartLogic / RestartLogic / FullReset` 上重置。
- 原因是如果 StateTree 自己在按住期间重启，我自己把闸门重置掉，下一帧 `Trigger` 又会当成新输入。

这次改动编译已经通过，但用户反馈是：

- **BUG 仍然存在。**

#### 4. 当前最怀疑的根因

最值得重点怀疑的是：

- `AOCombatStateTree` 和 `AOCombatLocomotionStateTree` 目前仍然同时订阅：
  - `Hero` 的原始输入广播
  - `InputBuffer` 的重放输入广播

也就是同一份技能输入语义，可能被两条链都喂进状态树。

关键文件：

- `Source\AegisOdyssey\StateTree\CombatStateTree\AOCombatStateTree.cpp`
- `Source\AegisOdyssey\StateTree\CombatStateTree\AOCombatLocomotionStateTree.cpp`
- `Source\AegisOdyssey\Character\AOHeroComponent.cpp`
- `Source\AegisOdyssey\Character\AOInputBufferComponent.cpp`

因此新 AI 接手时，不要只盯着一个 `TSet` 去重是否正确，更要检查：

1. StateTree 最终应该订阅几条输入来源链。
2. Hero 原始输入和 InputBuffer 重放输入各自的正式职责是什么。
3. 哪一层才应该是“本次按住周期”的唯一权威。

#### 5. 这一块不要再走的歪路

用户已经明确否掉过这些思路：

- 直接砍掉 `OnPressInputLoad`。
- 通过删除原有输入回调来“假装修好”。
- 再叠一层脏映射或额外缓存去掩盖重复输入。

用户要的是：

- **找到真正的根因。**
- **让 Release 成为下一次 Press 的唯一解锁条件。**

### BUG 2：技能拖拽装配时，仍然只能稳定放到第一个技能槽

#### 1. 当前现象

- 玩家从普通库存拖技能来源物品到技能条时，当前仍然表现为：
  - 第一个技能槽能放。
  - 后面的技能槽不稳定，或者基本不能放。

用户当前描述是：

- “还是只能放到第一个槽。”

#### 2. 已经做过的修正方向

此前已经做过一轮技能槽身份和目标容器方向的收敛：

- `UAOSkillSlotUI` 引入了 `ObservedSlotIndex`。
- `AOSkillBarUI` 在刷新构建每个技能槽时，显式给每个技能槽注入：
  - 自己的 `ObservedSlotIndex`
  - 自己所属的 `SourceContainer`
- 技能槽落点不再依赖蓝图自己随便推导，而是有正式 C++ 入口：
  - `CanAcceptDraggedSourceSlotForThisSkillSlot(...)`
  - `RequestEquipDraggedSourceSlotToThisSkillSlot(...)`

相关文件：

- `Source\AegisOdyssey\UI\Widgets\Skill\AOSkillBarUI.h`
- `Source\AegisOdyssey\UI\Widgets\Skill\AOSkillBarUI.cpp`
- `Source\AegisOdyssey\UI\Widgets\Skill\AOSkillSlotUI.h`
- `Source\AegisOdyssey\UI\Widgets\Skill\AOSkillSlotUI.cpp`

#### 3. 这次又做过的一轮修正

这次会话又加了一轮减法修正：

- 在 `UAOSkillSlotInventoryComponent::HandleChangeInitState(...)` 里，改成**客户端也先补齐技能槽库存投影的空槽位壳子**。
- 原因是之前非常怀疑出现了这种情况：
  - HUD / SkillComponent 这边知道有 4 个技能槽，所以 UI 能画出 4 个格子。
  - 但本地 `SkillSlotInventoryComponent` 如果没把投影容器补齐到 4 个槽位，那么拖拽落点真正进入统一库存交换主链前，`IsValidInventorySlotIndex()` 就可能只认现存的少数条目。
  - 这样就会表现成只有第一个技能槽能落点。

相关文件：

- `Source\AegisOdyssey\SkillSystem\AOSkillSlotInventoryComponent.cpp`

这轮改动编译通过了，但用户反馈是：

- **这个 BUG 仍然存在。**

#### 4. 当前最需要重点怀疑的方向

新的 AI 接手时，建议优先查下面几个点：

1. 技能槽蓝图的 `OnDrop` 是否真的调用到了**当前落点这个槽实例自身**。
2. 蓝图是否仍然在读旧的 `Index`、父控件缓存引用，或者某个固定第一格引用。
3. 统一库存交换主链里，目标容器和目标索引到达 `ExecuteExchangeRequest(...)` 之前，是否已经被改歪。
4. `SkillSlotViewData`、`ObservedSlotIndex`、`SourceContainer` 这三者里，是否仍有某一层被蓝图旧逻辑覆盖。

换句话说：

- 当前不一定是底层交换主链错了。
- 很可能是**真正落点身份在 UI 或蓝图入口层就已经丢了**。

#### 5. 这一块不要再走的歪路

用户已经多次明确表达过，不要：

- 再为技能槽单独造一套完全新的拖拽交换系统。
- 为了修这个问题去大改现有背包 / 库存统一交换架构。
- 叠新的映射表、缓存表、快照表，把问题越修越脏。

用户倾向的是：

- 能复用统一库存交换主链就复用。
- 技能槽只在“目标槽位准入合法性”这一层做特殊判断。
