# 技能系统设计方案：技能对象化与槽位装配框架

更新日期：2026-05-05

这份文档的用途，是把我们当前已经拍板的技能系统思路稳定记录下来，作为后续持续迭代时的长期设计笔记与交接基线。

当前阶段目标很明确：

- 先把技能系统框架搭稳
- 先把边界、分层、对象关系、触发链条讲清楚
- 暂时不进入具体技能执行表现的实现细节

也就是说，现阶段重点不是“火球怎么飞、雷链怎么跳、落雷怎么选点”，而是先把“技能是什么、放在哪、怎么装、怎么触发、谁负责管理、如何不破坏现有系统”这套骨架立住。

## 一、这套技能系统现在到底想解决什么问题

我们现在要做的，不是简单做几个按钮然后按下去放技能。

我们真正要做的是一套：

- 技能对象化
- 技能来源解耦
- 技能可获取
- 技能可作为对象存在于库存体系
- 技能可装入固定技能槽
- 技能可替换
- 技能可扩展
- 玩家与 AI 共用

的技能系统。

从游戏设计角度看，它更接近：

- 角色身上有几个固定技能槽位
- 角色通过不同来源获得技能对象
- 技能对象可以被拖入这些槽位
- 槽位被触发时，激活装在这个槽里的技能

这里必须再强调一次：

**技能石只是技能的一个载体，不是技能系统本体。**

我们可以做出“像流放之路 2 一样技能以技能石形式存在”的效果，但系统底层不能被设计成“只有技能石才能代表技能”。

## 二、当前已经拍板的核心原则

### 1. 技能必须和角色本体、固定键位解耦

角色不应该直接拥有一堆写死的：

- 火球术变量
- 雷链变量
- 落雷变量
- 固定按键对应固定技能

角色真正应该拥有的是：

- 固定数量的技能槽
- 一套已装配技能集
- 一条统一的触发链
- 一套后续可扩展的技能执行框架

### 2. 输入绑定的是技能槽，不是技能名

推荐语义应当是：

- `Input.SkillSlot1`
- `Input.SkillSlot2`
- `Input.SkillSlot3`
- `Input.SkillSlot4`

这样键位改动、技能换槽、不同角色同技能异槽位，都不会影响技能内容定义本身。

### 3. 技能可以存在于背包，但库存系统仍然只做库存系统

这是当前方案最重要的边界之一。

正确理解是：

- 技能可以作为物品对象待在背包或其他库存容器中
- 但库存系统仍然负责容器、槽位、交换、拖拽、增删改查、同步、观察
- 技能系统只把库存当成“承载技能来源对象的底层容器能力”

不能因为要做技能，就把库存系统改成围绕技能语义运转。

### 4. 只允许主动触发技能进入当前技能槽体系

当前阶段的技能槽，只服务：

- 主动触发
- 有明确输入或触发命令
- 装进槽后可直接使用

的技能。

被动技能、常驻天赋、纯光环类能力，当前不进入这套主动技能槽体系。

### 5. 当前不区分槽类型

当前阶段不做：

- 法术槽
- 位移槽
- 大招槽
- 反应槽

这种细分。

当前技能槽只表达一件事：

**角色当前可装配多少个可主动触发技能。**

### 6. 复用必须围绕技能系统需要，而不是围绕“少写代码”

后续判断某块代码能不能复用，标准不是“能不能勉强用”，而是：

- 这块复用的是基础能力还是旧系统语义
- 这块复用会不会限制技能未来变化
- 这块代码的核心关注点是不是技能

### 7. 玩家和 AI 共用同一套技能数据层

技能对象、技能槽、装配关系、冷却与长期状态，这些都是 Pawn 身上的战斗数据。

它们不应该因为控制器不同而拆成两套系统。

## 三、当前阶段的术语统一

这一节非常重要，后续不要再把旧术语和新术语混着用。

### 1. `SkillDefinition`

静态内容定义，用来描述：

- 这是什么技能
- 图标、名称、描述
- 标签、技能族 / 技能组
- 冷却、消耗
- 对应 AbilityClass
- 后续执行配置

当前正式口径补充：

- `SkillDefinition` 当前正式就是独立的 `DataAsset` / `PrimaryDataAsset` 技能静态定义资产。
- 它专门负责回答“这是什么技能”，不负责承担来源物品那一层语义。
- 来源物品如果要提供技能，应当通过单独的物品定义和 `SkillSource` 碎片去声明。

### 2. 技能载体物品

这是库存系统中的普通物品对象，只是它带有“技能语义”。

例如后续可能会有：

- 技能石
- 技能书
- 技能卷轴
- 技能芯片

它们仍然先是库存物品，再额外携带“关联哪个技能定义”的信息。

这里必须再补一句，避免后面继续绕：

- `SkillDefinition` 说的是“技能定义资产”
- “技能载体物品”说的是“技能来源物品定义”

这两个不是一回事。

更直白一点：

- 技能定义资产回答的是：**这是什么技能**
- 技能来源物品定义回答的是：**哪个物品会提供这个技能**

后续如果文档里再次提到“Definition”，必须优先写清楚到底是：

- 技能定义类
- 还是技能来源物品定义

### 3. `SourceItemInstance`

这里当前更准确的理解是：

**背包中的物品实例本身，就是技能实例身份锚点。**

也就是说：

- 一个技能载体物品实例，就是一个具体来源对象
- 同一个技能定义由两个不同物品提供时，就是两个来源实例
- 后续等级、品质、附加信息、来源差异，都可以挂在来源实例或由其驱动

### 4. `SkillInstance`

这是技能系统运行时真正使用的技能实例对象。

它至少应该知道：

- 指向哪个 `SkillDefinition`
- 它的来源锚点是谁
- 当前等级 / 品质 / 强化 / 来源附加数据
- 冷却和长期状态
- 当前是否已装配
- 当前装在哪个槽

### 5. `SkillSlotEntry`

这是装配关系对象，用来表达：

- 第几个技能槽
- 当前装了哪个 `SkillInstance`
- 该槽对应哪个输入 Tag
- 当前授予到 ASC 的 Handle 是什么

### 6. `已装配技能集`

这就是我们当前用来替代旧“技能库”说法的新术语。

它的含义不是“角色拥有的全部技能”。

它的含义是：

**当前已经被装入技能槽，并进入运行时可触发管理范围的技能实例集合。**

这意味着：

- 背包里的技能物品，在没有装入技能槽之前，和普通物品无异
- 只有装入技能槽后，才会进入 `已装配技能集`
- 所以当前阶段不再保留“拥有但未装配的独立技能库”这一层运行时集合语义

“拥有但未装配”的技能，在当前方案里主要由库存系统中的技能载体物品来承载。

## 四、哪些地方能复用，哪些地方不能直接复用

### 1. 可以复用的是基础能力

当前比较明确能复用的基础能力包括：

- 输入 Tag 分发链
- Hero 到 ASC 的桥接
- AbilitySet 授予与回收
- 组件挂在 Pawn 身上的组织方式
- 库存系统的拖拽 / 交换 / 观察 / 同步模式
- UI 的观察者模式
- AI 侧注入战斗命令的思路

### 2. 不应直接复用的是旧系统语义

下面这些不能因为“看起来像”就直接挪用为技能语义：

- QuickBar 的“当前选中槽位”语义
- 武器系统的 Equip / Unequip 语义
- 某些默认依赖本地玩家控制器的目标获取逻辑
- 某些默认依赖相机或玩家准星的实现

### 3. 结论

可以参考现有系统的方式：

- 数据怎么放
- 变化怎么通知
- 网络怎么同步
- 输入怎么桥接

但不要直接把：

- 装备栏
- 当前使用物品栏
- 玩家专用逻辑

当成技能系统本体。

## 五、当前推荐的系统分层

### 1. 技能定义层

回答：

**这个技能本身是什么。**

这里放静态配置和设计层信息，不关心谁拥有它、它装在哪、当前按哪个键触发。

### 2. 技能来源层

回答：

**这个技能是通过什么来源进入当前角色体系的。**

当前最重要的来源形态，是库存中的技能载体物品。

未来也允许扩展到：

- 职业解锁
- 任务奖励
- 武器附赠
- Buff 临时赋予
- Boss 固有配置

### 3. 技能槽层

回答：

**角色当前真正装了哪些技能。**

技能槽是固定数量、固定输入语义的装配位置。

### 4. 已装配技能集层

回答：

**当前进入运行时管理范围、可被查询、可被触发、可被 UI 观察的已装配技能实例有哪些。**

它不是“拥有列表”，而是“装配结果集合”。

### 5. 输入槽位层

回答：

**哪个输入在触发哪个技能槽。**

### 6. 技能执行层

回答：

**技能一旦被激活，后续怎么选目标、定原点、发射、跳链、爆炸、结算。**

这一层当前只保留为未来设计方向，暂不优先实现。

## 六、技能对象关系的当前方案

### 1. 技能定义不是物品

`SkillDefinition` 是技能内容本体，不属于某个具体背包实例。

### 2. 技能载体物品是来源对象

例如：

- 火球技能石物品
- 雷链技能书物品

它们是库存中的对象，同时也是“这个技能从哪来”的来源锚点。

### 3. 技能实例由来源驱动

当前方案不是“同定义合并实例”，而是：

**一个来源对应一个实例。**

也就是说：

- 火球技能石 A 提供一个火球实例
- 火球技能石 B 再提供一个火球实例
- 即便二者定义相同，也仍然是两个不同实例

### 4. 技能槽直接存技能实例引用

这是当前已经拍板的点。

技能槽位条目不应只存一个模糊 ID 再到处查，而应直接存：

- 当前装配的 `SkillInstance` 引用

同时：

- `SkillInstance` 再直接握住自己的来源锚点引用

这样槽位、实例、来源三者关系会比较清晰。

### 5. 同技能多槽的前提

当前允许：

**同一个技能定义的不同实例，分别装到多个槽位。**

当前不允许：

**同一个实例同时占多个槽位。**

一个实例就是一个对象，这一点语义上要和“背包里的一把武器就是一个对象”保持一致。

## 七、装配、卸下、删除、换槽时的行为规则

### 1. 从背包到技能槽

当一个技能载体物品从背包被装入技能槽时：

- 库存系统负责完成容器侧的数据变更
- 技能系统负责识别这是一个可装配主动技能
- 创建或激活对应的 `SkillInstance`
- 把它加入 `已装配技能集`
- 刷新该槽位的 Ability 授予结果

### 2. 从技能槽卸下

当技能从槽位卸下时：

- 从槽位移除装配关系
- 从 ASC 移除该槽位对应旧 Spec
- 从 `已装配技能集` 中移除该实例
- 但如果这个实例未来还有长期状态要保留，需要确保这些状态跟实例走，不跟槽位走

### 3. 背包中的技能物品被删除

当前方案下，背包中的技能物品如果只是普通背包状态、没有装入技能槽，那它和普通物品一样，直接按库存规则删除即可。

因为它当时并没有进入 `已装配技能集`。

### 4. 槽位结果变化时的 ASC 刷新规则

当前已经拍板：

**槽位装配结果一旦变化，就移除旧 Spec，再按新槽位结果重新授予新 Spec。**

也就是说：

- 换槽
- 覆盖槽位
- 卸下再装入

这些都应以槽位真实数据变化为准刷新授予结果。

### 5. 技能组件作为最终收口点

无论请求来自：

- 玩家 UI
- 玩家输入
- AI 指令
- 脚本注入

最后都应尽量收口到技能组件入口，而不是到处直接改 ASC 或直接改某个槽数组。

## 八、冷却、长期状态与技能族绑定规则

### 1. 冷却不跟槽位绑定，跟技能实例 / 技能族语义绑定

当前已经明确：

- 同技能不同实例可以占多个槽
- 但冷却不能因为多槽或换槽被绕开

所以更合理的方向是：

- 槽位只负责“装配关系”和“输入映射”
- 冷却与长期状态放在 `SkillInstance` 或更上层的技能运行时状态结构
- 共享规则按“同技能族 / 同技能组”来约束

### 2. 已经拍板的共享规则

当前结论：

**冷却按同技能族 / 同技能组共享。**

这意味着：

- 即使主显示图标相同
- 即使是不同实例
- 只要属于同技能族 / 同技能组

就不能通过多实例多槽的方式逃掉冷却。

### 3. 已经拍板的保留规则

以下情况都要保留冷却与长期状态：

- 技能正在冷却时被拖槽
- 技能被卸下后再装回
- 槽位变化导致旧 Spec 被移除再重新授予
- 来源状态变化但实例身份仍然延续

原则只有一句话：

**不允许玩家通过槽位操作刷新冷却或清空长期状态。**

---

## 九、UI 需要知道什么，怎么知道

当前阶段技能系统至少要维护两套观察数据：

### 1. 技能槽观察数据

回答：

- 第几个槽当前装了什么
- 该槽是否为空
- 该槽当前图标、名称、冷却表现是什么
- 该槽是否可用

### 2. 已装配技能集观察数据

回答：

- 当前有哪些技能实例处于已装配状态
- 这些实例的来源、等级、品质、冷却、附加信息是什么

这两套观察数据要分开保留，原因是：

- 技能槽是“显示位置语义”
- 已装配技能集是“运行时技能实例语义”

两者相关，但不是同一个视角。

### 3. UI 的职责边界

UI 只负责：

- 显示技能
- 显示来源、等级、品质等悬停信息
- 发起装入、卸下、交换、替换请求

UI 不负责：

- 直接改 ASC
- 直接持有真实技能状态
- 绕过技能组件直接改运行时集合

## 十、玩家与 AI 共用技能系统时的落点

### 1. 数据层共用

玩家与 AI 共用：

- `SkillDefinition`
- `SkillInstance`
- `SkillSlotEntry`
- `已装配技能集`
- 冷却与长期状态

### 2. 主要区别只在触发入口与目标选择

玩家可能通过：

- Enhanced Input
- HeroComponent
- HUD / UI

触发技能槽。

AI 可能通过：

- AI StateTree
- 决策结果
- 战斗命令注入

触发技能槽。

但它们最终都应尽量走同一条技能组件语义接口。

### 3. 编码时不要写死本地玩家假设

技能核心层不要默认依赖：

- 本地玩家控制器
- 一定存在摄像机
- 一定通过玩家准星选目标

技能核心层应优先依赖：

- `APawn`
- `AController`
- `ASC`
- `AbilityActorInfo`
- 目标选择策略接口

### 4. 这一部分当前有哪些可以复用

当前明确可以复用：

- HeroComponent 到 ASC 的输入桥接思路
- AI 当前已经存在的战斗命令注入思路
- Pawn / Controller / ASC 的战斗上下文组织方式

### 5. 如果现有逻辑不能直接复用，该怎么设计

如果某块逻辑天然写死了：

- 本地玩家视角
- 相机朝向
- 玩家准星

那它就不该直接放进技能核心基类。

更合理的新设计方向应该是把差异收进独立策略，例如：

- 玩家准星目标选择
- AI 当前战斗目标选择
- 控制器朝向目标选择
- 地面指定点选择

让差异落在策略层，不落在技能本体层。

## 十一、和当前 GAS / StateTree 的结合方式

### 1. 输入仍然走当前 Hero -> ASC -> StateTree 主链

我们不是重写一套输入系统，而是在现有主链上增加“技能槽触发语义”。

### 2. 技能槽变化驱动 Ability 授予结果

当技能装入某个槽位时：

- 授予该技能对应的 Ability
- 给该 AbilitySpec 打上该槽位输入 Tag

当槽位变化时：

- 回收旧授予
- 再按新结果授予

### 3. ASC 只承接当前装配结果

ASC 更适合承接：

- 当前已经进入技能槽
- 当前处于可触发状态

的技能结果。

当前不建议把所有潜在拥有的技能永久全塞进 ASC。

### 4. StateTree 的职责

当前更合理的分工是：

- StateTree 负责状态切换和触发时机
- 技能组件负责统一收口
- ASC / GA 负责能力生命周期
- 真正复杂的技能执行细节留到未来框架阶段

## 十三、当前已拍板结论汇总

这一节只保留已经明确拍板的结论，避免以后讨论时和旧说法混淆。

### 1. 技能可以作为背包中的对象存在

但不能破坏库存系统原有封装。

### 2. 当前阶段不保留“拥有但未装配”的独立运行时技能库

只有装入技能槽后，才进入 `已装配技能集`。

### 3. 背包中的技能物品，在未装配前与普通物品无异

库存系统照常管理它。

### 4. 当前技能槽只允许主动触发技能

被动技能暂不纳入这套槽位装配体系。

### 5. 当前不区分槽类型

槽位只表达“当前可装配多少个主动技能”。

### 6. 同一个技能定义允许多槽，但前提是不同实例

一个实例只能占一个槽。

### 7. 冷却按同技能族 / 同技能组共享

不能通过多实例多槽规避冷却。

### 8. 槽位变化时移除旧 Spec，再按新槽位结果重新授予

以槽位真实数据变化为准刷新 ASC 授予结果。

### 9. 需要保留两套观察数据

- 技能槽观察数据
- 已装配技能集观察数据

### 10. 玩家与 AI 各有触发路径，但技能组件作为最终统一入口

不要在各处直接分散改动技能真实状态。

### 11. 背包物品实例本身就是技能实例身份锚点

这点是当前方案稳定性的关键之一。

### 12. 相同技能图标与主名称可以不区分

但悬停详情里要显示来源、等级、品质等实例差异。

## 十四、当前阶段的总收束

到目前为止，这套方案已经可以用一句话概括：

**技能是可获取、可作为对象存在、可装入固定槽位、可通过统一链路触发的独立资源。**

更完整一点说，就是：

- 技能本体由 `SkillDefinition` 描述
- 技能来源可以是库存中的技能载体物品，也允许未来扩展到其他来源
- 背包中的技能物品在未装配前，和普通物品无异
- 只有装进技能槽后，才进入 `已装配技能集`
- 技能槽直接存运行时技能实例引用
- 同定义不同实例可以多槽，但冷却按技能族 / 技能组共享
- UI 只观察和请求，不直接持有真实逻辑
- 玩家与 AI 共用同一套技能数据层
- 当前先做框架，不先做具体技能执行表现

后续只要继续沿着这份文档更新，就能尽量避免：

- 上下文丢失
- 术语混乱
- 为了复用而复用
- 为了支持技能而破坏库存系统
- 为了眼前能跑而把技能系统写死

这就是我们当前阶段的技能系统方案基线。

## 十五、开工阶段划分与会话节奏

这一节不是讨论“技能设计是否正确”，而是把后续真正开工时的实施顺序固定下来。

目的只有两个：

- 避免后续会话反复重讲背景，浪费 token
- 保证每一阶段都有明确边界，不为了眼前跑通把后面结构写死

### 总原则

后续实现严格按下面顺序推进：

1. 先立运行时骨架，不先碰复杂技能表现
2. 先打通数据归属与装配链，不先堆 UI 细节
3. 先让玩家与 AI 共用统一入口，不先写玩家特化逻辑
4. 每一阶段都必须可独立验收，再进入下一阶段

### 第一阶段：核心对象与组件骨架

目标：

- 建立 `SkillDefinition`
- 建立 `SkillInstance`
- 建立 `SkillSlotEntry`
- 建立技能组件，作为最终统一收口点

本阶段要解决的问题：

- 技能定义放哪
- 技能实例怎么表示
- 来源锚点怎么挂到实例上
- 槽位怎么持有实例引用
- 已装配技能集怎么组织

本阶段暂不做：

- 技能执行表现
- 冷却 UI 表现
- 背包拖拽交互细节
- 复杂网络边角优化

阶段完成标志：

- 角色身上已经有独立技能组件
- 技能组件内部已经能表达“来源 -> 实例 -> 槽位 -> 已装配技能集”这套关系
- 同一实例不能重复装入多个槽
- 同定义不同实例允许装入不同槽

### 第二阶段：库存来源接入与装槽规则落地

目标：

- 让库存中的技能载体物品正式接入技能系统
- 打通“背包物品 -> 技能实例 -> 技能槽”的装配链

本阶段要解决的问题：

- 如何识别一个库存物品是否为技能载体
- 如何从 `SourceItemInstance` 创建或激活对应 `SkillInstance`
- 装入、卸下、换槽、覆盖时如何维护技能实例与槽位关系
- 删除来源物品时如何正确处理已装配状态

本阶段必须坚持：

- 库存系统仍只负责库存语义
- 技能系统不反向侵入库存底层结构
- 装配变化一律通过技能组件入口完成

阶段完成标志：

- 技能载体物品可以作为背包对象存在
- 可以从背包装入技能槽
- 可以卸下、换槽、覆盖
- 槽位变化后，技能组件内的数据关系保持正确

### 第三阶段：ASC 授予刷新与输入槽位化

目标：

- 让技能槽变化驱动 GAS 授予结果变化
- 把输入从“技能名语义”切到“技能槽语义”

本阶段要解决的问题：

- 增加 `Input.SkillSlot1~N` 这类输入标签
- 槽位装配后如何为对应 AbilitySpec 注入槽位 InputTag
- 槽位变化时如何移除旧 Spec 再授予新 Spec
- 技能组件如何调用现有 Hero -> ASC 输入链

本阶段必须坚持：

- ASC 只承接当前装配结果
- 不把所有潜在技能永久塞进 ASC
- 不复用 QuickBar 的“当前选中槽位”语义

阶段完成标志：

- 每个技能槽有明确输入 Tag
- 输入触发的是槽，不是具体技能名
- 装槽、换槽、卸下都会正确刷新 ASC 授予结果
- 玩家输入已能通过技能槽激活对应技能

### 第四阶段：AI 共用触发入口

目标：

- 让 AI 和玩家共用同一套技能触发入口

本阶段要解决的问题：

- AI 如何按技能槽语义发出触发命令
- 当前 StateTree / CombatCommand 如何接到技能组件入口
- AI 侧等待激活、等待完成时如何观察对应 Spec

本阶段必须坚持：

- 不额外分叉一套 AI 专属技能系统
- 玩家和 AI 只在触发入口与目标选择策略上有差异

阶段完成标志：

- AI 已经可以按技能槽语义触发技能
- 玩家与 AI 的触发最终都收口到技能组件
- AI 侧等待激活 / 完成的观察链条仍然可用

### 第五阶段：冷却、长期状态与共享规则

目标：

- 把冷却和长期状态从“槽位附属物”变成“实例 / 技能族语义状态”

本阶段要解决的问题：

- 冷却状态挂在 `SkillInstance` 还是独立运行时状态结构
- 同技能族 / 同技能组如何共享冷却
- 换槽、卸下、重新装入时如何保留长期状态

本阶段必须坚持：

- 不允许通过槽位操作刷新冷却
- 不允许通过多实例多槽规避共享冷却规则

阶段完成标志：

- 冷却不再依附槽位
- 槽位变化不会重置冷却
- 同技能族 / 同技能组共享规则成立

### 第六阶段：UI 观察数据与装配界面接入

目标：

- 让 UI 能观察技能槽与已装配技能集

本阶段要解决的问题：

- 技能槽观察数据结构如何定义
- 已装配技能集观察数据结构如何定义
- MVVM / ViewModel 如何复用当前观察模式
- UI 如何只发请求，不持有真实状态

本阶段必须坚持：

- UI 不直接改 ASC
- UI 不直接改技能真实运行时集合
- 真实数据仍在组件中维护

阶段完成标志：

- UI 能显示技能槽内容
- UI 能显示来源、等级、品质、冷却等实例信息
- UI 能发起装入、卸下、交换、替换请求

### 第七阶段：技能执行层扩展

目标：

- 在不破坏前六阶段骨架的前提下，逐步接入具体技能执行表现

本阶段才进入的问题：

- 投射物技能
- 锁定技能
- 范围技能
- 跳链技能
- 地面选点技能
- Boss 特殊技能

阶段完成标志：

- 新技能类型是在既有骨架上扩展出来的
- 不需要回头推翻前面的来源、槽位、授予、冷却、UI 结构

### 后续会话的执行规则

为了不浪费 token，后续新会话默认按以下方式衔接：

1. 先说明当前做到第几阶段
2. 只补充本阶段直接相关上下文
3. 不重复重讲整份技能系统总设计，除非发现与文档冲突
4. 若实现方案与本文档冲突，优先先回写本文档，再继续编码

### 当前建议的实际开工顺序

如果马上开始做，建议按下面顺序落代码：

1. 先做第一阶段：核心对象与技能组件骨架
2. 再做第二阶段：库存来源接入与装槽关系
3. 再做第三阶段：ASC 授予刷新与 `Input.SkillSlot`
4. 然后做第四阶段：AI 共用触发入口
5. 再补第五阶段和第六阶段
6. 最后才进入第七阶段的具体技能执行表现

一句话概括后续施工顺序：

**先把技能“作为资源如何存在、如何装、如何触发、如何被管理”做对，再去做它“怎么飞、怎么炸、怎么选目标”。**

## 十六、工程师接手时的阅读路径、思路建立与使用说明

这一节不是新增设计，而是把“现在这套代码到底该怎么理解、应该从哪看、后续应该怎么用”明确写出来。

目的只有一个：

- 避免后续工程师接手时只能靠猜
- 避免 UI、Hero、SkillComponent、ASC 之间再次职责串层
- 避免后面新增技能时又回头破坏前六阶段已经立住的骨架

### 1. 先记住整套系统的真相归属链

这套系统当前必须按下面的职责边界理解：

- `Hero` 只负责发送输入，不负责技能语义判断
- `SkillComponent` 是技能运行时总入口，负责装槽、实例管理、ASC 授予刷新、冷却查询、观察数据输出
- `SkillInstance` 代表某个具体技能在当前角色身上的运行时身份
- `SkillDefinition` 代表技能的静态定义
- `UI / MVVM` 只观察、只发请求，不持有技能真实运行时状态

换句话说：

- 技能真实状态不在 UI
- 技能真实状态不在 Hero
- 技能真实状态不在某个蓝图槽位 Widget
- 技能真实状态在 `SkillComponent + SkillInstance + ASC`

这条边界必须先记死，否则后面任何“临时为了跑通”的写法都会把层次重新写乱。

### 2. 工程师建立思路时，建议按这个顺序看代码

不要一上来就散着搜。

建议严格按下面顺序看：

#### 第一步：先看角色把技能系统挂在哪里

先确认技能系统作为角色常驻组件存在，而不是某个临时子系统或某个 UI 附属逻辑。

应该先看：

- `AAOCharacter`
- `CharacterSkillComponent`

先把“技能系统住在谁身上”看明白。

#### 第二步：再看 `UAOSkillComponent`

这是整套运行时技能系统的总入口。

接手时优先看这些能力：

- 技能槽如何维护
- 技能实例如何创建
- 来源物品如何转成技能实例
- 技能如何装入槽位
- 技能如何从槽位授予到 ASC
- 输入如何从 Hero 广播后被 SkillComponent 识别
- 冷却如何查询
- UI 观察数据如何导出

如果后续你要改技能运行时框架，大部分情况都应该优先从这里入手，而不是先去动 UI 或 Hero。

#### 第三步：再看 `UAOSkillDefinition`

这里回答的是：

- 这是什么技能
- 这个技能的显示名、描述、图标是什么
- 它对应哪个 `GameplayAbility`
- 它的冷却身份标签和基础冷却时长是什么

`SkillDefinition` 是静态资源，不是运行时状态容器。

#### 第四步：再看 `UAOSkillInstance`

这里回答的是：

- 当前角色身上的这个技能实例是谁
- 它来自哪个来源物品
- 当前是否已装配
- 当前装在哪个槽
- 当前等级、品质是多少

它是“技能对象化”的运行时落点。

#### 第五步：再看来源物品如何接入技能系统

要看清楚：

- 库存物品并不会天然变成技能
- 只有带 `SkillSource` 碎片的物品，才会被技能系统识别为技能来源

也就是说：

- 物品系统仍然只负责物品语义
- 技能系统只是在物品定义上读取“这个物品提供哪个技能”

这就是库存系统和技能系统的桥接边界。

#### 第六步：再看 ASC 授予刷新链

这里要建立的思路是：

- 槽位不是直接执行技能
- 槽位的职责是承载“当前这个输入位装了哪个 SkillInstance”
- `SkillComponent` 再把当前槽位结果授予到 ASC

所以后面如果出现“换槽后为什么 AbilitySpec 变了”、“为什么这个槽卸下后技能不能再触发”这类问题，应该优先回到授予刷新链排查。

#### 第七步：再看输入链

这里一定要记住你已经拍板确认过的架构：

- `Hero` 只发送
- `SkillComponent` 订阅接收
- `SkillComponent` 在自己内部判断这个输入是不是技能槽输入

所以后续如果要加：

- 技能槽级前置校验
- 槽位冷却门禁
- 输入埋点
- AI 技能意图反馈

都应该优先往 `SkillComponent` 的输入观察路径里加，而不是再回退到 `Hero` 去做技能语义判断。

#### 第八步：再看冷却链

这里的关键共识是：

- 冷却真相不挂在槽位上
- 冷却真相也不挂在 UI 上
- 冷却真相存在于 ASC 的激活效果中

`SkillDefinition / SkillInstance` 只负责提供“冷却身份语义”，
真正的剩余时间、总时长、共享冷却命中情况，都要去 ASC 查。

所以：

- 换槽不该重置冷却
- 卸下再装不该重置冷却
- UI 也不该自己缓存冷却真值作为唯一来源

#### 第九步：最后再看 UI / MVVM 观察层

这一层要按“观察层”理解，不要按“业务真相层”理解。

你应该这样看它：

- `SkillComponent` 输出技能槽快照和已装配技能快照
- `HUD ViewModel` 缓存展示快照并提供统一观察口
- 技能条 / 技能槽 Widget 基类只负责订阅刷新和缓存展示结果
- 蓝图只负责画，不负责保存真相

如果 UI 表现错了，先看观察数据有没有错；
如果观察数据本身错了，再回到 `SkillComponent` 查运行时真相。

### 3. 一条标准运行流程，工程师必须能脑内串起来

后续排查问题时，建议始终按下面这条标准链路思考：

1. 角色身上挂有 `SkillComponent`
2. 某个来源物品通过 `SkillSource` 碎片声明自己提供哪个技能
3. 技能系统根据来源物品找到 `SkillDefinition`
4. 技能系统创建或复用 `SkillInstance`
5. `SkillInstance` 被装入某个技能槽
6. `SkillComponent` 按当前槽位结果刷新 ASC 授予
7. `Hero` 广播输入
8. `SkillComponent` 订阅到输入后判断它是否命中某个技能槽
9. ASC 按当前授予结果去触发具体技能 Ability
10. UI 通过观察层看到当前槽位里装了什么、它来自哪里、等级/品质/冷却如何

这条链如果能在脑子里串起来，后面定位问题时就不会东一榔头西一棒子。

### 4. 工程师后续写代码时的使用说明

下面这些是后续编码时的“默认使用规则”。

正确顺序是：

#### 4.4 后续如果要做 UI，请坚持什么边界

UI 只做三件事：

- 观察
- 显示
- 发请求

UI 不做三件事：

- 不直接改 ASC
- 不直接改技能运行时集合
- 不在 Widget 里偷偷保存技能真相

#### 4.5 后续如果要做 AI 技能触发，请坚持什么边界

AI 要做的是：

- 调用统一触发入口

AI 不应该做的是：

- 自己复制一套技能语义判断
- 自己跳过 Hero / SkillComponent 的输入链直接篡改底层运行时状态

### 9. 2026-05-08 追加同步：技能槽拖拽准入的正式边界

这一条单独补，是为了避免后面把“技能槽拖拽准入”误写成一次对整个库存系统的大改。

当前正式口径如下：

- 技能槽拖拽准入，不通过大改 `InventoryComponent` 主交换链来做。
- 技能槽自己的拖拽合法性，优先收口在技能系统自己的入口中。
- 蓝图技能槽 `OnDrop` 只负责拿到被拖拽的 `ItemInstance`，然后向技能系统发起“这个物品能不能进入当前技能槽”的询问。
- 如果技能系统回答不合法，技能槽 UI 直接拒绝。
- 如果技能系统回答合法，再继续发起正式装槽请求。

这意味着当前阶段我们故意把职责压缩成：

- `SkillSlotUI`：拖拽入口、体验层预检查、发请求
- `SkillComponent`：权威校验、正式装槽
- `InventoryComponent`：保持现有库存交换主链，不因为技能槽拖拽这一个需求而整体重构

#### 一个非常容易误判的细节：空位置不是非法物品

这里必须明确：

- 技能槽和普通库存空格之间的拖拽，本质上仍然是和“空位置”做交换
- 空位置不是一个“非法物品”
- 所以不能把规则写成“凡是和技能槽相关的交换，都必须是技能来源物品”

真正正确的判断语义是：

- 只有当“一个真实物品实例即将进入技能槽”时，才检查它是不是合法技能来源物品
- 如果只是从技能槽把已有技能来源物品拖回背包空格、物品栏空格、或其他普通库存空格，这不属于“进入技能槽”的准入检查语义

#### 当前 C++ 已补的正式入口

当前代码里已经补了下面这几个技能系统自己的正式入口：

- `UAOSkillComponent::IsSkillSourceItem()`
- `UAOSkillComponent::CanAcceptSourceItemForSkillSlot()`
- `UAOSkillComponent::RequestEquipSourceItemToSlot()`
- `UAOSkillSlotUI::CanAcceptDraggedItemForThisSkillSlot()`
- `UAOSkillSlotUI::RequestEquipDraggedItemToThisSkillSlot()`

它们的职责分工是：

- `SkillSlotUI` 负责给蓝图拖拽 `OnDrop` 提供直接可调用的桥
- `SkillComponent` 负责给权威端提供统一准入判断和正式装槽入口

#### 蓝图侧现在应该怎么用

技能槽蓝图后续做 `OnDrop` 时，推荐顺序固定为：

1. 从 DragOperation 里拿到被拖拽的 `UAOInventoryItemInstance`
2. 调 `CanAcceptDraggedItemForThisSkillSlot()`
3. 如果返回 `false`，直接拒绝拖拽
4. 如果返回 `true`，再调 `RequestEquipDraggedItemToThisSkillSlot()`
5. 不要在蓝图里直接改 `SkillComponent` 内部数组，不要在蓝图里自己伪造技能实例

这样可以保证：

- 体验判断在技能槽 UI 侧完成
- 运行时真相仍由技能系统维护
- 不会因为这个需求去大动当前库存系统主链

### 10. 2026-05-08 追加同步：库存位置变化不等于技能装配变化

这一条必须单独补清楚，因为这里已经出现过一次“为了先跑通测试链，临时桥接逻辑混进正式语义”的风险。

#### 先把错误语义彻底否掉

下面这种语义，在正式方案里是错误的：

- 技能来源物品只要进入某个库存槽位，就自动装配到技能槽
- 技能来源物品只要离开某个库存槽位，就自动从技能槽卸下
- 库存里的槽位位置变化，直接等价于技能系统里的装配变化

这套语义不允许继续作为正式设计存在。

#### 正式语义应该是什么

正式方案里，必须把这两层关系彻底拆开：

##### 第一层：库存关系

它回答的是：

- 这个物品现在在哪个库存里
- 它现在在背包、物品栏、容器、还是别的普通库存槽位
- 它只是一个普通运行时物品实例，当前还没有自动变成“已装配技能”

##### 第二层：技能装配关系

它回答的是：

- 当前哪个技能来源物品，被明确装配到了哪个技能槽
- 当前哪个技能实例，正在作为“已装配技能”参与输入触发、ASC 授予和 UI 观察

这两层关系不能自动绑定。

#### 所以现在正式口径必须固定成下面这样

- 技能来源物品放在背包里，只代表“它在背包里”
- 技能来源物品放在物品栏里，只代表“它在物品栏里”
- 技能来源物品放在任意普通库存位置，都不应该自动装配到技能槽
- 只有当玩家明确把这个来源物品拖到技能槽上，或者显式发起技能装配请求时，才发生技能装配
- 同理，技能卸下也必须是“显式卸下技能槽”或“技能来源真正失效”，而不是普通库存位置变化自动触发

#### 这条规则的直接后果

后续正式代码里，不应该继续保留这种自动桥接思路：

- 某个现成库存组件槽位一变化
- 就立刻把这个变化解释成技能槽装配变化

无论这个现成库存组件叫 `QuickBar`、`BackPack`、`ItemBar`，还是别的名字，
都不能再把“库存位置变化”直接当成“技能装配变化”。

技能装配的正式入口必须收口到：

- 技能槽 `OnDrop`
- 技能系统自己的显式装配请求函数
- 后续如有需要，再补专门的装备/卸下命令接口

截至 2026-05-08，这条正式口径已经进一步明确成：

- 现成库存组件的槽位变化，不再自动驱动技能装配变化
- 之前为了跑通最小测试闭环而临时保留的“库存槽变化 -> 自动装配技能槽”桥接思路，已经不再作为正式设计保留
- 当前技能装配应当收口到显式请求入口，而不是继续绑定在 `QuickBar`、`BackPack` 或任何普通库存容器的槽位变化上

也就是说，从现在开始，正式代码应当满足：

- 技能来源物品放在普通库存里，不自动装配
- 技能来源物品离开普通库存位置，不自动卸下
- 只有技能槽明确收到装配请求时，才发生装配

### 11. 2026-05-08 追加同步：玩家技能输入的正式顺序必须先过状态树

这一条也必须单独写死，因为它和我们前面一版“技能组件先订阅 Hero 输入，再自己判断 SkillSlot”的实现顺序不一致。

#### 之前那版实现为什么不够正式

之前的实现更偏“先把技能槽输入语义跑通”：

- Hero 观察到输入
- 输入直接进入 Hero / ASC 的既有输入链
- SkillComponent 再作为订阅者去识别“这是不是某个技能槽输入”

这套实现对最小闭环测试是够的，
因为它可以快速验证：

- 输入 Tag 是否对上
- 技能槽是否已授予到 ASC
- 按键后技能是否能实际触发

但是这不是最终正式顺序。

#### 正式顺序必须固定成这样

玩家按下技能按键后，正式链路必须是：

1. Hero 先把这次输入当成“技能输入意图”广播出去
2. 角色战斗状态树先接住这次输入
3. 状态树先判断当前状态是否允许释放技能
4. 只有状态树明确放行之后，才去命中当前已装配的技能槽
5. 命中技能槽后，再真正触发技能执行

也就是说，正式方案里：

- 不是先命中技能槽，再看状态树
- 而是先过状态树，再命中技能槽

#### 为什么必须这样

因为技能释放本质上不是一个单纯的“输入映射问题”，而是一个“角色当前战斗状态是否允许执行”的问题。

如果顺序写反，就会导致下面这些正式玩法门禁很难接：

- 硬直中不能放技能
- 翻滚中不能放技能
- 某些攻击前后摇阶段不能立刻插技能
- 技能输入需要先进入预输入/缓存，再由状态树择机释放
- 某些状态下只能允许特定类型技能

这些规则都要求：

- 状态树是前置闸门
- 技能槽命中是状态树放行之后的执行阶段

#### 所以后续正式代码应该往哪个方向收口

Hero 层后续应该继续保持“输入桥接层”的职责，但技能输入正式要拆成两段：

##### 第一段：Intent

- Hero 观察到技能输入
- Hero 广播技能输入意图
- 状态树接住这次意图

##### 第二段：Commit

- 状态树判断允许执行
- 状态树显式调用“执行技能槽输入”
- 技能系统再按当前已装配技能槽去执行真正命中

#### 这一条和 AI 也是一致的

后续如果 AI 也要走技能槽语义，
正式口径同样应该是：

- AI 状态树 / 决策层先决定“现在是否应该发起技能输入”
- 再显式触发技能槽执行

而不是跳过状态树，直接把技能槽输入当成已经被允许执行的最终命令。

当前正式口径是：

- `UAOSkillBarUI::BuildSlotInputDisplayText()` 不再承担“解析真实键位”的职责。
- 这个函数现在只负责“当蓝图没有放真实按键显示控件，或者当前确实解析不到有效键位时，给一个统一兜底文本”。
- 当前统一兜底文本就是 `None`。

也就是说，它现在不是主逻辑，只是兜底逻辑。

之所以这么改，是因为技能槽位不能再把 `1/2/3/4` 当成主显示：

- `1/2/3/4` 已经被物品栏按键占用。
- 技能系统内部保留的是“槽位语义”而不是“物理按键”。
- 真实物理按键应该从 `InputAction` 当前绑定里解析，而不是从槽位序号硬推。

所以当前分层是：

- `BuildSlotInputDisplayText()`：只返回兜底文本 `None`
- `UAOSkillSlotUI::GetSkillSlotInputAction()`：负责把槽位 `InputTag` 解析成真实 `InputAction`
- `UAOSkillSlotUI::GetResolvedInputDisplayText()`：负责拿真正显示结果
- `UAOCommonActionWidget`：负责把当前玩家真实绑定键位显示出来

## 十八、单元测试功能示例：最小技能来源与完整链路快速验证方案

这一节单独写出来，是为了避免后面测试技能系统时一下子把变量铺太多，最后分不清到底是系统没通，还是内容没配完。

当前阶段最推荐的测试思路不是“立刻做完整技能内容”，而是先做一条 **最小完整闭环测试链**。

这条链的目标非常明确：

- 只做 1 个测试技能
- 只做 1 个测试技能来源物品
- 只验证 1 次从来源到输入再到 UI 的完整跑通

也就是说，我们这一步不是在做正式玩法内容，而是在做一条最小的系统级单元测试/集成测试样例。

### 1. 为什么当前最适合用“物品来源”做测试

当前技能系统正式方案里，技能来源已经明确落在：

- 物品定义
- `SkillSource` 碎片
- `SkillDefinition`
- `SkillInstance`
- 技能槽装配链

也就是说，**技能来源的正式入口不是手写一个临时技能实例塞进槽位，而是通过来源物品进入系统。**

所以如果现在要做最快、最稳、最贴近正式设计的测试，最适合的方法就是：

1. 做一个最小测试技能定义
2. 做一个最小测试物品定义
3. 给这个物品挂 `SkillSource` 碎片
4. 把这个测试物品放进技能来源槽
5. 看它能不能自动完成整条技能装配与显示链

这样测的好处是：

- 测的是正式设计，不是临时旁路
- 一次能测到来源解析、实例创建、槽位装配、能力授予、输入触发、UI 显示
- 后面正式做技能内容时，这个测试物品还能继续复用

### 2. 当前最推荐的最小测试闭环目标

当前最推荐的测试目标不是“做 4 个技能都通”，而是：

**先做 1 个测试技能，把下面这 6 层一起跑通。**

1. 技能来源物品是否能被识别为技能来源
2. 技能来源物品是否能正确解析出 `SkillDefinition`
3. `SkillDefinition` 是否能生成对应 `SkillInstance`
4. `SkillInstance` 是否能正确装进技能槽
5. 技能槽输入是否能真正触发技能
6. 技能槽 UI 是否能正确显示名字、图标、键位、冷却

只要这一条通了，说明系统主干已经成立。  
这时候再去补第 2 个、第 3 个、第 4 个技能，成本会低很多。

### 3. 最小测试资产制作单

当前建议你最少准备下面这几份内容：

#### A. 1 个测试技能定义

这个测试技能定义的目标不是做玩法深度，而是做 **系统验证锚点**。

建议它具备下面这些特征：

- 有明确的技能名
- 有明显的图标
- 有一个最简单可见的触发表现
- 最好带一个短冷却，方便顺便测 UI 冷却链

这个测试技能最重要的不是强度和平衡，而是：

**按下键后你能立刻肉眼判断“它到底有没有触发”。**

#### B. 1 个测试技能来源物品定义

这件物品只承担一件事：

**作为技能来源载体。**

最小配置要求就是：

- 它是一个正常物品定义
- 它挂了 `AOFragment_SkillSource`
- 这个碎片里的 `SkillDefinition` 指向上面的测试技能定义

做到这里，这件物品就已经从“普通库存物品”变成了“技能来源对象”。

#### C. 1 个测试装配位置

你现在不需要同时准备很多来源物品，也不需要一次塞满所有技能槽。

最小建议是：

- 先只测试 1 个技能来源槽位
- 先只让 1 个测试物品进去
- 先只观察 1 个技能槽位的最终结果

这样如果中间哪一环断了，你能立刻判断是哪个步骤出了问题，而不会被多槽位、多技能、多表现同时干扰。

### 4. 最小测试执行步骤

建议你按下面这个顺序执行，不要跳步。

#### 第一步：先只做技能来源闭环，不急着看玩法表现

先把测试物品放进技能来源槽，然后只看这几个结果：

1. 技能槽里有没有出现对应技能
2. 技能名和图标有没有出来
3. 技能槽当前键位显示是不是正常

如果这一步没通，说明先查来源解析、槽位装配、输入映射和 UI 观察链，不要急着怀疑技能玩法本体。

#### 第二步：再看输入触发是否成立

如果技能槽已经显示出来，再测试：

1. 按下对应键位能不能触发技能
2. 触发后有没有最基本的技能表现

这一步主要验证的是：

- 输入语义有没有对上
- 槽位授予给 ASC 的能力有没有真正生效
- Hero -> SkillComponent -> ASC 这条输入链有没有通

#### 第三步：最后顺便测冷却和 UI 同步

如果技能已经能触发，再顺手看：

1. 技能进入冷却时，技能槽 UI 有没有变化
2. 冷却结束后，UI 有没有恢复

这一步能顺便帮你确认：

- `SkillInstance / 冷却身份标签 / ASC Active GameplayEffect` 这条冷却真值链是不是通的
- HUD ViewModel 和技能槽 UI 的实时观察链是不是通的

### 5. 这个单元测试样例真正想验证什么

这套最小测试不是为了证明“玩法内容已经完成”，而是为了证明下面这条完整系统链已经成立：

`测试物品 -> SkillSource碎片 -> SkillDefinition -> SkillInstance -> 技能槽装配 -> ASC授予 -> 输入触发 -> UI显示 -> 冷却观察`

只要这条链成立，你后面新增技能内容时，更多是在“填内容”，而不是“继续怀疑系统骨架是不是还没搭好”。

### 6. 当前阶段不推荐的测试方式

为了避免后面走弯路，这里也把当前不推荐的测试方式写清楚。

当前不推荐你优先这样测：

- 直接手动在代码里临时 new 一个技能实例塞进槽位
- 直接跳过来源物品层，只测技能槽显示
- 一上来同时做 4 个测试技能
- 一上来同时测技能来源、技能表现、复杂 UI 动画、改键、冷却特效

这些方法不是永远不能做，而是 **不适合作为当前阶段的第一轮系统验证方式**。

因为它们会把：

- 来源问题
- 装配问题
- 输入问题
- UI 问题
- 内容问题

全部混在一起。

一旦出错，你就很难快速定位到底是哪一层没通。

### 7. 当前最推荐的测试完成标准

当前这一轮“单元测试功能示例”最推荐的通过标准是：

1. 测试物品进入技能来源槽后，技能槽能正确出现
2. 技能名、图标、键位文字都正常显示
3. 按下对应键后，技能能确实触发
4. 触发后如果有冷却，技能槽冷却 UI 能同步变化
5. 移除测试物品后，技能槽能回到空槽状态

只要这 5 条同时成立，就可以认为：

**当前技能系统的来源链、装配链、输入链、UI观察链，已经具备继续做正式技能内容的基础。**

### 8. 真正可执行的最小制作单：你现在一步一步该怎么做

上面讲的是测试目标和原则。  
这一节开始不再讲抽象思路，而是直接写成“施工步骤”。

在正式开始前，你必须先把下面这两种东西在脑子里完全分开：

#### 先分清楚：这里其实有两种完全不同的 Definition

##### 第一种：技能定义资产

例如：

- `DA_TestSkill_Fireball`

它回答的是：

- 这是什么技能
- 它叫什么
- 图标是什么
- 对应哪个 `AbilityClass`

##### 第二种：技能来源物品定义

例如：

- `BP_TestSkillSourceItem_Definition`

它回答的是：

- 这是什么物品
- 这个物品会不会提供技能
- 如果会，它提供的是哪个技能定义类

##### 你要记住的最重要一句话

**技能定义资产不是来源物品定义。**  
**来源物品定义也不是技能本体。**

它们的关系是：

- 技能定义资产负责描述技能本身
- 来源物品定义负责声明“我这个物品会提供哪个技能”

所以后面你会看到两个 Definition，是正常的，不是重复设计。

##### 一眼看懂版

如果你嫌上面术语多，就先只记下面这 4 句：

1. `DA_TestSkill_Fireball` 是技能本体定义。
2. `BP_TestSkillSourceItem_Definition` 是物品定义。
3. 这个物品定义通过 `AOFragment_SkillSource` 声明“我会提供 `DA_TestSkill_Fireball`”。
4. 运行时玩家拿到的是这个物品实例，然后技能系统再从它身上解析出技能。

你现在如果要做最小测试样例，建议就按下面这个顺序做，不要跳。

#### 第一步：先准备一个测试技能定义资产

你要新建 1 个 `UAOSkillDefinition` 资产。

这里当前正式就是技能 `DataAsset` 路线，不要和来源物品定义混在一起。

##### 如果你在编辑器里具体操作，建议这样做

1. 打开 `Content Browser`
2. 进入 `Content/Games/Skill/Test/`
3. 右键空白处
4. 选择 `Miscellaneous`
5. 选择 `Data Asset`
6. 选择 `UAOSkillDefinition`
7. 命名成 `DA_TestSkill_Fireball` 这种形式

这里最需要注意的是：

- 这里做的是技能定义资产
- 不是来源物品定义
- 也不是运行时技能实例

建议新建位置：

- `Content/Games/Skill/Test/`

建议命名：

- `DA_TestSkill_Fireball`
- 或者 `DA_TestSkill_Unit01`

你在这个资产里，当前最少要填下面这些字段：

##### 必填字段

- `SkillName`
  - 先填一个非常直白的名字，比如“测试火球”或“测试技能01”
- `SkillDescription`
  - 直接写清楚测试目的，比如“用于技能系统最小闭环测试”
- `AbilityClass`
  - 这里必须指向一个真的能被触发的 `GameplayAbility`

##### 强烈建议填

- `SkillIcon`
  - 不填也能测，但 UI 视觉确认会慢很多
- `CooldownDuration`
  - 建议先填一个很短的值，比如 `3.0`
  - 这样你可以顺便验证冷却链和 UI 冷却显示

##### 当前可以先不纠结

- `SkillTags`
- `SkillFamilyTag`
- `SkillGroupTag`
- `CooldownTags`

这些不是说没用，而是这轮“最小测试”不需要先把它们做复杂。

##### 这一步做完后，你要确认什么

这一步做完后，你要确认的不是“技能好不好玩”，而是：

- 这个 `SkillDefinition` 资产能稳定存在
- 它有名字
- 它有图标
- 它真的指向一个可触发的 `AbilityClass`

如果 `AbilityClass` 本身还没法触发，那后面所有测试都会被它拖住。

#### 第二步：给这个测试技能找一个最简单可见的 Ability

这一步是最容易偷懒但最不能糊弄的地方。

你现在不要选那种逻辑很重、依赖很多外部状态的技能。  
你应该选一个最容易肉眼确认“是否触发”的能力。

当前推荐标准是：

- 按下键后立刻能看出来
- 不依赖复杂目标选择
- 不依赖复杂动画窗口
- 不依赖复杂武器状态

如果你当前项目里已经有一个非常轻量的 GA 能满足这个条件，就直接复用。  
如果没有，建议你后面单独做一个最简测试用 GA。

这一步最重要的注意点是：

**测试技能的 Ability 不要太“正式”，要太“明确”。**

也就是说，这里优先追求：

- 一按就知道是否触发

而不是：

- 做得像正式技能内容

#### 第三步：新建一个测试技能来源物品定义

你现在要新建 1 个物品定义，用来充当“技能来源对象”。

这一层一定不要理解成“第二个技能定义”。  
它不是技能本体，它只是一个 **会提供技能的物品定义**。

建议新建位置：

- `Content/Games/Items/SkillTest/`

建议命名：

- `BP_TestSkillSourceItem_Definition`
- 或者 `BP_TestFireballSourceItem_Definition`

从你们现有物品风格看，建议你直接参考武器定义那套命名方式来做，这样项目里更统一。

这个物品定义最少要具备下面这些内容：

##### 必须有的碎片

- `AOFragment_SkillSource`
  - 这是最核心的
  - 它里面的 `SkillDefinition` 必须指向你刚才做的那个测试技能定义资产

##### 这一步的真实语义到底是什么

你现在做的不是：

- “再做一个技能”

而是在做：

- “做一个物品，并声明这个物品会提供前面那个技能”

所以这一层的真实链路是：

- `BP_TestSkillSourceItem_Definition`
  - 挂 `AOFragment_SkillSource`
  - `SkillDefinition = DA_TestSkill_Fireball`

它表达的完整意思就是：

- “这个物品会提供这个技能”

##### 强烈建议一起加的碎片

- `AOFragment_InventoryIcon`
  - 给这个测试技能来源物品一个图标
  - 这样你放进背包或来源槽时更容易确认自己放对了
- `AOFragment_SetStats`
  - 建议把 `CanStack` 关掉
  - 让它就是一个单独的测试物品，不要叠堆

##### 物品定义自身建议填

- `DisplayName`
  - 建议直接写“测试技能来源-火球”或“测试技能来源01”

##### 这一步最需要注意什么

最需要注意的是：

**这个物品不是“技能本体”，它只是技能来源载体。**

所以你现在做这个测试物品时，不要把思路搞成：

- “我要做一个技能按钮”

而是要理解成：

- “我要做一个普通物品，但它额外挂了一层技能来源语义”

这和你们当前正式方案是完全一致的。

#### 第四步：确保这个测试物品能真的生成成物品实例

这一步很重要，因为技能系统接的不是静态物品定义类本身，而是运行时物品实例。

也就是说，你后面真正进入技能系统的是：

- `UAOInventoryItemInstance`

它里面会带着：

- `ItemDef`
- `ItemCDO`

然后技能系统才会从 `ItemCDO` 上找 `AOFragment_SkillSource`，再从里面拿到 `SkillDefinition`，最后生成对应 `SkillInstance`。

所以你现在要确认：

- 这个测试物品定义能被你们现有库存/来源槽流程正常生成成物品实例

如果这一步都没通，那后面技能系统根本拿不到来源对象。

#### 第五步：把测试物品放进技能来源槽，不要先管 4 个槽位

现在你先不要想着一次测满。

建议你只做下面这件事：

- 把这个测试技能来源物品放进 **1 个** 技能来源槽位

此时你先只观察 3 件事：

1. 技能槽里有没有出现技能
2. 技能名和图标有没有出来
3. 技能键位文字有没有出来

##### 如果这一步失败，优先排什么

如果这一步失败，优先怀疑下面这些：

1. 测试物品实例有没有真的进入来源槽
2. 这个物品定义上有没有真的挂 `AOFragment_SkillSource`
3. `AOFragment_SkillSource` 里的 `SkillDefinition` 有没有指向对
4. 这个 `SkillDefinition` 资产里有没有真的设置 `AbilityClass`
5. 输入映射链和技能槽 UI 观察链有没有正常工作

这一步先不要急着看技能玩法表现，因为你连“来源 -> 槽位显示”都还没完全确认。

#### 第六步：再测输入触发，不要把玩法复杂度拉高

当你已经看到技能槽里出现了这个测试技能之后，再开始按键测试。

你现在要测试的是：

1. 按下对应键位后，技能有没有真的触发
2. 触发后有没有最基本可见表现

这里的“可见表现”只要求你能立刻判断触发了，不要求正式品质。

##### 这一步最需要注意什么

不要一边测输入触发，一边又同时去调复杂表现。

因为当前这一步的测试目标是：

- 输入语义对没对上
- 技能有没有真正授予给 ASC
- 触发链有没有通

不是要同时验证“这个技能做得帅不帅”。

#### 第七步：最后顺手测冷却，不要先做复杂冷却表现

如果你的测试技能定义里填了一个短冷却，比如 3 秒，那现在顺手再看：

1. 技能触发后槽位是否进入冷却
2. 冷却结束后是否恢复

这一步你当前只需要验证“有/没有、对/不对”，不需要先做复杂冷却特效。

也就是说，此时你只要确认：

- 真值在动
- UI 在跟

就够了。

#### 第八步：最后做一个移除测试

很多人测到“能装进去、能触发”就停了，但你们这套系统里还有一个非常重要的收尾验证：

- 把这个测试来源物品从来源槽移除

然后看：

1. 技能槽是否恢复为空
2. UI 是否正确清空
3. 后续按键是否不再触发这个技能

这一条一定要测，因为它能帮你确认：

- 来源解绑链有没有通
- 槽位卸载链有没有通
- 授予回收链有没有通

#### 第九步：当前这一轮测试，哪些东西先不要做

为了让这轮测试保持“最小闭环”，你现在先不要同时做这些：

- 同时做 4 个测试技能
- 同时测 4 个来源物品
- 同时调复杂技能表现
- 同时测完整改键菜单
- 同时做复杂拖拽换槽交互
- 同时做复杂冷却动画

因为这些会把问题源头搅在一起。

你现在这一轮只需要回答一个问题：

**“这套技能来源 -> 技能实例 -> 槽位装配 -> 输入触发 -> UI观察的正式链路，到底通没通？”**

#### 第十步：这一轮测试通过后，你就可以放心进下一步

当你完成下面这 5 条，就可以认为当前这轮测试通过：

1. 测试物品进入来源槽后，技能槽出现对应技能
2. 技能名、图标、键位文字都显示正常
3. 按下对应键后，技能能确实触发
4. 技能冷却与 UI 同步正常
5. 测试物品移除后，技能槽和触发一起恢复为空状态

到这个阶段，你后面继续做正式技能内容，就基本不再是“怀疑系统骨架没搭好”，而是正式进入内容填充阶段了。

## 十九、2026-05-09 追加同步：技能槽库存适配层正式落地说明

这一节是对前面相关描述的正式补充。

凡是和下面三件事直接冲突的旧描述，以本节为准：

- 技能槽拖拽装配到底走哪条链
- 技能槽自己的真实容器身份到底是什么
- 技能来源物品进入普通库存后是否应该自动装配

### 1. 这次改动到底解决了什么问题

这次改动不是单纯“补一个 OnDrop 判断”。

这次真正解决的是两个旧问题：

- 技能物品以前可能还在普通库存里，但技能已经先被装上，形成“物品位置”和“技能运行时状态”不一致
- 技能槽如果不作为正式库存容器参与交换，就会越来越多地在 UI 层补特判，后面维护会越来越乱

这次改完之后，正式规则变成：

- 技能是否装上，不再由 UI 直接告诉 `SkillComponent`
- 技能来源物品必须先真实进入“技能槽容器”
- 只有当技能槽容器里的最终结果发生变化后，`SkillComponent` 才根据这份结果同步正式技能运行时状态

换句话说：

- 以前更像“先装技能，再想办法解释 UI”
- 现在是“先完成真实容器交换，再由技能系统解释这次交换的技能语义”

### 2. 现在的正式结构是什么

当前正式结构是：

- `SkillDefinition(DataAsset)`
  - 负责“这是什么技能”
- `SourceItemDefinition(物品定义)`
  - 负责“这个物品会提供哪个技能”
- `SourceItemInstance`
  - 负责运行时来源锚点
- `SkillInstance`
  - 负责运行时技能状态
- `UAOSkillComponent`
  - 负责技能运行时真相
- `UAOSkillSlotInventoryComponent`
  - 负责让技能槽以“库存容器”的身份进入现有拖拽/交换系统

最重要的一句话是：

**`UAOSkillSlotInventoryComponent` 不是新的技能真相层。**

它只是一个“库存语义外壳”。

真正的技能真相仍然只在：

- `UAOSkillComponent`
- `UAOSkillInstance`
- `ASC`

### 3. 现在技能槽的正式工作方式

现在技能槽的正式工作方式是：

1. 玩家从背包、物品栏、箱子或其他库存拖出一个物品
2. 技能槽 UI 先拿到 `SourceContainer + SourceSlotIndex`
3. 技能槽 UI 先做一次本地预检查
4. 正式交换时走统一库存交换入口
5. 服务端再次做双边校验
6. 如果这次交换真的让某个技能来源物品进入了技能槽容器
7. `UAOSkillSlotInventoryComponent` 才把整份槽位结果同步给 `UAOSkillComponent`
8. `UAOSkillComponent` 再决定：
   - 哪个槽现在装了哪个技能
   - 是否要创建或复用 `SkillInstance`
   - 是否要授予 / 回收 Ability
   - UI 观察数据该怎么刷新

这里最关键的正式变化是：

- 技能来源物品进入背包，不会自动装到技能槽
- 技能来源物品离开背包，也不会自动卸下技能槽
- 只有它真实进入技能槽容器，才算正式装配
- 只有它真实离开技能槽容器，才算正式卸下

### 4. 这次复用了什么，没复用什么

这次明确复用的是旧系统的基础能力：

- 现有库存交换主链
- 现有库存容器 / 槽位语义
- 现有拖拽时的 `SourceContainer + SourceSlotIndex` 输入方式
- 现有服务端执行交换的权威链
- 现有 `SkillComponent -> HUD ViewModel -> Skill UI` 观察链

这次明确没有复用旧系统的错误语义：

- 没有把 `SkillComponent` 继续当成技能槽 UI 的容器身份
- 没有继续走“UI 直接请求 SkillComponent 装配”的旧旁路

- 没有把技能运行时真相搬进 `UAOInventoryComponent::InventoryList`

所以这次不是“用库存系统替代技能系统”。

而是：

**用库存系统处理真实交换语义，用技能系统处理真实技能语义。**

### 6. 每个关键文件各自负责什么

#### `AOInventoryComponent`

现在新增了一层“按目标槽位做准入校验”的统一接口。

它回答的问题是：

- “如果某个物品交换后要进入我的这个槽位，我允不允许？”

普通背包、箱子、快捷栏可以继续用默认逻辑。

技能槽适配层则重写这一层，把“非技能来源物品禁止进入技能槽”的规则收在正式库存链里。

#### `AOSkillSlotInventoryComponent`

这是这次方案 B 的核心新增组件。

它负责三件事：

- 让技能槽真的成为一个库存容器
- 在交换前判断目标槽是否允许接收这个物品

它不负责：

- 技能冷却
- 技能触发
- 技能 Ability 授予逻辑本身
- 技能实例长期真相存储

#### `AOSkillComponent`

它现在新增了一个重要正式入口：

- `SyncSkillSlotsFromInventoryProjection`

这个函数的职责是：

- 接收“技能槽容器当前真实摆着什么”
- 把这份结果翻译成技能运行时状态
- 处理同一技能来源在技能槽之间移动 / 交换
- 最终刷新 Ability 授予结果和 UI 观察结果

这里要特别记住：

现在技能槽之间互换时，已经不是“看见一个旧槽空了就立刻销毁旧技能实例”的思路。

而是：

- 先看整份最终结果
- 再统一调整运行时状态

这样才能避免 A 槽和 B 槽交换时出现中间态误判。

#### `AOSkillBarUI / AOSkillSlotUI`

现在 UI 的正式职责更清楚了：

- `SkillBarUI`
  - 负责构建整条技能条
  - 负责把正式 `SourceContainer` 注入给每个技能槽
- `SkillSlotUI`

这里最重要的变化是：

- 技能槽 UI 不再把 `SkillComponent` 当容器身份
- 技能槽 UI 不再把“装配技能”直接写回 `SkillComponent`

### 1. 用一句人话说清楚这次改动

现在的技能槽，不再是“UI 看着像 4 个格子，但底层其实不是正式容器”的状态。

现在它已经被整理成：

- **技能槽先是一个真正参与库存交换的容器**
- **技能再根据这个容器里的最终结果，去同步自己的运行时状态**

所以现在的顺序是：

1. 先交换容器里的物品
2. 再同步技能系统

你可以把现在这套东西理解成两层：

- **库存语义层**

它们分别对应：

- `UAOSkillSlotInventoryComponent`
  - 这是技能槽的“库存外壳”
- `UAOSkillComponent`

最关键的边界就是：

- `UAOSkillSlotInventoryComponent` 不是第二个技能系统

## 二十一、2026-05-09 追加同步：三项运行期 BUG 修复说明

这一节对应本轮已经落地并编译通过的三项 BUG 修复：

- 技能键位显示有时正确、有时显示 `None`
- 技能只能放到第一个技能槽
- 单次触发技能按住后会持续重复激活

### 1. 键位显示为什么会时好时坏

这次排查后确认，根因不是单纯“异步加载”四个字，而是两件事叠在一起：

1. 技能条之前没有直接监听本地输入映射真正重建完成的时机
2. 技能槽取 `MappingName` 时，之前更偏向从 `InputAction` 自身取，而项目实际很多时候是把 `Player Mappable` 配在 `IMC` 映射项上

所以就会出现一种现象：

- HUD 刚创建那一刻，输入映射还没真正重建完，技能槽读不到真实键位，于是显示 `None`
- 后来当你打开背包或别的界面时，某条 UI 刷新链又顺手触发了一次技能条刷新，这时映射已经准备好了，于是又突然显示正常

现在改完后的正式处理是：

- `UAOSkillBarUI` 直接监听 `UEnhancedInputLocalPlayerSubsystem::ControlMappingsRebuiltDelegate`
- 每次本地输入映射真正重建完成后，技能条自己重建一次
- `UAOSkillSlotUI` 解析映射名时，优先从当前真实 Player Mappable 映射结果里找，而不是只赌 `InputAction` 自身一定带设置

这意味着现在键位显示不再依赖“打开别的界面时碰巧刷新到”。

### 2. 为什么之前只能放到第一个技能槽

这次排查后确认，问题不是库存交换链本身坏了，而是技能槽 UI 这一层和你现有库存槽蓝图的约定没有完全对齐。

更直白地说就是：

- 你现有很多库存拖拽蓝图习惯直接读一个统一的 `Index`
- 但技能槽之前主要靠 `SkillSlotViewData.SlotIndex` 和 `TrueIndex`
- 如果蓝图还沿用老习惯去读 `Index`，技能槽这边没有把同语义字段稳定喂进去，就很容易退化成永远命中第一个槽

现在改完后的正式处理是：

- `UAOSkillSlotUI` 新增并正式维护 `Index`
- `UAOSkillBarUI` 在重建每个技能槽时，把真实槽位索引直接写进 `SetIndex(SlotViewData.SlotIndex)`
- `UAOSkillSlotUI::SetSkillSlotData` 里也会同步一次 `Index = SkillSlotViewData.SlotIndex`

这样做的目的不是新造一套索引体系，而是让技能槽和你现有库存槽蓝图约定完全对齐。

### 3. 为什么按一下技能会一直打印 Hello

这次排查后确认，根因在 `UAOAbilitySystem` 的输入收集策略。

之前的行为是：

- `Triggered` 事件在按键按住期间可能每帧都会来一次
- `AbilityInputTagPressed` 每次收到都会往 `InputPressedSpecHandles` 里再塞一次
- 对于 `OnInputTriggered` 这种“按下一次就该触发一次”的技能，就会在整段按住期间持续反复激活

所以你看到的现象才会是：

- 按下后一直打印 `Hello`
- 松开之前不会停

现在改完后的正式处理是：

- `AbilityInputTagPressed` 先看这个 `AbilityHandle` 当前是不是已经处于 `Held`
- 只有从“未按住”进入“按住”的第一帧，才会记一次 `InputPressed`
- 后续同一次长按里再来的 `Triggered` 不会继续重复排队激活

这就把“单次触发技能”和“按住持续生效技能”的输入语义重新分开了。
