# 技能系统设计方案：技能执行语义与隐式分类框架
更新日期：2026-05-09

这份文档不是重讲整套技能系统。

它只解决一个专门问题：

- 当我们进入第七阶段以后，所谓“技能类型”到底该怎么设计。
- 这个“类型”是否需要做成显式的 `SkillType` / `ESkillType` 变量。
- 如果不做显式类型枚举，那么程序到底靠什么去区分火球、落雷、跳链、护盾、Boss 清场技这些技能。

这份文档的结论先写在最前面：

- **程序层不应该依赖一个总的、显式的“技能类型枚举”来驱动整个技能系统。**
- **技能之间的差异，本质上不是“它属于哪个大类”，而是“它在执行时采用了哪几段语义”。**
- **所以后续要设计的，不是 `SkillType = Projectile / AOE / Chain` 这种大分类变量，而是一套可组合的执行语义框架。**

也就是说，程序不需要先回答“这是什么类技能”，程序真正需要回答的是：

- 这个技能怎么拿目标。
- 这个技能从哪里发出。
- 这个技能如何把效果送到目标上。
- 这个技能怎么收集命中对象。
- 这个技能如何结算。
- 这个技能是否要分阶段、持续、蓄力、跳链或脚本化执行。

---

## 一、为什么不做显式 `SkillType`

如果后续加一个：

- `ESkillType::Projectile`
- `ESkillType::GroundAOE`
- `ESkillType::Chain`
- `ESkillType::Channel`
- `ESkillType::BossSpecial`

表面上看很清楚，但实际会很快失控。

原因不是“枚举不能用”，而是它对这套系统来说，**信息密度太低，语义又太粗**。

因为一个真实技能往往不是单一类别，而是多个执行语义叠加出来的结果。

例如：

- 一个火球技能，可能是“朝向释放 + 投射物飞行 + 单体碰撞 + 爆炸范围结算”。
- 一个落雷技能，可能是“目标点选择 + 延迟生效 + 区域采样 + 范围结算”。
- 一个连锁闪电技能，可能是“先锁主目标 + 命中后跳链 + 每跳重新选目标 + 多段结算”。
- 一个 Boss 清场技，可能是“脚本启动 + 多阶段执行 + 若干次地面选点 + 若干次范围伤害 + 最后挂持续区”。

如果这些东西都靠一个 `SkillType` 去表达，就会立刻遇到下面这些问题：

### 1. 一个技能会同时像多个类型

它既像投射物，又像范围技；
既像持续技，又像引导技；
既像 Boss 技，又像地面区域技。

这时候：

- 你要么强行给它归到某一类；
- 要么开始做“主类型 + 子类型 + 二级标志 + 例外逻辑”；
- 最后重新发明一套更难维护的语义系统。

### 2. 系统层会被迫认识越来越多的“技能种类”

一旦 `SkillType` 被当成系统分发入口，后面就很容易出现这种代码：

- `if SkillType == Projectile`
- `if SkillType == GroundAOE`
- `if SkillType == Chain`
- `if SkillType == BossSpecial`

这样一来，复杂度就会从具体技能的 `Ability` 内部，反灌回：

- `SkillDefinition`
- `SkillComponent`
- 状态树任务
- AI 触发桥
- UI 展示逻辑

这和我们前六阶段已经立住的边界是冲突的。

### 3. 显式类型变量往往只对“人”有用，对“程序”没那么有用

我们平时说“火球是投射物技能”“雷链是跳链技能”，这是方便人沟通。

但程序真正执行时，并不会因为“它叫投射物类技能”就自然知道：

- 发射点在哪
- 目标怎么取
- 是否追踪
- 命中后要不要爆炸
- 爆炸后要不要继续跳链
- 是否要持续存在

也就是说：

**“像什么”是人类认知分类。**
**“怎么执行”才是程序真正需要的分类。**

## 二、我们真正需要的不是“技能类型”，而是“执行语义”

到了第七阶段以后，系统关心的核心不再是：

- 技能怎么装槽
- 技能怎么授予到 ASC
- 技能怎么从输入被触发

这些事情前六阶段已经有骨架了。

第七阶段真正新增的是：

- 技能一旦被激活，后续执行链怎么展开。

所以后续这套“分类”应该围绕执行链展开，而不是围绕一个总枚举展开。

我建议把技能执行拆成下面这几个语义问题。

### 1. 触发后先拿什么上下文

技能激活以后，第一件事不是判断“我是哪个类型”，而是先拿上下文：

- 施法者是谁
- 当前 `SkillInstance` 是谁
- 当前 `SkillDefinition` 是谁
- 是玩家触发还是 AI 触发
- 当前输入是 Press / Release / Started 的哪一种
- 当前是否已经有锁定目标、准星目标、AI 战斗目标或脚本目标

这里的语义，当前代码骨架已经能承接：

- `UAOSkillComponent` 负责把槽位技能触发到真正授予的 `AbilitySpec`
- `UAOSkillGameplayAbility` 能从 `SourceObject` 反查 `SkillInstance`
- `UAOSkillGameplayAbility` 也能继续反查 `SkillDefinition`

所以第七阶段不需要再回去发明新的“技能类型分发层”，而是应该让 `Ability` 在自己内部根据上下文推进执行。

### 2. 目标获取语义

程序需要先回答：

- 这个技能是否需要目标
- 这个目标是“自己”还是“别人”
- 是单目标、范围中心点，还是一串链式目标

这不是技能类型，而是目标获取语义。

常见语义有：

- 自身
- 当前锁定目标
- 当前准星命中对象
- 当前朝向前方
- 当前地面点
- AI 当前战斗目标
- AI 查询到的最优点位
- 脚本直接指定目标
- 无目标也可释放

注意，这一层只回答“目标从哪来”，不回答“效果怎么送过去”。

### 3. 原点/发射点语义

程序还需要知道：

- 效果是从角色脚下发出
- 从武器插槽发出
- 从手部 Socket 发出
- 直接以目标点为原点生成
- 从上空生成
- 围绕自身生成一个区域

这也不是技能类型，而是空间原点语义。

一个“火球技能”和一个“雷枪技能”在人类看来都像投射物，
但一个可能从手部发射，一个可能从武器尖端发射。

程序真正关心的是原点，而不是“它大类上也算投射物”。

### 4. 投递语义

拿到目标和原点以后，接下来程序需要决定：

- 效果如何被送到目标身上

这一层我叫“投递语义”。

常见投递语义包括：

- 立即生效
- 近战命中盒/命中扇区
- 直线投射物
- 追踪投射物
- 地面区域生成
- 延迟落点生效
- 持续区域存在
- 命中后继续弹射
- 召唤一个中间执行体

到了这里，程序仍然不需要一个总的 `SkillType`。

因为所谓“投射物技能”，本质上只是“投递语义 = 投射物”。

所谓“范围技能”，本质上只是“投递语义 = 地面区域或范围采样”。

所谓“跳链技能”，本质上只是“投递语义/后续传播语义 = 命中后继续跳链”。

### 5. 命中采集语义

效果送出以后，还需要知道：

- 命中对象怎么收集

例如：

- 单体命中
- 首个命中
- 穿透多个目标
- 半径内全部敌人
- 扇形内全部敌人
- 每次跳链重新筛选最近目标
- 持续区域每秒重新扫描一次

这层语义的意义是把“命中对象收集”从“效果投递”里拆开。

因为有些技能虽然都是区域型，
但一个是命中一次后结束，
一个是持续区域每跳扫描，
一个是先单体命中再爆炸扩散。

它们不是一个枚举能清楚表达的。

### 6. 结算语义

最后程序还要决定：

- 命中后到底结算什么

例如：

- 造成一次伤害
- 施加持续伤害
- 施加治疗
- 施加控制
- 上 Buff
- 上 Debuff
- 触发二段效果
- 命中后生成后续执行节点

这里真正落地的依然应该在具体 `Ability` 或它驱动的执行对象里，而不是在 `SkillComponent` 里写通用大分支。

### 7. 生命周期语义

除了“怎么打出去”，还要描述“这个技能活多久、分几段”。

常见生命周期语义包括：

- 瞬发
- 持续施法
- 长按维持
- 蓄力后释放
- 固定阶段序列
- 可中断多段技能
- 持续存在物
- Boss 脚本阶段技能

这就是为什么我不建议单独做一个 `SkillType = Channel / Boss / AOE`。

因为这些很多时候不是“类型”，而是生命周期结构。

### 8. 动画执行语义

这一层是当前技能方案里必须正式补上的一层，
而且它不是“表现细节”，而是**技能执行主链的一部分**。

程序后续不能只回答：

- 技能往哪里打
- 技能怎么收集命中
- 技能怎么结算

还必须回答：

- 技能激活以后，动画是否参与执行
- 动画在什么时候驱动真正的逻辑节点发生
- 一个技能的前摇、执行点、后摇分别由谁控制
- 动画时序和技能逻辑时序如何对齐

如果这一层不写清楚，
程序就会很自然地退化成：

- 用一个 `Delay`
- 猜一个秒数
- 时间到了再触发技能真正逻辑

这种写法也许能暂时跑通，
但它不是正式技能框架。

#### 8.1 为什么动画不是“纯表现”

在技能系统里，动画至少有四种职责：

##### 1. 表现载体

这是最表层职责：

- 播放抬手
- 播放挥击
- 播放蓄力
- 播放拍地
- 播放收招

这一层只是“玩家看到什么动作”。

##### 2. 时序驱动器

这是最关键的职责。

很多技能不是“Ability 一激活就立刻进入真正逻辑”，
而是：

- Ability 先进入技能流程
- 播放动画
- 动画在某个时点发出事件
- 技能逻辑在这个时点正式进入执行

例如：

- 火球术：角色抬手到某一帧，才真正发射火球
- 火山喷发：角色拍地到某一帧，才真正开始第一波喷发

所以动画不是“附属演出”，
而是技能执行链上的正式时序驱动器。

##### 3. 阶段切分器

动画还负责把一个技能切成多个阶段：

- 前摇
- 执行
- 后摇

程序不应该长期依赖固定秒数去猜这三个阶段。

更合理的方式是：

- 技能阶段边界尽量和动画事件或动画窗口对齐

##### 4. 状态约束来源

技能在动画过程里通常还会带来：

- 是否允许移动
- 是否允许转向
- 是否允许取消
- 是否允许再次接输入
- 什么时候恢复自由状态

这些约束很多也应该由动画窗口或动画事件参与驱动，
而不是完全脱离动画另起一套猜秒数逻辑。

#### 8.2 但动画不能决定什么

动画虽然参与技能执行，
但它也有明确边界。

动画**不应该决定**：

- 最终命中了谁
- 最终伤害范围多大
- 最终结算什么效果
- FX 大小是不是等于程序逻辑范围

正式口径必须固定成：

- 动画负责“什么时候进入某个技能逻辑阶段”
- `ExecutionDefinition` 负责“这个阶段执行什么空间/命中/结算逻辑”

也就是说：

- **动画是时序真相的一部分**
- **不是命中判定真相本身**

#### 8.3 为什么这层不能塞回 `ExecutionDefinition`

动画参与是一个跨技能执行结构的正交维度。

例如：

- 射弹技能需要动画
- 区域序列技能需要动画
- 持续引导技能需要动画
- 召唤技能也可能需要动画

但它们的空间执行结构完全不同。

所以不能把动画写成：

- “只有射弹执行定义才有动画语义”
- “只有区域执行定义才有动画语义”

这样会把两个维度重新搅在一起。

更合理的理解是：

- `ExecutionDefinition` 负责空间与命中执行结构
- 动画执行语义负责时间与阶段驱动结构

这两者共同描述一个完整技能。

#### 8.4 当前项目中动画执行语义的正式驱动方式

结合当前项目已有基础能力，
正式驱动方式应优先建立在：

- 动画蒙太奇
- `AnimNotify`
- `AnimNotifyState`
- 必要时配合 `GameplayEvent`

也就是说，后续技能框架中：

- Ability 激活后可以先播蒙太奇
- Ability 可以等待动画事件
- 动画事件到达后，Ability 再进入真正执行节点

而不是优先建立在：

- `Delay`
- 固定秒数
- “大概播到这里了”的人工猜测

#### 8.5 什么场景可以使用时间参数，什么场景不可以

这点必须写死，不然后面还会反复回到同一个坑。

##### 可以使用时间参数的场景

时间参数可以用于：

- 一个阶段内部的固定波次节奏
- 一个持续区每次 Tick 的扫描间隔
- 没有动画参与时的纯逻辑技能测试版本
- 调试用 fallback

例如：

- `WaveInterval`
- 持续伤害 Tick 间隔
- 纯程序测试技能的生命周期时间

##### 不应使用时间参数充当主方案的场景

下面这些事情，不应再默认靠 `Delay` 主驱动：

- 技能真正开始执行的时机
- 第一发射弹真正发射的时机
- 第一波喷发真正开始的时机
- 从前摇切到执行阶段的时机

这些时机应优先由动画事件驱动。

#### 8.6 火球术和火山喷发在动画语义上的正式口径

##### 火球术

火球术的正式执行顺序应理解为：

1. Ability 激活
2. 播放施法动画
3. 动画事件到达“发射点”
4. 在这一时点生成火球射弹
5. 射弹后续飞行、碰撞、爆炸继续走射弹执行结构

所以火球术里：

- 动画负责决定“什么时候发射”
- 射弹执行定义负责决定“发射后怎么飞、怎么撞、怎么收集命中”

##### 火山喷发

火山喷发的正式执行顺序应理解为：

1. Ability 激活
2. 播放拍地或施法动画
3. 动画事件到达“喷发开始点”
4. 在这一时点正式进入喷发阶段
5. 喷发阶段内部再按 `WaveInterval` 推进每一波
6. 每一波继续走区域序列执行结构

所以火山喷发里：

- 动画负责决定“什么时候开始喷发”
- `WaveInterval` 只负责“喷发开始以后，波次之间的内部节奏”

这两个职责不能再混用。

#### 8.7 当前方案的正式结论

后续技能系统中，动画必须被视为技能执行的一层正式语义，而不是纯表现附属层。

正式口径固定为：

1. 技能执行至少由“空间执行结构”“动画时序结构”“网络表现同步结构”三部分共同描述。
2. `ExecutionDefinition` 负责空间、目标、命中、结算与阶段内部逻辑结构。
3. 动画负责前摇、执行点、后摇以及阶段切换时机。
4. 真正关键执行点应优先由 `AnimNotify / AnimNotifyState / GameplayEvent` 驱动。
5. `Delay` 或纯时间参数只能作为辅助节奏参数或调试 fallback，不应长期承担正式技能起爆时机。
6. 联机下真实执行应坚持服务端权威；客户端主要负责预测输入体验与接收表现同步。
7. 技能运行时对象不负责自己发明一套随手的网络表现真相；正式表现同步优先走 `GameplayCue`，而不是把多播散落在具体技能里。

## 三、隐式分类到底怎么成立

既然我们不做显式 `SkillType`，
那程序到底如何“区分技能”？

答案是：

**程序不是先通过一个总类型去区分技能，而是通过一组执行语义的实际组合结果，隐式地区分技能。**

例如：

### 1. 火球

它之所以被我们称为“投射物技能”，不是因为某个地方写了：

- `SkillType = Projectile`

而是因为它的执行语义组合大致是：

- 目标获取：朝向前方或锁定目标
- 原点：手部 / 武器 Socket
- 投递：直线或追踪投射物
- 命中采集：首个碰撞对象
- 结算：单体伤害，必要时附带爆炸
- 生命周期：命中或超时后结束

程序真正识别到的，是这一组语义。

### 2. 落雷

它之所以像“地面范围技”，不是因为有枚举值叫 `GroundAOE`，
而是因为它的组合是：

- 目标获取：地面点/目标点
- 原点：目标点上空或目标点本身
- 投递：延迟生效
- 命中采集：半径内对象
- 结算：范围伤害
- 生命周期：延迟后结算一次结束

### 3. 连锁闪电

它之所以像“跳链技能”，不是因为枚举写了 `Chain`，
而是因为它的组合是：

- 目标获取：先取主目标
- 原点：主目标或施法者
- 投递：瞬时命中
- 命中采集：主目标命中后继续筛选下一个可跳目标
- 结算：每跳一次各自结算
- 生命周期：直到跳数耗尽或无合法目标

### 4. Boss 清场技

它之所以像“Boss 特殊技能”，不是因为 `SkillType = BossSpecial`，
而是因为它的组合是：

- 目标获取：脚本指定/多点位计算
- 原点：多个脚本点或区域
- 投递：分阶段投递
- 命中采集：每阶段独立收集
- 结算：多段结算
- 生命周期：脚本化分段流程

所以所谓“分类”，其实是：

- **人看见这些语义组合以后，给它起了一个方便交流的名字。**

而程序本身只需要维护：

- **这些语义片段如何组合**
- **这些语义片段由谁负责执行**

---

## 四、这些语义应该落在哪一层

这一节是整份方案最重要的边界部分。

### 1. `UAOSkillDefinition` 负责什么

`UAOSkillDefinition` 这一层继续只回答：

- 这是什么技能
- 它默认绑定哪个 `AbilityClass`
- 它有哪些技能标签、族标签、组标签、冷却身份
- 它有哪些静态展示信息

它可以逐步承载“执行语义配置”，但前提是：

- 这些配置必须是**静态定义信息**
- 它们不能把执行本身搬到 `SkillDefinition` 里

也就是说，后续如果要扩展这一层，应该加的是类似：

- 目标获取配置
- 原点配置
- 投递配置
- 命中采集配置
- 生命周期配置

而不是加一个：

- `ESkillType SkillType`

因为 `SkillType` 只会把很多本来独立的语义重新压扁。

### 2. `UAOSkillInstance` 不应该承担“类型判定”

`UAOSkillInstance` 当前是运行时身份对象。

它负责的是：

- 来源物品是谁
- 当前技能等级是多少
- 当前品质是多少
- 当前是否装配
- 当前在哪个槽位

后续它可以承载少量运行时执行状态，例如：

- 当前蓄力层数
- 当前脚本阶段
- 当前持续对象引用

但它仍然不应该成为“技能类型判断中心”。

换句话说：

- `SkillInstance` 可以有状态
- 但不该承担“我是投射物类所以去走哪条分支”这种职责

### 3. `UAOSkillComponent` 不认识复杂技能种类

这一层当前边界已经很清楚了：

- 装槽
- 授予
- 触发
- 冷却查询
- UI 观察输出

它不应该继续长成：

- 技能执行分发器
- 技能类型判断中心
- 火球/落雷/跳链/Boss 技总控制器

也就是说，`UAOSkillComponent` 的职责应该永远停留在：

- “把正确的技能送进正确的 `Ability`”

而不是：

- “根据技能类型决定具体怎么执行”

### 4. `UAOSkillGameplayAbility` 及其子类才是执行中心

当前代码里最正确的执行落点，已经是这里了。

因为：

- `SkillComponent` 已经能按槽位把技能触发到授予出去的 `AbilitySpec`
- `UAOSkillGameplayAbility` 已经能从 `SourceObject` 反查 `SkillInstance`
- `UAOSkillGameplayAbility` 也已经能继续拿到 `SkillDefinition`

所以后续真正应该发展的，是这条链：

- 先由 `SkillDefinition` 决定默认使用哪个 `AbilityClass`
- 再由具体 `Ability` 读取静态执行语义配置
- 再在 `Ability` 内部决定目标、原点、投递、采集、结算、生命周期

这才符合当前系统边界。

---

## 五、后续程序里如何“分类”而不显式写 `SkillType`

这一节说的是实操层面的落法。

### 1. 第一原则：用“语义片段组合”代替“总类型枚举”

后续程序里，不要依赖：

- `SkillType == Projectile`
- `SkillType == AOE`
- `SkillType == Chain`

而应该依赖：

- 目标怎么来
- 原点怎么定
- 投递怎么做
- 命中对象怎么收
- 生命周期怎么推进

也就是说，技能之间的差别，不是一个总变量决定的，
而是一组语义片段共同决定的。

### 2. 第二原则：让“人类分类”只停留在文档、命名、标签和策划认知层

后续我们当然仍然可以在沟通里说：

- 这是投射物技能
- 这是范围技能
- 这是跳链技能
- 这是 Boss 技

但这些称呼更适合存在于：

- 方案文档
- 命名约定
- 策划表
- 调试标签
- AI 选技偏好标签

而不适合成为底层执行总开关。

### 3. 第三原则：让 Ability 层做“执行结构”的继承与复用

虽然不做显式 `SkillType`，
但并不代表后续所有技能都各写各的，完全无结构。

真正应该复用的，不是“类型枚举”，而是“执行结构”。

例如后续可以自然形成这样一层继承关系：

- 技能专用基础 `Ability`
- 投射物执行基类
- 地面范围执行基类
- 跳链执行基类
- 持续/引导执行基类
- 多阶段脚本技执行基类

这里的基类意义不是“我在系统里注册了一个显式类型”，
而是：

- **我复用了某一类执行结构。**

这才是程序真正需要的“分类”。

换句话说，程序里的分类，不应该首先表现为：

- 一个枚举字段

而应该首先表现为：

- 一种执行结构
- 一种配置结构
- 一种流程复用结构

---

## 六、推荐的后续扩展顺序

为了避免第七阶段一上来就又写散，我建议按下面顺序推进。

### 1. 先补“执行语义配置层”

第一步先把“执行语义”本身的静态配置结构整理出来。

先不要急着上很多具体技能。

先统一想清楚：

- 目标获取配置要怎么描述
- 原点配置要怎么描述
- 投递配置要怎么描述
- 命中采集配置要怎么描述
- 生命周期配置要怎么描述

这一步的目标不是把技能做出来，
而是把“技能以后如何被描述”做对。

### 2. 再补最小可复用的执行基类

第二步不是立刻做十几个技能，
而是先挑最有代表性的执行结构：

- 一个投射物基类
- 一个地面区域基类
- 一个持续/引导基类

先把最基础的执行复用骨架立住。

### 3. 然后再往上长具体技能

等执行结构站稳以后，再去做：

- 火球
- 冰枪
- 落雷
- 治疗圈
- 连锁闪电
- Boss 清场技

这样每新增一个技能，新增的主要是内容差异，
而不是重新发明一条技能执行总链。

---

## 七、这一份方案的最终结论

后续技能系统在“技能类型”这件事上的正式口径，应当统一成下面这句话：

**技能不靠一个显式的总类型枚举来驱动系统。**
**技能之间的区别，本质上是执行语义的组合差异。**
**程序真正维护的是目标获取、原点、投递、命中采集、结算与生命周期这些语义片段，而不是一个粗粒度的 `SkillType`。**

因此：

- 对人沟通时，可以继续说“投射物技能”“范围技能”“跳链技能”
- 对程序实现时，不要把这些称呼硬做成总开关变量
- 对代码扩展时，优先扩“语义配置结构”和“执行基类结构”
- 对系统边界时，坚持让 `SkillComponent` 只负责技能运行时管理，让具体 `Ability` 负责执行

这才是和当前技能系统骨架最一致，也最适合长期扩展的做法。

---

## 八、用具体技能反压这套框架是否成立

前面讲的都是原则。

但第七阶段最终一定要回到一个最现实的问题：

- 这套“隐式分类 + 执行语义组合”的设计，到底能不能承接真实技能。
- 如果后面技能越做越多，或者出现特别特殊的技能，这套框架会不会逼着我们又去改 `SkillComponent`、改槽位、改输入桥、改状态树。

所以这里我直接用两个明确样例来反压框架：

- 火球术
- 火山喷发

这两个样例不是随便举的。

因为它们分别覆盖了两种很关键的执行结构：

- **火球术**验证“投射物 + 命中后二段结算”。
- **火山喷发**验证“动画驱动 + 前方范围内多次分批随机落点 + 每次局部范围伤害”。

如果这两个技能都能在不破坏前六阶段骨架的前提下自然落进去，
说明这套框架是健康的。

### 1. 先定验收口径

这两个技能不是要求“先做出来能看”就算过。

真正的验收口径应该是：

- 能做出来
- 不需要引入一个总的 `SkillType`
- 不需要回头污染 `SkillComponent`
- 不需要为了某个技能去改状态树输入主链
- 特殊点只在执行层扩展
- 如果以后出现同结构技能，能复用这次长出来的执行骨架

也就是说，我们在验的不是某一个技能，
而是在验：

- **这套技能执行框架，是否真的能长期接技能内容。**

---

## 九、样例一：火球术

### 1. 技能描述

角色施法后，从手部或武器 Socket 发出一个火球射弹。
火球命中目标或阻挡后爆炸，对爆点半径内目标造成范围伤害。

### 2. 当前方案下的具体实现

火球术第一版直接按下面这条链实现：

1. `UAOSkillDefinition`
- 配置发射 Socket
- 配置射弹类
- 配置最大飞行时间
- 配置直接命中伤害
- 配置爆炸半径
- 配置爆炸伤害

2. `UGA_Skill_Fireball`
- 继承 `UAOSkillGameplayAbility_ProjectileBase`
- 激活后播放施法动画
- 到发射 Notify 时生成火球射弹

3. `AProjectile_Fireball`
- 负责飞行、碰撞、命中
- 命中后先处理直接命中
- 再以命中点做一次爆炸范围采样

4. 伤害结算
- 对命中的每个目标组装 `FAttackedInfo`
- 调 `CombatInterface->ApplyDamageToTarget`
- 复用 `UAOCharacterCombatManagerComponent`

### 3. 关键控制点

- 发射时机：由 `UGA_Skill_Fireball` 控制，动画 Notify 只提供信号
- 射弹命中：由射弹 Actor 控制
- 爆炸范围：以命中点为圆心，以 `ExplosionRadius` 做逻辑范围判定
- 表现播放：跟随发射和命中事件触发，但不反向决定逻辑命中

### 4. 这一类技能的最小改动原则

火球术第一版只应新增：

- 火球执行配置
- 投射物基类
- 火球 Ability
- 火球射弹 Actor

不应优先改：

- `UAOSkillComponent`
- 输入桥
- 状态树技能执行主链

---

## 十、样例二：火山喷发

### 1. 技能描述

角色播放重拍地面的施法动画。
到喷发开始时机后，在角色前方一个圆形区域内按波次随机选点。
每一波在一个随机点触发一次局部喷发事件，对该点半径内目标造成范围伤害。

### 2. 当前方案下的具体实现

火山喷发第一版直接按下面这条链实现：

1. `UAOSkillDefinition`
- 配置前方圆区中心前移距离 `AreaForwardOffset`
- 配置前方圆区半径 `AreaRadius`
- 配置喷发总波数 `EruptionCount`
- 配置第一波延迟 `InitialDelay`
- 配置每波间隔 `IntervalBetweenEruptions`
- 配置局部伤害半径 `ImpactRadius`
- 配置每波伤害 `ImpactDamage`
- 配置调试开关 `bEnableDebugDraw`
- 配置调试持续时间 `DebugDrawDuration`

2. `UGA_Skill_VolcanoBurst`
- 继承 `UAOSkillGameplayAbility_AreaSequenceBase`
- 激活后播放拍地动画
- 到喷发开始 Notify 时，正式进入喷发阶段
- 计算角色前方逻辑大圆
- 按波次和间隔驱动后续每一波

3. 每一波喷发
- 在前方逻辑大圆中随机选一个点
- 这个点一旦确定，就立刻产生一次局部喷发事件
- 服务器以该点和 `ImpactRadius` 做一次球形范围采样
- 收集合法目标并去重
- 对每个目标组装 `FAttackedInfo`
- 调 `CombatInterface->ApplyDamageToTarget`

4. 表现层
- 在该点播放喷发 Niagara、音效、Decal
- 这一层只负责表现，不负责伤害真相

### 3. 关键控制点

- 喷发开始时机：由 `UGA_Skill_VolcanoBurst` 控制，动画 Notify 只提供开始信号
- 前方大圆：只用于随机选点，不直接造成伤害
- 每波小圆：以随机点为圆心，以 `ImpactRadius` 做真正伤害判定
- 每波间隔：由 Ability 内部波次调度控制，不由 FX 控制
- 表现播放：跟随每一波局部喷发事件触发，但不反向决定逻辑命中

### 4. 调试口径

火山喷发第一版必须支持调试绘制，方便观察逻辑范围是否正确。

建议固定绘制三层：

1. 前方逻辑大圆
- 颜色：黄色
- 用途：看随机选点总范围

2. 每波随机点
- 颜色：白色
- 用途：看每一波实际落点

3. 每波局部伤害小圆
- 颜色：红色
- 用途：看本波真正的伤害判定范围

调试开关建议由两层共同控制：

- 技能定义本地开关 `bEnableDebugDraw`
- 后续可补一个全局调试开关

### 5. 这一类技能的最小改动原则

火山喷发第一版只应新增：

- 火山喷发执行配置
- 多波区域基类
- 火山喷发 Ability
- 局部范围判定助手
- 可选的局部表现对象

不应优先改：

- `UAOSkillComponent`
- 输入桥
- 状态树技能执行主链

## 十一、这两个样例给我们的正式结论

如果火球术和火山喷发都能自然落进去，
那我们就可以正式确认一件事：

- **这套系统不需要一个显式总类型变量，也能稳定承接真实技能。**

更进一步说，这两个技能分别说明：

### 1. 火球术说明

这套框架可以承接：

- 射弹类
- 命中后二段效果类
- 单体 + 范围复合类

并且不需要系统层认识“火球类技能”。

### 2. 火山喷发说明

这套框架可以承接：

- 动画起手类
- 多阶段时序类
- 区域随机采样类
- 多波局部范围结算类

并且不需要系统层认识“火山喷发类技能”。

### 3. 这两个样例共同说明

所谓“技能类型”，对程序来说真正有价值的，不是显式类别名，
而是这些可组合的执行语义：

- 目标获取
- 原点确定
- 投递方式
- 命中采集
- 结算逻辑
- 生命周期推进

只要这六层能持续扩展，
后面技能再多，框架都还是稳的。

---

## 十二、后续如果出现“特别特殊的技能”，最小改动原则是什么

这一节非常关键。

后面一定会出现一些你一眼看上去就觉得“这个技能很特殊”的东西。
但特殊不等于要回头推翻框架。

最小改动原则应该固定成下面这个顺序。

### 1. 先判断是不是只是参数特殊

如果只是这些不同：

- 发射点不同
- 飞行速度不同
- 爆炸半径不同
- 波次数量不同
- 随机点范围不同

那就不要改结构。

只改：

- `SkillDefinition` 静态配置

### 2. 再判断是不是同结构、不同内容

如果执行结构没变，只是内容不同，例如：

- 火球换成冰球
- 小喷发换成毒沼爆点
- 连锁闪电换成连锁治疗

那就不要改系统层。

优先做：

- 新技能定义
- 新技能表现资源
- 必要时新 `Ability` 子类

### 3. 再判断是不是缺一个新的执行结构

如果不是简单参数差异，而是现有执行结构不够表达，例如：

- 需要“射弹命中后再分裂成多个次级射弹”
- 需要“一个范围内持续追踪最强敌人反复落雷”
- 需要“先吸附敌人，再延迟爆炸，再残留地面持续区”

那优先扩的是：

- 新的执行基类
- 新的执行助手
- 新的执行语义配置结构

依然不要第一反应去改：

- `SkillComponent`
- 输入主链
- 状态树触发主链

### 4. 只有当“技能的触发方式本身变了”，才考虑动系统主链

真正应该动主链的情况非常少。

只有当技能不再是：

- 槽位触发
- Ability 激活
- Ability 内部完成执行

这种基本结构时，才需要重新审视系统层。

也就是说，只有在下面这种级别的问题上，
才值得考虑回头改主链：

- 技能不再依赖普通槽位输入
- 技能需要完全不同的授予模型
- 技能需要脱离当前 `SkillInstance -> AbilitySpec` 的绑定方式

在这之前，默认都应该先在执行层解决。

---

## 十三、这两个样例就是第七阶段的第一轮测试与验收样例

所以从现在开始，
“火球术”和“火山喷发”这两个技能，不只是未来要做的两个内容点。

它们同时还是第七阶段第一轮正式验收样例。

验收问题不是“能不能做出来”，而是：

- 做它们时有没有被迫引入显式 `SkillType`
- 做它们时有没有被迫污染 `SkillComponent`
- 做它们时有没有被迫回头动输入/槽位/状态树主链
- 做完以后有没有自然长出可复用的执行骨架
- 以后出现相似技能时，是否主要复用执行结构和静态配置，而不是重写系统链

如果这些问题的答案都是健康的，
那就说明我们这份“技能执行语义与隐式分类框架”不是纸面设计，
而是真的能接项目后面的技能生产。

---

## 十四、所有技能的数值到底该怎么控制

这一节不再只讨论火山喷发。

它要解决的是整个技能系统进入第七阶段以后都会遇到的统一问题：

- 所有技能的玩法数值到底该放在哪
- 哪些值应该暴露
- 哪些值可以写死
- 程序、策划、平衡调参后面到底靠什么控制

这一节的目标，是给后面所有技能建立统一口径。

如果这一层没想清楚，后面就会出现两种都很糟糕的情况：

- 要么所有值都写死在 `Ability` 里，程序每调一次数值都得改代码。
- 要么什么都暴露，最后 `SkillDefinition` 上挂一大堆没有层次的裸参数，谁也不知道哪些该调、哪些不该调。

所以这里先把口径定死。

### 1. 先说总原则

对于火山喷发、火球术以及后面绝大多数技能：

- **玩法数值要暴露**
- **执行结构不要暴露成随便乱拼的脚本**
- **极少数纯实现常量可以写死**

换句话说：

- 能影响玩法结果、手感、AI 价值判断、技能平衡的数值，原则上都不应该写死。
- 会破坏执行结构边界的底层实现细节，不应该直接暴露给策划层。
- 只有那种纯程序保护性质的值，才适合写死在代码里。

### 2. 哪些值属于“玩法数值”，应该暴露

这里说的“玩法数值”，不是某个技能独有的概念。

只要一个数值会影响下面任意一件事，它就属于应该优先暴露的玩法参数：

- 技能的有效范围
- 技能的命中方式
- 技能的施法节奏
- 技能的伤害或治疗结果
- 技能的控制强度
- 技能的持续时间
- 技能的成长曲线
- AI 对这个技能的释放价值判断

换句话说，只要某个值改了以后，玩家体感、战斗平衡、AI 选择或技能身份会变化，
那它原则上就不该写死。

常见应该暴露的玩法数值可以统一分成下面几类：

#### 第一类：空间与目标相关数值

- 施法距离
- 锁定范围
- 目标搜索半径
- 前方区域半径
- 扇形角度
- 地面落点半径
- 爆炸半径
- 跳链搜索半径
- 追踪修正角度

#### 第二类：时序与生命周期相关数值

- 前摇时间
- 后摇时间
- 第一段延迟
- 波次间隔
- 持续时间
- 引导最大时长
- 蓄力时间
- 多段技能每段之间的间隔
- 射弹最大飞行时间

#### 第三类：结算相关数值

- 基础伤害
- 基础治疗
- 护盾量
- 韧性削减
- 控制时长
- DoT/HoT 每跳数值
- 爆炸伤害
- 直接命中伤害
- 二段结算伤害

#### 第四类：次数与容量相关数值

- 波次数量
- 最大跳链次数
- 最大穿透数量
- 可命中目标上限
- 分裂射弹数量
- 召唤物数量
- 可同时存在的持续区数量

#### 第五类：成长与平衡相关数值

- 每级伤害成长
- 每级范围成长
- 每级持续时间成长
- 属性系数
- 武器系数
- 难度缩放系数
- Boss 版倍率
- PvE / PvP 分离倍率

这些值之所以要暴露，不是因为“改起来方便”这么简单。

而是因为它们本身就是技能设计的一部分：

- 改范围，技能覆盖身份就变了
- 改时序，技能节奏就变了
- 改伤害或控制，平衡就变了
- 改成长，后期表现就变了

这类值如果写死在代码里，后面每调一次平衡都要重新进 C++，这会很快拖垮迭代效率。

### 3. 哪些值不该暴露，适合写死

也不是所有数值都应该暴露。

有一类值更适合写死在执行代码里，因为它们不是玩法语义，而是实现保护常量。

例如：

- 随机采点失败时的最大重试次数
- 浮点误差容忍值
- 内部数组预留数量
- 判定空指针后的兜底返回
- 调试绘制默认持续时间

这些值如果暴露出来，反而会污染配置层。

因为它们不是“这个技能想怎么玩”，而是“程序如何安全执行”。

所以这里要分清：

- **玩法数值暴露**
- **实现保护常量写死**

### 4. 应该暴露到哪一层

按我们现在的边界，这类数值最合理的落点应该是：

- 主要放在 `SkillDefinition` 的执行语义配置里

而不应该放在：

- `SkillComponent`
- 状态树任务
- `Hero`
- UI

原因很简单：

- 这些值描述的是“这个技能本身怎么执行”
- 它们属于技能静态定义，不属于槽位，也不属于输入链

也就是说，后面不管是什么技能，它的核心玩法参数都应该优先归属于：

- 这个技能自己的定义配置

而不是散落在：

- 某个槽位
- 某个状态树状态
- 某个输入桥
- 某个 UI 蓝图

### 5. 用什么类型控制这些数值

这里我建议不要只有一种控制方式。

不同数值，应该用不同层级的控制工具。

#### 第一层：固定静态值

如果这个数值只是固定配置，不需要随等级或属性动态变化，
最简单的方式就是：

- 直接作为 `SkillDefinition` 上的 `EditDefaultsOnly` 参数

例如：

- 固定施法距离
- 固定爆炸半径
- 固定锁定角度
- 默认波次数

这一层最直接，也最适合大多数基础参数。

#### 第二层：可成长数值

如果这个值会随着技能等级、角色属性或难度变化，
那就不该只用裸 `float`。

更合适的是：

- `FScalableFloat`

这类值典型包括：

- 基础伤害
- 基础治疗
- 持续时间
- 范围成长
- 控制时长成长
- 跳链数量成长
- 护盾量成长

`FScalableFloat` 的意义不是为了“高级”，而是它能让我们以后自然接：

- 技能等级成长
- DataTable 驱动
- 平衡表调参

也就是说：

- **固定不成长的值用普通参数**
- **会成长、会被平衡层长期调的值用 `FScalableFloat`**

#### 第三层：时序或阶段控制

有些值不是单个数字，而是一条过程。

例如：

- 多段技能每段伤害不是固定值，而是逐段变化
- 引导技能每秒消耗不是固定值，而是逐步提升
- 召唤持续区的半径会随时间膨胀
- 火山喷发每一波间隔前快后慢
- Boss 技不同阶段倍率不同

这种时候，单个 `float` 或 `FScalableFloat` 还不够。

更合理的是：

- 曲线
- 数组序列
- 或受控的阶段配置结构

也就是说，只有当技能真的需要“过程变化”时，
我们才引入曲线或阶段配置，
而不是一上来所有东西都曲线化。

### 6. 推荐的统一数值分层

为了让所有技能后面都能按同一套方法调参，
我建议统一分成下面四层。

#### 第一层：技能定义静态基准值

这一层描述“这个技能默认是什么样”。

适合放：

- 默认施法距离
- 默认影响半径
- 默认持续时间
- 默认基础伤害
- 默认波次数
- 默认飞行时间

这是所有技能最基础的一层。

#### 第二层：技能成长值

这一层描述“这个技能随着等级、品质、角色属性如何变化”。

适合放：

- 每级伤害成长
- 每级范围成长
- 每级持续时间成长
- 属性加成系数
- 武器类型加成系数

这一层最好优先用 `FScalableFloat` 或同等成长结构承接。

#### 第三层：执行结构参数

这一层描述“这个技能具体怎么跑”。

适合放：

- 射弹速度
- 追踪强度
- 跳链搜索半径
- 波次间隔
- 最小落点间距
- 多段技能各段间隔

这类值虽然和执行有关，但只要它们会影响玩法表现，依然应该配置化。

#### 第四层：程序保护常量

这一层不是给玩法调参的，而是给程序稳定性兜底的。

适合写死：

- 最大重试次数
- 容错 epsilon
- 默认调试绘制时长
- 数组保底容量
- 无效引用后的快速返回

这一层不应混进技能配置主结构里。

### 7. 这些值要不要写死在 `Ability` 里

我的结论是：

- **基础玩法值不要写死在 `Ability` 里**

`Ability` 更适合负责：

- 读取配置
- 执行流程
- 在合适时机触发生成、采样、结算

而不是自己持有一堆“这技能半径 500、波次 6、间隔 0.3”这种裸常量。

因为一旦值写死在 `Ability` 里，后面你做：

- 高级火山喷发
- Boss 版火山喷发
- 小怪版弱化火山喷发

就会非常难受。

### 8. 那要不要什么都暴露成可配置

也不要走到另一个极端。

我不建议把这类技能做成一个“什么都能拼”的超级通用表。

原因是：

- 过度通用化会让配置结构失真
- 会让原本清楚的执行结构变成一堆布尔开关拼接
- 最后还是会出现“表能配，但谁都不敢改”的问题

所以正确方向不是：

- 一个万能技能表，啥都往里塞

而是：

- 先长出稳定的执行结构
- 每个执行结构暴露自己真正需要的参数

这才符合“最小扩展、边界清晰”的原则。

### 9. 后面所有技能的正式控制口径

从现在开始，后面所有技能的数值控制都建议统一按下面这个顺序判断：

1. 先问这个值会不会影响玩法、平衡、手感或 AI 选择。
2. 如果会，优先放进 `SkillDefinition` 的技能执行配置层。
3. 如果它会成长，优先用 `FScalableFloat`。
4. 如果它描述的是阶段变化或时间过程，再考虑曲线或阶段配置。
5. 如果它只是程序保护常量，就写死在执行代码里，不要污染配置层。

### 10. 这一节的最终结论

关于“所有技能的数值怎么控制”，正式口径可以固定成下面这句话：

- **所有技能的玩法数值，原则上都应该收口到技能定义的执行配置层。**
- **会影响成长和平衡的值，优先使用 `FScalableFloat`。**
- **阶段变化、时序变化或过程变化，再考虑曲线或阶段配置。**
- **纯实现保护常量可以写死在执行代码里。**
- **不要把这些数值写死在 `SkillComponent`、状态树或输入链里。**

## 十五、回到当前项目，真正准备开做时应该怎么落

前面那几节已经把方向讲清楚了。

但如果这份方案要真正写进项目，并且后面我们要直接照着开工，
那就不能只停留在“原则上应该怎样”。

这一节开始把整件事收成**项目落地版设计**。

这一版只围绕当前项目已经存在的真实类来设计，不重新发明一套脱离现状的新系统。

当前我们必须承认的既有事实是：

- `UAOSkillDefinition` 已经是技能静态定义资产
- `UAOSkillInstance` 已经是运行时技能身份对象
- `UAOSkillComponent` 已经是技能槽、运行时实例、ASC 授予与输入桥接的总入口
- `UAOSkillGameplayAbility` 已经是技能 Ability 的统一基类
- `UAOFragment_SkillSource` 已经是库存物品到技能定义的正式桥接层

所以这次第七阶段的扩展，原则上只允许做两件事：

- 在这些既有边界上**继续长执行语义配置与执行基类**
- 在必要时新增独立执行对象

不允许做的事是：

- 重新定义技能系统主链
- 把执行逻辑塞回 `SkillComponent`
- 为了技能类型回头改输入桥或状态树主链

### 1. 先明确这次不动什么

为了避免后面开工时边写边飘，先把“不动项”写死。

这次技能执行层扩展，不应该主动改下面这些主语义：

- `UAOSkillComponent` 的槽位结构
- `UAOSkillComponent` 的输入接收职责
- `UAOSkillComponent` 到 ASC 的授予主链
- `UAOSkillInstance` 作为运行时身份对象的定位
- `UAOFragment_SkillSource` 作为库存桥接边界的定位
- 状态树技能触发走“技能槽执行入口”这一条已经修好的主链

也就是说，当前项目的技能执行主链继续保持为：

1. 来源物品通过 `UAOFragment_SkillSource` 指向 `UAOSkillDefinition`
2. `UAOSkillComponent` 创建并管理 `UAOSkillInstance`
3. 槽位变化驱动 `UAOSkillComponent::GrantSkillToSlot()`
4. 授予结果把 `SkillInstance` 作为 `SourceObject` 写进 AbilitySpec
5. `UAOSkillGameplayAbility` 子类激活后再回查 `SkillInstance / SkillDefinition`
6. 具体技能执行全部落在 Ability 及其执行对象里

这一条主链，当前项目已经真实存在，不应该再推翻。

### 2. 这次真正要新增的，不是“技能类型系统”，而是“技能执行配置层”

从当前代码来看，`UAOSkillDefinition` 现在已经有：

- 展示信息
- 标签
- 冷却信息
- 默认等级
- `AbilityClass`

但是它还没有承接第七阶段真正需要的东西：

- 目标获取配置
- 原点配置
- 投递配置
- 命中采集配置
- 执行时序配置
- 伤害/治疗/控制等结算配置

所以第七阶段第一步，不应该先写一堆具体技能，
而应该先让 `UAOSkillDefinition` 能正式描述“这个技能怎么执行”。

换句话说，当前项目里最先要长出来的是：

- **技能执行配置结构**

而不是：

- 一个新的 `SkillType` 枚举系统

## 十六、当前项目建议新增的配置结构长什么样

这一节不写伪概念，直接按项目可落地的形式说。

### 1. 顶层思路

我建议 `UAOSkillDefinition` 后面新增一个总的执行配置字段，
但这个字段本身不要是“万能大表”，而是一个总入口结构。

例如它的语义应该是：

- `FAOSkillExecutionConfig`

这个顶层结构本身不负责一切细节，
它只负责把几个稳定的大块收在一起。

### 2. 顶层结构建议拆成哪几块

第一版我建议固定拆成下面六块。

#### 第一块：目标获取配置

它回答：

- 这个技能怎么找目标

建议结构语义：

- 是否必须有目标
- 默认目标来源
- 搜索半径
- 锁定优先还是朝向优先
- 无目标是否允许释放

这一块是所有技能通用的，不应该散写在具体 Ability 里。

#### 第二块：空间原点配置

它回答：

- 这个技能从哪里发出
- 如果是区域技，这个区域相对施法者摆在哪里

建议结构语义：

- 原点模式
- Socket 名称
- 前移距离
- 偏移量
- 是否跟随施法者朝向

这一块会同时服务：

- 火球
- 落雷
- 火山喷发
- 护盾环
- Boss 多点区域技

#### 第三块：投递配置

它回答：

- 效果是怎么被送出去的

建议结构语义：

- 立即生效
- 近战判定
- 生成射弹
- 地面区域
- 连续多波
- 持续区域

注意这里依然不是总 `SkillType`。

这里的意义只是：

- 这个技能主投递结构是什么

也就是说，这一层是执行结构选择，不是系统层分类。

#### 第四块：命中采集配置

它回答：

- 命中对象怎么收
- 是首个命中、范围命中、跳链命中，还是持续扫描

建议结构语义：

- 单体
- 半径采样
- 扇区采样
- 链式搜索
- 周期扫描
- 命中数量上限

#### 第五块：结算配置

它回答：

- 命中后到底结算什么

建议结构语义：

- 基础伤害
- 基础治疗
- 控制时长
- 是否附带 GE
- 是否命中后有二段效果
- 是否有爆炸
- 爆炸半径
- 爆炸伤害

第一版先以项目真正会用到的基础结算项为主，
不要试图一次把所有 RPG 结算都塞满。

#### 第六块：生命周期配置

它回答：

- 这个技能是一段、几段、持续多久、按什么节奏推进

建议结构语义：

- 瞬发
- 固定持续
- 波次数量
- 波次间隔
- 初始延迟
- 最大飞行时长
- 引导时长

这一块对于火山喷发这种技能尤其关键。

### 3. 第一版不要做成什么样

这一点很重要。

第一版不要做成下面这种危险形态：

- 一个超级大 `USTRUCT`
- 几十个布尔开关
- 几十个裸 `float`
- 每种技能都共享同一堆字段

这样最后只会得到一个：

- 看起来通用
- 实际上谁都不敢配
- 稍微改一个技能就怕影响别的技能

所以正确做法不是“一个万能表”，
而是：

- 顶层统一
- 子结构分治
- 第一版只收当前项目真正要做的执行语义

## 十七、这些配置具体应该放进哪个类

### 1. `UAOSkillDefinition` 放静态执行配置

这是第一优先级。

因为从当前项目代码来看，`UAOSkillDefinition` 本来就是回答：

- 这是什么技能

第七阶段以后，它自然继续回答：

- 这个技能默认怎么执行

所以：

- 目标获取配置
- 原点配置
- 投递配置
- 命中采集配置
- 结算配置
- 生命周期配置

都应该优先挂在 `UAOSkillDefinition` 上。

### 2. `UAOSkillInstance` 只放运行时状态，不放静态配置

从当前 `UAOSkillInstance` 的定位来看，它只应该继续承接：

- 当前等级
- 当前品质
- 当前槽位
- 当前是否装备

后面如果第七阶段需要扩它，也只应该扩运行时态。

例如未来可能有：

- 当前蓄力阶段
- 当前剩余可跳次数
- 当前持续区引用
- 当前技能内部阶段索引

但它不应该承接“火球默认半径 300、火山喷发默认 6 波”这种静态值。

这些仍然应该回到 `SkillDefinition`。

### 3. `UAOSkillComponent` 只读配置，不持有执行配置

`UAOSkillComponent` 当前已经负责很多事了：

- 槽位
- 实例
- 授予
- 观察
- 冷却查询

所以第七阶段不要再让它变成：

- 技能执行配置中心
- 技能数值存储中心
- 技能类型判断中心

它最多只需要在少量必要地方：

- 从 `SkillDefinition` 读取配置
- 或给 `Ability` 提供回查入口

但不应该自己存一份执行配置真相。

### 4. `UAOSkillGameplayAbility` 负责消费配置并执行

这是当前项目最自然的落点。

因为现在 `GrantSkillToSlot()` 已经会把：

- `SkillDefinition->AbilityClass`
- `SkillInstance` 作为 `SourceObject`

送进 ASC。

这意味着 Ability 激活以后，已经天然可以拿到：

- 这个技能是谁
- 这个技能实例是谁
- 它的静态定义是什么

所以第七阶段真正的执行逻辑，就该从这里长。

## 二十二、回到程序视角，火山喷发这类技能的伤害判定到底怎么做

这一节是对前面方案最重要的一次补完。

因为如果只写：

- 每一波生成一次局部喷发效果

那这句话确实更像是在说 FX，
而不是在说程序里的真实伤害判定链。

所以这里必须把两件事彻底拆开：

- **表现层看到的喷发效果是什么**
- **程序层真正用于判定和结算的对象是什么**

这两个东西有时可以是同一个 Actor，
但在设计上不能默认把它们绑死成同一个概念。

### 1. 先看当前项目里真实已经存在的伤害主链

当前项目里，近战已经有一条真实成立的伤害链：

1. `GA_LightAttack` / `GA_HeavyAttack` 的 AbilityTask 收集命中结果  
   参考 [GA_LightAttack.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Abilities/Attack/Combat/GA_LightAttack.cpp:448) 和 [GA_HeavyAttack.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Abilities/Attack/Combat/GA_HeavyAttack.cpp:391)
2. 命中结果被去重后，组装成 `FAttackedInfo`  
   结构定义在 [CombatInterface.h](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/CombatInterface.h:8)
3. 然后调用 `CombatInterface->ApplyDamageToTarget(AttackedInfo)`  
   调用点见 [GA_LightAttack.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Abilities/Attack/Combat/GA_LightAttack.cpp:502) 和 [GA_HeavyAttack.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/AbilitySystem/Abilities/Attack/Combat/GA_HeavyAttack.cpp:438)
4. `AAOCharacter` 把请求转发给 `UAOCharacterCombatManagerComponent`  
   见 [AOCharacter.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOCharacter.cpp:358)
5. `UAOCharacterCombatManagerComponent` 再把 `MetaGameplayEffects` 应用到目标 ASC  
   见 [AOCharacterCombatManagerComponent.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOCharacterCombatManagerComponent.cpp:40)

也就是说，当前项目并不是没有伤害链。

真正缺的不是“怎么打伤害”这件事本身，
而是：

- **技能执行层怎么把自己的命中结果接进这条现有伤害链**

### 2. 所以火山喷发不应该重新发明一条伤害体系

按当前项目最稳的做法，
火山喷发、火球术、落雷、跳链这类技能，
都不应该自己再各自重写一套“目标怎么扣血”的底层。

它们应该复用当前项目已经存在的尾部结算链：

- 收集合法命中目标
- 组装 `FAttackedInfo`
- 调 `CombatInterface->ApplyDamageToTarget`
- 让 `UAOCharacterCombatManagerComponent` 去应用 GE

换句话说：

- **技能层负责“我打到了谁”**
- **现有战斗链负责“这些目标怎么正式吃到效果”**

这才和项目现状一致。

### 3. 先把“局部喷发效果”这个词重新定义

从程序角度讲，火山喷发里的“局部喷发效果”不能只理解成 Niagara 或 Decal。

它更准确的程序语义应该是：

- **一次局部喷发事件**

这次事件至少包含四类信息：

1. 逻辑位置
- 本次喷发点在世界中的 `Location`
- 本次局部判定半径

2. 逻辑上下文
- 来源施法者是谁
- 来源 `SkillInstance` 是谁
- 来源 `Ability` 是谁
- 当前是第几波喷发

3. 逻辑结算信息
- 本次命中应该应用哪些伤害/控制/附加效果
- 本次目标去重规则是什么

4. 表现信息
- 这一波对应什么 Niagara
- 什么音效
- 什么地面贴花
- 什么镜头震动

所以从程序设计上要明确：

- **一次局部喷发事件 = 判定事件 + 结算事件 + 表现事件**

而不是只有 FX。

### 4. 火山喷发在程序里的真实职责拆分

如果按当前项目落地，我建议把火山喷发拆成下面四层职责。

#### 第一层：`Ability` 负责导演整段技能流程

火山喷发 Ability 的职责是：

- 播放拍地动画
- 等待动画事件到达“正式开始喷发”的时点
- 只在服务端生成并启动喷发运行时对象
- 把后续波次生命周期从 Ability 交接给运行时对象

它不应该直接承担：

- 每一波真正的目标重叠检测细节
- 每一波真正的最终伤害应用细节
- 表现资源如何在各端同步播放的全部实现

它是导演，不是全包工头。

#### 第二层：运行时执行层负责“波次推进与本次喷发命中了谁”

这一层才是真正的长生命周期执行核心。

每一波喷发产生以后，程序应该在服务器上：

- 维护波次数量与波次间隔
- 在角色前方逻辑区域内选出本波落点
- 对本次喷发点做一次范围采样

最直接的逻辑就是：

- 以喷发点为中心
- 以 `ImpactRadius` 为半径
- 做一次球形重叠检测或等价的范围查询
- 找出实现了 `CombatInterface` 的目标
- 做本波内目标去重

这里最关键的一点是：

- **判定应以逻辑圆心和逻辑半径为准**
- **而不是以 Niagara 视觉范围为准**

也就是说，FX 可以大一点、小一点、滞后一帧甚至提前播一点，
但真正能不能命中，仍然以程序判定参数为准。

#### 第三层：结算层负责“把命中目标接入现有伤害链”

当本波已经拿到命中目标列表以后，
接下来就不要再各写各的“直接扣血”了。

而应该像你们当前近战一样：

- 对每个合法目标组装一份 `FAttackedInfo`
- 填好 `SourceASC`
- 填好 `TargetASC`
- 填好来源上下文
- 填好本技能本次要应用的 GameplayEffect 列表
- 再调用 `CombatInterface->ApplyDamageToTarget`

这样火山喷发在尾部结算上，就和现有项目主链保持一致。

#### 第四层：表现层只负责“让玩家看到喷发”

这一层才是：

- Niagara
- 音效
- 地裂
- 烟尘
- 屏幕震动

它可以由技能运行时对象在结算点发出，
也可以由专门的 `GameplayCue` 资产承接。

但不管哪种方式，都要记住：

- **它是表现对象，不是伤害真相本身**
- **它的联网同步应优先收口到 `GameplayCue`，而不是在具体技能里长期散写多播**

## 二十三、所以“表演对象”和“判定对象”在项目里应该怎么配合

这一节直接回答你最关心的那个点：

- “程序的角度怎么解释这些技能怎么去配合这些效果”

### 1. 第一种情况：判定和表现是同一个对象

这适合：

- 火球术这类投射物技能

例如火球：

- 火球 Actor 本身既有视觉模型
- 也有飞行
- 也有碰撞

这时它可以同时承担：

- 表现对象
- 判定对象

因为它的运动路径本身就是玩法的一部分。

### 2. 第二种情况：判定和表现分离

这更适合：

- 火山喷发
- 连续落雷
- 脚本化落点技

因为这类技能的核心不是“有个东西在空间里飞”，
而是：

- 某个逻辑点在某个时刻发生一次区域命中事件

这时更合理的做法通常是：

- `Ability` 先在服务端启动运行时执行对象
- 运行时对象在服务器确定逻辑喷发点
- 服务器按这个点做范围判定和伤害结算
- 结算点再触发 `GameplayCue` 给所有客户端播放表现

也就是说，火山喷发默认更适合：

- **逻辑点先成立**
- **表现随后附着到这个逻辑点**

而不是反过来拿 FX 去倒推命中。

### 3. 为什么这点很重要

因为如果把喷发 FX 当作判定真相，
后面很快会出问题：

- FX 缩放和真实判定半径不一致
- 客户端先看到特效，但服务端判定稍后才发生
- 不同机器上的粒子表现差异影响你对命中的理解
- 策划想改视觉大小时，会误伤玩法判定

所以正式设计口径应该写死：

- **判定半径是逻辑数值**
- **表现半径是表现资源**
- **两者可以默认保持一致，但不互为真相**

## 二十四、火山喷发在当前项目里建议长出来的最小程序结构

如果只看“怎么把这技能做出来”，
最小可行结构我建议是下面这样。

### 1. `UGA_Skill_VolcanoBurst`

职责：

- 维护波次节奏
- 每波选点
- 调用“单次局部喷发结算”
- 通知表现层播喷发 FX

### 2. 一个局部范围判定助手

这个东西不一定非得是 Actor。

第一版更建议做成：

- Ability 内部私有函数
- 或一个通用静态函数 / Helper
- 或一个专门的 AbilityTask

它的职责就是：

- 输入：喷发点、半径、来源 Skill/Ability/ASC、结算配置

如果后面这类技能很多，

### 3. 一个可选的局部表现对象

这个对象只负责：

- 播放地裂 FX
- 播音效
- 可选地播地面 decal

它可以存在，也可以不存在。

重要的是：

- **即便没有它，逻辑伤害判定也应该完整成立**

这才说明程序层真正站住了。

## 二十五、火球术和火山喷发在判定层上的真正区别

这两者表面上都叫“技能”，
但程序里的判定结构其实完全不同。

### 1. 火球术

核心判定问题是：

- 一个运动中的对象何时撞到谁

所以它的判定载体天然是：

- 射弹 Actor

射弹负责：

- 飞行
- 碰撞
- 命中
- 命中后可再做一次爆炸范围采样

### 2. 火山喷发

核心判定问题是：

- 某个时刻在某个逻辑点上，哪些目标落在这一波局部半径里

所以它的判定载体不需要是飞行 Actor，
而更像是：

- 一次瞬时的区域命中事件

换句话说：

- 火球更像“运动碰撞判定”
- 火山喷发更像“定点区域采样判定”

这就是为什么我前面说，
第七阶段真正该抽象的是执行结构，不是大类名。

## 二十六、当前方案还需要补上的项目级改动点

如果按你们当前项目继续往下做，
这里还有一个必须面对的现实：

当前 `FAttackedInfo` 和 `UAOCharacterCombatManagerComponent` 这条伤害尾链，
是从武器近战思路长出来的。

它现在能很好复用的地方是：

- SourceASC / TargetASC
- CombatInterface
- MetaGameplayEffects 应用

但如果技能后面要真正丰富起来，
这里大概率还需要逐步增强：

### 1. 需要更清楚的“技能伤害来源上下文”

现在 `FAttackedInfo` 里有：

- `SourceASC`
- `TargetASC`
- `ObjectContext01`
- `MetaGameplayEffects`

这能跑，但表达力还不够强。

后面技能系一般还会想知道：

- 来源 `SkillInstance`
- 来源 `SkillDefinition`
- 本次命中点
- 本次命中波次索引
- 本次是否暴击

这些不是今天就必须全改，
但这确实是后续技能伤害链的自然扩展点。

### 2. 技能伤害不应永远复用“武器 AbilitySet MetaEffects 收集方式”

你们现在近战是从武器 `AbilitySet` 里收集 `MetaGameplayEffects`，
这个路径对武器攻击成立。

但技能系后面更合理的是：

- 技能自己从 `SkillDefinition` 的结算配置里拿伤害/附加效果

也就是说：

- 武器攻击的效果来源是武器定义
- 技能攻击的效果来源应该是技能定义

这一点后面真正开写技能时，必须在设计里明确区分。

### 3. `AOGameData` 里的 SetByCaller GE 入口值得纳入技能方案

## 二十七、这一节的最终结论

关于火山喷发这类技能的程序解释，正式口径应该固定成下面这几条：

1. 火山喷发的“局部喷发效果”不只是 FX，而是一种局部喷发事件。
2. 一次局部喷发事件必须同时包含逻辑位置、判定半径、来源上下文与结算信息；表现信息可以独立承接，不应反过来充当逻辑真相。
3. 服务器上的真实伤害判定应以逻辑点和逻辑半径做范围采样，而不是以 FX 视觉范围做真相。
4. 命中目标确定后，应复用当前项目已经存在的 `FAttackedInfo -> CombatInterface -> UAOCharacterCombatManagerComponent` 这条伤害尾链。
5. FX 只负责让玩家看到喷发；没有 FX，逻辑判定也必须能完整成立。
6. 联机下，火山喷发这类长生命周期区域技能，应采用“服务端运行时执行对象 + 表现层 `GameplayCue`”的正式结构。
7. 火球术偏“运动碰撞判定”，火山喷发偏“定点区域采样判定”，两者的差别应收口在执行结构，而不是回头改系统主链。

### 1. 到目前为止，已经真正完成了什么

先说结论：

- 技能系统已经不是概念方案，而是已经落进项目主工程的可编译、可运行骨架
- 技能系统的对象模型、技能槽装配模型、技能来源模型、技能执行模型，已经都有正式代码落点
- 技能系统相关 UI、HUD ViewModel、技能槽观察链、键位显示链，也已经接回工程主链
- 这轮最后还顺手完成了一次项目级编译清障，当前工程已经能完整编译通过

更具体一点，当前已经落地的内容包括：

1. 技能系统主骨架已经建立完成  
   现在正式存在 `SkillDefinition -> SkillInstance -> SkillSlot -> SkillComponent -> ASC` 这条主链。

2. 技能来源和技能本体已经解耦  
   技能不再等同于“某个物品本身”，而是由技能来源物品通过 `SkillSource` 语义提供技能定义，再生成运行时技能实例。

3. 技能槽已经成为正式装配层  
   输入绑定的是技能槽，不是某个技能名字。技能换槽时，输入语义不需要跟着重做。

4. 技能槽库存适配层已经建立  
   技能槽现在可以复用现有库存交换/拖拽链路，但 `SkillSlotInventoryComponent` 只是库存投影层，不是第二套技能系统真相。

5. 技能执行结构已经从“一个大 Definition 堆配置”重构为多态结构  
   当前正式落地的是：
   - `UAOSkillExecutionDefinition`
   - `UAOSkillProjectileExecutionDefinition`
   - `UAOSkillAreaSequenceExecutionDefinition`
   - `UAOSkillGameplayAbility_ProjectileBase`
   - `UAOSkillGameplayAbility_AreaSequenceBase`

6. 火球术和火山喷发已经作为第一批执行案例落地  
   它们的意义不是“做了两个技能”，而是用两个差异明显的执行结构验证框架是否站得住：
   - 火球术验证“动画时机 -> 服务端射弹 -> 命中 -> 爆炸范围结算”
   - 火山喷发验证“动画时机 -> 服务端运行时波次 -> 区域采样 -> 局部范围结算”

7. 技能执行父类边界已经收紧  
   `UAOSkillGameplayAbility` 现在只保留真正的公共能力：
   - 技能实例 / 定义 / 执行定义获取
   - 冷却辅助
   - 公共效果尾链
   - 调试辅助

   它不再默认接管：
   - 播放蒙太奇
   - 等待单个 GameplayEvent
   - “播放动画 -> 等事件 -> 执行”的统一模板

8. 动画时机已经被确认必须纳入技能执行语义  
   这件事已经不再被当成某个单独技能的特例。
   也就是说：
   - 技能不一定激活就播动画
   - 技能也不一定只等一个事件
   - 父类不能默认替每个技能决定这些行为

9. 联机表现同步边界已经补充清楚  
   当前正式方向不是把网络表现长期散写在各个技能自己的多播里，而是：
   - 服务端负责权威执行
   - 运行时对象或 Ability 在关键结算点发出表现事件
   - 表现同步优先收口到 `GameplayCue`

10. StateTree 技能触发链路边界已经明确  
   之前出现过“状态进入后又回灌输入，最终形成死循环”的问题。
   现在已经明确：
   - 玩家真实输入链可以走 `Hero -> SkillComponent -> ASC`
   - StateTree / AI 触发技能时，应走 `StateTree -> SkillComponent -> ASC`
   - 不能再把 StateTree 技能触发重新广播回 Hero 输入语义层

11. 技能 UI 相关链路已经被整理回正式工程结构  
   包括：
   - `AOHUDViewModelComponent`
   - `MVVM_HUD`
   - `AOSkillBarUI`
   - `AOSkillSlotUI`

   这一层现在已经不再是临时拼的，而是明确接在 HUD / ViewModel / SkillComponent 观察链上。

### 3. 当前阶段最重要的已拍板边界

这几条是后续接手时不能再轻易推翻的：

1. 技能系统的中心是技能，不是 QuickBar，不是武器系统，也不是输入系统  
   其他系统只能复用能力，不能反过来定义技能语义。

2. 父类不能管太多  
   特别是动画、事件等待、是否造成伤害、等几个事件才继续执行，以及具体 `GameplayCue` 资源如何播放，这些都不能默认塞进技能父类。

3. 不要再增加显式全局 `SkillType` 枚举来硬分技能类别  
   当前方向是：用执行定义子类、能力子类和表现事件入口表达结构差异，而不是用一个大枚举到处 `switch`。

4. 网络表现同步优先走 `GameplayCue`  
   不要把技能表现长期建立在零散的技能级多播堆叠上。多播最多只该是临时过渡，不应成为最终正式规范。

5. 技能是否能激活，不应该由 Task 去做最终裁决  
   Task 的职责是“通知技能该尝试执行了”，
   冷却、资源不足、条件不满足这些，应由技能 / GAS 自己决定。

6. StateTree 不要再回灌 Hero 输入  
   这一条之前已经出过死循环问题，后续不要再改回去。

7. UI 尽量只观察，不自己维护第二套真相  
   不要再给技能 UI 叠额外镜像数组、额外状态表、额外手写缓存真相。

8. 文件不能再重新塞回一个大文件里  
   用户已经明确否掉过“多态做了但全塞一个文件”的写法。
   后续新增执行定义、Ability 基类或具体技能时，保持分文件。

## 三十三、2026-05-10 战斗系统衔接正式口径补充

这一节不是重新讲技能框架，而是把“技能系统已经成型之后，如何把所有攻击正式接入战斗系统”的新增共识写死。

后续不管是继续做普攻、重击、技能、投射体、AOE、多段伤害，还是做翻滚、格挡、弹反、受击反馈，都应以这一节为准。

### 1. 当前要统一的不是“技能命中”，而是“所有攻击命中”

这里的攻击明确包括：

- 普攻
- 重击
- 技能
- 投射体
- AOE
- 多段攻击
- 持续伤害
- 玩家与 AI 两侧的正式攻击来源

也就是说，接下来的工作重点不是“技能自己怎么打出去”，而是：

- **所有攻击命中之后，怎样统一进入战斗系统主链**

正式主链口径应继续收束为：

1. 各攻击实现负责自己的命中采集
2. 命中采集结果统一回送战斗系统
3. 战斗系统统一决定无敌、格挡、弹反、伤害、韧性、体力、消息、反馈
4. UI 与表现层只订阅统一结果，不自行猜结算

### 2. 战斗系统的资源语义已经拍板

当前正式定义如下：

- `Stamina` 是**韧性条**
- `Vigor` 是**体力条**

#### 2.1 韧性条

- 韧性条会在**任何受击**时扣除
- 无论是否格挡，只要受击就会扣韧性
- 格挡成功时仍扣韧性，但扣得更少
- 韧性条清空后，角色进入**破韧状态**
- 破韧期间角色**无法移动，也无法做任何动作**
- 破韧持续一段时间后，韧性条**直接回满**

正式边界：

- 这套韧性条**不做成只狼那种呼吸式持续对抗条**
- 韧性条是被攻击驱动的正式战斗资源，不是纯 UI 观测值

#### 2.2 体力条

- 体力条用于奔跑、翻滚、格挡等动作消耗
- 体力条会缓慢恢复
- 当前翻滚还未正式接入体力消耗，但后续应补齐，不再长期留空

### 3. 防御优先级与防御结果已经拍板

命中进入战斗系统后，防御优先级正式按下面这条链处理：

1. 先判定是否命中无敌帧
2. 再判定是否命中弹反窗口
3. 再判定是否命中格挡窗口
4. 最后才进入正常受击与正常伤害结算

这条优先级的意义是：

- 无敌帧成立时，后续不应再落入格挡或普通受击
- 弹反成立时，后续不应再退化成普通格挡
- 格挡成立时，后续不应再按普通受击处理

#### 3.1 无敌帧

翻滚无敌帧的正式口径已经确定为：

- 成立时**直接视为没打到**
- 不掉血
- 不跳字
- 但统一战斗上下文里仍然要留下“命中被无敌帧拦截”的真相，供日志、消息与后续表现层复用

#### 3.2 格挡

格挡第一版必须支持：

- 完全抵消
- 部分减伤

同时格挡不是纯标签成立，而是正式会影响：

- 伤害结果
- 韧性条扣减结果
- 体力条消耗
- 防御反馈

当前已经明确：

- `Stamina` 与 `Vigor` 都会一定程度参与格挡消耗
- 但具体比例与公式可以后续继续细化，不必在第一版把所有参数一步做死

并且：

- **完全格挡不跳提示字**

#### 3.3 弹反

弹反目标参考《只狼》那种“强交互”方向，但第一版正式结果已经拍板：

- 弹反成功会**大幅扣除攻击方韧性条**
- 在攻击方还没破韧前，弹反成功也必须：
  - 打断攻击
  - 让攻击方进入明显的被弹反反馈
- 一旦韧性条被打空，攻击方进入正式破韧状态

所以弹反不是“只播个特效”，而是正式接进：

- 攻击打断
- 韧性资源变化
- 受击反馈
- 消息层
- `GameplayCue`

### 4. 多段命中与持续命中不再允许一刀切窄处理

当前已经明确，后续不能继续用“同一次攻击永远只命中一次”的窄逻辑覆盖整套战斗系统。

第一版通用命中策略至少应支持：

1. 单次命中
   - 一次攻击激活期间，同目标只结算一次
2. 分段命中
   - 一招里有多个独立命中窗，每个命中窗各自允许对同目标结算一次
3. 间隔重复命中
   - 同目标可以反复命中，但必须满足最小时间间隔
4. 周期持续命中
   - 目标停留在区域内时，按固定周期重复结算

这一层应做成统一战斗语义，而不是：

- 普攻一套
- 技能一套
- 投射体一套
- AOE 一套

否则后面翻滚、格挡、弹反与提示字都很容易继续出现重复结算或重复反馈问题。

### 5. 统一攻击来源字段要克制，但必须够用

第一版不要无上限地扩来源字段，但至少要保证下面这组最小集成立：

- `AttackTag`
- `SkillTag`（有技能来源时再带）
- `WeaponTag`（有武器来源时再带）

选择这组最小集的原因是：

- 它已经够支撑“这次到底是什么攻击打中的”
- 又不会在第一版就把 Context 过度膨胀

同理，战斗上下文第一版应优先承载那些真正影响结算解释权的字段，例如：

- `Critical`
- `Blocked`
- `Parried`
- `HitInvulnerability`
- `HitResult`
- `DamageType`

### 6. 伤害类型可以进入统一主链，但不应抢走命中主问题

当前已经拍板，伤害类型后续可以正式纳入上下文与结算链。

但顺序上仍然要坚持：

1. 先统一攻击来源与命中真相
2. 再让伤害类型成为这条主链里的一个正式字段

不要一上来因为想做很多伤害类型，就把“谁打中了谁、为什么最终没掉血、为什么被格挡/被无敌/被弹反”这些更基础的真相层先做乱。

### 7. 敌我关系与友伤现在先留正式收束点

当前单人 PVE 测试阶段，不把友伤规则作为第一版主目标。

但这不代表可以完全不留边界。

正式口径应是：

- 当前阶段先以单人 PVE 验证战斗主链
- 但命中的最终裁决层必须留有**统一敌我/阵营判定收束点**

这样后续真正接玩家、敌人、友军、阵营关系时，不会严重冲击现有战斗系统结构。

### 8. UI、消息层与反馈层的边界已经拍板

这条必须作为硬规则保留：

- **UI 只订阅消息，不自己猜结算**

也就是说：

- UI 不自己判断“是不是暴击”
- UI 不自己判断“是不是格挡”
- UI 不自己判断“是不是无敌”

这些真相都必须由统一战斗主链先得出，再广播给 UI 和表现层。

原因不是只为了性能，而是为了：

- 服务端与客户端口径一致
- 普攻、技能、投射体、AOE 不再各自维护一套猜测逻辑
- 提示字、真实掉血、受击反馈之间不再互相打架

#### 8.1 提示字第一版边界

消息化之后，第一版至少应支持区分：

- 普通伤害
- 暴击
- 弹反
- 免疫 / miss 语义
- 受击反馈相关上下文

但有两个已经拍板的特殊边界：

- **完全格挡不跳字**
- **无敌帧命中失败不跳字**

这两类“不显示”是正式结果，不是漏做。

#### 8.2 反馈层第一版的最低目标

第一版不是封包式大而全方案，而是最小闭环方案。

但“最小闭环”不等于框架缺胳膊少腿。

第一版至少必须形成这条完整结果链：

1. 命中真相正确
2. 伤害 / 无敌 / 格挡 / 弹反结果正确
3. 消息广播正确
4. `GameplayCue` / 反馈层能吃到结果
5. UI 与表现层只观察，不二次发明真相

最低反馈要求包括：

- 正常受击时有基础受击反馈
- 格挡成功时有基础防御反馈
- 弹反成功时攻击方会被中断并有明显被弹反反馈

### 9. 后续实现顺序已经正式拍板

后续继续推进时，推荐顺序已经明确为：

1. 先统一所有攻击命中的 EffectSpec / EffectContext 数据语义
2. 再补上下文里真正影响解释权的字段
3. 再统一多段命中、重复命中、持续命中的正式策略
4. 再让 `AOHealthAttributeSet` 成为正式伤害广播总入口
5. 再补翻滚无敌帧正式结算
6. 再补格挡正式结算
7. 再补弹反正式结算
8. 最后把提示字、受击反馈、防御反馈、`GameplayCue` 与消息层完整接起来

这个顺序背后的原则不变：

- **先收干净战斗真相层，再做表现层**

如果下一次新会话继续做这一块，不应该再从“技能怎么设计”或者“某个攻击怎么先临时放出来”开始想，而应该从：

- **所有攻击命中之后，战斗真相怎么统一**

这个问题直接推进。
