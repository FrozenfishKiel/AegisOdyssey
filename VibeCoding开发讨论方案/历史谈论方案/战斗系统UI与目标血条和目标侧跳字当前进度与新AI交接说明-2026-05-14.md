## 1. 这份文档的用途

这份文档不是旧方案补丁，也不是再讲一遍抽象理念。

它现在只承担四件事：

1. 记录本轮战斗 UI / MVVM / 目标血条 / 目标侧跳字的真实落地结果。
2. 记录这轮工作里已经踩过并解决掉的问题，避免下一个 AI 再走回头路。
3. 明确当前各组件职责边界，尤其是 `Observer`、`TargetHealthBarComponent`、`CombatFloatingTextComponent` 三者的关系。
4. 给下一个 AI 一份小型知识库和阅读顺序，确保一上来先理解项目边界，再继续做表现层。

这份文档的核心目标只有一个：

**让下一个 AI 不要再把血条、观察逻辑、跳字逻辑、战斗结算广播逻辑重新混成一坨。**

## 2. 这轮工作最终确认下来的结构

### 2.1 当前战斗 UI 主链

当前稳定主链如下：

1. 战斗结算层产出统一 `FAOCombatResultMessage`
2. `UAOCombatMessageSubsystem` 在本地世界内广播
3. `UAOHUDViewModelComponent` 订阅消息并构建 `FAOCombatFeedbackViewData`
4. `UMVVM_HUD` / `UMVVM_CombatFeedbackFeed` 接收本地已路由的反馈数据
5. 表现层只消费 `ViewData` 或 `Feed`
6. 目标血条和目标侧跳字都挂在目标对象身上，但不是同一种组件

一句话概括就是：

**战斗系统先产出统一真相，HUD 桥接层把真相翻译成本地表现数据，表现层只消费这份数据，不再自己回头猜。**

### 2.2 当前目标侧 UI 组件职责拆分

这次最关键的结构性结论就是这一条。

#### `UAOLocalTargetHealthBarObserverComponent`

它只负责：

- 站在本地玩家视角，记录哪些目标进入了“值得显示血条”的观察列表
- 根据距离、战斗状态、最近交战时间决定这个目标血条该不该显示
- 对目标身上的 `UAOTargetHealthBarComponent` 下发 `SetRequestedVisible(true/false)`

它不负责：

- 目标血量真相
- 伤害跳字
- 原始战斗消息解释
- HUD 表现

一句话：

**它是本地玩家视角下的“目标血条观察资格管理器”。**

#### `UAOTargetHealthBarComponent`

它只负责：

- 目标自己的生命值真相同步
- 自己的 `UMVVMTargetHealthBar`
- 自己的头顶血条 `WidgetComponent`
- 血条显隐执行

它不负责：

- 伤害跳字
- 命中点跳字锚点
- 多个独立跳字实例管理

一句话：

**它是目标头顶血条组件，不是目标侧所有表现的总管。**

#### `UAOCombatFloatingTextComponent`

这是本轮新拆出来的目标侧独立组件。

它只负责：

- 接收已经完成本地路由的 `FAOCombatFeedbackViewData`
- 决定这条反馈的世界锚点位置
- 生成或复用跳字 `WidgetComponent`
- 把跳字数据交给跳字 Widget 蓝图表现

它不负责：

- 目标血条显隐
- 目标血量真相
- 本地观察资格判定

一句话：

**它是目标身上的世界跳字组件。**

## 3. 这轮工作里解决掉的关键问题

### 3.1 CombatMessage dynamic multicast 引发 Script VM 复制链和栈溢出

之前 `UAOCombatMessageSubsystem::OnCombatResultMessage` 走的是 dynamic multicast。

这条链会把 `FAOCombatResultMessage` 送进 Script VM 参数复制路径，真实触发过：

- `UScriptStruct::CopyScriptStruct`
- `FProperty::CopyCompleteValueToScriptVM_InContainer`
- `GetDestructionSentinelStackTls().Add(&DestructionSentinel)`
- `EXCEPTION_STACK_OVERFLOW`

这不是小 bug，而是机制选错了。

当前修复结果：

- `OnCombatResultMessage` 已改成 **native multicast**
- 订阅统一走 `AddUObject`
- 不再让这类战斗结果结构走蓝图 dynamic multicast 参数复制链

### 3.2 客户端回放战斗消息时形成递归广播回环

之前服务端广播后通过 Client RPC 发给客户端，客户端收到后又重新走源广播函数，结果形成回环。

当前修复结果：

- `BroadcastCombatResult(...)`：源入口，负责本地广播和服务端定向转发
- `BroadcastCombatResultLocal(...)`：只在本地广播一次，不做任何网络转发
- 客户端 RPC 收到后只调用 `BroadcastCombatResultLocal(...)`

这样切断了递归。

### 3.3 `Gameplay.AbilityInputBlocked` 标签不是临时字符串，而是应该走已注册标签

中间排查过一次错误来源：

- 不是“属性变化收不到”
- 不是“简单逻辑判断错”
- 本质问题是这里不该继续用 `FGameplayTag::RequestGameplayTag(TEXT("Gameplay.AbilityInputBlocked"))` 这种临时请求式写法

当前修复方向已经落地：

- `RefreshLocalCombatStateFromSource()` 里改成使用已定义的 `TAG_Gameplay_AbilityInputBlocked`

也就是说，**这个标签应该作为项目标签体系的一部分使用，而不是运行时现拼。**

### 3.4 `UMVVM_HUD::ApplyCombatFeedbackViewData()` 一度出现递归和栈溢出假象

中间排查时会看到：

- `EnsureChildViewModels()`
- `CombatFeedbackFeedViewModel->ApplyCombatFeedbackViewData(...)`
- `LatestCombatFeedback = FeedbackViewData`
- `GetOwnedGameplayTags(...)`

这些位置不断断。

最终定位后确认，根病不是某一行赋值本身，而是：

- 旧 dynamic multicast + Script VM 复制链
- 客户端消息回环
- 旧链条没有完全切断导致的多层重入

这次修完后，这类问题已经从根上处理了，而不是只在栈顶止血。

## 4. 这轮工作里最重要的设计纠偏

### 4.1 不能把所有目标侧 UI 都塞进 `UAOTargetHealthBarComponent`

一开始容易产生一个错觉：

- 既然血条挂在目标身上
- 那伤害跳字也直接塞进血条组件是不是最省事

后来已经明确证明这条路不对。

原因很简单：

- 头顶血条只有一个固定锚点
- 伤害跳字要支持命中点、身体中心、多个独立数字同时存在
- 一个固定头顶 `WidgetComponent` 根本不适合承载多个瞬时跳字实例

所以最终结论是：

**目标侧表现要挂在目标身上，但不同职责必须拆成不同组件类型。**

### 4.2 不能靠“挂多个 `UAOTargetHealthBarComponent`”解决不同表现

中间已经把这个问题讲透了：

如果一个目标上挂多个同类型 `UAOTargetHealthBarComponent`，那观察组件根本没法靠类型判断谁是血条、谁是跳字。

这就是类型语义失效。

所以这次最终结构坚持的是：

- `UAOTargetHealthBarComponent` 只表示头顶血条组件
- `UAOCombatFloatingTextComponent` 只表示目标侧跳字组件

**一个类型只表示一种职责。**

## 6. 当前还没做完、下一步应该做什么

### 6.1 跳字蓝图表现还没完成

这次完成的是 **C++ 架构和接线**，不是最终视觉表现。

也就是说：

- 目标侧跳字组件已经有了
- 跳字数据已经能送到独立 Widget
- 但具体的蓝图视觉表现、动画、字号、颜色、飞行轨迹、生命周期，仍然要继续做

下一个 AI 如果继续做，重点应该落在：

- 跳字 Widget 蓝图实现 `OnWorldCombatFeedbackReceived`
- 根据 `FeedbackViewData.FloatingTextType` 区分普通伤害 / 暴击 / 破韧 / 弹反等样式
- 根据 `RecommendedText` 或 `HealthDamage` 显示文本
- 根据 `WorldAnchorLocation` 处理出生位置和动画

### 6.2 目标对象上要确保真的挂了 `UAOCombatFloatingTextComponent`

当前 C++ 只负责：

- 找目标上的 `UAOCombatFloatingTextComponent`
- 找到就调用

所以要继续做时必须确认：

- 敌人 Blueprint / 角色 Blueprint 是否真的加上了该组件

否则逻辑路径是对的，但不会有显示。

### 6.3 当前池化实现是第一版，后续可以继续精修

现在 `UAOCombatFloatingTextComponent` 里的池化是很轻量的一版：

- 一个数组维护活跃 `WidgetComponent`
- 超过上限后复用最早一个

这版足够继续做表现验证，但不算最终完美版。

后续如果要继续优化，可以看：

- 是否需要更明确的空闲池 / 活跃池
- 是否需要蓝图回调通知组件“该实例动画结束，可归还”
- 是否需要更稳定的随机偏移策略、分散策略

这属于第二阶段，不是当前阻塞项。

## 7. 当前必须记住的测试结论和坑点

### 7.1 这次修的是根因，不是临时止血

下一个 AI 不要再怀疑“是不是只是在某个函数上绕过报错”。

这次修的是以下根因：

- dynamic multicast 导致 `FAOCombatResultMessage` 进入 Script VM 复制链
- 客户端战斗消息广播回环
- 标签使用方式不规范
- 目标侧表现组件职责不清

这几件事都已经结构性纠偏。

### 7.2 不要再把 `TargetHealthBarComponent` 当成“目标侧表现总入口”

这条很重要。

当前项目边界已经收紧为：

- 头顶血条是一类目标侧表现
- 伤害跳字是另一类目标侧表现

两者同属“目标侧表现”，但不是同一个组件。

### 7.3 不要再让 `Observer` 处理跳字

`Observer` 现在只剩“谁该显示血条”的权力。

如果后续有人再让它去：

- 转发跳字
- 解释伤害
- 驱动目标侧视觉表现

那就是又越界了。

## 8. 小型知识库：下一个 AI 开工前必须先理解什么

这一节不是让你去读全项目，而是读“这次问题为什么会出现”的知识点。

### 8.1 必须理解的项目内知识点

1. **战斗结算真相和 HUD 表现数据不是一回事**
   - `FAOCombatResultMessage` 是统一战斗真相
   - `FAOCombatFeedbackViewData` 是本地玩家视角下的表现数据

2. **MVVM 边界**
   - UI 不再自己从原始战斗 message 回推本地语义
   - UI / 蓝图应该消费 `ViewModel` 或 `Feed`

3. **目标侧表现挂在对象身上，不挂在 MainUI 身上**
   - 但“挂在对象身上”不等于“都塞进一个组件”

4. **一个组件类型只能表达一种稳定职责**
   - 不要靠“同类型组件挂多个”去区分语义

5. **网络同步链最怕回环和多层重复解释**
   - 当前 combat message 的网络回放链已经固定，不要再随便改回去
