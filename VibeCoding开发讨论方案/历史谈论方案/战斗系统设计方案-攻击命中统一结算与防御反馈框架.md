# 战斗系统设计方案：攻击命中统一结算与防御反馈框架

更新时间：2026-05-10

---

## 一、这份方案解决什么问题

当前项目已经不再缺“能不能打到人”的零散实现。

现在真正要解决的是：

- 普攻、重击、技能、投射体、AOE、多段命中、持续伤害，怎样统一进入**同一条战斗系统主链**
- 玩家与 AI，怎样复用**同一套命中解释权**
- 翻滚无敌帧、格挡、弹反，怎样在命中后进入**正式可结算**的防御语义
- 韧性、体力、伤害、暴击、提示字、受击反馈，怎样从“局部能跑”收口到**可信、可扩展、可联机同步**的正式结构

这份方案不是旧技能方案的附录，也不是只给技能系统用的补丁说明。

这是一份新的、独立的**战斗系统设计方案**。

---

## 二、当前阶段的硬规则

后续实现默认遵守以下规则：

1. 本次要一口气覆盖整套“攻击命中”主链。
2. 覆盖对象同时包含玩家与 AI。
3. 覆盖范围默认包含：
   - 普攻
   - 重击
   - 技能
   - 投射体
   - AOE
   - 多段反复命中
   - 持续伤害
4. 命中采集可以分散在不同攻击实现里，但**命中结算必须统一回战斗系统**。
5. UI 只能订阅战斗结果消息，**不能自己猜测结算真相**。
6. 服务端裁决命中与结算，客户端只消费结果做表现。
7. 第一版按“最小闭环”落地，但框架必须完整，不能靠临时硬写把后续路线堵死。
8. 不区分命中部位。
9. 友伤本轮暂不启用，但必须预留**统一敌我判定收口点**，保证未来接入时不推翻现有主链。

---

## 三、核心术语与统一语义

### 1. 攻击命中

指一次攻击实现已经确认：

- 谁发起了攻击
- 谁被命中
- 在什么位置命中
- 属于哪一种攻击
- 当前命中属于哪种命中策略

命中本身不等于已经造成最终伤害。

### 2. 命中采集层

命中采集层负责：

- Trace / Overlap / Projectile Hit / Runtime AOE 命中检测
- 生成命中目标列表
- 根据命中策略控制重复命中
- 把命中结果送入战斗系统结算入口

命中采集层不负责：

- 自己独立决定暴击
- 自己独立决定格挡
- 自己独立决定无敌帧
- 自己独立决定最终掉血
- 自己独立决定 UI 提示字

### 3. 战斗结算层

战斗结算层负责：

- 攻击来源解释
- 敌我关系过滤
- 防御窗口判定
- 伤害、体力、韧性、暴击等数值结算
- 破韧、受击、弹反、格挡等结果产出
- 统一消息广播
- 表现层与 UI 的可信数据来源

### 4. Stamina 与 Vigor 的正式定义

#### `Stamina`

`Stamina` 在本项目中定义为**韧性条**。

语义如下：

- 角色在受击时会扣除韧性
- 无论是否格挡，只要受击就会扣韧性
- 格挡成功时，韧性扣除会更少
- `Stamina` 清空后，角色进入**破韧状态**
- 破韧期间角色无法移动，也无法做任何动作
- 破韧持续一段时间后，韧性条直接回满
- 本项目不采用《只狼》那种持续呼吸式架势条恢复方案

#### `Vigor`

`Vigor` 在本项目中定义为**体力条**。

语义如下：

- 角色执行动作时消耗体力
- 典型消耗来源包括：
  - 奔跑
  - 翻滚
  - 格挡
  - 其他后续会接入的动作行为
- `Vigor` 会缓慢恢复
- 当前翻滚尚未正式接入体力消耗，本方案要求后续补齐

## 四、统一战斗主链

后续所有攻击命中，统一走下面这条主链：

1. 攻击实现完成命中采集
2. 构建统一攻击上下文
3. 进入统一敌我关系判定点
4. 进入统一防御语义判定点
5. 进入统一伤害 / 韧性 / 体力结算点
6. 产出统一战斗结果
7. 广播统一消息
8. GameplayCue / 动作反馈 / UI 提示字只订阅结果，不再各自推测

这条主链适用于：

- 普攻
- 重击
- 技能命中
- 投射体命中
- AOE 波次命中
- 周期伤害命中
- 玩家对 AI
- AI 对玩家

---

## 五、统一攻击来源模型

本轮遵守“先少做，但把必要字段做对”的原则。

统一攻击来源最小字段定为：

- `AttackTag`
- `SkillTag`
- `WeaponTag`
- `DamageTypeTags`

约束如下：

### 1. `AttackTag`

必须有。

它是当前这次命中的**统一攻击身份**，例如：

- 轻击第一段
- 重击蓄力段
- 火球术命中
- 火山喷发波次

后续命中策略、日志、消息、反馈、调试都优先以它作为统一主键。

### 2. `SkillTag`

有技能来源时才带。

没有技能来源的普攻、投射体、环境类命中不强行补。

### 3. `WeaponTag`

有武器来源时才带。

### 4. `DamageTypeTags`

本轮纳入统一上下文，但**不在第一阶段强行扩成完整抗性系统**。

本轮目标是先把伤害类型标准化带入主链，保证未来做：

- 物理
- 火焰
- 爆炸
- 元素抗性
- 类型相关反馈

时不需要回头改攻击来源结构。

## 六、统一上下文模型

本轮统一战斗上下文至少要具备以下字段：

- `bIsCritical`
- `bWasBlocked`
- `bWasParried`
- `bHitInvulnerability`
- `AttackTag`
- `SkillTag`
- `WeaponTag`
- `DamageTypeTags`
- `HitResult`

说明如下：

### 1. 这些字段属于“战斗真相”

它们不是 UI 字段，也不是局部调试字段。

它们代表的是：

- 这次命中最后被解释成了什么
- 为什么会掉血或不掉血
- 为什么会破韧或不破韧
- 为什么会显示反馈或不显示反馈

### 2. 这些字段必须从统一上下文产出

后续不允许出现以下情况：

- 飘字层自己猜“是不是暴击”
- 某个技能 runtime 自己猜“是不是格挡”
- 投射体自己猜“是不是无敌”

所有这些都必须先回到统一上下文，再由消息层和表现层读取。

---

## 七、敌我关系与最终判定收口点

虽然本轮暂时不做友伤，但必须从一开始就保留统一收口点。

正式要求如下：

### 1. 所有命中在正式结算前，都要先经过统一敌我关系判定

这一步是未来接入以下内容的唯一自然落点：

- PVE
- PVP
- 队伍关系
- 友伤开关
- 中立单位
- 召唤物归属

### 2. 本轮默认行为

本轮单人 PVE 默认允许：

- 玩家命中敌人
- 敌人命中玩家

本轮暂不正式开启：

- 玩家打玩家
- AI 打 AI
- 友军互伤

### 3. 重要约束

即使本轮还没做完整阵营系统，也不能把“敌我判断”散写到每个攻击实现里。

必须留一个统一最终判定位置做收束。

---

## 八、防御语义与命中处理顺序

这里的“优先级”指的是：

**当一次命中同时可能碰到多个防御条件时，系统按什么顺序解释这次命中。**

本方案默认命中处理顺序为：

1. 敌我关系过滤
2. 方向与角度过滤
3. 无敌帧判定
4. 弹反窗口判定
5. 格挡窗口判定
6. 正常受击结算

这条顺序的意义是：

- 先判断这次命中是否本来就不该成立
- 再判断是否被翻滚无敌帧直接规避
- 再判断是否被更高优先级的弹反接管
- 最后再落到普通格挡与正常受击

---

## 九、翻滚无敌帧

翻滚无敌帧的正式语义已经确定：

- **直接视为没打到**

这意味着：

- 不扣血
- 不扣韧性
- 不扣体力
- 不跳字
- 不进入普通受击链

但可以保留必要的局部表现反馈，例如：

- 闪避成功相关效果
- 局部声音或 Cue

后续实现上应通过以下结构收口：

- 动画窗口或战斗窗口标签定义无敌帧
- 防御判定阶段统一检查
- 一旦成立，直接产出 `bHitInvulnerability = true`

---

## 十、格挡

格挡本轮的正式目标不是“播放一个格挡动作”，而是成为**能改写命中结果**的战斗语义。

### 1. 格挡成立条件

格挡成立至少受以下因素影响：

- 是否处于格挡窗口
- 是否满足方向/角度要求
- 是否不是被更高优先级的无敌帧或弹反接管

### 2. 格挡结果

格挡需要支持两种正式结果：

- 完全格挡
- 部分格挡

### 3. 完全格挡

完全格挡时：

- 不掉血
- 不跳提示字
- 扣除体力
- 扣除较少的韧性
- 播放格挡反馈

### 4. 部分格挡

部分格挡时：

- 伤害减免后再掉血
- 扣除体力
- 扣除较少的韧性
- 播放格挡反馈
- 是否显示提示字由结果类型决定，但本方案不要求一定跳专门数字

### 5. 格挡资源消耗

格挡一定程度同时消耗：

- `Vigor`
- `Stamina`

但两者职责不同：

- `Vigor` 代表动作资源消耗
- `Stamina` 代表受击后韧性压力

### 6. 方向与角度

格挡需要做角度判定。

第一版先给默认角度，并做成可配置参数，不在代码里写死。

---

## 十一、弹反

弹反目标参考《只狼》式交互，但不直接照搬其呼吸架势系统。

### 1. 弹反成立条件

弹反成立至少受以下因素影响：

- 是否处于弹反窗口
- 是否满足方向/角度要求
- 是否命中未被无敌帧规避

### 2. 弹反成立后的第一版正式效果

第一版弹反成功后需要同时具备以下结果：

- 本次命中不进入普通受击结算
- 攻击者被打断当前攻击
- 攻击者播放被弹反反馈
- 大幅扣除攻击者 `Stamina`
- 通过消息和 GameplayCue 触发明确反馈

### 3. 与破韧的关系

弹反成功会大幅扣除对方韧性条。

在攻击者被破韧前：

- 弹反成功只会打断其攻击
- 并触发被弹反反应

当其韧性被正式打空后：

- 进入破韧状态

这保证弹反在第一版就具备明确交互性，而不是只有一个标签结果。

---

## 十二、破韧状态

本轮需要正式把破韧纳入战斗系统主链。

### 1. 破韧触发条件

`Stamina` 归零时进入破韧状态。

### 2. 破韧效果

破韧状态下角色：

- 无法移动
- 无法做任何动作
- 持续一段时间
- 结束后韧性条直接回满

### 3. 破韧来源

破韧可能来自：

- 正常受击累积
- 格挡中承受攻击
- 弹反成功后被大幅削减韧性

---

## 十三、多段命中与持续命中的统一策略

当前普攻命中实现已经暴露出“同目标只处理一次”过窄的问题。

本轮要把命中策略从固定逻辑升级为通用策略。

第一版统一支持以下四类：

### 1. 单次命中

一次攻击激活期间，同一目标只结算一次。

适合：

- 单段轻击
- 单次爆发技能

### 2. 分段命中

一招里有多个独立命中窗口，每个窗口对同一目标都可各结算一次。

适合：

- 连段技能
- 多段刀光
- 具有多个明确命中窗的攻击

### 3. 间隔重复命中

同一目标可以被重复命中，但必须满足最小时间间隔。

适合：

- 连续擦伤型判定
- 高速多次打击

### 4. 周期持续命中

目标停留在区域或持续接触期间，按固定周期反复结算。

适合：

- 持续燃烧区域
- AOE 持续伤害
- 周期性波次区域

### 5. 设计要求

这四类策略必须对以下攻击统一可用：

- 普攻
- 重击
- 技能 runtime
- 投射体
- AOE

不能再让不同攻击各自偷偷维护一套重复命中规则。

---

## 十四、伤害、韧性、体力的统一结算目标

本轮统一结算层需要同时解释三条结果线：

### 1. 生命伤害

决定：

- 最终是否掉血
- 掉多少血
- 是否暴击

### 2. 韧性伤害

决定：

- 本次命中对 `Stamina` 造成多少压力
- 是否进入破韧

规则明确为：

- 只要受击就会扣韧性
- 格挡时韧性扣得更少
- 无敌帧命中不成立时，不扣韧性
- 弹反成功时，攻击者大幅掉韧性

### 3. 体力消耗

决定：

- 格挡动作是否消耗 `Vigor`
- 翻滚是否消耗 `Vigor`
- 奔跑等动作是否继续复用现有体力链

这三条结果线必须来自同一个正式结算阶段，而不是散落在动作层、技能层、UI 层分别维护。

---

## 十五、UI、消息、GameplayCue 的职责边界

### 1. UI 只订阅消息，不自己猜

这是硬规则。

正确做法是：

- 战斗系统先得出可信结果
- 消息层广播结果
- UI 只根据结果显示

不允许：

- UI 自己根据标签猜是不是暴击
- UI 自己根据翻滚状态猜是不是 MISS
- UI 自己根据格挡状态猜是不是应该不掉血

### 2. 消息层负责什么

消息层负责把战斗真相广播给：

- UI
- ViewModel
- 表现层
- 需要订阅结算结果的系统

### 3. GameplayCue 负责什么

GameplayCue 负责：

- 特效
- 音效
- 局部战斗反馈

它不负责改写伤害真相。

### 4. 动作反馈负责什么

动作反馈负责：

- 正常受击反馈
- 格挡反馈
- 弹反反馈
- 破韧反馈

动作反馈同样不负责改写伤害真相。

---

## 十六、提示字规则

第一版结果类型至少需要支持：

- 普通伤害
- 暴击
- 格挡
- 弹反
- 无敌 / 闪避成功
- 免疫

但显示规则已经明确：

### 1. 完全格挡

- 不跳字

### 2. 无敌帧规避

- 不跳字

### 3. 其他类型

可根据统一消息结果决定是否显示：

- 普通伤害数字
- 暴击伤害数字
- 弹反提示
- 免疫提示

重点不是“每种都必须强行显示”，而是**显示权必须来自统一消息结果**。

---

## 十七、受击反馈第一版要求

第一版不追求一开始把全部高级演出做满，但必须做成可扩展的最小闭环。

最低要求如下：

1. 正常受击时，目标有基础受击反馈。
2. 格挡成功时，防守方有明确格挡反馈。
3. 弹反成功时，攻击方被中断，并有明显被弹反反馈。
4. 破韧时，目标进入明确的失能状态。
5. 这些反馈统一通过“结果消息 + GameplayCue + 基础动作反应”接出。

---

## 十八、推荐实现顺序

这是当前最合适的正式落地顺序。

在项目推进层面，建议把下面这些步骤再收束成 **4 个阶段**，避免后续开发时一边按步骤说、一边按阶段说，导致协作口径不统一。

### 阶段一：真相层收口

这一阶段只解决一个核心问题：

- **攻击命中之后，战斗系统到底凭什么解释这次命中**

阶段一包含：

- 统一攻击来源字段
- 统一战斗上下文字段
- 统一伤害类型入口
- 统一敌我关系收口点
- 统一伤害 / 韧性 / 体力结算入口

阶段一不追求的内容：

- 不先做完整防御反馈
- 不先做完整提示字
- 不先做完整 GameplayCue 表现

阶段一完成标准：

- 普攻、重击、技能、投射体、AOE 命中后，都能进入统一上下文与统一结算入口
- 玩家和 AI 走的是同一条结算主链
- UI 和表现层不需要自己猜测命中结果

### 阶段二：命中策略层统一

这一阶段解决的是：

- **不同攻击怎样以统一规则处理单次、多段、重复、持续命中**

阶段二包含：

- 单次命中
- 分段命中
- 间隔重复命中
- 周期持续命中

阶段二完成标准：

- 现有普攻“同目标只处理一次”的过窄逻辑被替换为可配置策略
- 技能 runtime、投射体、AOE 与普攻共享同一套命中策略模型
- 新增攻击不再需要临时手搓一套重复命中规则

### 阶段三：防御结算层

这一阶段解决的是：

- **命中成立后，防御、弹反、无敌帧、破韧怎样正式改写战斗结果**

阶段三包含：

- 翻滚无敌帧
- 格挡
- 弹反
- 破韧
- 体力消耗
- 韧性扣减
- 防御方向与角度判定

阶段三完成标准：

- 无敌帧、格挡、弹反都不再只是动作语义，而是正式进入结算主链
- 破韧状态成为统一可判定、可广播、可反馈的结果
- 防御结果能够真实影响掉血、韧性、体力、动作中断与反馈

### 阶段四：反馈与表现层

这一阶段解决的是：

- **战斗结果怎样被可信地显示、播放、反馈，而不是靠局部猜测**

阶段四包含：

- 消息广播正式收口
- GameplayCue 接入
- 受击反馈
- 格挡反馈
- 弹反反馈
- 伤害数字
- 暴击提示
- 其他战斗提示字

阶段四完成标准：

- UI 只订阅消息，不再推测结果
- 受击、格挡、弹反、暴击等反馈都来自统一结果层
- 表现层与结算层职责分离，但联动闭环完整

### 第 1 步：统一攻击来源与战斗上下文

先补齐：

- `AttackTag`
- `SkillTag`
- `WeaponTag`
- `DamageTypeTags`
- `Blocked / Parried / HitInvulnerability / Critical / HitResult`

目标是先把“命中解释权”收口。

### 第 2 步：统一命中策略

把普攻、重击、技能、投射体、AOE 的命中策略统一成四类：

- 单次命中
- 分段命中
- 间隔重复命中
- 周期持续命中

目标是先解决“当前命中逻辑过窄”的结构问题。

### 第 3 步：统一敌我判定收口点

即使本轮先不做完整友伤，也必须把最终判定位置先立住。

### 第 4 步：统一伤害 / 韧性 / 体力结算入口

让所有攻击都进入同一条：

- 生命伤害
- 韧性伤害
- 体力消耗

结算主链。

### 第 5 步：翻滚无敌帧正式收口

先把“直接视为没打到”的语义做成正式结算规则。

### 第 6 步：格挡正式收口

把格挡从“动作 + 标签”推进为：

- 完全格挡
- 部分格挡
- 体力消耗
- 韧性较少扣除

的正式战斗结算。

### 第 7 步：弹反正式收口

把弹反推进为：

- 打断攻击
- 大幅削韧
- 被弹反反馈
- 可能触发破韧

的正式链路。

### 第 8 步：消息系统正式打开

让伤害、暴击、格挡、弹反、无敌等结果都通过统一消息广播。

### 第 9 步：GameplayCue、动作反馈、提示字接结果层

最后再接：

- 受击反馈
- 格挡反馈
- 弹反馈
- 暴击反馈
- 伤害数字

这样不会反过来绑架主链设计。

## 二十、绝对不要再走的歪路

### 1. 不要让命中实现自己偷着结算完整战斗真相

命中实现只负责：

- 检测命中
- 管理命中窗口
- 管理命中策略
- 把结果送回统一战斗系统

不要让它们继续自己硬算：

- 暴击
- 格挡
- 无敌
- 破韧
- 提示字

### 2. 不要让 UI 自己推测战斗结果

UI 只能读消息，不能解释真相。

### 3. 不要把表现层和数值层混成一层

必须尽量分清：

- 数值真相
- 联机真相
- 表现真相
- UI 真相

### 4. 不要把未来友伤/阵营关系散写在各个攻击实现里

必须保留统一敌我判定收口点。
