# 技能系统输入映射隐性Bug排查笔记：IMC软引用与 `RegisterWithSettings` 误用

## 这篇笔记是干什么的

这篇笔记不是给人查代码跳转的，也不是写给“当下这次会话”看的。

它是为了以后无论什么时候重新碰到类似问题，只要翻到这篇，就能很快想起来：

1. 这类问题表面会长什么样。
2. 为什么它很容易把人带偏。
3. 真正的根因通常藏在哪一层。
4. 以后应该先查什么，再查什么。

这类坑非常值得记，因为它不是那种“变量写错了”“资源忘填了”的直观错误，而是一种 **表面像资源配置问题，实际上是运行时输入映射没有真正生效** 的隐性问题。

---

## 这次问题一开始长什么样

这次最开始看到的现象是这样的：

1. 技能槽 UI 不显示真实键位。
2. 明明已经给技能输入动作配了名字、配了按键、也配了 `Player Mappable`。
3. 但界面还是拿不到当前真实键位，最后只能显示 `None`。

更迷惑的是，当时继续往里看，会发现几件事同时成立：

1. 技能槽自己的输入语义标签是有的。
2. 这个标签也确实能反查到对应的输入动作。
3. 输入动作看起来也不是空资源。
4. 但系统还是拿不到当前映射键位。

这时候人很容易产生一种直觉：

“是不是 `Player Mappable` 没配对？”

这当然是一个合理怀疑，但这次真正的问题并不在这里。

---

## 这类问题为什么特别容易把人带偏

因为它会呈现出一种很有迷惑性的状态：

- 静态资源看起来大部分都在。
- 技能槽和输入动作之间的关系也能对上。
- 按理说只差最后一步“把当前键位显示出来”。

于是人会自然而然地把排查重点放到这些地方：

1. 输入动作是不是没配 `Player Mappable Key Settings`
2. 名字是不是填错了
3. `Setting Behavior` 是不是选错了
4. 改键系统是不是没有生效

这些方向本身不算错，但它们都默认了一个前提：

**这份输入映射上下文已经真正进入了当前玩家的输入系统。**

这次恰恰就是这个前提没有成立。

也就是说，当时看到的并不是：

“映射内容错了”

而是：

**“映射根本没有真正参与运行时输入。”**

这两个问题看起来很像，但本质完全不是一回事。

---

## 这次问题的本质到底是什么

一句话概括：

**技能槽不是拿不到键位信息，而是当前那份输入映射上下文根本没有稳定进入本地玩家的运行时输入系统。**

这就是整件事最核心的本质。

换一种更容易记住的话来说：

> 资源配上了，不代表运行时真的生效了。  
> 输入动作存在了，也不代表当前玩家真的在用这份映射。

这次真正的问题有两个，而且它们刚好会叠在一起，把现象变得特别像“资源配置错了”。

---

## 第一个根因：输入映射上下文是软引用，但运行时没有把它稳定加载出来

你可以把这件事理解成：

系统里虽然写着“这里应该用某份输入映射资源”，但这个“写着”只是一个软引用关系，不代表这个资源此刻真的已经进了内存、真的已经能拿来用了。

如果这时候代码只是“试着拿一下”，而不是“明确把它加载出来”，就会发生一种很阴的情况：

1. 编辑器里看，一切都配好了。
2. 数据资产里也能看到这份映射资源。
3. 但运行到真正初始化输入的时候，它可能根本没被解析成一份可用的运行时对象。
4. 后续自然也就不会真正加入玩家当前输入系统。

这类问题最大的迷惑点就在于：

**静态配置是对的，但运行时对象并没有真的建立起来。**

所以以后只要遇到“资源明明配了，但运行时像没配一样”的问题，一定要立刻想到：

是不是哪里拿的是软引用，但是运行时并没有显式把它变成真正可用的资源。

---

## 第二个根因：把“注册到设置系统”和“真正加入运行时输入栈”混成了一件事

这次还有一个非常值得记住的设计错误。

本来有一个配置项，它的语义应该只是：

“这份输入映射要不要参与玩家设置、改键、存档这些系统。”

这听起来是一个很正常、也很局部的配置。

但当时实际的逻辑却把它写成了：

“如果不参与设置系统，那也不加入运行时输入系统。”

这就是大问题。

因为这等于把两件层级完全不同的事绑死在一起了：

1. 要不要进入可改键系统
2. 要不要真正成为当前玩家的有效输入映射

这两个概念本来不应该互相绑架。

正常语义应该是：

- 这份输入映射是否参与可改键，是一回事
- 这份输入映射是否在当前游戏里真正生效，是另一回事

但当时的逻辑把这两者混在了一起，于是只要这个开关没开，后果就不只是“改不了键”，而是 **连技能输入本身都可能不生效，连 UI 查询都一起失效。**

这就是为什么这次会出现一种很让人困惑的现象：

- 看起来是键位显示坏了
- 但继续往下查，发现连当前真实映射都拿不到
- 再往下查，发现不是显示逻辑坏，而是更上游的运行时输入映射根本没进来

---

## 这次最有价值的经验是什么

这次最值得记住的，不是某一行代码怎么改，而是下面这条工程经验：

**在输入系统里，资源存在、映射存在、名字存在，都不等于当前玩家运行时真的在使用它。**

以后碰到类似现象，要先区分两类问题：

### 第一类：资源关系层的问题

这类问题是：

- 标签没配
- 输入动作没配
- 映射名字没填
- `Player Mappable` 配置不完整

这类问题的特点是：

“静态关系本身就不成立。”

### 第二类：运行时生效层的问题

这类问题是：

- 资源存在
- 名字存在
- 输入动作也存在
- 但当前玩家拿不到真实映射

这类问题的特点是：

“静态关系成立了，但运行时那一步没真正落地。”

这次就属于第二类。

以后只要遇到“名字都在、资源也在、但当前还是查不到键位”，就不要一头扎进配置面板死查，要优先想到：

**是不是这份输入映射根本没有真正进入当前本地玩家的输入系统。**

---

## 这类问题以后应该怎么排

为了以后少绕路，这里直接记一套最实用的排查顺序。

### 第一步：先问自己，这到底是资源没配，还是运行时没生效

如果你发现：

- 输入语义标签在
- 输入动作也能找到
- 但真实键位就是查不到

那就不要先怀疑“名字填错了”，而要先怀疑：

**运行时映射有没有真的进当前玩家。**

### 第二步：优先确认输入映射上下文是不是实际被加入了当前玩家

这是最关键的一步。

要先确认的不是“资源面板里有没有这份 IMC”，而是：

**当前这个本地玩家在运行时到底有没有真的挂上这份 IMC。**

因为只要这一步没成立，后面一切围绕键位查询、改键显示、技能槽展示的逻辑都会一起失真。

### 第三步：再区分“是否参与改键系统”和“是否参与运行时输入”

这个也非常重要。

有些配置项名字看起来像是“跟设置系统有关”，但如果实现时偷带了运行时主流程含义，就会造成巨大的误导。

所以以后看到类似开关时，一定要问一句：

“这个开关控制的到底只是设置系统，还是它还偷偷控制了运行时输入是否生效？”

只要这个边界没分清，就很容易再次踩这种坑。

### 第四步：最后才去查 `Player Mappable` 细节

只有在你确认：

- 运行时输入映射已经真的进当前玩家
- 当前玩家也确实在用这份输入动作

之后，再去查：

- `Player Mappable Key Settings`
- 映射名字
- `Setting Behavior`
- 改键设置存档

这样排查顺序才是高效的。

不然很容易在资源配置层面绕很久，最后才发现根因根本不在那。

---

## 这次问题能沉淀成什么长期记忆

这次最适合沉淀成一句长期记忆的话是：

> 当技能键位显示查不到，先别急着怀疑 `Player Mappable`，先怀疑这份输入映射上下文是不是根本没真正进当前玩家的运行时输入系统。

再展开一点，就是下面这两条：

1. 软引用资源如果不显式处理，静态上“配了”不等于运行时“真有”。
2. 只和设置系统有关的开关，不应该顺手控制运行时主流程。

这两条记住了，以后再碰到类似问题，排查速度会快很多。

---

## 最后把这次问题翻译成人话

如果以后有人问：

“为什么技能键位名字都配了，输入动作也有了，结果还是显示不出来？”

可以直接用最人话的方式解释：

> 因为这次不是最后显示那一步坏了，而是更前面的输入映射根本没有真正挂到当前玩家身上。  
> 所以后面不管是查当前真实键位，还是查可改键映射，都会一起拿不到。  
> 看起来像是显示问题，实际上是运行时输入初始化问题。

这句话，基本就把整件事说明白了。

## 本项目里的具体落点

上面说的是通用逻辑，下面把这次在 **AegisOdyssey** 项目里实际发生的问题串起来，方便以后从抽象经验直接回到项目现场。

### 这次涉及到的输入资产

本次技能键位显示链路里，直接相关的输入资产都在：

`D:\UE_Project\AO\AegisOdyssey\AegisOdyssey\Content\Games\Input`

这次重点涉及的是：

- [DA_AOInputConfig.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/DA_AOInputConfig.uasset)
- [IMC_Default.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/IMC_Default.uasset)
- [IA_Ability01.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/IA_Ability01.uasset)
- [IA_Ability02.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/IA_Ability02.uasset)
- [IA_Ability03.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/IA_Ability03.uasset)
- [IA_Ability04.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/IA_Ability04.uasset)

当时表面上看，这几份资产之间的关系已经配得差不多了：

1. 技能槽有自己的 `InputTag`
2. `DA_AOInputConfig` 能把 `InputTag` 反查到 `IA_Ability01~04`
3. `IA_Ability01~04` 也在尝试承担技能槽 1~4 的真实输入动作
4. `IMC_Default` 里也承担了这些动作的物理按键绑定

也就是说，**资产层看起来不是完全没配，而是“看起来应该能用”。**

这就是这次特别容易误判的根源。

### 这次问题在项目里的表面表现

这次在项目里真正看到的表面现象是：

1. 技能槽 UI 的文字键位显示拿不到结果。
2. 技能槽最终只能显示 `None`。
3. 明明 `InputAction` 能查到，`MappingName` 也有值，但还是拿不到当前映射键位。
4. 连运行时的按键反查结果也是空的。

这时候如果只站在 UI 或输入资产层去看，直觉上特别容易怀疑：

- `Player Mappable` 没配对
- `IMC_Default` 里那几条映射没继承对
- `MappingName` 写错了

但这次真正卡住的地方不是这些。

### 这次在项目里的真实链路

这次项目里的真实链路可以概括成下面这条：

1. 技能槽 UI 先拿当前槽位里的 `InputTag`
2. 再通过 `PawnData -> InputConfig` 反查出对应的 `InputAction`
3. 再尝试从当前本地玩家的输入系统里查这份 `InputAction` 的真实键位
4. 如果能查到，就显示真实键位文字
5. 如果查不到，就只能回退成 `None`

这一段具体落在技能槽 UI 文件里：

- [AOSkillSlotUI.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/Widgets/Skill/AOSkillSlotUI.cpp:64)
- [AOSkillSlotUI.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/Widgets/Skill/AOSkillSlotUI.cpp:91)
- [AOSkillSlotUI.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/Widgets/Skill/AOSkillSlotUI.cpp:109)

这一步本身没有方向性问题。  
它做的事情其实很正常，就是：

“我已经知道技能槽在用哪个输入语义了，那我就去查这个语义现在实际对应哪个键。”

真正出问题的是再往上的那层：

**Hero 在初始化输入的时候，没有把对应的 IMC 稳稳地挂进当前本地玩家。**

### 这次真正出问题的项目位置

这次真正需要记住的项目位置是：

[AOHeroComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOHeroComponent.cpp:292)

这一段就是当前项目里 Hero 初始化默认输入映射的地方。

这次的问题不是“技能槽不会查”，而是“Hero 这边没有稳定把技能相关 IMC 放进玩家输入系统”。

具体来说，这里当时有两个项目内的实际问题：

1. 这里拿 `DefaultInputMappings` 里的 IMC 时，用的是软引用直接取值的方式，没有确保它一定已经变成运行时可用资源。
2. 这里把“是否注册到设置系统”和“是否真正加入当前玩家输入栈”混在了一起。

于是项目里就出现了一个很微妙的状态：

- `DA_AOInputConfig` 看起来是对的
- `IA_Ability01~04` 看起来也在
- `IMC_Default` 看起来也配了
- 但 Hero 初始化输入时，这份 IMC 并没有稳定落到当前玩家运行时输入里

从而导致后面技能槽 UI 这边一查全空。

### 这次修复在项目里改了什么

这次最终修的是 [AOHeroComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOHeroComponent.cpp:292) 这一段，核心改了两件事：

1. 不再假设 IMC “此时碰巧已经加载好了”，而是明确把软引用解析成运行时资源。
2. 把“注册到 `UserSettings`”和“加入当前玩家输入映射栈”拆开处理。

这样修完之后，项目里的这条链才重新成立：

`技能槽 InputTag -> DA_AOInputConfig -> IA_Ability01~04 -> IMC_Default 真正挂到本地玩家 -> UI 成功查到真实键位`

### 这次项目里最值得记住的一点

这次最值得记住的不是“某个 UI 函数怎么写”，而是下面这句话：

> 在本项目里，只要技能槽 UI 同时出现“可改键映射查不到”和“当前运行时键位也查不到”，就优先不要怀疑 UI，要先回头看 Hero 的默认输入映射到底有没有真正进本地玩家。

换句话说，**以后在 AegisOdyssey 里再碰到技能键位显示全空，第一反应应该去看 `AOHeroComponent` 的输入初始化链，而不是先死盯技能槽 UI。**

### 以后回看这个问题时的项目级排查顺序

如果以后在这个项目里再次碰到“技能键位显示不出来”，建议按下面这个顺序回看：

1. 先看 [DA_AOInputConfig.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/DA_AOInputConfig.uasset) 里技能槽 `InputTag` 和 `IA_Ability01~04` 对没对上。
2. 再看 [IMC_Default.uasset](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Content/Games/Input/IMC_Default.uasset) 里这 4 个 `InputAction` 有没有真的绑键。
3. 然后直接回头看 [AOHeroComponent.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/Character/AOHeroComponent.cpp:292) 这段默认输入映射初始化逻辑。
4. 最后再看 [AOSkillSlotUI.cpp](D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/Widgets/Skill/AOSkillSlotUI.cpp:109) 这边的显示查询链。

这样排，速度会比一上来就死磕 `Player Mappable` 高很多。
