## 一、这份说明书现在的定位

这不是旧设计稿的备份，也不是零散交接记录的拼接版。
这份文档现在承担两个职责：

1. 说明当前战斗系统已经落地到什么程度。
2. 给后续继续开发和验收的人提供明确的实施基线，尤其是不要把已经收好的边界重新写乱。

本次更新重点补充一条新的硬性基线：

- **世界目标血条必须按 MVVM 方式收束**
- **目标自己的数据归目标侧**
- **本地玩家是否应该看到目标血条，归本地观察者侧**
- **UI 只绑定 ViewModel，不自己猜结算，不自己维护一套影子数据真相**

## 二、当前战斗系统已经落地的主线能力

当前代码已经围绕“攻击命中统一结算与防御反馈”搭出主链路，重点不是单独某个普攻或某个技能能不能打到，而是把各种攻击命中统一收口到战斗系统里解释。

当前已经落地的方向可以概括为：

1. 攻击命中进入统一战斗结算入口，而不是各打各的。
2. 战斗结果通过统一消息向表现层广播，UI 不再自己猜结果。
3. 无敌帧、格挡、弹反、韧性、体力、提示字这些战斗语义，已经开始按统一主链收束。
4. 世界目标血条现在也开始按同样的原则收束，不再让 Widget 自己缓存一份“看起来像真相”的数据。

这份说明书当前最重要的新增内容，是下面这一章。

## 三、世界目标血条 MVVM 架构基线

### 3.1 为什么这里必须改成 MVVM

原来这块如果继续沿着“组件拿到属性变化后，直接往 Widget 里推一堆 ViewData”去写，短期看起来能跑，长期会很乱，主要问题有三类：

1. 数据归属会乱。
2. 本地观察资格和目标真实血量会被揉在一起。
3. 蓝图层后续一旦扩展表现，很容易又在 UI 内部偷偷维护第二套状态。

这和当前项目已经形成的 UI 风格不一致。
项目里更合适的做法，是把“可绑定的数据对象”明确成 ViewModel，把“谁拥有这个数据”与“谁决定它该不该显示”拆开。

所以这里正式收束为：

- **目标血条数据真相走 ViewModel**
- **Widget 只读 ViewModel**
- **本地玩家观察资格单独由观察者组件决定**
- **运行时需要有明确的 ViewModel 实例获取入口**

### 3.2 这一块现在的归属边界

这一块以后不要再写混，边界已经定死：

#### A. 目标侧负责什么

目标侧负责“这个目标自己到底有多少血、是否死亡、当前血条是否最终允许渲染”。

也就是说，下面这些内容属于目标自己：

- 当前生命值
- 最大生命值
- 血量百分比
- 是否死亡
- 当前最终可见状态字段
- 目标血条对应的 ViewModel 实例

#### B. 本地玩家侧负责什么

本地玩家侧只负责“我这个本地观察者，现在应不应该看到这个目标的世界血条”。

也就是说，下面这些内容属于本地观察者：

- 这条战斗结果消息跟本地玩家有没有关系
- 某个目标是否进入过本地观察集合
- 脱战隐藏延迟是否已到
- 本地玩家与目标是否超出显示距离 / 隐藏距离
- 本地玩家脱战且目标也脱战后是否应该隐藏

#### C. UI 侧不负责什么

UI 侧不允许负责以下事情：

- 不自己猜血量真相
- 不自己从 AttributeSet 拼一套逻辑
- 不自己推断“该不该显示”
- 不自己维护第二份 ViewData 影子状态

UI 只做两件事：

1. 拿到明确的 ViewModel 实例。
2. 绑定字段做表现。

### 3.4 当前明确的 ViewModel 实例获取路径

这一点是硬要求，后续不要走“只有隐式绑定，没有明确入口”的路子。

当前已经提供的明确入口：

#### 目标组件侧

- `UAOTargetHealthBarComponent::GetTargetHealthBarViewModel()`

适用场景：

- 蓝图逻辑想直接从目标组件拿目标血条 VM
- 调试时确认当前目标侧是否已经创建并刷新 VM

#### Widget 侧

- `UAOTargetHealthBarWidget::GetTargetHealthBarViewModel()`

适用场景：

- Widget Blueprint 初始化后，需要明确拿到当前绑定的 VM
- 表现层脚本需要检查运行时实际注入的 VM 实例

### 3.5 当前运行时注入路径

当前运行时注入不是只做一半，而是两条路都在：

1. 目标组件通过 `UMVVMSubsystem / UMVVMView::SetViewModel(...)` 把 VM 注入到 MVVM Source。
2. 目标组件同时把 VM 传给 `UAOTargetHealthBarWidget::SetTargetHealthBarViewModel(...)`，给蓝图侧一个显式初始化时机。

当前默认 Source 名称是：

- `TargetHealthBar`

这意味着蓝图 Widget 侧后续应遵守同一个命名约定，避免运行时能拿到 VM，但绑定名称对不上。

### 3.6 当前显示规则基线

世界目标血条的当前显示规则已经敲定为：

1. 只显示和本地玩家相关的目标血条。
2. 不保留最近目标血条。
3. 目标死亡时立刻隐藏。
4. 本地玩家脱战，且目标也脱战，且超过隐藏延迟，才隐藏。
5. 显示距离与隐藏距离分离，当前默认值是 1500 / 2000，但必须可配置。
6. 隐藏延迟当前默认值是 6 秒，必须可配置。

当前这套规则的职责归属不能改：

- **规则计算在本地观察者组件**
- **最终显隐执行在目标组件**
- **UI 只绑定 `bVisible` 做表现**

### 3.7 当前这块故意没有做的事情

为了避免第一版就写散，现在明确下面这些内容**故意不做**：

1. 不做“所有玩家都应该看到同一目标血条”的全局广播式逻辑。
2. 不做“最近目标保留显示”。
3. 不做特殊例外规则堆叠。
4. 不做额外的观察者子系统大总管。
5. 不把目标血条 VM 塞进本地玩家 HUD VM。
6. 不为了图省事回退成 Widget 自己缓存 ViewData。

### 3.8 残留代码与后续清理检查项

用户这里特别担心“写着写着残留没清干净”，所以这部分单独列为检查基线。

后续继续做这章内容前，必须再次核以下事项：

1. 旧的 `ViewData` 术语是否还残留在血条相关源码或注释里。
2. 旧的“组件直接推 Widget 数据”描述是否还残留在说明书或注释里。
3. 蓝图 Widget 资产是否还依赖旧逻辑入口。
4. 是否还有地方试图绕开 ViewModel，直接从 Widget 内部自己拉取目标属性。
5. 是否有新的调用路径又把“目标数据归属”和“本地观察资格”重新写混。

当前建议排查关键词：

- `FAOTargetHealthBarViewData`
- `ApplyViewData`
- `OnViewDataChanged`
- `GetViewData`

后续如果继续补世界目标血条功能，默认遵守下面四条：

1. 先看这一章，再动代码。
2. 先判断功能属于目标侧、观察者侧，还是纯表现层。

## 五、更大范围的战斗 MVVM 拆分基线（当前先记方案，后续按此展开）

这一章说的不是刚才已经落地的单目标世界血条本体，而是**围绕整个战斗 UI / 战斗表现数据层，后续还没有继续铺开的那一大块 MVVM 收束方向**。

这一块现在先定基线，不在这一步里继续一口气全实现。
目的只有一个：

- **先把拆分边界写死**
- **后续继续做的时候不再临时拍脑袋往 `UMVVM_HUD` 里塞**
- **避免某个功能一急着接 UI，就又退回到“先暴露点零散 getter 再说”的旧路子**

这一章从现在开始，视为后续战斗 UI MVVM 扩展的总基线。

### 5.1 当前已经明确要继续拆分的几块

后续继续展开时，重点是下面五块：

1. `CombatResources` 独立 ViewModel
2. `LocalCombatState` 独立 ViewModel
3. `CombatFeedbackFeed` 从 `UMVVM_HUD` 里继续拆分
4. `TargetHealthBarCollection` 这类集合型 ViewModel
5. 说明书 / 验收文档对本次 MVVM 改法的补写

注意，这五块现在是**已确定方向**，不是“有空再想”的松散备忘。

### 5.2 为什么现在就要先记这章

如果现在不把这几块先记清楚，后面最容易出现的问题是：

1. `UMVVM_HUD` 继续膨胀，什么都往里塞。
2. 某个 UI 临时要数据时，又在组件上补一堆零散接口。
3. 同一个战斗语义同时出现在 HUD VM、角色组件、Widget Blueprint 三处，各自维护一半。
4. “单目标状态”和“本地玩家视角下的观察集合”重新写混。
5. 文档跟代码不同步，后面回头验收时大家都看懵。

所以这一章的核心目的，不是立刻把功能做完，而是**先防止架构继续发散**。

### 5.3 `CombatResources` 独立 ViewModel

这一块后续应独立成一块专门的战斗资源 ViewModel，用来承接“和资源条直接相关、并且适合 UI 直接绑定”的本地玩家战斗资源数据。

这块以后默认应承接的内容包括：

- `Health`
- `MaxHealth`
- `HealthPercent`
- `Vigor`
- `MaxVigor`
- `VigorPercent`
- `Stamina`
- `MaxStamina`
- `StaminaPercent`

如果后续有更明确的资源型战斗字段，只要本质上属于“本地玩家自身的资源条真相”，也应优先归到这一类 ViewModel，而不是继续塞回 `UMVVM_HUD` 大杂烩。

这块的边界要注意：

- 它是**本地玩家自己的资源状态**
- 它不是反馈流
- 它不是目标集合
- 它也不是单个目标血条

### 5.4 `LocalCombatState` 独立 ViewModel

这一块后续应独立承接“本地玩家当前战斗状态语义”，而不是资源数值。

它关注的不是“还剩多少条”，而是“当前处在什么战斗态、当前能不能做什么、当前战斗系统给 UI 的状态结论是什么”。

这块未来适合承接的典型信息包括：

- 是否处于战斗中
- 是否处于格挡态
- 是否处于弹反窗口或弹反成功后的某种状态
- 是否处于破韧状态
- 是否处于受击硬直或受控状态
- 是否允许某些关键战斗输入 / 行为

边界要写死：

- `CombatResources` 管资源条数值
- `LocalCombatState` 管本地玩家战斗状态语义
- 两者不要重新揉成一个“大而全”的本地战斗 VM

### 5.5 `CombatFeedbackFeed` 从 `UMVVM_HUD` 继续拆分

当前 `UMVVM_HUD` 里已经承担了一部分战斗反馈路由和缓存职责，但这块后续不应无限继续膨胀。

已经明确的方向是：

- **战斗反馈流要继续从 `UMVVM_HUD` 往外拆**

这里说的 `CombatFeedbackFeed`，本质上是“给 HUD / 飘字 / 其他表现层消费的本地战斗反馈流 ViewModel 或等价收束层”。

它未来承接的不是资源条，不是状态条，而是这类东西：

- 最新一条本地相关战斗反馈
- 待消费反馈列表
- 是否应该进 HUD
- 是否应该进世界飘字
- 文本推荐结果
- 反馈分类语义

这里最重要的不是名字，而是边界：

- 反馈流应该是反馈流
- 不要把资源条字段塞进反馈流
- 不要把本地状态字段塞进反馈流
- 更不要把目标集合塞进反馈流

### 5.6 `TargetHealthBarCollection` 这类集合型 ViewModel

单目标世界血条已经按“目标自己的 ViewModel”收束了，但这不等于“本地观察者视角下的一组目标”也不需要结构化。

后续如果要继续把这一块做得更统一，已经明确可以往**集合型 ViewModel**方向收：

- 例如 `TargetHealthBarCollection`

但这里有一个硬边界：

- **集合归本地观察者视角**
- **单个目标的血条数据仍然归目标自己**

也就是说，后续如果真做这类集合型 ViewModel，它负责的更像是：

- 本地当前正在观察哪些目标
- 当前有哪些目标血条可用于 UI 层做列表 / 调试 / 统一观察
- 集合变化通知

它不应该把每个目标的生命值真相再抄一份缓存进集合自己内部，避免重新造出第二套状态真相。

### 5.7 `UMVVM_HUD` 后续的角色定位

`UMVVM_HUD` 以后仍然可以保留，但定位要明确收敛。

更合适的方向是：

- 它作为 HUD 总入口或聚合根存在
- 它持有或暴露若干子 ViewModel 的实例入口
- 它不再无限吸收所有战斗 UI 字段本体

也就是说，后续理想状态下更像这样：

- `UMVVM_HUD`
- `CombatResources`
- `LocalCombatState`
- `CombatFeedbackFeed`
- 其他明确职责的子 ViewModel

而不是继续把所有内容堆在一个类里。

### 5.8 这几块后续展开时的实现顺序原则

这五块后续不是乱做，顺序上建议遵守下面这条总原则：

1. 先拆“本地玩家自身且稳定的状态数据”
2. 再拆“本地反馈流”
3. 最后再考虑“集合型观察模型”

更具体一点：

1. 优先 `CombatResources`
2. 然后 `LocalCombatState`
3. 再拆 `CombatFeedbackFeed`
4. 最后看是否需要正式引入 `TargetHealthBarCollection`

原因很简单：

- 资源和本地状态边界最稳定
- 反馈流次之
- 集合型 ViewModel 最容易一不小心又写成新的复杂中间层，所以放后面更稳

### 5.9 这章对后续开发的硬约束

后续只要继续做这几块，默认必须遵守下面这些约束：

1. 不要为了图快继续给 `UMVVM_HUD` 塞越来越多原始字段。
2. 不要在 Widget Blueprint 里自己拼状态真相。
3. 不要把单目标数据归属和本地观察集合归属写混。
4. 不要把资源、状态、反馈、目标集合重新混成一个“大 ViewModel”。
5. 不要只做隐式绑定，不给明确实例获取路径。
6. 文档要跟着代码一起收口，不允许代码改完、说明书还是旧说法。

### 5.10 这一章当前的状态结论

这一章现在只是**方向已敲定、实现尚未继续铺开**。
