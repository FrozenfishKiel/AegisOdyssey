# 战斗系统UI与目标血条-MVVM改造当前进度与新AI交接说明-2026-05-13
更新时间：2026-05-14

---

## 1. 这份文档现在的用途

这不是旧方案存档，也不是只讲理念的说明。

这份文档现在承担三件事：

1. 说明战斗 UI / MVVM / 目标血条链路当前已经改成什么样了。
2. 说明旧方案哪些点已经失效，后续不要再按旧思路写。
3. 给接下来的战斗表现层实现提供可直接执行的接入步骤和测试方案。

看完这份文档后，新的 AI 或后续开发不应该再去走：

- 旧 HUD 事件镜像方案
- 让 Widget 自己猜战斗真相
- 底层 combat message 直接给蓝图 dynamic 广播
- 客户端收到战斗结果后又走回服务端转发链

## 2. 当前已经确定的总设计

### 2.1 战斗 UI 现在按什么层次走

当前链路已经明确拆成四层：

1. 战斗结算层  
   负责给出统一 `FAOCombatResultMessage` 真相，不负责 UI 表现。

2. 本地战斗消息层  
   `UAOCombatMessageSubsystem` 只负责在本地世界内广播战斗结果，以及在服务端把相关结果定向转发给相关客户端。

3. HUD / MVVM 桥接层  
   `UAOHUDViewModelComponent` 负责把统一战斗结果翻译成 HUD 可直接消费的 `FAOCombatFeedbackViewData`，并写入 `UMVVM_HUD` 及其子 ViewModel。

4. 表现层  
   Widget / 蓝图只绑定 ViewModel、消费队列、做动画和显示，不自己回头推理战斗真相。

### 2.2 当前严格边界

必须继续遵守：

- 底层 combat message 不等于 UI 数据。
- UI 不直接订阅战斗结算真相后再自己二次解释。
- UI 要消费的是 ViewModel 数据或桥接后队列。
- MVVM 是当前主方向，不能一半 MVVM、一半旧事件回调拼在一起。

## 3. 本轮之后，方案已经更新了什么

这一节是本次必须同步的重点。

### 3.1 CombatFeedback 旧 HUD 方案已经失效

旧思路里，`UMVVM_HUD` 自己镜像一份战斗反馈状态，并带额外事件广播。

这个方案现在视为旧方案，原因是：

- HUD 聚合根承担了太多“既存数据又发事件”的混合职责。
- UI 继续依赖旧回调的话，会和新的 `CombatFeedbackFeed` 子 ViewModel 并行，形成双轨。
- 这不符合当前项目希望收束到 MVVM 数据面的方向。

当前有效方案是：

- `UMVVM_HUD` 只负责把反馈写入 `UMVVM_CombatFeedbackFeed`
- `UMVVM_CombatFeedbackFeed` 作为战斗反馈流子 ViewModel 暴露数据
- UI / 蓝图从 feed 消费队列，不再依赖旧 HUD 动态回调

### 3.2 战斗消息总线已经改成纯 C++ native multicast

旧方案里，`UAOCombatMessageSubsystem::OnCombatResultMessage` 是 dynamic multicast。

这个方案已经被证明有根本问题：

- dynamic multicast 会把 `FAOCombatResultMessage` 送进 Script VM 参数复制链
- 这条链已经真实触发过 `UScriptStruct::CopyScriptStruct` 栈溢出
- 这不是“某个 if 没写”的问题，而是底层消息分发机制选错

当前有效方案：

- `UAOCombatMessageSubsystem::OnCombatResultMessage` 已改为 native multicast
- 订阅端走 `AddUObject`
- 参数按 `const FAOCombatResultMessage&` 传递

### 3.3 客户端回播链已经拆成“源广播”和“本地回播”

旧方案里，服务端广播后定向 RPC 到客户端，客户端收到后又重新调用 `BroadcastCombatResult()`。

这个方案已经被证明会递归：

- 服务端 `BroadcastCombatResult()`
- `ClientBroadcastCombatResultMessage()`
- 客户端又调用 `BroadcastCombatResult()`
- 重新进入转发链，形成回环

当前有效方案：

- `BroadcastCombatResult()`：源入口，只负责“本地广播 + 定向转发”
- `BroadcastCombatResultLocal()`：只在当前世界内广播一次，不做网络转发
- 客户端 RPC 收到后只调用 `BroadcastCombatResultLocal()`

## 4. 当前战斗 UI / MVVM 主链现状

### 4.1 HUD 聚合根和子 ViewModel

当前 `UMVVM_HUD` 已经不是一个大杂烩容器，而是 HUD 聚合根。

当前已经接入的子 ViewModel：

- `UMVVM_CombatResources`
- `UMVVM_LocalCombatState`
- `UMVVM_CombatFeedbackFeed`
- `UMVVM_TargetHealthBarCollection`

桥接入口在：

- [AOHUDViewModelComponent.h](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/AOHUDViewModelComponent.h)
- [AOHUDViewModelComponent.cpp](/D:/UE_Project/AO/AegisOdyssey/AegisOdyssey/Source/AegisOdyssey/UI/AOHUDViewModelComponent.cpp)

可直接拿的入口：

- `GetCombatResourcesViewModel()`
- `GetLocalCombatStateViewModel()`
- `GetCombatFeedbackFeedViewModel()`
- `GetTargetHealthBarCollectionViewModel()`

### 4.2 统一战斗结果如何进入 HUD

当前链路：

1. 结算层产出 `FAOCombatResultMessage`
2. 写入 `UAOCombatMessageSubsystem`
3. `UAOHUDViewModelComponent` 订阅该消息
4. `BuildLocalCombatFeedbackViewData()` 按本地玩家视角整理成 `FAOCombatFeedbackViewData`
5. `UMVVM_HUD::ApplyCombatFeedbackViewData()` 写入 `UMVVM_CombatFeedbackFeed`
6. 表现层从 `CombatFeedbackFeed` 消费

这条链已经是当前标准入口，不要再绕开它去让 UI 重新直连 combat message。

### 4.3 本地战斗状态镜像

`UMVVM_LocalCombatState` 当前承担的是“本地玩家状态 UI 镜像”，不是战斗结算真相。

当前由 `UMVVM_HUD::RefreshLocalCombatStateFromSource()` 统一刷新：

- 是否在战斗中
- 是否格挡中
- 是否被破韧
- 是否被弹反
- 是否禁止能力输入
- 最近一次本地相关结果类型

注意：

- 这块状态来源主要是 ASC tag 和最近一次本地相关反馈
- 表现层读它可以做 HUD 状态显示
- 但不要把它再反过来当战斗结算事实源

### 4.4 目标血条主链

当前目标血条链路已经基本成型：

1. 目标 Actor 侧：`UAOTargetHealthBarComponent`
2. 目标单体 VM：`UMVVMTargetHealthBar`
3. 本地观察者：`UAOLocalTargetHealthBarObserverComponent`
4. HUD 集合入口：`UMVVM_TargetHealthBarCollection`

职责拆分：

- `UAOTargetHealthBarComponent`  
  负责目标自身血量真相、单体 VM、WidgetComponent 可见性驱动。

- `UAOLocalTargetHealthBarObserverComponent`  
  只负责本地玩家视角下，“我现在该不该看到这个目标血条”。

- `UMVVM_TargetHealthBarCollection`  
  不持有目标真相，只暴露观察者入口给 UI / 蓝图。

## 6. 接下来要做的“战斗表现层显示”怎么接

这一节是新增的执行方案，不是空泛建议。

### 6.1 CombatFeedbackFeed 的正确使用方式

当前推荐表现方式是：

1. 表现层持有或获取 `UMVVM_CombatFeedbackFeed`
2. 在合适时机调用 `ConsumePendingCombatFeedbackList()`
3. 逐条驱动飘字、受击提示、格挡提示、弹反提示、破韧提示

不要做的事：

- 不要再给底层 combat result message 加蓝图回调
- 不要从 `UMVVM_HUD` 自己再维护一套战斗反馈镜像
- 不要在 Widget 里自己读 `Instigator/Target` 再做一次“我猜这是不是本地相关”

### 6.2 建议先落地的表现项目顺序

建议顺序：

1. 本地 HUD 提示文案 / 图标  
   例如格挡、弹反、破韧、普通伤害提示。

2. 世界飘字  
   只消费 `bShouldEnqueueForWorldFloatingText == true` 的反馈。

3. 目标血条进入 / 延迟隐藏 / 距离隐藏表现

4. 本地状态条边框或特殊状态闪烁  
   例如 `LocalCombatState` 的格挡中、破韧中、输入封锁中。

### 6.3 当前表现层的数据分流标准

战斗反馈 UI 不要再自定义规则，先按下面字段走：

- `bIsLocalRelevant`
- `bIsLocalInstigator`
- `bIsLocalTarget`
- `bShouldEnqueueForHUD`
- `bShouldEnqueueForWorldFloatingText`
- `bIsImportantCombatFeedback`
- `ResultType`
- `FloatingTextType`

建议：

- HUD 主提示：优先消费 `bShouldEnqueueForHUD`
- 世界飘字：优先消费 `bShouldEnqueueForWorldFloatingText`
- 强交互结果强调：优先看 `bIsImportantCombatFeedback`

### 6.4 目标血条表现层怎么接

当前目标血条表现层接入建议：

1. 目标 Actor 是否有世界血条资格，由是否挂 `UAOTargetHealthBarComponent` 决定。
2. 目标单体血量显示绑定 `UMVVMTargetHealthBar`。
3. 是否显示由 `UAOLocalTargetHealthBarObserverComponent` 驱动 `SetRequestedVisible()`。
4. 不要在 Widget 里自己算距离、自己算隐藏延迟、自己判断战斗态。

也就是说：

- Widget 负责“怎么显示”
- 观察者负责“该不该显示”
- 目标组件负责“显示什么血量真相”

## 7. 现在开始做表现层时，建议的实际操作顺序

这是给“下一步要怎么一步一步做”的明确执行表。

### 第一步：先接 CombatFeedbackFeed 的可视化消费

目标：

- 确认主 HUD 能稳定拿到反馈队列并消费一次

操作：

1. 从 `UAOMainUI` 或蓝图便捷库拿到 `UMVVM_CombatFeedbackFeed`
2. 调 `ConsumePendingCombatFeedbackList()`
3. 逐条打印或驱动一个最简单的提示

测试：

1. 本地攻击敌人
2. 确认有反馈进入 feed
3. 确认重复 Tick/重复事件不会把同一条消息无限消费

### 第二步：做 HUD 内战斗反馈提示

目标：

- 把 `ResultType` / `FloatingTextType` 变成稳定的 HUD 提示

操作：

1. 先处理 `Damage`
2. 再处理 `Parry`
3. 再处理 `Broken`
4. 最后补 `Blocked` / `Invulnerable`

测试：

1. 普通命中是否提示
2. 格挡是否走防御提示
3. 弹反是否走高优先级提示
4. 破韧是否走高优先级提示

### 第三步：做世界飘字

目标：

- 只为本地应显示的攻击结果生成世界飘字

操作：

1. 仅消费 `bShouldEnqueueForWorldFloatingText == true`
2. 使用 `HitResult` / `Target` / `BuildRecommendedCombatText()` 辅助定位和文案

测试：

1. 本地玩家打到目标时有飘字
2. 与本地玩家无关的结果不乱飘
3. 格挡/无敌命中不会误当普通伤害飘字

### 第四步：做目标血条显隐联调

目标：

- 验证当前本地观察者链是否完全满足战斗中显示需求

操作：

1. 确认目标有 `UAOTargetHealthBarComponent`
2. 确认本地 `AAOPlayerController` 上有 `UAOLocalTargetHealthBarObserverComponent`
3. 确认攻击命中后观察者记录目标
4. 确认距离、战斗态、隐藏延迟共同生效

测试：

1. 客户端攻击敌人后目标血条出现
2. 脱战后不立即消失，按延迟隐藏
3. 拉开超过隐藏距离后立刻隐藏
4. 目标死亡后隐藏

## 8. 当前必须记住的测试重点

后续每次改战斗 UI / 表现层，都至少回归这组测试。

### 8.1 消息链测试

1. 本地命中一次，只应消费一次本地反馈
2. 不应再出现 `BroadcastCombatResult` 回环递归
3. 不应再出现 `UScriptStruct::CopyScriptStruct` 的 dynamic delegate 栈溢出

### 8.2 HUD 反馈测试

1. 攻击敌人时 HUD 提示出现
2. 格挡 / 弹反 / 破韧提示分流正确
3. 非本地相关结果不乱进本地 HUD

### 8.3 世界飘字测试

1. 本地攻击命中时飘字正常
2. 与本地无关结果不乱飘
3. 无敌命中 / 全挡不误当普通伤害

### 8.4 目标血条测试

1. 客户端攻击敌人时目标血条出现
2. 本地脱战与目标脱战后按延迟隐藏
3. 超距离立即隐藏
4. 死亡隐藏

## 9. 当前仍然存在的结构性注意事项

### 9.1 `UMVVM_HUD` 仍然保留了部分网络相关声明

当前 `UMVVM_HUD` 仍然有：

- `IsSupportedForNetworking()`
- `GetLifetimeReplicatedProps()`
- 多组 `ReplicatedUsing`

但当前它并不是一个完整接入了 replicated subobject 管理的对象链。

这意味着：

- 当前不要继续往 `UMVVM_HUD` 上叠更多“像复制对象一样使用”的职责
- 后续如果真要把 HUD VM 当 replicated UObject 用，需要单独完整设计
- 当前阶段它的主要定位仍然是本地 HUD 聚合根和桥接节点

这不是当前立刻要重构的点，但后续不能认知混乱。

### 9.2 当前文档已经覆盖到表现层，不要再分裂成旧思路和新思路两套

从现在开始，方案认知应统一成一句话：

战斗结算产出统一结果，本地消息层只转发，HUD 桥接层整理成 ViewModel 数据，表现层只消费 ViewModel。
