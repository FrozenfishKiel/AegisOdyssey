## 一、当前主线已经变了

当前阶段主线已经不是继续深挖 AI 战斗决策，而是：

**先把可交互对象系统做成正式骨架。**

当前要服务的对象不是只有箱子，还包括但不限于：

- 箱子
- 工作台
- 拉杆
- 按钮
- 后续商店、特殊功能对象、可供 AI 使用的对象

所以“箱子”始终只是第一个示范对象，不是架构的终点。

---

## 二、已经稳定下来的硬约束

下面这些不是建议，而是后续实现必须遵守的硬约束。

### 1. 必须基于现有项目架构推进

不能脱离项目现有链路，另起一套“看起来很通用”的空中方案。

必须贴着现有这些真实链路做：

- GAS 输入与能力链
- `Interaction` 交互链
- `Inventory` 库存交换链
- 现有 MVVM / UI 绑定链

### 2. 必须统一交互，不准围绕对象类型扩散主链

用户认可的是：

- 玩家或 AI 发起一次统一交互
- 统一交互链负责扫描、选项、触发
- 对象自己决定后续行为

用户不认可的是：

- 箱子一个 GA
- 工作台一个 GA
- 按钮一个 GA
- 玩家侧根据对象类型分流

### 3. 必须对象侧多态，不准把行为写死在玩家侧

交互能力应该只负责“发出交互”。

对象自己决定这次交互是：

- 拾取
- 打开 UI
- 建立会话
- 切换状态
- 其他对象特有行为

### 4. UI 不是纯展示层

UI 不只是看数据，也必须能发起数据操作请求。

正确方向是：

- UI 展示标准化数据
- UI 发起标准化操作请求
- 服务端处理权威逻辑
- 结果再同步回 UI

### 5. 联机同步必须和 UI 数据层一起考虑

当前默认共识是：

- 观察者才需要容器详细内容
- 非观察者不需要容器详细内容
- 世界状态同步和容器详细内容同步是两层

### 6. 注释必须认真写，且以中文为主

这是用户明确提出的工程要求，后续新增代码仍要保持。

## 三、目前可以当成“项目记忆”的稳定判断

### 1. 箱子方向里，观察者会话模型是成立的

这部分不是纯文档设想，代码里已经有明确落点：

- `AAOChest` 维护观察者
- `UAOInteractionSessionComponent` 只把会话状态复制给拥有者
- `ReplicatedContainerSlots` 使用 `COND_OwnerOnly`

这意味着当前方向上，下面这些判断可以继续沿用：

- 谁打开对象，谁才有会话模型
- 没打开对象的人，不应该默认拿到容器详细内容
- A/B 同时打开同一个箱子时，应该共享同一份容器变化

### 2. 统一交互能力 + 对象侧执行 也是成立方向

当前 `UAOGameplayAbility_Interact::TriggerInteractionByIndex(...)` 的顺序是：

1. 组装统一交互事件数据
2. 优先 `UInteractionStatics::TryExecuteInteraction(...)`
3. 对象侧没接住时，再回退到旧能力事件链

这说明当前代码方向确实在往下面这个共识收口：

- 统一交互负责发消息
- 对象优先执行自己的正式逻辑
- 旧链兼容只是过渡，不是终态

### 3. 容器详细同步目前已经走玩家私有会话

`UAOInteractionSessionComponent` 当前会复制：

- `ReplicatedSessionType`
- `ReplicatedInteractableActor`
- `ReplicatedSessionWidgetClass`
- `ReplicatedContainerSlots`

而且都是 `COND_OwnerOnly`。

这部分已经不是纸面设计，而是当前代码现状。

### 4. AI 的非 UI 入口已经有雏形

当前 `AAOChest` 里已经有：

- `TransferItemToInteractorInventory(APawn* InteractingPawn, int32 ChestSlotIndex, int32 TargetSlotIndex)`

这说明“AI 不依赖 UI，直接调用对象侧正式入口”的方向已经开始落地，可以继续沿用。

## 四、当前必须牢记的现实状态

这里记录的是“现在代码到底处于什么状态”，不是理想终态。

### 1. 当前代码仍然处在新旧并存过渡期

表现包括：

- `InteractionOption` 里还保留旧链兼容字段
- `AT_WaitForInteractableTargets` 仍会补旧链能力句柄
- `AOGameplayAbility_Interact` 还是“对象优先 + 旧链回退”

所以现在不能误判为“旧链已经干净下线”。

### 2. 当前拾取链仍然是第一优先级问题

不是容器 UI 最优先，也不是会话模型最优先，而是：

**统一交互接入过程中，把原本稳定的拾取链改坏了。**

已知症状包括：

- 单机或服务器侧按 `E` 可能重复进包
- 某些阶段客户端按 `E` 完全无法拾取
- 用户已经把怀疑点收敛到输入句柄收集阶段

### 3. 当前最值得警惕的地方在输入收口上游

现有判断是：

- 问题不一定在 `ProcessAbilityInput(...)` 的循环体内部
- 更可能在进入这些循环前，交互能力句柄就没有被正确收进数组

优先排查链路是：

1. `UAOHeroComponent::Input_AbilityInputTagPressed`
2. `UAOHeroComponent::Input_AbilityInputTagStarted`
3. `UAOAbilitySystem::AbilityInputTagPressed`
4. `UAOAbilitySystem::AbilityInputTagStarted`
5. `UAOAbilitySystem::GatherAbilityHandlesForInputTag`

### 4. 当前 `ProcessAbilityInput(...)` 里的补激活逻辑只能视为临时补丁

如果后续新会话看到下面这种逻辑，不要直接把它当成最终正确方案：

- 统一交互能力未激活时，输入到来先 `TryActivateAbility(...)`
- 再立刻走 `AbilitySpecInputPressed(...)`

这段逻辑产生的前提，是当时怀疑“能力没激活”。

但用户后续已经把问题进一步收敛到：

- 客户端甚至没走进 `InputPressedSpecHandles` / `InputStartedSpecHandles` 的遍历

所以这段更像临时止血，而不是最终根因修复。

## 五、已经踩过、以后不要再踩的坑

这一节最重要，后续 AI 必须先记住。

### 1. 不要再给“箱子”单独长专用交互主链

箱子只是示范对象。

如果箱子单独一套，后面工作台、按钮、拉杆都会继续复制，最后会回到按对象类型扩散系统的老路。

### 2. 不要再让玩家侧硬判断对象类型

错误方向包括：

- 玩家判断“这是箱子”
- 玩家判断“这是工作台”
- 玩家自己决定打开哪个 UI

正确方向一直都是：

- 玩家负责发起交互
- 对象自己提供行为和 UI

### 3. 不要为了双触发给对象加布尔锁

如果一次交互会双触发，核心问题不是“锁没加上”，而是：

- 为什么存在两条并行交互主链
- 为什么一次输入会走多条路

加锁只是在掩盖架构错误。

### 4. 不要把库存交换继续扩散成“当前容器专用函数链”

用户明确更认可统一四参数交换模型：

- 源库存
- 目标库存
- 源索引
- 目标索引

不要继续围绕箱子扩散出大量：

- `RequestMoveToInventory`
- `RequestMoveFromInventory`
- 其他只服务某一类容器的入口

### 5. 不要把“武器优先进快捷栏”之类规则硬写死在交互修复里

这类规则如果以后要做，也应该是更通用的物品归位策略。

不能因为当前修交互 Bug，就临时写成只对武器生效的窄逻辑。

### 6. 不要脱离旧版可工作基线继续远端补丁式修复

旧版可工作源码位置：

- `D:\UE_Project\AegisOdyssey\Source`

当前工作区源码位置：

- `D:\UE_Project\AO\AegisOdyssey\AegisOdyssey\Source`

如果新会话只盯着“现在多进了几把剑”，不回头对照旧版为什么原来能稳定拾取，就会一直修出新问题。

### 7. 不要把详细箱子方案文档里的旧思路当成最终事实

`联机交互箱子设计方案-玩家共享可见-AI可用-UI与同步策略.md` 里有价值，但它不是现在唯一真相。

后续如果它和：

- `交互系统当前进度与新会话交接说明.md`
- 用户最新口头要求

发生冲突，以后两者为准。

## 六、当前代码和文档之间，最值得记住的几个“现状差”

这些差异记录下来，是为了防止后续 AI 又把“方向”误当成“已经全部落地”。

### 1. 会话模型方向是对的，但库存交换并没有完全改成“会话层统一转发”

当前 `UAOInventoryUI::RequestExchangeBetweenInventories(...)` 仍然会：

- 服务端直接走 `ExecuteExchangeRequest(...)`
- 客户端走 `WhenItemExchange(...)`

也就是说：

- UI 已经开始统一组织源/目标库存参数
- 但库存交换主入口依然主要落在现有库存系统上

这不算坏事，但要知道它是当前真实状态。

### 2. `Server_ExecuteInteractionRequest(...)` 还在，但还不能当成最终稳定结构

`AAOPlayerController` 里这个入口还在。

它可以说明某一阶段尝试过让控制器参与服务端转发，但是否长期保留，应等拾取链稳定后再评估。

### 3. 当前 `AAOChest` 更像“玩家容器会话已成立，AI 入口初步存在”

但“工作台、按钮、拉杆”那套对象级共性层，还没有真正全面验证。

所以后续不要因为箱子先跑起来，就误以为对象体系已经完整闭环。

## 七、后续新会话最建议的工作顺序

### 第一步：先把优先级摆正

先修拾取稳定性，再继续扩容器功能。

当前不建议优先做：

- 更复杂的容器 UI
- 更多容器类型
- 大规模 AI 交互扩写

### 第二步：优先确认输入句柄为什么没进数组

重点不是先改，而是先证据化排查：

- 客户端有没有走到 `UAOHeroComponent` 的输入函数
- 有没有走到 `UAOAbilitySystem::AbilityInputTagPressed/Started`
- `GatherAbilityHandlesForInputTag(...)` 产出的 `MatchingHandles` 是否为空
- 如果为空，是能力没授予、动态标签没带上，还是统一收口逻辑误过滤

### 第三步：对照旧版最短稳定拾取链

先找出旧版“按 `E` 到稳定进包”的最短调用链，再看当前工作区哪一步被改偏了。

### 第四步：拾取稳定后，再回头清理临时补丁

重点包括：

- `ProcessAbilityInput(...)` 里的临时补激活逻辑
- 不再需要的旧链兼容层
- `Server_ExecuteInteractionRequest(...)` 是否还能删或收口

## 九、一句话版本

当前这套交互系统的长期记忆可以压缩成一句话：

**方向上已经确认要走“统一交互 + 对象侧多态 + 观察者会话 + 复用现有库存/UI 链”，但在把这套结构接进项目时把旧拾取链改坏了；现阶段最重要的不是继续发散功能，而是先回到旧版稳定拾取基线，再收口临时兼容逻辑。**
