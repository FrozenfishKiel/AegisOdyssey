# 采集系统设计方案：对象定义、状态驱动、结算与同步框架

更新日期：2026-05-08

这份文档的用途，是把当前已经讨论并拍板的采集系统设计思路稳定记录下来，作为后续持续迭代时的长期设计笔记与交接基线。

当前阶段目标很明确：

- 先把采集系统框架搭稳
- 先把对象边界、状态入口、采集结算链、入包链、网络同步链讲清楚
- 暂时不进入具体采集资源、美术表现、数值平衡的最终细化阶段

也就是说，现阶段重点不是“某棵树的木屑怎么飞、某把斧头的特效怎么闪”，而是先把“采集对象是什么、采集工具是什么、角色如何进入采集状态、一次采集命中如何判定、奖励如何结算并进入库存、多人联机下谁说了算”这套骨架立住。

## 一、这套采集系统现在到底想解决什么问题

我们现在要做的，不是简单做几个“树被砍一下掉木头”的临时逻辑。

我们真正要做的是一套：

- 采集对象对象化
- 采集工具对象化
- 角色采集状态化
- 采集结算统一化
- 奖励入包统一化
- 玩家与 AI 可共用
- 联机下服务器权威裁决

的采集系统。

从玩法设计角度看，它更接近：

- 角色装备一件采集工具
- 角色进入一次采集动作状态
- 在命中窗口按当前工具配置真正做一次命中检测
- 谁在命中窗口里被这次挥击真实打到，谁才是这次采集目标
- 命中的目标对象依据自身定义与当前上下文决定这次是否接受、掉什么、掉多少
- 奖励通过统一入包链进入背包

这里必须再强调一次：

**“斧头砍树”只是采集系统的一个例子，不是采集系统本体。**

我们可以先用“斧头砍树”“矿镐挖矿”“采摘浆果”做第一版落地对象，但系统底层不能被设计成“只有砍树才算采集”。

## 二、当前已经拍板的核心原则

### 1. 采集系统的设计中心是“采集”，不是“砍树”

系统不围绕某一类对象特化，不围绕某一把工具特化，也不围绕某一种掉落特化。

第一版可以先做树、矿、浆果，但架构层必须一开始就按“采集系统”来设计。

### 2. 能不能被采，优先由对象决定

当前已经明确：

- 不能先靠工具侧写死 `SupportedNodeTags`
- 不能先把“这把工具能砍树/能挖矿”写成系统唯一裁决来源

更合理的方向是：

- 工具提供自己的采集能力与采集参数
- 对象自己决定当前是否接受这次采集请求

也就是说：

- 工具负责“我怎么采”
- 对象负责“我接不接受这次采”

### 3. 采集是角色的一种状态

当前已经明确：

- 采集不是一次普通交互按钮调用
- 采集不是一个布尔状态
- 采集应该作为角色现有 StateTree 风格中的一个动作状态

但也已经明确：

- 不应该为了采集单独发明一套复杂的大状态机
- 应该尽量贴近当前项目里 `STT_PlayAnimation`、`STT_PlayHeavyAttack` 这类“一个状态做一件动作”的写法

### 4. 长按采集的体验目标，是动画连续，逻辑离散

当前已经明确：

- 每次采集结算，仍然应该是离散的一次命中
- 不能做成每帧持续掉资源
- 不能做成一个无限 Tick 的资源光束

但同时也要注意：

- 如果长按完全做成“每一下完整退回待机再起手”，动画会很容易不连贯

所以更合理的方向是：

- 逻辑上是一下一下结算
- 动画上支持持续采集段或循环挥击段

### 5. 奖励入包必须走统一库存入口

当前已经明确：

- 采集对象不应直接改玩家库存
- 采集系统不应绕过库存系统直接拼 UI 结果
- 奖励应该先形成统一采集结果，再由角色侧统一走背包入包

库存系统仍然只做库存系统。

### 6. 网络权威必须在服务器

当前已经明确：

- 目标发现可以在客户端先做
- 动画表现可以在客户端先播
- 但真正的采集命中判定、节点进度变化、奖励生成、背包入包，必须以服务器为准

不允许客户端本地直接决定资源结果。

这里再补一条明确约束：

- 客户端可以先做“可能命中谁”的轻量提示或预览
- 但不能把“当前交互对象”直接当作正式采集目标塞进采集主链
- 正式采集目标只能在命中窗口里由本次挥击的真实命中结果产生

### 7. Definition 要有边界，Fragment 也要有边界

当前已经明确：

- 工具需要有自己的 Definition
- 但工具也不应该脱离现有 `ItemDefinition + Fragment` 体系，搞成完全独立的新系统

更合理的方向是：

- `HarvestToolDefinition` 提供工具这一类对象的定义边界
- `HarvestToolFragment` 提供这类工具内部可组合的采集配置块

### 8. 看现有项目，是为了正确接入基础能力，不是为了反过来绑架需求

这一条是当前方案的明确原则。

我们之所以要看当前项目，是为了：

- 复用合适的库存入包能力
- 复用合适的装备与输入主链
- 复用合适的 StateTree 动作状态风格
- 复用合适的联机复制与观察模式

但这不意味着：

- 采集系统必须强行继承当前武器系统语义
- 采集节点必须照搬当前交互对象语义
- 只要项目里已有某种实现方式，就优先向那种实现方式妥协

后续所有设计判断都必须先问清楚三件事：

- 这个能力本质上属于采集系统，还是属于现有系统
- 这里复用的是基础能力，还是旧系统语义
- 这样做是更贴当前需求，还是只是更像现有代码

换句话说：

**参考当前项目，是为了让采集系统接在正确的基础设施上；不是为了让现有实现反过来定义采集系统应该长成什么样。**

当前再补一条已经拍板的反例约束：

- 交互系统可以给准星提示、候选高亮、可采反馈
- 但交互系统不是采集主链的目标权威来源
- 不能做成“先从交互系统预选目标，再在命中窗里验证这个预选目标”

## 三、当前阶段的术语统一

这一节非常重要，后续不要再把旧术语和新术语混着用。

### 1. `HarvestableDefinition`

静态采集对象定义，用来描述：

- 这是什么采集对象
- 它的基础采集进度是多少
- 它的基础掉落规则是什么
- 它是否可重生
- 它自身被采时的对象侧表现是什么
- 它面对不同工具机械语义时的响应规则是什么

它不描述：

- 当前被谁采
- 当前剩余多少进度
- 当前这一下最终会掉多少

### 2. `HarvestToolDefinition`

静态采集工具定义，用来描述：

- 这是一类什么采集工具
- 它的基础采集能力是什么
- 它默认授予什么采集 Ability / AbilitySet
- 它的默认装备与表现语义是什么

它是工具这一类对象的 Definition 边界。

### 3. `HarvestToolFragment`

采集工具定义内部的可组合配置块，用来描述：

- 命中检测参数
- 采集动作参数
- 基础采集强度
- 长按支持策略
- 工具命中表现

它不是工具本体 Definition 的替代品，而是 Definition 内部的可组合配置块。

### 4. `HarvestToolInstance`

运行时这把具体工具的实例对象。

如果后续需要支持：

- 稀有度
- 词条
- 附魔
- 临时强化
- 耐久

这些都应该优先挂在实例层，而不是定义层。

但当前阶段已经明确：

- 只为实例层预留扩展位
- 不优先落完整实例级系统

当前补充明确：

- `HarvestToolInstance` 已经是正式存在的运行时层，不再只是概念预留。
- 当前采集主链允许优先携带 `HarvestToolInstance`，而不只是回头读取 `HarvestToolDefinition`。
- 这样后续如果要给“这把具体工具”加耐久、词条、临时增益、个体修正，不需要再重写采集入口协议。

### 5. `HarvestResourceDefinition`

进入背包后的采集产物定义对象。

它负责描述：

- 这类采集资源本身是什么
- 它属于什么资源分类
- 它后续在制造 / 熔炉 / 烹饪 / 检索里怎么被识别

它不负责描述：

- 世界节点当前剩余多少进度
- 这棵树当前是不是 depleted
- 这次掉落到底掉了几份

### 6. `HarvestResourceItemInstance`

进入背包后的采集产物实例对象。

如果后续资源需要支持：

- 品质
- 纯度
- 新鲜度
- 批次
- 个体差异

这些都应该优先挂在这一层，而不是回写到节点 Definition。

### 7. `HarvestableComponent`

挂在世界对象上的运行时采集组件。

当前标准落地方式是：

- 默认直接继承 `AAOHarvestableActor`
- `AAOHarvestableActor` 统一提供 `AActor + IAOHarvestableTarget + UAOHarvestableComponent`
- 只有确实已经有自己的 Actor 继承体系时，才走“自定义 Actor + `IAOHarvestableTarget` + `UAOHarvestableComponent`”兼容路径

它负责：

- 当前对象的采集状态
- 当前剩余进度
- 当前是否 depleted
- 当前是否接受一次采集请求

它不负责：

- 角色输入
- 角色状态推进
- 背包入包
- 最终统一概率公式

### 6. `HarvestRuntimeContext`

采集动作的短生命周期运行时上下文。

当前阶段已经明确：

- 不给主角新增常驻采集组件
- 当前工具快照、动作参数、命中上下文，只存在于运行中的 `STT_PlayHarvest`、`GA_Harvest`、`TargetData`、`AbilityTask` 等短生命周期链路里
- 采集动作结束、被打断或目标失效后，这些上下文自然释放

它负责承载：

- 当前这次采集动作使用的工具与命中参数快照
- 当前这次命中提交所需的 `HarvestHitContext`
- 如果命中窗口里真实打到了对象，则承载“这一次真实命中的对象与组件”

### 7. `HarvestResolver`

统一采集结算器。

它不是世界对象，不是角色组件，不是工具实例。

它是一块纯系统规则代码，负责：

- 合并对象基础数据
- 合并工具实例修正
- 合并角色 Buff 修正
- 跑最终公式
- 生成最终采集结果

### 8. `ItemCatalog DataTable`

全项目统一物品总表入口。

它的职责是：

- 用数字 ID 查询物品
- 集中遍历所有物品元数据
- 不再依赖物品名称做身份寻址
- 为采集、制造等系统提供统一物品索引

### 9. `HarvestRegistry`

全项目统一采集定义注册入口。

它的职责是：

- 集中收集采集对象定义
- 集中收集采集工具定义
- 方便遍历、查询、校验、编辑时管理

## 四、哪些数据该挂在哪个对象上

这一节是当前方案的核心之一。

### 1. 采集对象自己拥有的数据

这些应该挂在 `HarvestableDefinition` / `HarvestableComponent` 上：

- 这是什么采集对象
- 基础总进度
- 基础掉落规则
- 基础稀有掉落概率
- 掉落条目的奖励时机
- 是否可重生、多久重生
- 节点自身被采时的对象侧表现
- 当前剩余进度
- 当前是否 depleted
- 对不同工具机械语义的响应规则

一句话：

**对象负责“我是什么、我能掉什么、我现在还能不能被采”。**

### 2. 工具自己拥有的数据

这些应该挂在 `HarvestToolDefinition` / `HarvestToolFragment` / `HarvestToolInstance` 上：

- 采集动作类型
- 采集动作动画
- 命中检测配置
- 基础采集强度
- 长按支持策略
- 工具特效 / 音效 / 皮肤表现
- 工具稀有度
- 工具词条
- 工具额外掉落修正
- 工具所属的机械语义 Profile

一句话：

**工具负责“我怎么采、我采得多猛、我这把具体个体当前带着什么额外修正”。**

### 3. 采集产物自己拥有的数据

这些应该挂在 `HarvestResourceDefinition` / `HarvestResourceItemInstance` 上：

- 资源自己的类型身份
- 资源标签、分类与后续制造筛选入口
- 未来可能存在的品质、纯度、新鲜度、批次信息等实例级语义

不要把这些语义反塞回 `HarvestableDefinition`。
`HarvestableDefinition` 负责描述“节点掉什么”，不负责描述“掉出来的这份物品实例之后是什么状态”。

### 4. 角色自己拥有的数据

这些应该挂在角色 Buff / Attribute / GAS 上：

- 采集数量加成
- 稀有掉率加成
- 特殊掉落加成
- 采集效率加成
- 额外 roll 次数

一句话：

**角色负责“我当前带着什么加成去采”。**

### 5. 系统统一拥有的规则

这些不属于对象、不属于工具、不属于角色定义，应放在统一系统结算代码里：

- 最终概率公式
- 最终数量公式
- 修正因子的叠加顺序
- 上限/下限/clamp 规则
- 最终随机流程

一句话：

**公式属于系统，不属于某一个具体对象。**

## 五、Definition、Fragment、Instance 三层的当前方案

### 1. 采集工具层

当前推荐结构：

- `UAOInventoryItemDefinition`
  - `UAOEquipmentDefinition`
    - `UAOHarvestToolDefinition`

同时建议增加一层独立机械语义资产：

- `UAOHarvestToolProfile`

它不是具体工具物品，而是“这类工具在采集规则里的机械身份”。

当前已经明确：

- 不要把工具机械语义写死成 C++ 枚举
- 未来工具类型应该通过可扩展资产承载，而不是通过写死代码枚举承载

同时：

- `UAOHarvestToolDefinition` 内部可以持有一个或多个 `UAOHarvestToolFragment`

如果后续需要实例级稀有度和词条：

- `UAOInventoryItemInstance`
  - `UAOEquipmentInstance`
    - `UAOHarvestToolInstance`

### 2. 采集对象层

当前推荐结构：

- `AAOHarvestableActor`
- `UAOHarvestableDefinition`
- `UAOHarvestableComponent`
- 默认由 `AAOHarvestableActor` 通过 `IAOHarvestableTarget` 暴露采集能力
- 特殊对象允许继续使用“任意 Actor + `IAOHarvestableTarget` + `UAOHarvestableComponent`”的兼容接入方式

### 3. 注册入口层

当前推荐结构：

- `UAOHarvestRegistry`
- `全项目物品总表 DataTable`

其中：

- `UAOHarvestRegistry` 用于集中收集 `HarvestableDefinition`、`HarvestToolDefinition`、`HarvestToolProfile`
- 物品数字 ID 统一通过全项目大 `DataTable` 组织

当前已经明确：

- `HarvestRegistry` 是手动维护的 `DataAsset`
- C++ 不写死任何现有采集定义
- Registry 不是为了替代 Definition，而是为了集中收集和查询这些 Definition

## 六、采集状态的当前方案

### 1. 采集是角色的一种动作状态

当前已经明确：

- 采集应该进入现有 StateTree 体系
- 采集状态风格必须贴近当前项目现有 `STT_PlayAnimation` / `STT_PlayHeavyAttack` 这种“一个状态做一件动作”的写法

当前不建议：

- 为采集单独发明一套复杂子状态机
- 在一个状态里自己写 while 循环
- 在 Ability 里无限 Tick 自动发资源

### 2. 当前推荐的采集状态写法

当前推荐新增一个类似于：

- `STT_PlayHarvest`

它的职责应该和现有动作状态保持同风格：

#### EnterState

- 取角色
- 取 ASC
- 取当前装备工具实例
- 组装一次 `HarvestTargetData`
- 按 `InputTag` 激活 `GA_Harvest`

#### Tick

- 找对应 `AbilitySpec`
- 如果 Ability 仍在激活，则返回 `Running`
- 如果 Ability 结束，则返回 `Succeeded`

#### ExitState

- 只做必要清理，不发明复杂新状态机逻辑

### 3. 采集状态树和工具的关系

这一点需要单独说清楚，避免后续实现时把边界写偏。

当前方案**不是**：

- 每把采集工具自己带一棵独立 StateTree
- 玩家切换到工具时，把这棵 StateTree “装到角色身上”

当前方案**是**：

- 角色自己继续使用现有的 StateTree / 动作状态体系
- 采集工具在被装备时，通过现有装备链授予采集所需的 Ability / AbilitySet
- 采集工具 Definition / Fragment / Profile 提供这把工具的采集动作数据、命中参数、表现参数、机械语义
- 角色侧的采集状态任务，例如 `STT_PlayHarvest`，在运行时读取当前已装备工具的数据并触发 `GA_Harvest`
- `STT_PlayHarvest` 只负责发起动作，不负责正式决定“这次已经在采谁”

也就是说，链路应理解为：

1. 采集工具作为可装备物进入背包、QuickBar、装备链
2. 玩家切换到该工具时，沿用现有 `QuickBar -> Equipment/WeaponManager -> AbilitySet/ASC` 主链完成装备
3. 工具被装备后，角色当前就具备了采集动作所需的 Ability 与工具数据
4. 角色现有 StateTree 中的采集动作状态负责启动这次采集动作
5. 该状态和 Ability 在运行时读取“当前装备的采集工具”数据，而不是去切换整棵工具专属 StateTree

一句话收束：

**采集工具提供“这把工具怎么采”的数据与能力；角色自己的 StateTree 决定“角色现在是否进入采集动作状态”。**

### 4. 长按采集的当前理解

当前已经明确：

- 长按采集的玩法目标，是“一下下重复采集”
- 但动画体验目标，是“尽量连续、不回待机硬抖”

所以更合理的方向是：

- 逻辑上：每次命中仍然是离散的一次采集结算
- 动画上：支持持续采集段或循环挥击段

这意味着：

- 长按不应等于“每帧直接掉资源”
- 长按也不应粗暴等于“每一下完整退回待机再起手”

更合理的实现方向是：

- 状态层维持采集动作语义
- Ability 层支持持续中的挥击循环
- 每个命中通知各自结算一次采集命中

## 七、采集判定的当前方案

### 1. 当前只保留两种检查时机：本地轻量检查、服务器最终提交

这是当前方案的关键拍板点之一。

不能把“当前准星看着树”直接等同于“本次采集命中成立”。

但当前已经明确：

- 不需要为了采集单独设计两套复杂接口体系
- 只需要保留两种检查时机

#### 第一种：本地轻量检查

回答：

**当前玩家是否满足进入采集状态和显示提示的最基本条件。**

这一步主要服务于：

- 准星提示
- 是否允许进入采集状态
- 当前“可能命中对象”的轻量预览

这一步可以相对宽松，例如只看：

- 是否命中实现了采集接口的对象
- 对象是否已经 depleted
- 当前是否存在可用工具或徒手规则
- 当前距离是否大体合理

#### 第二种：服务器最终提交

回答：

**这一次挥击，在命中帧，是否真的打到了一个可采对象，并允许把它作为本次正式采集目标结算。**

这一步必须更严格，而且必须以服务器为准。

### 2. 命中提交时服务器至少要校验的内容

当前推荐：

- 角色仍装备合法工具
- 工具实例未变化
- 当前距离合法
- 当前朝向合法
- 当前命中窗口合法
- 当前 Sweep / 短距离命中是否合法，并且真实命中了一个可采对象
- 命中的对象仍然有效
- 命中的对象仍然实现采集接口
- 命中的对象组件未 depleted
- 当前遮挡检测合法
- 对象侧最终接受本次命中请求

### 3. 对象决定可采，不等于对象独占全部逻辑

当前已经明确：

- 能不能采，优先由对象决定
- 但对象只负责对象自己的接受规则与基础掉落逻辑
- 不负责角色状态与最终统一公式

也就是说：

- 对象不等于整个采集系统
- 对象只是采集系统中“节点侧裁决者”

## 八、采集结算的当前方案

### 1. 奖励结算不能写成“树自己直接掉木头进背包”

当前已经明确：

- 采集对象不应直接改角色背包
- 采集对象不应直接掌握角色库存语义

更合理的链路是：

1. 角色侧在命中窗口构建一次 `HarvestHitContext`
2. 用这次挥击的真实命中结果解析出被打中的 `HarvestableComponent`
3. 把这次命中请求提交给命中的 `HarvestableComponent`
4. `HarvestableComponent` 返回“基础采集结果候选”
5. `HarvestResolver` 合并对象基础数据、工具实例修正、角色 Buff 修正，生成最终结果
6. `GA_Harvest` 在服务端拿最终结果统一走背包入包

### 2. 结算结果至少应维护一份运行时结构

当前推荐至少有：

- `FAOHarvestRewardEntry`
- `FAOHarvestResult`

#### `FAOHarvestRewardEntry`

应表达：

- 产出的是哪个物品
- 数量是多少
- 是否成功入包

#### `FAOHarvestResult`

应表达：

- 本次是否接受
- 本次是否成功
- 本次奖励列表
- 本次扣了多少节点进度
- 节点是否 depleted
- 如果失败，失败原因是什么

### 3. 对象基础概率和最终公式必须分开

当前已经明确：

- 对象定义上放的是基础掉落概率、基础掉落范围
- 工具实例和角色 Buff 提供修正因子
- 最终公式在统一 `HarvestResolver` 中计算

例如：

- 树定义上：高级木材基础概率 10%
- 工具实例上：稀有度额外 +3% 稀有掉率
- 角色 Buff 上：特殊掉落乘算 1.25

最终怎么合成，不写在对象上，也不写在工具上，而写在系统统一结算代码中。

### 4. 奖励时机按掉落条目配置

当前已经拍板：

- 采集奖励的发放时机不应由整个系统统一写死成一种
- 应当由每个掉落条目自己决定

当前推荐每个掉落条目支持：

- `PerHit`
  说明：每次合法命中时发放
- `OnDepleted`
  说明：只有节点被彻底采空时发放
- `Both`
  说明：命中时发一部分，采空时再发一部分

## 九、奖励进入库存的当前方案

### 1. 入包必须走服务端统一收口

当前推荐：

- `HarvestableComponent` 只返回结果
- `GA_Harvest` 服务端结算后统一调用背包入包

默认可复用的库存入口包括：

- `UAOInventoryComponent::AddItemDefinition(...)`
- `UAOInventoryComponent::AddItemInstance(...)`

当前第一版更适合默认走：

- `BackPackComponent->AddItemDefinition(...)`

因为多数采集产物本质上是按定义生成的新物品，而不是已有实例搬运。

### 2. 背包满的当前处理原则

当前已经明确：

- 背包满时，这次采集直接不结算
- 不允许对象进度已经扣掉但玩家什么都没拿到

当前推荐：

- 先检查本次采集结果是否能够按当前规则完整入包
- 如果当前设计规则下不能完整入包，则这次采集直接视为结算失败
- 不扣节点进度，不发奖励

同时保留未来开发方向：

- 后续可扩展为“掉落到地上”
- 后续可扩展为“部分成功、部分掉落”

但这些不进入当前第一版拍板实现范围。

## 十、网络同步的当前方案

### 1. 服务器权威的范围

当前已经明确必须以服务器为准的内容：

- 采集命中是否合法
- 节点进度如何变化
- 最终奖励是什么
- 最终奖励是否进包
- 节点是否 depleted
- 节点是否开始 respawn

### 2. 客户端负责的内容

当前客户端可负责：

- 准星预览
- 播采集动画
- 播本地前摇表现
- 展示当前采集状态

但客户端不应负责：

- 最终资源结果裁决
- 节点进度最终结果
- 背包最终结果

### 3. 多人同时采集同一节点的第一版建议

当前已经正式拍板：

**默认共享采集、无独占、服务器顺序结算。**

也就是说：

- 不做先锁定再采
- 不做先占坑再独占
- 谁的命中请求先被服务器合法处理，谁先结算
- 如果别人先一步把节点采空了，后到的这一下直接失败
- 这不是异常，也不做特殊补偿，它就是正常玩法结果

### 4. 节点状态与背包状态分别独立同步

当前推荐：

- 背包仍复用现有库存 FastArray 同步与 ViewModel 刷新链
- 节点自身的 `CurrentProgress`、`bIsDepleted` 等由 `HarvestableComponent` 自己负责复制

不要把“节点状态同步”和“背包状态同步”混成同一层。

## 十一、注册入口与数字 ID 的当前方案

### 1. 全项目所有物品都需要数字 ID

当前已经明确：

- 未来项目需要支持语言切换
- 物品不应再通过物品名称做身份寻址
- 物品名称只负责显示，不负责逻辑身份

所以当前推荐：

- 全项目物品统一拥有 `ItemId`
- 后续通过数字 ID 查询物品，而不是查名字

### 2. 物品数字 ID 统一走全项目大 DataTable

当前已经拍板：

- 物品总索引不上单独的物品 Registry DataAsset
- 而是统一走全项目大 `DataTable`
- 这个总表后续不仅服务采集，也服务制造等其他系统

也就是说：

- 物品身份统一使用数字 ID
- 全项目通过大 `DataTable` 完成 `ItemId -> 物品定义/元数据` 查询
- 物品名称只负责显示，不再承担身份职责

### 3. `HarvestRegistry`

当前推荐新增：

- `UAOHarvestRegistry : UPrimaryDataAsset`

它的职责是：

- 集中收集所有 `HarvestableDefinition`
- 集中收集所有 `HarvestToolDefinition`
- 集中收集所有 `HarvestToolProfile`
- 提供遍历、查询、校验、编辑时总览入口

### 4. 为什么这里要 Registry，而不是把所有采集定义硬塞进表

当前已经明确：

- 我们需要一个地方把这些定义“集合起来”
- 但不代表所有数据都要 DataTable 化

Registry 的意义是：

- 保持对象自己的 Definition 边界
- 同时提供集中入口

它不是为了替代对象 Definition，而是为了集中收集它们。

当前已经拍板：

- `HarvestRegistry` 由人工手动维护
- C++ 不写死任何现有资源

## 十三、当前阶段最小可落地版本建议

在具体开发执行上，当前也已经明确一条重要工作原则：

- 采集系统按阶段逐段落代码
- 一次只做一个阶段，避免一次性铺太多代码浪费上下文
- 每个阶段只实现该阶段必须落地的边界与链路
- 不提前偷做下一阶段的逻辑，避免把错误边界扩散到后面所有代码
- 每个阶段完成后先自检，再进入下一个阶段

为了避免一开始把系统做得过重，当前推荐的第一版最小落地顺序如下。

### 第一阶段：先立对象定义边界

目标：

- 建立 `HarvestableDefinition`
- 建立 `HarvestToolDefinition`
- 建立 `HarvestToolProfile`
- 建立 `HarvestToolFragment`
- 建立 `HarvestRegistry`
- 建立物品总表 `DataTable`

本阶段解决的问题：

- 采集对象定义放哪
- 工具定义放哪
- 工具机械语义如何可扩展且不写死在 C++ 枚举里
- 工具 Fragment 怎么保留边界
- 所有采集定义如何集中查询
- 所有物品如何统一数字 ID 寻址

本阶段暂不做：

- 真正采集动作
- 真正命中结算
- 背包入包
- 多人同步细节

### 第二阶段：建立运行时组件骨架

目标：

- 建立 `HarvestableComponent`
- 明确 `STT_PlayHarvest` / `GA_Harvest` 的运行时上下文承载方式
- 建立基本的采集命中上下文与运行时状态容器

本阶段解决的问题：

- 采集节点运行时状态放哪
- 当前工具快照、命中上下文、命中窗口里真实打到的对象信息放在哪条短生命周期链路里
- 采集请求通过什么状态 / Ability 链路提交

本阶段暂不做：

- 完整公式
- 完整掉落补偿
- 多人共享采集

### 第三阶段：接入状态与 Ability

目标：

- 建立 `STT_PlayHarvest`
- 建立 `GA_Harvest`
- 接通一次采集动作状态到 Ability 的主链

本阶段解决的问题：

- 采集如何进入现有状态体系
- 采集动作如何走 Input -> Hero -> ASC -> Ability
- 单次采集动作的状态生命周期如何组织

### 第四阶段：接通命中判定与统一结算

- 建立 `HarvestHitContext`
- 建立 `HarvestResolver`

本阶段解决的问题：

- 命中判定怎么拆
- 对象基础概率与角色/工具修正怎么合并
- 最终奖励如何统一生成

### 第五阶段：接通奖励入包与联机同步

目标：

- `GA_Harvest` 服务端统一入包

本阶段解决的问题：

- 采集完如何真正进背包
- 背包满时如何直接让这次采集不结算
- 多人联机谁说了算
- 节点 depleted / respawn 如何同步

## 十四、程序员验收、阅读路径与手工测试规范

这一节不是补充说明，而是当前采集系统的正式验收口径。

程序员拿到代码后，不应该自己脑补测试资产、自己猜先后顺序、自己在项目里盲找入口。

**正确交付标准是：程序员只看这一节，就知道先准备什么、先读哪里、先开哪个关卡、先做哪一步、做完以后看什么结果。**

### 1. 验收目标

本阶段验收不是泛泛地问“功能是不是差不多能跑”，而是要明确确认下面四件事：

- 角色是如何进入采集动作状态的。
- 一次采集命中最终由谁裁决。
- 奖励是如何进入库存的。
- 节点状态、结算逻辑、库存接收各自的边界在哪里。

如果程序员做完整套验收后，仍然回答不出这四件事，那么本阶段交付不合格。

### 2. 开始验收前必须先准备好的东西

正式开始测试前，程序员不要先按 PIE。

必须先把下面这张准备清单逐项完成；少一项，就先停下来补，不要带着缺资产、缺配置、缺映射的状态开始验。

#### A. 测试关卡准备

至少准备一个专门的采集测试关卡，建议只放和采集相关的最小内容：

- 一个玩家出生点。
- 一组用于单人测试的采集节点。
- 一组用于多人同时采集测试的采集节点。
- 一个背包能明确观察到容量变化的测试角色。

不要在正式大地图里做第一次验收，避免被无关 AI、任务、掉落物、动画事件干扰。

#### B. 采集节点准备

至少准备一个测试节点蓝图，要求同时满足：

- 默认父类直接使用 `AAOHarvestableActor`；如果不是这个父类，必须自己实现 `IAOHarvestableTarget`。
- 节点身上必须存在有效的 `UAOHarvestableComponent`。
- 已绑定有效的 `UAOHarvestableDefinition`。

这份 `UAOHarvestableDefinition` 至少要配置清楚：

- `TotalHarvestProgress` 不是 0。
- `DefaultToolResponse` 或 `ToolProfileResponses` 允许当前测试工具采集。
- `DropEntries` 至少有一条稳定必出的掉落。
- 如果当前要测 depleted 行为，确保节点不是“打一下一定采空”的极端配置，除非本轮就是专门验证 depleted。

#### C. 采集工具准备

至少准备一件测试用采集工具，要求同时满足：

- 该物品能进入现有装备链，而不是只存在于背包。
- 它的 Definition 是 `UAOHarvestToolDefinition`。
- 它带有 `UAOHarvestToolFragment`。
- 它绑定了有效的 `UAOHarvestToolProfile`。
- 它通过现有装备链授予了采集所需的 `GA_Harvest` 或对应 `AbilitySet`。

如果工具只是“看起来像斧头”，但没有真正授予采集 Ability，那么不要继续后面的测试。

如果当前项目里还没有现成可复用的测试采集工具，按下面步骤创建一套最小可跑通配置：

1. **先建 ToolProfile 资产**
   
   - 在内容浏览器里新建一个 `UAOHarvestToolProfile` 资产。
   - 建议命名：`DA_HTP_TestAxe`。
   - 先至少填写：
     - `ProfileName`：例如“测试斧头”。
     - `ProfileTags`：当前可以先留空；它的目的主要是后续检索和分组，不是本轮能不能采的核心开关。
   - 这一步的目的：
     - 给“这类工具在采集规则里的机械身份”一个明确资产。
     - 后续节点不是按“工具长得像什么”判断，而是按这个 `ToolProfile` 决定响应规则。
   - 通过标准：
     - 你能在编辑器里单独打开这份 `ToolProfile`，并且名字不是空白、资产路径清楚。

2. **再建 HarvestToolDefinition**
   
   - 新建一个 `UAOHarvestToolDefinition` 子类资产或蓝图资产，作为测试工具 Definition。
   - 建议命名：`ID_HarvestTool_TestAxe`。
   - 这份资产本质上仍然属于现有 `ItemDefinition -> EquipmentDefinition` 体系，不是独立的一套新采集物品体系。
   - 先至少确认下面几项：
     - `DisplayName` 之类的基础显示字段不是空白，方便在背包或调试界面辨认它。
     - `InstanceType` 是项目里当前合法的装备实例类型，而不是空值。
     - `AbilitySetsToGrant` 里已经放入会授予 `GA_Harvest` 的 `AbilitySet`；如果这里没有采集能力，工具即使能装备，也不会进入采集主链。
   - 这一步的目的：
     - 让测试工具能真正进入现有装备链。
     - 让角色装备它以后，ASC 能拿到采集 Ability。
   - 通过标准：
     - 这份资产的父类型确实是 `UAOHarvestToolDefinition`。
     - `AbilitySetsToGrant` 不是空的，并且其中确实包含采集 Ability 授予链。

3. **在 Definition 的 Fragments 里添加 HarvestToolFragment**
   
   - 打开这份 `UAOHarvestToolDefinition`。
   - 在它继承自 `UAOInventoryItemDefinition` 的 `Fragments` 数组里新增一个元素，类型选 `UAOHarvestToolFragment`。
   - 先至少填写：
     - `BaseHarvestPower`：建议测试值先填 `20` 或 `25`，避免一击采空，也避免打很多下都没变化。
     - `bSupportsHoldHarvest`：如果这轮要测长按，勾上；如果只测单次采集，可以先关掉。
     - `HoldHarvestInterval`：如果开了长按，测试值建议先填 `0.5` 秒，方便观察固定节奏命中。
     - `HitCheckConfig.MaxDistance`：建议先用默认值或略大于默认值，保证测试时不是因为距离过短误判失败。
     - `HitCheckConfig.SweepRadius`：先保留默认值，避免第一轮测试把命中盒做得太苛刻。
     - `HitCheckConfig.MaxFacingAngleDegrees`：先保留默认值，避免还没测到主链就被朝向校验挡掉。
   - 这一步的目的：
     - 给工具补齐“它怎么采、每一下多强、是不是长按、命中怎么判”的工具侧静态配置。
     - `STT_PlayHarvest` 运行时会从 Definition 的 `Fragments` 容器里通过 `FindHarvestToolFragment()` 找这个配置块；没配这一块，主链会直接断。
   - 通过标准：
     - 这份工具 Definition 的 `Fragments` 数组里能明确看到一个 `UAOHarvestToolFragment`。
     - `BaseHarvestPower` 大于 `0`。

4. **把 ToolProfile 绑定回 HarvestToolDefinition**
   
   - 仍然打开同一份 `UAOHarvestToolDefinition`。
   - 在 `HarvestToolProfile` 字段里，选择刚刚创建的 `DA_HTP_TestAxe`。
   - 这一步的目的：
     - 让这把具体工具拥有一个“机械语义身份”。
     - 后续节点 Definition 会用这个 `ToolProfile` 去匹配 `ToolProfileResponses`；如果这里是空，系统只能退回节点的 `DefaultToolResponse`。
   - 通过标准：
     - `HarvestToolProfile` 字段不是空引用。
     - 打开节点的 `HarvestableDefinition` 时，程序员能明确说清楚“这把工具现在是靠 DefaultToolResponse 走通，还是靠某条 ToolProfileResponses 走通”。

5. **最后确认它真的能被装备和触发**
   
   - 把这件工具配置进当前测试角色可拿到、可装备的正式链路里，不要只停留在内容浏览器里建好了资产。
   - 进入编辑器后要能做到两件事：
     - 在背包或快捷栏里看到它；
     - 装备后，角色真实拿到采集 Ability，而不是只是 UI 里显示“好像装备了”。
   - 这一步的目的：
     - 确保你测的是完整主链：`背包/快捷栏 -> 装备 -> AbilitySet 授予 -> STT_PlayHarvest -> GA_Harvest`。
   - 通过标准：
     - 装备这件工具后，触发采集输入时，角色进入采集动作，而不是普通攻击、普通交互或完全无响应。

#### D. 物品总表准备

在 `DT_ItemCatalog` 中确认本轮测试用掉落条目都能查到：

- `ItemId` 有值。
- `ItemId` 能映射到目标物品定义。
- 目标物品定义和实例类都有效。

如果掉落条目只配了数字 ID，但总表里查不到，就不要继续测“奖励进包”。

#### E. 输入与装备准备

开始 PIE 之前，程序员必须确认：

- 测试用采集动作已经有明确 `InputTag`。
- 当前 Pawn 的输入链能把这个 `InputTag` 广播到 Hero / ASC。
- 测试工具被装备后，ASC 里确实存在会响应这个 `InputTag` 的采集 Ability。

如果这些没确认，后面就会把“输入没接上”和“采集逻辑有问题”混成一个问题。

### 3. 代码阅读顺序

程序员第一次看这套系统时，不要先翻 `Definition`、`Registry`、`DataTable`。

固定按下面顺序读：

1. `Source/AegisOdyssey/Harvest/StateTree/STT_PlayHarvest.h/.cpp`
2. `Source/AegisOdyssey/Harvest/Abilities/GA_Harvest.h/.cpp`
3. `Source/AegisOdyssey/Harvest/Components/AOHarvestableComponent.h/.cpp`
4. `Source/AegisOdyssey/Harvest/System/AOHarvestResolver.h/.cpp`
5. `Source/AegisOdyssey/Harvest/Types/AOHarvestTypes.h`
6. `Source/AegisOdyssey/Inventory/AOInventoryStatics.h/.cpp`
7. `Source/AegisOdyssey/Inventory/AOInventoryComponent.h/.cpp`

这条顺序不是建议，是验收时默认的主链阅读顺序。

原因很简单：

- 先看状态如何启动。
- 再看 Ability 如何组织本次采集。
- 再看节点如何接受结果。
- 再看系统如何裁决。
- 最后看奖励如何真正进入库存。

### 4. 模块验收清单

手工测试开始前，程序员先按下面这组问题过一遍代码。

只要这里有一项答不上来，就先不要进运行时测试。

#### A. 状态入口检查

检查文件：

- `Source/AegisOdyssey/Harvest/StateTree/STT_PlayHarvest.h/.cpp`

必须确认：

- 这里负责的是“进入采集动作并等待 Ability 完成”，不是负责结算。
- 这里不会直接改库存。
- 这里不会直接推进节点进度。
- 长按和持续命中逻辑仍然留在 Ability 或动画链，不是在状态任务里自己写循环。

#### B. Ability 主链检查

检查文件：

- `Source/AegisOdyssey/Harvest/Abilities/GA_Harvest.h/.cpp`

必须确认：

- 采集主链统一从这里收口。
- 服务端是最终结算权威。
- 奖励只有在库存接收成功后，才允许真正推进节点进度。
- 失败路径不会错误地产生“节点被采掉，但奖励没拿到”的结果。

#### C. 节点组件检查

检查文件：

- `Source/AegisOdyssey/Harvest/Components/AOHarvestableComponent.h/.cpp`
- `Source/AegisOdyssey/Harvest/Interfaces/AOHarvestableTarget.h`

必须确认：

- 节点组件只维护节点自己的运行时状态。
- 节点组件负责“接不接受本次请求”，但不直接改背包。
- depleted / remaining progress 这些状态是挂在节点自己身上的，不是挂在角色身上的。

#### D. 统一结算检查

检查文件：

- `Source/AegisOdyssey/Harvest/System/AOHarvestResolver.h/.cpp`
- `Source/AegisOdyssey/Harvest/Types/AOHarvestTypes.h`

必须确认：

- 命中是否合法由系统层统一重判定。
- 工具修正、对象修正、掉落条目时机都在这里合并。
- `FAOHarvestResult` 足够让上层知道这次是成功、失败、掉了什么、是否 depleted。

#### E. 统一库存接收检查

检查文件：

- `Source/AegisOdyssey/Inventory/AOInventoryStatics.h/.cpp`
- `Source/AegisOdyssey/Inventory/AOInventoryComponent.h/.cpp`
- `Source/AegisOdyssey/Interaction/PickUpable.h/.cpp`

必须确认：

- 采集和拾取都走统一库存接收能力。
- 采集不是伪装成“掉地上再捡”的旧拾取流程。
- 统一接收入口是按优先级选容器，不是靠组件枚举顺序碰运气。

### 5. 手工测试总规则

下面的测试步骤不是参考示例，而是正式执行步骤。

执行时必须遵守下面几条：

- 每次只改一个变量，不要一边改工具、一边改节点、一边改背包容量。
- 每轮测试开始前，把玩家状态、节点状态、背包状态恢复到该轮要求的初始值。
- 没有看清结果前，不要连续多次按输入，避免把第一次结果和第二次结果混在一起。
- 如果某一步失败，先记录是“哪一步失败”，不要直接跳到修代码。

### 6. 手工测试一：单人基础成功链

目标：

- 验证“装备工具 -> 进入采集状态 -> 服务端结算 -> 奖励进库存 -> 节点进度推进”这一整条成功链。

开始前必须满足：

- 玩家背包有足够空间。
- 测试节点当前不是 depleted。
- 测试工具已经放进玩家可装备容器。
- `DT_ItemCatalog` 能查到本轮测试掉落的 `ItemId`。

执行步骤：

1. 打开测试关卡，把玩家出生点放在测试节点附近，保证进入游戏后不需要跑图找节点。
2. 在编辑器里选中测试节点，先确认它是否直接继承 `AAOHarvestableActor`；如果不是，再确认它自己实现了 `IAOHarvestableTarget`，并且身上确实挂有 `UAOHarvestableComponent`。
3. 打开这份 `HarvestableDefinition`，确认：
   - `TotalHarvestProgress` 大于 0；
   - 至少有一条 `DropEntries`；
   - 至少有一条掉落是稳定必出的，方便这轮验证奖励进包。
4. 打开测试工具的 Definition，按下面顺序逐项确认，不要只看一眼父类名字就算通过：
   - 先确认这份资产的父类型确实是 `UAOHarvestToolDefinition`。
     目的：确认它真的会进入采集工具链，而不是普通物品或普通装备链。
   - 再确认 `HarvestToolProfile` 字段不是空，并且你知道它当前指向的是哪一份 `UAOHarvestToolProfile` 资产。
     目的：确认这把工具拥有明确的机械语义身份，后续节点才能按 `ToolProfileResponses` 精确响应它。
   - 再确认 `Fragments` 数组里确实存在一个 `UAOHarvestToolFragment`。
     目的：`STT_PlayHarvest` 运行时就是从这里拿工具采集配置；缺这个 Fragment，采集主链会在工具解析阶段失败。
   - 点开这份 `UAOHarvestToolFragment`，至少确认：
     - `BaseHarvestPower` 大于 `0`；
     - 如果这轮要测长按采集，`bSupportsHoldHarvest` 已勾选，且 `HoldHarvestInterval` 大于 `0`；
     - `HitCheckConfig.MaxDistance` 不是一个明显错误的小值，例如 `0`。
       目的：确认这把工具不只是“有一个 Fragment”，而是真的有有效采集参数。
   - 最后确认这份工具 Definition 的 `AbilitySetsToGrant` 里已经接上采集 Ability 授予链。
     目的：确认装备后角色真的能拿到 `GA_Harvest`，否则后面测试会表现成“工具存在，但输入无效”。
5. 进入 PIE。
6. 打开背包或快捷栏界面，确认测试工具当前只是“在玩家身上可用”，还没有因为测试前状态异常而丢失。
7. 把测试工具真正装备到角色身上。
8. 装备完成后，不要立刻去砍节点，先确认角色已经进入“当前武器/工具已切换完成”的稳定状态。
9. 关闭背包界面，把准星对准测试节点。
10. 确认角色此时面对的是本轮要测试的那个节点，并且本次挥击路径会真实经过它。
11. 按一次采集输入，不要长按。
12. 观察角色是否进入采集动作，而不是播放普通攻击、普通交互或完全无响应。
13. 如果项目当前可见日志或调试输出，确认本次动作链实际命中了 `STT_PlayHarvest -> GA_Harvest`。
14. 等这一次采集动作结束，不要在动作中途连续按第二次。
15. 动作结束后，先看节点状态：
    - 节点没有凭空消失；
    - 节点如果不是一击采空型配置，应仍然留在场上；
    - 节点进度应该发生变化。
16. 再打开背包，确认本轮测试的掉落物已经进入统一库存接收入口选择的容器。
17. 确认奖励不是先生成落地拾取 Actor 再让玩家去捡，而是直接进入库存。
18. 再重复一次单次采集，确认这条链不是“第一次偶然成功，第二次断链”。

通过标准：

- 角色每次按下采集输入都能稳定进入采集动作。
- 节点进度在服务端结算成功后才发生变化。
- 奖励直接进入库存。
- 整条链没有绕过 `GA_Harvest -> Inventory Intake`。

失败时先排查：

- 没进动作：先查输入链、装备链、Ability 授予链。
- 进了动作但没结果：先查 `GA_Harvest` 到 `AOHarvestResolver`。
- 节点掉了但没奖励：优先查库存接收链。
- 奖励进了但节点没变化：优先查 `ApplyHarvestResult`。

### 7. 手工测试二：库存满时不结算

目标：

- 验证“库存不能完整接收奖励时，这次采集直接失败，节点不推进”这条规则。

开始前必须满足：

- 使用和测试一完全相同的节点与工具，避免把资产差异带进来。
- 玩家当前统一库存接收容器只剩很少空间，确保本轮奖励无法完整进入。

执行步骤：

1. 先按测试一的成功链确认这套节点和工具本身是能正常产出奖励的。
2. 退出 PIE，或者在同一轮里把玩家背包装到接近满格。
3. 重新进入 PIE 后，先打开背包，目视确认当前用于接收奖励的容器确实接近满格。
4. 不要猜“应该差不多满了”，要明确看到只剩不足以容纳本轮奖励的空间。
5. 再把同一把测试工具装备到角色身上。
6. 对准同一个仍可采的节点。
7. 只执行一次采集输入，不要连续多次按。
8. 等这次动作完整结束。
9. 动作结束后，先看库存：
   - 不应收到部分奖励；
   - 不应出现“只进去一半”的结果。
10. 再看节点：
    - 节点当前进度不应被扣减；
    - 节点不应因为这次失败采集而进入 depleted。
11. 再清理背包空间，恢复可接收状态。
12. 对同一个节点再次执行一次合法采集。
13. 确认恢复空间后，该节点仍能正常被采，说明上一次失败没有把节点状态偷偷推进。

通过标准：

- 满包时本次采集结果直接失败。
- 失败时节点进度不变。
- 失败时库存不收部分奖励。
- 清出空间后再次采集，节点仍按原状态继续工作。

失败时先排查：

- 如果节点进度变了：优先查“奖励提交成功前是否提前推进节点”。
- 如果收到了部分奖励：优先查统一库存接收是否仍允许部分成功。
- 如果失败后节点也失效：优先查失败路径是否误调用了 `ApplyHarvestResult`。

### 8. 手工测试三：多人同时采同一节点

目标：

- 验证“共享采集、无独占、服务器按请求顺序结算”这条多人规则。

开始前必须满足：

- 能启动两名玩家的同一测试会话。
- 两名玩家都能拿到相同的合法采集工具。
- 至少有一个测试节点不是一击采空，方便观察先后顺序。

执行步骤：

1. 启动双人测试会话。
2. 两名玩家都出生在同一测试节点附近，避免跑图导致时序差太大。
3. 两名玩家分别确认自己已经装备合法采集工具。
4. 两名玩家先不要马上开始采集，先都把视角对准同一个节点。
5. 由其中一名程序员倒数，尽量让两边在接近同一时刻按下采集输入。
6. 第一轮先观察普通命中阶段，不要只盯 depleted 瞬间。
7. 第二轮专门把节点打到接近 depleted，再让两名玩家几乎同时发起最后几次采集。
8. 观察结果时按下面顺序看：
   - 先看两边动作是否都能正常播出；
   - 再看服务器是否按顺序处理；
   - 最后看接近 depleted 时谁成功、谁失败。
9. 如果前一名玩家已经把节点采空，后一名玩家的请求应直接失败。
10. 失败的一方不应收到补偿奖励，也不应把这视为异常。
11. 再换一个新节点，交换两名玩家的站位和先后时机，再重复一次，避免误把站位因素当成规则本身。

通过标准：

- 节点不会先被某个玩家锁定成独占状态。
- 服务器按收到的合法请求顺序处理。
- 当前一个请求已经采空节点时，后一个请求直接失败即可。
- 后到失败请求不补偿、不重试、不把节点打成非法状态。

失败时先排查：

- 如果出现独占：优先查节点侧是否偷偷引入了 owner/lock 语义。
- 如果两边都拿到最后一击奖励：优先查服务端顺序结算与节点状态提交时机。
- 如果失败请求还拿到补偿：优先查失败分支和奖励分支是否没彻底分开。

### 9. 手工测试四：程序员阅读路径验收

目标：

- 验证这套代码的结构本身是否足够清楚，而不是只验证“功能能跑”。

执行步骤：

1. 让一名没有参与本轮实现的程序员参与这项验收。
2. 只把这份方案文档和当前代码交给他，不做额外口头讲解。
3. 要求他严格按本节第三部分给出的阅读顺序看代码。
4. 给他限定一个短时间窗口，例如 10 到 20 分钟，不允许他全项目随意乱搜。
5. 时间到后，要求他只回答下面四个问题：
   - 采集状态入口在哪个文件。
   - 服务端最终结算入口在哪个文件。
   - 节点运行时状态由哪个对象维护。
   - 奖励统一进入库存的入口在哪个文件。
6. 如果他回答不出来，不要先怪程序员不熟项目，先把责任视为本阶段命名、注释、结构不清晰。

通过标准：

- 他不需要全项目盲搜入口。
- 他不需要靠猜测拼主链。
- 他能快速指出主文件和边界文件。

### 10. 后续所有阶段都必须遵守的交付要求

- 每次交付后都必须给出固定阅读路径，不允许让程序员自己找入口。
- 每次交付后都必须给出完整可执行的手工测试步骤，不允许只写“自行测试”。
- 如果当前实现复用了旧系统基础能力，必须明确写清“复用了什么”，也必须明确写清“没有复用什么旧语义”。

## 十五、当前已经拍板的结论汇总

这一节只保留已经明确拍板的结论，避免后续讨论时和旧说法混淆。

### 1. 采集系统的设计中心是“采集”，不是“砍树”

### 2. 能不能被采，优先由对象决定，不靠工具侧写死 `SupportedNodeTags`

### 3. 采集是角色的一种状态，且应该贴近现有 StateTree 动作状态写法

### 4. 长按采集的目标是“逻辑离散、动画连续”

### 5. 奖励入包必须统一走服务端 `GA_Harvest` 收口与库存系统入口

### 6. 客户端可预测动作，不可最终裁决资源结果

### 7. 服务器必须权威决定命中是否合法、掉什么、掉多少、是否进包

### 8. 工具必须有自己的 Definition 边界，但仍应留在现有 Item/Equipment 体系里

### 9. Fragment 不是 Definition 的替代品，而是 Definition 内部的可组合配置块

### 10. 所有物品需要统一数字 ID，后续不再依赖物品名称做身份寻址

### 11. 物品数字 ID 统一走全项目大 DataTable；采集定义则通过手动维护的 HarvestRegistry 集中收集

### 12. 公式属于统一系统结算层，不属于对象 Definition，也不属于工具 Definition

### 13. 看现有项目是为了接入正确基础设施，不是为了让现有实现绑架当前需求

### 14. 多人同采默认共享、无独占、服务器顺序结算

### 15. 背包满时，这次采集直接不结算

### 16. 奖励时机按掉落条目自己配置，而不是系统统一写死

### 17. 采集判定只保留两种检查时机：本地轻量检查、服务器最终提交

### 18. 工具机械语义不写死成 C++ 枚举，而由可扩展的 HarvestToolProfile 资产承载

---

### 19. 后续每个阶段的代码交付，都必须同时提供必要中文注释、程序员阅读路径、模块验收入口与手工测试步骤

## 十六、当前阶段的一句话总收束

到目前为止，这套方案可以用一句话概括：

**采集系统是一套以采集对象 Definition、采集工具 Definition、角色采集状态、统一命中判定、统一结算器、统一入包链和服务器权威同步为核心的对象化采集框架。**

更完整一点说，就是：

- 采集对象自己拥有自己的基础采集语义
- 采集工具自己拥有自己的工具边界
- 工具机械语义通过可扩展 Profile 资产承载，而不是通过写死枚举承载
- 角色通过现有状态与 Ability 主链执行采集动作
- 采集判定只保留本地轻量检查与服务器最终提交两种时机
- 每次命中都要经过服务器校验
- 基础掉落、工具修正、角色 Buff 修正统一交给系统结算层
- 奖励时机按掉落条目自己配置
- 最终奖励统一走库存系统入包
- 采集资产通过手动维护的 HarvestRegistry 集中收集，物品数字 ID 则统一走全项目大 DataTable

后续只要继续沿着这份文档推进，就能尽量避免：

- 把采集系统写成砍树特例
- 把库存系统污染成采集系统子模块
- 把工具、对象、角色、公式的数据边界写乱
- 因为第一版图快而把联机与同步链写死

这就是我们当前阶段的采集系统设计基线。
