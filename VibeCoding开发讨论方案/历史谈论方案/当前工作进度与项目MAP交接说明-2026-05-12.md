# 当前工作进度与项目MAP交接说明

## 1. 这份文档的用途

这是一份给下一个 AI 或新接手程序员看的快速交接文档。

目标只有三个：

1. 先说清楚我们现在做到哪了。
2. 再说清楚已经确认的问题和根因是什么。
3. 最后给出下一位接手者必须先看的文档、关键代码入口，以及整个项目当前的模块 MAP。

如果时间很紧，只看这份文档和本文列出的前置文档，就应该能快速理解我们最近到底在做什么。

---

## 2. 当前阶段在做什么

当前主线工作，集中在以下几块：

1. 战斗系统、技能系统、状态树之间的衔接与落地。
2. 采集系统的对象化、状态驱动、工具驱动与结算同步框架。
3. 装备、工具、库存、快捷栏、使用入口的统一。
4. 采集工具与战斗武器的能力复用，尤其是动画驱动、输入驱动、判定时序驱动的统一思路。

目前已经非常明确的一条设计方向是：

- 采集不是“定时器到了就立刻采到”那种粗糙逻辑。
- 采集命中时序应该和战斗攻击一样，由动画窗口驱动。
- 工具未来既可以采集，也可以攻击，因此输入、状态树、蒙太奇、判定窗口这些设计都要尽量统一。

## 3. 这次阶段性工作已经确认的结果

### 3.1 采集系统方向已经明确

- 采集对象需要有明确的对象基类语义，不能只让“节点”这个词自己承担全部含义。
- 工具应该走和武器相近的设计思路，而不是单独搞一套很散的逻辑。
- 采集判定应该吃动画时序，不能靠 Delay 硬等。
- 重生暂时采用“对象自己维护定时器”的方向，不采用基于世界时间推进的成长状态机。
- 原因不是世界时间成长状态机不能做，而是当前阶段不做种植系统，先不要把系统复杂度提前拉高。

### 3.2 库存与使用职责边界已经重新明确

用户已经明确过一条很重要的边界：

- 库存组件只提供“使用入口”。
- 能不能使用、怎么使用、使用后消耗多少，属于物品实例自己决定。
- 库存层不应该承担过多具体物品语义，更不应该写一大堆特判去替物品做决定。

这条边界是后续继续清理库存、工具、装备、消耗品逻辑时的最高优先级约束之一。

### 3.3 工具 / 资源实例化策略当前暂不继续深化

我们讨论过：

- 工具是否需要像武器一样有自己的 Item/Instance 分层。
- 资源是否也需要 Instance。
- 可堆叠物品如果每次入包都 New 一个实例，会不会造成严重设计问题。

当前阶段结论是：

- 不继续把“所有可堆叠物都实例化”推进下去。
- 暂时只保留“可堆叠”和“不可堆叠”的基础区分。
- 不要因为追求理论统一，先把实现复杂度和同步复杂度做爆。

### 3.4 装备动画问题已经查清，不是表面配置问题

最近最关键的一次排查结果是：

- “快捷栏数字键切换时装备动画不播放”这个问题，根因已经确认。
- 它不是单纯的 `InputTag` 配置错了。
- 也不是简单的 `AbilitySpec` 没加 `AssetTag`。
- 更不是 `GiveAbility()` 一定异步、一定延迟这么粗糙的结论。

真正根因见第 4 节。

---

## 4. 已确认问题与根因

## 4.1 数字键切换装备时，装备动画不播放

### 现象

- 客户端有时正常。
- 单机模式和服务器路径下，按数字键切换快捷栏时，经常没有装备动画。
- 但滚轮切换快捷栏，或者把物品拖到当前选中槽位时，装备动画又可能是正常的。

### 已确认根因

根因不是“数字键入口没走到装备逻辑”，而是更深一层的 GAS 内部行为差异：

- 数字键切换这条调用链，发生在 `ASC->AbilityScopeLockCount > 0` 的上下文里。
- 在这个上下文里，`GiveAbility()` 虽然执行了，但新增能力不会立刻进入 `ActivatableAbilities.Items`。
- 这时新能力会先被压进 `AbilityPendingAdds`。
- 如果你在同一条调用链里立刻尝试通过 `AbilitySpec` 查找并触发刚刚动态授予的能力，就会失败。
- 滚轮切换时 `AbilityScopeLockCount == 0`，所以同样的动态授予能力会立即出现在 `ActivatableAbilities` 中，表现上就像“滚轮正常、数字键不正常”。

### 核心结论

不要再把这个问题理解成普通的标签配置问题。

真正的问题是：

**动态授予装备能力，并且在同一条调用链里立刻依赖这份新能力去播放装备动画，这个做法在特定 Scope Lock 场景下天然有风险。**

### 建议方向

如果未来要彻底规避这类问题，最稳定的方向是：

- 把装备动画相关能力改成角色常驻能力。
- 装备和卸下时只发送 `GameplayEvent`。
- 不要依赖“临时 GiveAbility 后马上激活它”这条链。

注意：

- 这个方向已经讨论清楚。
- 但是否由本轮继续实现，用户可能会自己处理。
- 所以下一个 AI 不要擅自继续大改，先确认用户最新意图。

### 必看说明文档

- `Notice/快捷栏数字键切换导致装备动画不播放-GAS Scope Lock问题排查说明.md`

那份文档里已经专门把现象、排查过程、`AbilityScopeLockCount` 的意义、为什么滚轮和数字键行为不一致，都单独写清楚了。

## 9. 下一个 AI 的建议推进顺序

如果下一个 AI 继续接手开发，建议顺序如下：

1. 先看本文和 `GAS Scope Lock` 问题文档，避免再重复踩“动态授予后立即激活”的坑。
2. 再看采集系统方案和战斗系统说明书，统一设计语言和说明书写法。
3. 然后核对当前代码里是否还有残留旧语义、临时兼容补丁、职责越界逻辑。
4. 如果要继续做装备动画链路，优先确认用户是否要把动画能力改成角色常驻能力。
5. 如果要继续做采集状态树，必须先参考现有战斗状态树的设计，不要再把配置硬塞进 GA。

## 10. 本次交接最重要的三条提醒

### 提醒一

用户非常在意职责边界。

不要因为“先能跑起来”就把库存、装备、工具、采集、状态树、GA 的责任乱塞。

### 提醒二

用户非常反感“兼容式残留代码”和“旧语义不删干净”。

如果确定废弃某个设计，就应当清理，不要保留看起来像 fallback 的脏入口。

### 提醒三

用户希望文档不是抽象描述，而是能指导程序员上手的“说明书”。

以后再写验收、配置、接入说明时，要默认读者会问：

- 在哪里配？
- 为什么这么配？
- 不这么配会怎样？
- 运行时应该看到什么现象？
- 如果结果不对，先查哪一步？

如果没回答这些问题，就还不算真正写清楚。

## 物品获取通知当前状态补充 - 2026-05-13

这一轮已经把“获取物品 UI 通知”正式接到统一库存入包链里了。

当前正式结论：

1. 这不是采集专属功能。
2. 这不是拾取专属功能。
3. 只要结果最终真正进入玩家背包，就应该能进入统一获取物品通知链。

当前已经落地的关键点：

1. 新增世界级库存消息层：
   - `Source/AegisOdyssey/Inventory/AOInventoryAcquisitionMessage.h`
   - `Source/AegisOdyssey/Inventory/AOInventoryMessageSubsystem.h/.cpp`
2. 通知广播挂在统一入包成功链，而不是各来源系统各自手写：
   - `Source/AegisOdyssey/Inventory/AOInventoryComponent.h/.cpp`
3. 当前只有玩家背包组件会正式对外发获取物品通知：
   - `Source/AegisOdyssey/Inventory/AOBackPackComponent.h`
4. HUD 桥接和可消费通知队列已经接好：
   - `Source/AegisOdyssey/UI/AOHUDViewModelComponent.h/.cpp`
   - `Source/AegisOdyssey/UI/ViewModel/AOInventoryAcquisitionViewData.h`
   - `Source/AegisOdyssey/UI/ViewModel/MVVM_HUD.h/.cpp`
   - `Source/AegisOdyssey/UI/Widgets/HUD/AOMainUI.h/.cpp`

当前给 UI / 蓝图的直接用法：

1. 最省事入口是 `UAOMainUI::ConsumePendingInventoryAcquisition()`。
2. 如果直接拿 HUD ViewModel，也可以用：
   - `OnInventoryAcquisitionReceived`
   - `ConsumePendingInventoryAcquisitionList()`
3. 每条通知已经整理好：
   - `DisplayName`
   - `Count`
   - `IconBrush`
   - `bHasValidIcon`

当前配置位置：

1. 物品名字来自 `UAOInventoryItemDefinition::DisplayName`
2. 通知图标来自 `UAOFragment_InventoryIcon`
3. 不是在通知系统里单独配“采集图标”或“拾取图标”

当前设计边界：

1. 容器库存变化不弹“获得物品”
2. 快捷栏 / 技能槽 / 其他中间库存变化不弹“获得物品”
3. 以后制作系统如果也想自动弹通知，正确做法是继续复用统一入包链，而不是自己再写一套 HUD 旁路

对应的正式说明书已经替换到：

- `Notice/消耗品与库存右键使用设计方案-现状-方案-实施阶段.md`

后续如果要继续做这块，优先顺序应该是：

1. 先做正式的 Toast / 提示条 Widget
2. 再决定是否把这条通知流从 `UMVVM_HUD` 继续拆成独立子 ViewModel
3. 不要回头把采集、拾取、制作各自补一套专属通知逻辑
