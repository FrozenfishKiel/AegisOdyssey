这部分不是未来计划，而是当前已经改进代码里的事实。

## 第二章 制造系统当前真实设计口径

### 2.1 当前边界先只做角色身上的制造系统

虽然整个方案一开始就明确要兼容“可制造对象”，但当前首版边界仍然是：

- **先做角色身上的制造系统**

这意味着当前默认上下文是：

1. 配方来源是角色。
2. 材料扫描范围是角色当前允许参与制造的全部库存。
3. 制造速度加成先按角色身上的总制造加成走。
4. 产物默认先回角色统一库存入口。

这不是说以后不做工作台。

真正的意思是：

**当前已经写下来的结构，必须兼容工作台，但当前首版落地优先收在角色制造闭环。**

### 2.2 物品身份规则已经被用户明确钉死

这一条非常关键，后续任何 AI 接手都不能改口径。

当前项目的物品身份规则是：

**物品有且只有一个物品 ID。**

具体含义是：

1. 全项目物品总表负责收揽物品身份。
2. 通过 `ItemId` 查到物品定义。
3. 制造系统不能自己再发明一套平行物品身份。
4. 配方里涉及材料和产物时，本质都应该围绕 `ItemId` 组织。

所以后续如果再讨论配方设计，不要再走“每个配方单独挂另一套资产身份”的方向。

这件事不是编码风格选择，而是当前项目的硬原则。

### 2.3 当前配方和来源表的关系

从现有方案和代码状态来看，当前制造链至少包含两层数据语义：

1. 制造配方表。
2. 制造来源表。

其中角色这边的来源表，会和 `PawnData` 上的配置关联。

也就是说，配方系统当前不是简单的“全局一张配方表然后所有角色天生全开”，而是已经有“角色可访问哪些配方”的来源层设计。

这和最初讨论时的需求是一致的：

- 角色身上的制作表会随着等级逐渐开放。
- 可交互对象的制作表以后会固定提供。

### 2.4 材料池口径已经确定

用户后来明确纠正过一次口径：

**当前角色制造支持扫描角色身上全部库存。**

这句话不能再写偏成“只扫背包”。

因为用户后来专门强调过一次：

- 不是单指背包，是库存。

所以后续任何文档、代码解释、测试说明里，只要提材料检索范围，都应该写成：

- 角色当前允许参与制造的全部库存组件集合

而不是只写 `BackPack`。

### 2.5 入队时就扣材料，这条已经定了

当前制造系统的一个正式规则是：

- **入队就扣材料**

不是完成时扣，也不是开始激活时扣。

这样做的直接影响是：

1. UI 上能否点击制造，要先看材料和容量。
2. 真正成功入队后，材料就已经被占用并扣掉。
3. 后续任务执行中途不允许取消，因此也不需要补取消返还链。

### 2.6 队列、取消、中断、死亡口径已经定了

这几条都已经在讨论里定过口径。

第一，制造要做队列。

第二，中途不能取消。

第三，如果角色异常中断，比如死亡，当前规则先按：

- **直接清空队列，不返还材料**

这条规则比较狠，但它是当前用户明确接受的边界，不要在未确认前擅自改成“返还一部分”或者“保留未完成进度”。

### 2.7 完成时包满的兜底也已经定了

当前产物发放规则不是“完成前锁死必须有足够空间，否则不让做到底”这么单一。

已经明确补了一条完成兜底：

- 如果制造完成时不能入包，就把物品掉到角色脚下。

当前掉落边界是：

1. 掉到角色脚下。
2. 先持续五分钟。
3. 可以被拾取。
4. 不做所有权保护。

这条规则非常重要，因为它直接影响制造完成路径的容错设计。

### 2.8 制造速度加成口径也已经定了

GAS 派生属性的问题，用户明确说已经解决。

所以当前角色制造这边，制造时间加成口径是：

- 角色身上有一个总制造加成属性。
- 语义类似 Attack 这种总属性。
- 制造组件读取这个总属性，算最终制造时长。

从代码入口看，当前相关点包括：

- `UAOCraftingComponent::ResolveCraftingDurationSeconds(...)`
- `UAOCraftingComponent::ResolveTotalCraftingSpeedBonus()`
- `AOCombatAttributeSet` 里的 `CraftingSpeedBonus`

这意味着当前方向已经不是“先写死一个乘数”，而是已经接入正式属性链。

## 第三章 制造系统当前真实代码状态

### 3.1 `UAOCraftingComponent` 已经是主入口

当前主组件是：

- `Source/AegisOdyssey/Crafting/Components/AOCraftingComponent.h`
- `Source/AegisOdyssey/Crafting/Components/AOCraftingComponent.cpp`

从头文件就能看出来，它现在至少已经承担了这些职责：

1. 接收入队请求。
2. 保存制造队列。
3. 构建配方列表视图数据。
4. 构建配方详情视图数据。
5. 构建队列视图数据。
6. 处理开始下一个激活项。
7. 处理完成结算。
8. 解析制造速度加成。
9. 处理掉落到世界的兜底。
10. 处理运行中断。

这说明当前组件已经不是一个空壳。

### 3.2 当前队列结构已经是正式结构

当前队列条目结构是：

- `FAOCraftingQueueEntry`

里面已经有：

1. `QueueEntryId`
2. `RecipeRowName`
3. `State`
4. `ResolvedDurationSeconds`
5. `StartServerWorldTimeSeconds`
6. `ExpectedFinishServerWorldTimeSeconds`
7. `OutputEntries`

这说明当前制造系统不是只做“立刻产出”，而是已经完整走进了：

- 服务端时间驱动的队列制造模型

### 3.3 当前材料消耗已经不是 UI 假扣

当前制造组件内部已经有：

1. `BuildMaterialConsumePlan(...)`
2. `ExecuteMaterialConsumePlan(...)`
3. `RollbackMaterialConsumePlan(...)`
4. `CountAvailableMaterialByItemId(...)`

这说明材料扣除并不是只停留在表现层禁点，而是服务端运行时已经有正式的消耗计划和回滚结构。

虽然用户说“不需要在内部做太多判断”，但那句话的真实意思更像是：

- 表现层先挡住明显不合法点击

不是说服务端可以完全不要收口。

当前代码层面看，也确实没有放弃服务端收口。

### 3.4 当前产物发放已经考虑统一入包和掉落兜底

当前制造组件内部已经有：

1. `BuildOutputReceiveBatch(...)`
2. `DropCraftingOutputsToWorld(...)`

这和当前方案口径是对上的。

也就是说，当前制造完成路径已经不是“自己私发一份物品”，而是明显围绕：

1. 先翻译成统一入包批次。
2. 能入包就走统一库存入口。
3. 不能入包再走掉落兜底。

这条思路后续不要打散。

### 3.5 当前角色已经挂上制造组件

当前角色接线已经存在：

- `Source/AegisOdyssey/Character/AOCharacter.h`
- `Source/AegisOdyssey/Character/AOCharacter.cpp`

这意味着当前制造不是“只有 UI 和 ViewModel，角色本体还没接”，而是角色侧已有真实组件挂接。

### 3.6 当前 `PawnData` 已经进入制造来源链

当前 `AOPawnData` 已经进入制造来源配置链。

后续如果发现某个角色没有可制造配方，优先查：

1. 角色当前到底吃的是哪份 `PawnData`。
2. 那份 `PawnData` 上是否配了制造来源表。

不要一上来先怀疑 `MVVM_Crafting`。

## 第四章 制造系统当前 MVVM 与 UI 状态

### 4.1 当前制造 ViewModel 已经存在

当前制造主 ViewModel 是：

- `Source/AegisOdyssey/UI/ViewModel/MVVM_Crafting.h`
- `Source/AegisOdyssey/UI/ViewModel/MVVM_Crafting.cpp`

它当前已经承接：

1. 当前观察的制造组件。
2. 当前选中的配方行名。
3. 配方列表快照。
4. 配方详情快照。
5. 队列列表快照。
6. 通过 ViewModel 发起入队请求。

所以当前制造 UI 的推荐方向很明确：

**Widget 和蓝图应该通过 `UMVVM_Crafting` 统一拿数据、统一发请求，而不是直接四处找 `UAOCraftingComponent`。**

### 4.2 当前制造请求入口已经开始往 ViewModel 收

这轮里已经明确加过一层用户意图：

- `RequestEnqueueSelectedRecipe()`

这件事的意义不是只多了一个便利函数。

真正的意义是：

1. UI 选中哪条配方，应该由 ViewModel 统一维护。
2. “点击当前选中配方去制造”这件事，也应该回收到 ViewModel。
3. Widget 层不再自己手拼“当前选中行名 + 直接调组件”这种零散入口。

这和右键菜单收束时的思路是一致的。

## 第五章 库存右键菜单当前真实状态

这一章只写最关键的事实，细节请直接看：

- [[库存右键菜单与MVVM最新收束说明]]

### 5.1 当前右键菜单主链

当前主链在：

- `Source/AegisOdyssey/UI/Widgets/Inventory/AOInventoryUI.cpp`

主路径是：

1. 恢复右键来源。
2. 生成动作决议。
3. 从 `SourceInventory` 取菜单主 ViewModel。
4. 把本次快照写进 `UMVVM_InventoryItemContextMenu`。
5. 菜单 Widget 消费这份 ViewModel。

### 5.2 当前唯一正确的 ViewModel 来源

当前正确来源是：

- `SourceInventory->GetOrCreateContextMenuViewModel()`

不是：

- `UMVVM_InventoryMenu`
- 统一背包宿主
- 别的全局 UI 宿主缓存

### 5.3 当前 `InventoryComponent` 只存，不解耦

这一条是用户明确强调的。

库存组件现在在右键菜单这条链里只做一件事：

- 存一份属于自己的菜单主 ViewModel

不要再往里面补：

1. 统一宿主解析。
2. 玩家控制器推断。
3. 背包兜底。
4. “如果没有就帮你猜一个来源”。

### 5.4 当前仍然保留一个临时蓝图路径兜底

如果 `InventoryItemContextMenuClass` 为空，当前代码会尝试加载：

- `/Game/Games/UI/InventoryMenu/Information/WBP_InventoryContext_Action.WBP_InventoryContext_Action_C`

这条是按用户要求留的临时兜底。

它现在能帮助调试，但也显然是后续风险点，因为名字看起来不像菜单宿主蓝图。

后续如果 UI 这边继续收束，最好把菜单宿主类和动作项类的蓝图接线重新彻底理清楚。

### 5.5 当前 MVVM 蓝图命名坑不能再踩

动作项 Widget 这边，C++ 已经有：

- `MVVM_InventoryItemContextAction`

所以蓝图里不要再重复创建一个同名属性或同名 Source。

否则会直接报：

- property already exists
- source invalid
- viewmodel name could not be found

这类错误现在已经定位过根因，不要让下一个 AI 又从头排。

## 第六章 当前明确不能乱改的用户约束

这一章非常重要。后续接手时，优先遵守这些约束。

### 6.1 不要脱离现有方案发散

用户已经多次强调：

- 不要重编方案。
- 不要在无关模块乱改。
- 不要为了“更优雅”去推翻当前收束好的结构。

所以后续动作应该是：

- 顺着当前方案和现有代码补齐

不是：

- 重新设计一套更理想的库存系统或制造系统

### 6.2 物品 ID 原则不能动

再次强调：

- 物品有且只有一个 `ItemId`

任何接手的人如果想在制造、右键、掉落、背包展示里引入第二套物品身份，都是越界。

### 6.3 `InventoryComponent` 在右键菜单上不要继续加逻辑

当前用户明确要求：

- 它只负责存菜单 ViewModel

别再往里加来源推断、宿主解耦、统一路由。

### 6.4 代码不要替蓝图写 UI 样式

用户已经明确反感这些做法：

1. C++ 手写 Slate 样式按钮。
2. C++ 越界改 UI 大小。
3. C++ 自动做一堆默认视觉行为。

所以后续如果还要继续改右键菜单 UI，记住边界：

- 代码做逻辑和数据
- 蓝图做样式和排版

### 6.5 RPC 尽量少写，但该写的要写

用户对网络这边的要求是：

- 不是不准写 RPC
- 而是能少写就少写
- 状态同步优先，非必要不要为了方便堆一堆 RPC

这个口径尤其影响制造系统后续扩展时的网络设计。

## 第七章 当前最值得警惕的风险点

### 7.1 右键菜单蓝图类路径目前看起来不稳定

虽然现在代码有兜底，但那条路径的命名明显可疑。

后续如果又出现：

1. `AddToViewport()` 进了但看不见菜单。
2. 菜单宿主出现了但没有动作项。
3. 动作项蓝图和菜单宿主蓝图概念混用。

优先从蓝图类配置和路径正确性查，不要先怀疑逻辑层。

### 7.2 右键菜单很容易在“复用 + 切换来源”时出现旧快照残留

这类问题我们已经踩过一次。

后续如果又出现“第一次对，切换后错”，优先查：

1. 当前 `SourceInventory` 是谁。
2. 当前拿到的 ViewModel 挂在哪个组件上。
3. 打开前是否真的重灌了完整快照。
4. 动作项 ViewModel 和动作项 Widget 是否一一刷新到了最新状态。

### 7.3 制造系统虽然代码已落地，但仍然需要完整联调验证

当前制造系统虽然已经不是纸面方案，但它仍然有明显的联调风险：

1. 配方表与来源表是否都在资源层接对。
2. `PawnData` 是否确实给对角色。
3. 材料扫描是否真的覆盖了角色全部允许库存。
4. 统一入包与完成掉落兜底是否真的按预期走通。
5. `CraftingSpeedBonus` 是否真的影响最终时长。
6. 中断清队且不返还材料的规则是否按当前方案生效。

也就是说，当前更像“框架已落地，接下来要做系统性验收”，不是“从零开始设计”。
