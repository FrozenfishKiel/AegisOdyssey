更新时间：2026-05-29

## 第一章 这份设计方案现在在解决什么

前一份预研笔记，已经把需求侧的主干收出来了。  
现在这份文档不再停留在“我们想做什么”，而是要进一步回答：

**结合 AegisOdyssey 当前的工程现状，如果以后真的开始做多人联机，我们应该怎么设计这套系统。**

这里要强调两点。

第一，这份文档仍然不是实施计划。  
它不会细到“今天改哪个文件、明天写哪个函数”，也不会直接展开成开发任务清单。

第二，这份文档也不是泛泛而谈的 Unreal 联机教程。  
它要尽量贴着当前项目的真实结构来写，尤其是下面这些已经存在的东西：

1. `UAOGameInstance : UCommonGameInstance`
2. `UAOGameInstanceSubsystem`
3. `AAOGameMode`
4. `CommonUser`
5. `CommonSessionSubsystem`
6. 当前项目已经存在的服务端权威玩法同步思路

换句话说，这份设计方案真正要做的事，是把“联机需求”翻译成“项目内该怎么分层、怎么挂接、为什么这么挂接”。

## 第二章 当前项目的联机目标，先收成什么样

如果把当前需求方案压成一句正式一点的话，那么本项目的多人联机目标可以先定义成：

**AegisOdyssey 未来希望成为一个发布在 Steam PC 场景下、以互联网联机为主、支持玩家自托管并预留独立服务器托管升级路径的多人游戏。**

这句话其实已经决定了后面设计时的很多边界。

### 2.1 这里的“联机目标”不是局域网演示

虽然项目可以保留局域网联机能力，但它不是主目标。  
主目标仍然是：两个处于不同网络环境下的玩家，能够通过打包后的正式游戏版本进入同一局游戏。

这意味着后面的系统设计，不能建立在 PIE 双开、编辑器内多实例、或者“只要同网就能玩”的假设上。

### 2.2 这里的“多人模式”要同时容纳两种服务器承载方式

这一点是本次需求里最关键的地方。

项目最终希望容纳的，不是单一联机形态，而是两种并存的产品形态：

1. **玩家自托管**
玩家自己创建一局，自己的游戏进程同时承担服务器职责，朋友加入这局。

2. **独立服务器托管**
一台单独的服务器进程运行在本机、另一台电脑、实验室机器，或者云服务器上，玩家只是去连接它。

从 Unreal 的语义看，这两条线大致对应：

1. `Listen Server`
2. `Dedicated Server`

但从玩家产品语言上，不需要一开始就把这两个术语直接暴露给玩家。  
系统设计时要知道它们的区别，界面表达可以更自然。

### 2.3 首版目标不是大规模商业化运营

当前阶段的现实约束也很清楚。  
项目拥有明确的联机目标，但没有高成本长期运营大型官方服务器的条件。

所以首版设计目标不应该设成：

1. 一开始就做复杂的官方服务器集群
2. 一开始就做跨区、扩容、运维和高可用体系
3. 一开始就把商业化后期那一整套成本和复杂度背上

更合理的设计目标应该是：

1. 先把多人链路做通
2. 先把玩家入口做清楚
3. 先支持低成本可验证的在线联机
4. 工程上保留 Dedicated Server 升级路径

这意味着后面的设计核心，不是“做最大”，而是“做完整、做干净、可扩展”。

## 第三章 先不要急着想 UI，先把系统分层想清楚

多人联机最容易出问题的地方，就是把所有事情都塞进“联机功能”这四个字里。

但对项目设计来说，联机不是一个单点功能，它至少要拆成下面四层：

1. **产品入口层**
2. **会话与连接层**
3. **游戏世界与玩法同步层**
4. **服务器运行与部署层**

如果这四层在设计阶段就混在一起，后面很容易出现两种坏结果：

1. UI 写得很早，但背后没有稳定会话链路
2. 底层能联机，但玩家根本没有一条清楚的进入路径

所以这份方案后面会一直按这四层去讲。

### 3.1 产品入口层在解决什么

产品入口层不负责真正联网。  
它负责的是让玩家知道：

1. 我该从哪里进入多人模式
2. 我要自己开一局，还是加入别人的一局
3. 当前系统有没有给我明确、稳定、可预期的操作路径

它对应的是主界面、多人菜单、建局页、加入页这些玩家可见内容。

### 3.2 会话与连接层在解决什么

这一层是真正把“玩家点了按钮”翻译成“建立联机关系”的地方。

它负责的是：

1. 创建会话
2. 搜索会话
3. 加入会话
4. 处理登录、在线权限、连接状态
5. 触发 `ServerTravel` / `ClientTravel`

从当前项目来看，这一层最值得利用的现成基础，就是：

1. `UCommonUserSubsystem`
2. `UCommonSessionSubsystem`

这说明项目并不是要从零手写一整套会话基础设施。

### 3.3 游戏世界与玩法同步层在解决什么

这一层才是我们平时最容易想到的“联机玩法本体”。

它负责的是：

1. 玩家进入地图后怎么生成
2. 当前世界如何确定加载哪套玩法体验
3. 哪些状态是服务端真相
4. 哪些状态复制给客户端
5. 哪些状态只是本地显示

从当前项目来看，这一层其实已经有不少基础了。  
尤其是：

1. `AAOGameMode`
2. `UAOExperienceManagerComponent`
3. `OwnerOnly Session Snapshot` 这一类知识库里已经明确存在的玩法同步边界

这意味着当前项目并不是零联机思维，而是缺一层把这些玩法基础接到正式多人产品流上的骨架。

### 3.4 服务器运行与部署层在解决什么

这一层最容易被学生项目忽略。  
因为它在写功能时不显眼，但一旦要脱离编辑器，它就马上变成硬问题。

它负责的是：

1. 有没有单独的 `Server Target`
2. 能不能产出独立服务器程序
3. 客户端怎么连到它
4. 后面如果迁移到远程机器，结构上有没有阻碍

当前项目最明显的工程缺口，就在这一层。  
现在只有：

1. `AegisOdyssey.Target.cs`
2. `AegisOdysseyEditor.Target.cs`

还没有独立的 `Server Target`。

## 第四章 结合当前工程，现状到底说明了什么

要做设计，不能只讲理想结构，还得先看项目现在站在哪。

从当前工程入口来看，AegisOdyssey 的现状可以概括成一句话：

**玩法同步层已经有联机土壤，会话基础设施有一部分现成能力，但项目级联机产品骨架和 Dedicated Server 工程基线还没有真正立起来。**

这句话可以拆开讲。

### 4.1 当前已有的会话基础，不应该浪费

项目已经启用了：

1. `CommonGame`
2. `CommonUser`
3. `OnlineFramework`
4. `Networking`
5. `NetCore`

尤其是 `CommonUser` 插件里，已经包含现成的：

1. 用户初始化与在线登录入口
2. 会话创建请求对象
3. 会话搜索请求对象
4. 建局、搜局、入局的基础流程
5. `ServerTravel` / `ClientTravel` 相关承接

这意味着设计上完全没必要绕开这套基础设施，另起一套平行的“自制会话系统”。

对当前项目更合理的做法应该是：

**以 `UCommonUserSubsystem` 和 `UCommonSessionSubsystem` 为底座，在项目层增加 AegisOdyssey 自己的业务封装层。**

### 4.2 当前 GameInstance 很轻，这反而是个好事

当前 `UAOGameInstance` 只是一个很薄的 `UCommonGameInstance` 子类，几乎还没有承载联机业务逻辑。

这件事表面上看像“还没做东西”，但从设计角度反而是好事。  
因为这说明我们还没有被一套错误的旧逻辑绑死。

这意味着后面可以比较干净地在 `GameInstance` 维度引入：

1. 联机入口协调逻辑
2. 会话状态持有逻辑
3. 菜单层可消费的联机 ViewModel / 状态对象

不会和大量遗留逻辑强耦合。

### 4.3 当前 GameInstanceSubsystem 已经存在，但职责还很薄

当前 `UAOGameInstanceSubsystem` 主要承载的是 Escape 菜单相关 ViewModel。

这说明项目已经接受了一种思路：  
**把跨关卡、跨世界、偏全局的 UI / 状态协调逻辑放在 `GameInstanceSubsystem` 里。**

这个模式对联机系统是有价值的。  
因为联机菜单、会话状态、当前联机模式选择、当前房主参数、当前搜索结果这些东西，本来就更适合挂在 `GameInstance` 级别，而不是某张具体地图里的 Actor 上。

所以后面设计多人系统时，一个自然的方向就是：

**新增一个专门的多人联机子系统，而不是把多人逻辑硬塞进现有 Escape 子系统里。**

### 4.4 当前 GameMode / Experience 流已经具备正式多人玩法承载能力

`AAOGameMode` 当前已经承担了标准的服务端世界管理职责：

1. 初始化世界
2. 选择 Experience
3. 等待 Experience 加载
4. 处理玩家登录后生成
5. 控制 Pawn、HUD、重生与 PlayerStart 相关流程

这说明进入一局游戏之后，项目并不是没有服务端结构。  
恰恰相反，它已经有了比较像样的服务端世界控制中心。

所以多人系统设计时，不应该去发明第二套“进入游戏后如何生成玩家”的平行流程。  
而应该让会话层最终把玩家导向一张使用现有 `AAOGameMode` / `Experience` 流的可联机世界。

也就是说，设计重点不是替换 `AAOGameMode`，而是把玩家从菜单入口稳定送进 `AAOGameMode` 管理的多人地图。

### 4.5 当前最大的工程性缺口，仍然是 Dedicated Server 基线

这是最需要明确写进设计方案的现实问题。

当前工程没有独立 `Server Target`，而且 `Build.cs` 里项目级 `OnlineSubsystem` 依赖仍然处于注释状态。

这说明：

1. 项目还没有正式进入服务器独立打包阶段
2. 项目还没有正式决定在线服务路线

所以设计方案必须正面承认这一点，而不能假装这些基础已经存在。

## 第五章 针对当前项目，推荐的总体设计方向是什么

如果把所有约束、目标和工程现状一起考虑，那么我认为 AegisOdyssey 的多人系统最合理的总体设计方向应该是：

**项目层新增一套“联机产品协调层”，底层复用 CommonUser / CommonSession，会话成功后进入现有 GameMode / Experience 驱动的多人地图；首版优先跑通互联网下的玩家自托管闭环，同时从工程结构上预留 Dedicated Server 升级路径。**

这句话里每个部分都有原因。

### 5.1 为什么不能直接把多人逻辑散落进各个 Widget

因为多人系统不是单纯 UI 功能。

如果把登录、建局、搜局、入局、状态同步、失败提示这些逻辑直接分散写在多个 Widget 蓝图或零散 C++ Widget 类里，后面一定会出现：

1. 页面切换和会话状态绑定在一起
2. 失败重试路径混乱
3. 换一种加入方式就要重做一套逻辑
4. Dedicated Server 支持进来后入口树越来越乱

所以设计上一定要有一个比 Widget 更高一层的协调中心。

### 5.2 为什么不建议直接在 GameMode 里做联机菜单逻辑

因为 `GameMode` 是世界内、服务端侧的运行时对象。  
它适合管“进入游戏以后”的世界规则，不适合管“进入游戏之前”的产品菜单流程。

多人菜单、建局参数、搜索结果、当前选中的加入方式，这些都属于：

1. 更偏客户端入口
2. 更偏跨地图存在
3. 更偏 GameInstance 生命周期

所以它们不应该放进 `AAOGameMode`。

### 5.3 为什么要在项目层引入“联机产品协调层”

因为当前项目需要的不是再造底层会话系统，而是要有一层把：

1. 玩家可见入口
2. CommonUser 登录/权限
3. CommonSession 建局/搜局/入局
4. 项目自己的地图、模式、人数、是否公开等产品参数

统一组织起来。

这层的职责，不是直接承担所有在线功能，而是做“业务翻译器”。

举个最直观的例子：

玩家点了 `创建游戏`，这对底层来说不等于一句固定 API。  
中间还要经过：

1. 当前用户是否已具备在线游玩资格
2. 当前选择的是互联网还是 LAN
3. 当前局是玩家自托管还是将来扩展成独立服务器会话
4. 要进哪张地图
5. 最大玩家数是多少
6. 是否公开可搜

这些东西都不应该散落在 UI 里。

## 第六章 推荐的系统结构，应该长什么样

如果按当前项目的现状去落，我建议多人联机系统先收成下面这套结构。

### 6.1 第一层：现有底层能力继续保留

这一层不需要你自己重新发明。

直接复用：

1. `UCommonUserSubsystem`
2. `UCommonSessionSubsystem`
3. `UCommonGameInstance`
4. Unreal 原生 `ServerTravel` / `ClientTravel`

这一层的职责是：

1. 用户初始化
2. 在线权限检查
3. 会话创建/搜索/加入
4. 底层连接与切图

这层尽量少改，主要做“用”，而不是“重写”。

### 6.2 第二层：AegisOdyssey 自己的联机协调子系统

这是当前项目最需要新增的一层。

建议新增一个专用的 `GameInstanceSubsystem`，它的职责大致应该是：

1. 持有当前多人入口状态
2. 持有当前建局参数
3. 发起在线登录或本地初始化
4. 组装 `HostSessionRequest`
5. 组装 `SearchSessionRequest`
6. 接收会话完成事件
7. 向 UI 暴露可读状态
8. 统一处理联机错误与失败提示

这层不是底层网络层，也不是世界玩法层。  
它的作用是把“产品动作”翻译成“底层会话动作”。

如果用一句更直接的话说：

**Widget 不应该直接懂得怎么建会话，Widget 应该只会对这个子系统说‘我想创建一局’。**

### 6.3 第三层：多人菜单与联机 ViewModel 层

这一层是给 UI 用的。

建议后面把下面这些东西都整理成 ViewModel / UI 可绑定状态：

1. 当前是否正在登录
2. 当前是否正在搜索房间
3. 当前是否正在创建游戏
4. 当前是否正在加入游戏
5. 当前最近一次联机失败原因
6. 当前搜索结果列表
7. 当前建局配置

这一层的目标是：  
**让多人菜单只负责表现，不直接承担业务判断。**

当前项目已经接受 `MVVM` 和 `CommonUI` 组合，这一点对联机菜单是有利的。  
后面完全可以沿用同样思路，而不是回到“按钮里全写逻辑”的旧模式。

### 6.4 第四层：现有 GameMode / Experience 继续作为对局承载层

当会话创建成功或加入成功之后，真正的游戏世界仍然应该由现有系统承载：

1. `AAOGameMode`
2. `AAOGameState`
3. `UAOExperienceManagerComponent`
4. 当前玩家生成与玩法同步链

这层不需要因为要做多人菜单就推翻重做。  
多人系统要做的是把玩家可靠地送进这层，而不是替代这层。

### 6.5 第五层：Dedicated Server 目标与部署层作为未来扩展层

这一层首版不需要做成复杂运营系统，但结构上必须预留。

最起码要为以后留出：

1. 单独 `Server Target`
2. 单独服务器打包路径
3. 服务器模式下的启动参数规范
4. 将来服务器列表 / 直接连接 的接入位置

这样首版即使先用玩家自托管，也不会把未来 Dedicated Server 路线堵死。

## 第七章 玩家入口设计，为什么现在这样收是合理的

前面的预研笔记已经把多人入口先压成了：

`主界面`

1. 单人游戏
2. 多人游戏
3. 设置
4. 退出

`多人游戏`

1. 创建游戏
2. 加入游戏
3. 返回

这个入口骨架看起来很简单，但从系统设计角度，它其实是对的。

### 7.1 为什么首版只保留“创建游戏 / 加入游戏”

因为当前项目真正需要的是稳定的闭环，而不是华丽的分类。

如果现在一开始就把：

1. 服务器列表
2. 好友游戏
3. 房间浏览器
4. 直接连接
5. 匹配
6. 推荐服务器

全部铺出来，设计上会过早暴露太多还没稳定的分支。

对首版来说，更合理的是先把产品入口收成：

1. 我自己开一局
2. 我去加入一局

这和底层会话系统的主能力也是一致的。

### 7.2 “创建游戏”当前应该怎么定义

从当前需求和预算约束看，`创建游戏` 首版默认应该定义成：

**玩家自己创建一局多人对局，并由自己的游戏进程承载这局服务器。**

这意味着它在技术语义上更接近 `Listen Server`，但在产品文案上不必直接叫这个名字。

这条路径的价值在于：

1. 成本最低
2. 最容易证明正式打包联机链路成立
3. 最适合作为学生项目的第一阶段在线演示

### 7.3 “加入游戏”当前应该怎么定义

`加入游戏` 首版更适合被设计成一个总入口，而不是一开始就硬拆成很多页。

它的含义应该是：

**玩家希望进入别人的一局游戏，但当前具体用哪种加入方式，可以随着版本迭代慢慢展开。**

所以系统设计上，`加入游戏` 下面以后可以继续承载：

1. 好友加入
2. 房间列表
3. 服务器列表
4. 直接连接

这意味着当前入口结构是具备扩展性的。

## 第八章 首版联机 MVP，针对当前项目到底要设计成什么

如果只谈 AegisOdyssey 当前阶段最合理的第一版，我建议首版联机 `MVP` 的设计目标直接收成下面这句话：

**玩家通过打包后的正式客户端，能够进入多人菜单，创建一局互联网联机游戏，另一名玩家能够加入这局，并共同进入现有玩法地图完成基础游玩。**

这句话里已经隐含了范围控制。

### 8.1 MVP 必须成立的内容

首版至少要成立下面这些东西。

#### 第一，正式客户端入口成立

也就是：

1. 不是只在 PIE 里能跑
2. 主菜单里真的有多人入口
3. 玩家能从正式客户端点进去

#### 第二，在线创建一局成立

也就是：

1. 玩家可以创建游戏
2. 创建动作会触发会话创建
3. 创建成功后能够进入多人地图

#### 第三，另一名玩家加入成立

也就是：

1. 另一名玩家可以看到这局
2. 可以发起加入
3. 加入成功后能够被送进同一地图

#### 第四，进入地图后的基本多人玩法成立

这一步不要求首版所有玩法都完美联机化。  
但至少要有一条你最核心、最能代表项目的玩法链，在联机下是成立的。

这里一定要强调：  
**首版验证的重点不是“所有功能都联机化”，而是“正式多人链路真的成立”。**

#### 第五，退出与失败路径成立

这是很多项目容易漏掉的地方。

首版至少要有：

1. 创建失败后的回退
2. 加入失败后的提示
3. 断开后的返回路径
4. 退出当前局后的返回逻辑

如果这些路径没有设计，系统表面看像能玩，实质上仍然不完整。

### 8.2 MVP 当前不应该强行塞进去的内容

首版设计里，下面这些内容都不应该抢在闭环之前：

1. 复杂大厅系统
2. 匹配
3. 跨区
4. 断线重连
5. 大型服务器浏览器
6. 高级筛选器
7. 官方服运营后台

不是因为这些不重要，而是因为对当前项目阶段来说，它们会大幅稀释精力。

## 第九章 针对当前项目，推荐的阶段化设计顺序是什么

设计方案最关键的，不是列出所有想法，而是决定推进顺序。

对 AegisOdyssey 来说，我建议后面真正做的时候按下面这个顺序推进。

### 9.1 第一阶段：先立项目级联机产品骨架

这一步解决的是“入口”和“协调中心”问题。

要完成的核心设计是：

1. 明确多人入口结构
2. 明确联机业务由哪个项目级子系统承接
3. 明确 UI 只调用业务层，不直接碰底层会话 API

如果这一步不先立起来，后面再多的在线细节都会越来越乱。

### 9.2 第二阶段：先跑通玩家自托管的在线闭环

这一步是最值得优先实现的 `MVP` 主线。

为什么先做这条线，而不是先冲 Dedicated Server？

因为它最符合当前项目的现实目标：

1. 成本低
2. 学习曲线更平滑
3. 最快能得到“打包后真实在线联机”的成果

这一步真正验证的是：

1. 用户初始化与在线权限
2. 创建会话
3. 搜索/加入会话
4. 地图切换
5. 多人进入现有玩法世界

### 9.3 第三阶段：把 Dedicated Server 基线补上

这一阶段不是为了立刻做大规模运营，而是为了把架构升级路径正式打开。

这一阶段最重要的不是玩家入口，而是工程层：

1. 增加 `Server Target`
2. 能产出服务器程序
3. 能独立启动
4. 客户端能连接它

这一步立住以后，后面才有资格继续谈“服务器列表”“直接连接”“云服务器演示”。

### 9.4 第四阶段：再把加入入口扩成多承载方式

也就是把当前的总入口 `加入游戏` 继续往下展开成：

1. 好友游戏
2. 房间列表
3. 服务器列表
4. 直接连接

这一步不应该抢在第二阶段前面。  
因为在闭环没跑通之前，细分入口只会增加分支复杂度。

## 第十章 为什么这个方案和当前项目是相容的

写设计方案最怕的一种情况，是方案听起来对，但一落到项目上就要把半个工程推翻。

我认为当前这个方案和 AegisOdyssey 是相容的，原因主要有下面几条。

### 10.1 它没有绕开项目现有的 CommonGame / CommonUser 基础

这很重要。  
因为这些模块本来就是为了承接用户、会话、UI、启动流这类产品级逻辑而存在的。

如果项目明明已经有 `CommonUser` / `CommonSessionSubsystem`，却还要重新造一整套平行系统，那只会增加维护成本。

### 10.2 它没有试图推翻现有的 GameMode / Experience 流

当前 `AAOGameMode` 和 `Experience` 系统，已经是项目很核心的一条世界初始化主链。

这个方案不要求你重写它，而是让多人会话的成功结果，最终落到这条主链上。  
这就保证了：

1. 世界初始化逻辑仍然统一
2. 玩家生成逻辑仍然统一
3. 多人对局和单人对局不会变成完全不同的两套世界规则入口

### 10.3 它尊重当前项目已经存在的服务端权威玩法思路

项目知识库里已经能看到很明确的趋势：

1. 服务端整理真相
2. 客户端消费同步结果
3. `OwnerOnly Session Snapshot`
4. 时间基准和进度真相建立在服务端

这说明当前项目并不是要从“纯单机思维”硬拐到多人，而是已经有一些多人玩法边界意识。

这个方案做的，是把这些已有边界放进一条真正的联机产品链里，而不是重新定义所有同步规则。

### 10.4 它适合学生项目先做出可信演示

这一点也不能忽视。  
方案再完整，如果第一步就要求高成本运营和复杂部署，那对当前项目阶段其实没有意义。

当前这套设计最大的优点是：

1. 先能做出打包后真实在线联机
2. 先能证明项目具备多人产品方向
3. 以后还能继续长到 Dedicated Server

这比“一开始就想象商业大服，但长期落不了地”更健康。

## 第十一章 关于 Server Target 和 Dedicated Server 的补充说明

这一轮讨论里，又补清楚了一个非常关键、但很容易被初学者误解的点：

**当前项目缺少的“Dedicated Server 目标”，本质上是构建层缺口，不是玩法逻辑层缺口。**

很多人第一次接触 Unreal 联机时，会把下面几件事混成一件事：

1. 编辑器里看到的 Dedicated Server 调试模式
2. 工程里的 `Server Target`
3. 真正可独立部署的 Dedicated Server 程序
4. 服务器本身承载的玩法逻辑

这几个概念实际上不是一回事。

### 11.1 当前项目现在到底缺什么

当前工程里已经存在：

1. `AegisOdyssey.Target.cs`
2. `AegisOdysseyEditor.Target.cs`

它们分别代表：

1. `Game` 目标
2. `Editor` 目标

但当前项目还没有：

1. `Server` 目标

所以当前项目能明确产出的，是正式客户端和编辑器开发目标；  
但它还不能明确产出一个**单独的服务器程序**。

这就是前面提到的“项目还没有正式进入服务器独立打包阶段”的真正含义。

### 11.2 什么叫服务器独立打包

所谓“服务器独立打包”，说白了就是：

**除了玩家客户端之外，项目还要能额外产出一份专门给服务器运行的程序。**

这个程序和玩家客户端不是同一个用途。

玩家客户端负责：

1. 画面
2. 输入
3. UI
4. 本地表现

独立服务器程序负责：

1. 维护世界真相
2. 接受客户端连接
3. 驱动服务端玩法规则
4. 同步状态给客户端

所以这里的重点不是“项目是不是全部做完了”，而是：

**这套工程能不能单独产出一份不依赖编辑器、专门承担服务器职责的程序。**

### 11.3 这里的 Server Target 本质上在写什么

`Server Target` 本身并不是在写房间系统、加入逻辑、同步逻辑或者玩家生成逻辑。

它本质上是在告诉 Unreal：

> 这套项目除了能构建成 `Game` 和 `Editor` 之外，还要能构建成 `Server`。

也就是说，`Server Target` 更像是一个**构建身份声明**。

它真正负责的是：

1. 标记这是 `Server` 类型目标
2. 指定这个目标要构建哪些项目模块
3. 让引擎按“服务器程序”的规则去编译和裁剪工程

所以要明确记住：

**`Server Target` 是构建入口，不是业务实现层。**

### 11.4 那服务器逻辑本身放在哪里

服务器逻辑本身并不写在 `Server Target` 里。

它本来就应该主要存在于项目当前的服务端世界主链中，比如：

1. `AAOGameMode`
2. `GameState`
3. `Experience`
4. 各种服务端权威玩法系统

换句话说，当前项目并不是“先有 Server Target，才会有服务端逻辑”。  
真实情况更接近：

**项目已经有一部分服务端逻辑了，只是还没有被正式产出成独立服务器程序。**

这也是为什么 Dedicated Server 设计，不应该推翻当前 `GameMode / Experience` 主链，而应该继续复用它。

### 11.5 编辑器里看到的 DS 和正式 Dedicated Server 有什么区别

这是当前最值得单独记住的一个区别。

开发阶段在编辑器里看到的 Dedicated Server，通常更接近：

1. PIE 下的服务器模拟
2. 本地开发环境里的调试服务器世界
3. 用来验证复制、RPC 和基本联机流程的测试形态

它解决的是：

1. 某个同步逻辑是不是成立
2. 某个 RPC 能不能打到服务端
3. 本地测试环境里多人流程能不能跑通

但它不等于真正的独立服务器程序。

真正由 `Server Target` 构建出来的 Dedicated Server，才更接近：

1. 不依赖编辑器运行
2. 可以单独启动
3. 可以部署到另一台机器
4. 可以被正式客户端连接

所以最简短的总结是：

**编辑器里的 DS 更像调试服务器形态，`Server Target` 产出的 DS 才是可独立部署的正式服务器程序。**

### 11.6 为什么这一步不能拖到项目做完才想

这件事非常重要，因为很多项目都会误以为：

“等游戏内容做完了，最后再顺手打一个服务器包就行。”

这通常是不对的。

更合理的理解应该是：

**一旦项目准备从‘编辑器内联机调试’走向‘正式客户端与正式服务器联调’，就应该尽早验证 Dedicated Server 基线。**

因为一旦真的按 `Server` 目标去构建，很多隐藏问题会马上暴露出来，比如：

1. 项目是否混入了 Editor-only 模块依赖
2. 某些系统是否默认假设本地一定有玩家和 UI
3. 某些初始化链路是否只能在编辑器里正常跑
4. 某些代码是否错误依赖了客户端表现层

这些问题越晚发现，返工成本越高。

### 11.7 当前项目已经能预见到的一个风险点

从当前工程配置来看，`AegisOdyssey.Build.cs` 里直接包含了 `UnrealEd` 依赖。

这在当前编辑器开发阶段未必立刻出问题，但一旦项目正式开始补 `Server Target`，这类依赖通常就是第一批要重点排查的对象。

原因不是它“写错了”，而是：

**Dedicated Server 不是编辑器，服务器构建通常不能继续带着 Editor 专属模块一起走。**

所以 `Server Target` 的价值，不只是多一个目标文件。  
它还会帮助项目把“哪些模块和代码其实只适合编辑器环境”这件事照出来。

### 11.8 这一轮关于 Dedicated Server 最该记住的结论

如果把这轮新增讨论压成几句话，当前最该记住的是：

1. 当前项目缺的首先是单独的 `Server Target`
2. `Server Target` 写的是构建身份，不是多人业务逻辑
3. 当前项目很多服务端逻辑其实已经部分存在于 `GameMode / Experience` 主链里
4. 编辑器里看到的 DS 调试形态，不等于正式独立服务器程序
5. Dedicated Server 基线不应该拖到项目做完才第一次验证

## 第十二章 这份设计方案当前真正给出的结论

如果把全文收成几个最关键的设计结论，那么当前可以明确记住下面这些。

### 11.1 结论一：当前项目不应该直接写成“联机功能”，而应该补一层项目级联机协调架构

也就是在现有 `CommonUser` / `CommonSession` 之上，新增 AegisOdyssey 自己的业务协调层。

### 11.2 结论二：首版联机目标应当优先是互联网下的玩家自托管闭环

这最符合当前预算、学习阶段和演示目标。

### 11.3 结论三：Dedicated Server 不是首版运营目标，但必须是架构预留方向

这意味着不能一开始就强压商业化运维，但也不能把工程结构设计死。

### 11.4 结论四：多人菜单应当只承载产品入口，不直接承担底层联机逻辑

UI 负责表现，项目级联机子系统负责业务协调，会话底层负责真正联网。

### 11.5 结论五：进入多人对局之后，应当继续复用现有 GameMode / Experience 世界主链

多人系统要做的是“把玩家送进去”，而不是“再造一套世界初始化框架”。

## 第十三章 这份设计方案的边界

最后再把边界说清楚。

这份文档当前回答的是：

1. 当前项目的多人系统应该怎么分层
2. 各层为什么这么分
3. 首版目标和长期路径怎么平衡
4. 当前项目的哪些现有结构可以直接利用

它还没有展开的是：

1. 具体类设计要拆成哪些文件
2. 菜单页逐页怎么实现
3. 会话参数对象最终怎么定字段
4. Dedicated Server 的构建与打包步骤
5. 后续实施计划怎么拆任务

这些内容应该进入下一阶段文档，而不是继续挤在这一份设计方案里。

换句话说，到这一步为止，我们已经不是在问：

**“联机到底是什么？”**

而是在回答：

**“对 AegisOdyssey 来说，这套联机系统应该以什么结构被设计出来。”**
