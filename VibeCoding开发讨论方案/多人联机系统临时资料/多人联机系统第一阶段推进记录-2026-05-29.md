# 多人联机系统第一阶段推进记录

更新时间：2026-05-29

---

## 第一章 这份记录在解决什么

前面的预研笔记和设计方案，已经把“为什么要做多人联机”和“当前项目应该怎么设计”收得比较完整了。

这份文档不再重复讲需求背景，而是专门记录另一件事：

**如果现在真的准备按当前方向开始推进，那么第一阶段最重要的动作到底是什么。**

这份文档的定位不是正式实施计划，也不是精确到类和函数的任务拆解。  
它更像是一份“第一阶段行动主线记录”，用于防止后面讨论时又重新回到散乱状态。

换句话说，这份文件记录的是：

1. 现在最先该做什么
2. 为什么先做这个
3. 哪些东西故意先不做

---

## 第二章 当前最重要的认识：不是立刻把整套多人系统做完

这一轮讨论里最重要的一点，不是某个技术细节，而是推进顺序。

对当前项目来说，现在不应该把目标理解成：

1. 立刻完成正式上线级多人系统
2. 立刻把大厅、房间、Dedicated Server、在线服务、部署运维一次做完
3. 立刻把所有多人玩法都完全打磨好

更合理的理解应该是：

**先开一条最小联机验证支线，先验证工程基线和最基本的多人闭环。**

这意味着第一阶段真正要解决的，不是“功能有多少”，而是：

1. 工程能不能产出正式客户端
2. 工程能不能产出正式 Dedicated Server
3. 客户端能不能连 Dedicated Server
4. 两个玩家能不能进入同一张测试地图

---

## 第三章 第一阶段的最小验证目标应该怎么定

当前最值得先写死的一句话是：

**我要让 AegisOdyssey 产出一个正式客户端和一个正式 DS，客户端能连上 DS，两名玩家能进入同一张测试地图。**

这句话非常重要，因为它会直接约束第一阶段的工作范围。

### 3.1 这个目标为什么要故意定得这么小

因为如果第一阶段目标写成：

1. 完整多人菜单
2. 房间系统
3. 好友邀请
4. 服务器列表
5. 云服务器部署
6. 多张地图联机
7. 各种玩法完全适配

那项目很快就会失控。

当前阶段最合理的做法，是先用一个很小但很硬的目标，验证这条路线到底能不能走通。

### 3.2 这个目标真正验证的是什么

它验证的不是“项目内容做完了没有”，而是：

1. 工程结构能不能进入 Dedicated Server 阶段
2. 项目能不能脱离编辑器联机模拟
3. 现有世界主链能不能承接正式多人进入流程
4. 当前联机架构是不是至少具备最小可行性

---

## 第四章 第一阶段最先该动的，不是大厅 UI，而是工程层

这是当前最需要单独记住的一点。

很多人做联机时，很容易先去做：

1. 主界面按钮
2. 创建房间页面
3. 加入房间页面
4. 房间列表 UI

但对当前项目来说，这些都不应该排在最前面。

现在最先该动的是工程层，尤其是下面三件事。

### 4.1 第一件事：补 `Server Target`

当前工程已经有：

1. `AegisOdyssey.Target.cs`
2. `AegisOdysseyEditor.Target.cs`

但还没有：

1. `AegisOdysseyServer.Target.cs`

所以第一阶段最基础的动作，就是把项目正式带入“可以构建 Dedicated Server 程序”的状态。

这件事的意义不是“多一个文件”，而是：

1. 项目开始正式拥有服务器构建目标
2. 项目能开始验证 Dedicated Server 是否能独立构建
3. 后面所有真正的 DS 联调才有工程入口

### 4.2 第二件事：排查 `Server` 构建不该带的依赖

当前 `AegisOdyssey.Build.cs` 里已经能看到一个很值得警惕的点：

1. 直接包含了 `UnrealEd`

这种依赖在编辑器开发阶段不一定立刻有问题，但一旦开始构建 Dedicated Server，通常就是第一批需要重点排查的对象。

这一阶段真正要明确的是：

1. 哪些模块只适合 Editor
2. 哪些代码路径默认依赖编辑器环境
3. 哪些内容在 Server 构建下需要隔离

也就是说，`Server Target` 一旦补上，就不只是“生成新程序”，它还会顺便照出工程里的 Editor-only 污染。

### 4.3 第三件事：选定一张最小多人测试地图

第一阶段不应该拿最复杂、最重、最容易耦合各种玩法的地图来做 Dedicated Server 初测。

更合理的做法是先定一张最小多人测试地图，它至少能承接：

1. 进入世界
2. 玩家生成
3. 基础移动
4. 至少一条关键玩法链

这张图的目标不是“代表项目最终内容规模”，而是“最低成本验证联机主链”。

## 第五章 Dedicated Server 的第一轮验证，应该先在本地完成

这一点也很关键。

当前阶段完全不需要一上来就租云服务器，也不需要先搭复杂部署流程。

更合理的顺序应该是：

1. 在本机构建出 `Server` 程序
2. 在本机启动 Dedicated Server
3. 在本机或另一台电脑启动客户端
4. 客户端连接到这个 DS
5. 验证两个玩家能不能进入同一张测试地图

### 5.1 为什么先本地做这轮验证

因为这轮验证要解决的是工程事实问题，而不是部署问题。

它优先回答的是：

1. DS 能不能独立启动
2. 客户端能不能连
3. `GameMode / Experience` 主链在 DS 下能不能跑
4. 项目是否真的脱离了编辑器内模拟

如果这一轮在本地都没跑通，提前上云服务器只会把问题变得更难定位。

### 5.2 这一轮验证最容易暴露什么

它最容易暴露的是下面这类问题：

1. 工程不能正确构建 DS
2. 某些依赖不允许进入 Server 构建
3. 某些系统默认世界里一定有本地玩家和 UI
4. 某些初始化链路只能在编辑器里正常工作
5. 客户端虽然能启动，但连不上独立 DS

所以本地 DS 验证不是形式动作，而是正式多人开发的第一道真实门槛。

## 第六章 当前阶段要先把“进入一局”的链路跑通，而不是先把菜单包装完

这也是这轮讨论里特别重要的一个判断。

多人入口、多人菜单当然要做，但它们不应该抢在联机主链本身前面。

对当前项目来说，更合理的顺序是：

1. 先找到一条最简方式触发进服
2. 先让建局、进局、进图链路成立
3. 再把它包装成正式的 `创建游戏 / 加入游戏` 菜单入口

这背后的原因很简单。

如果 UI 先做得很完整，但底层链路还没跑通，那么后面：

1. 页面要反复改
2. 状态管理会反复推翻
3. 失败路径会非常混乱

所以当前最该记住的一句话是：

**先有可运行链路，再有正式菜单入口。**

## 第七章 项目层要尽快补一层“联机协调子系统”

这一步不一定是构建 DS 前的第一动作，但它很快就会成为必须项。

原因是：

多人系统的业务逻辑，不适合直接散在 Widget 里，也不适合直接塞进 `GameMode`。

### 7.1 为什么不该直接写在 Widget 里

因为 Widget 更适合承担：

1. 显示
2. 输入响应
3. 页面切换

它不适合直接承担：

1. 登录判断
2. 会话创建
3. 搜索状态持有
4. 当前多人模式状态管理
5. 失败重试和错误提示协调

如果把这些都写在 Widget 里，后面入口一多，逻辑会非常散。

### 7.2 为什么也不该直接写在 `GameMode` 里

因为 `GameMode` 更适合管理“进入对局之后的服务端世界逻辑”，而不是“进入对局之前的产品入口逻辑”。

联机菜单、搜索结果、建局参数、当前选择的加入方式，这些都属于：

1. 客户端入口层
2. 跨地图状态
3. `GameInstance` 生命周期

所以它们更适合被挂在项目级 `GameInstanceSubsystem` 上。

### 7.3 当前项目更合适的方向是什么

当前项目已经有：

1. `UAOGameInstance`
2. `UAOGameInstanceSubsystem`

这说明项目本来就接受“跨关卡、偏全局协调逻辑由 `GameInstanceSubsystem` 承载”的模式。

所以多人联机这块，后面最自然的做法应该是：

**新增一个专门的多人联机子系统，用来承接项目级联机业务协调。**

## 第八章 底层联机能力应当优先复用现有 CommonUser / CommonSession

当前项目不是零基础，所以这部分必须单独记住。

后面真正开始做联机业务时，不应该自己从零手搓一套新的底层会话系统。

当前更合理的方向是：

1. 项目层新增 AegisOdyssey 自己的联机协调层
2. 底层用户初始化、登录、建局、搜局、入局优先复用现有 `CommonUser` / `CommonSession`

### 8.1 为什么这点重要

因为当前项目已经启用了：

1. `CommonGame`
2. `CommonUser`
3. `OnlineFramework`

而且 `CommonSessionSubsystem` 已经具备很核心的基础能力：

1. 创建 Host 请求
2. 创建 Search 请求
3. Host Session
4. Find Sessions
5. Join Session
6. `ServerTravel` / `ClientTravel` 相关承接

所以当前设计的正确方向，不是绕开它们，而是把它们组织起来。

### 8.2 项目层和底层各自应该干什么

这里最好先把边界记清楚。

项目层联机子系统负责：

1. 当前多人模式状态
2. 当前建局参数
3. 当前搜索结果
4. 菜单状态
5. 错误提示协调

底层 `CommonUser / CommonSession` 负责：

1. 在线权限
2. 用户初始化
3. 会话创建
4. 会话搜索
5. 会话加入
6. 旅行到游戏世界

这两个层次不能再写混。

## 第九章 首版范围一定要继续砍小

这部分虽然前面的文档已经反复讲过，但在“第一阶段推进记录”里仍然值得再单独写一次。

当前最合理的首版范围，应该只剩下下面这一条最小闭环：

1. 启动客户端
2. 进入多人入口
3. 创建一局
4. 另一名玩家加入
5. 一起进入测试地图
6. 完成基础游玩
7. 正常退出或断开返回

### 9.1 这一步故意先不做什么

当前阶段可以明确先不做：

1. 复杂大厅
2. 服务器浏览器
3. 好友系统全套
4. 匹配
5. 云服务器部署自动化
6. 多区域运营能力
7. 所有玩法一次性全部适配

这些东西以后都可以做，但不应该挤进第一阶段。

### 9.2 当前阶段最重要的不是“做多”，而是“做硬”

也就是说，第一阶段最该追求的不是页面数量多、功能标签多，而是：

1. DS 构建是真的
2. 客户端连接是真的
3. 两人进同一局是真的
4. 这条链路脱离编辑器仍然成立

---

## 第十章 如果把第一阶段收成一周级别的主线，最先该做哪几件事

如果把当前讨论压成最直接的行动主线，那么第一阶段最先要盯的，应该就是这四件事：

1. 补 `Server Target`
2. 清理或隔离阻碍 `Server` 构建的 Editor 依赖
3. 选定一张最小多人测试地图和一条最小玩法链
4. 验证 `DS 启动 + 客户端连接 + 两人进图`

这四件事之所以重要，是因为它们共同回答了一个问题：

**AegisOdyssey 是否已经具备进入正式多人工程阶段的最低条件。**

如果这四件事没有先立住，后面继续做 `创建游戏 / 加入游戏` 菜单，或者继续谈服务器列表、云服务器、Dedicated Server 扩展，都还是飘的。

---

## 第十一章 这份推进记录当前真正记住什么

如果把这份文件压缩成几条最值得以后快速回看的结论，那么当前最重要的是：

1. 现在不是立刻做完整多人系统，而是先开最小联机验证支线
2. 第一阶段最小目标是“正式客户端 + 正式 DS + 两名玩家进同一张测试地图”
3. 当前最先该动的是工程层，而不是大厅 UI
4. Dedicated Server 的第一轮验证应当先在本地完成，而不是先上云
5. 先把“进入一局”的链路跑通，再把它包装成正式多人菜单
6. 项目层需要一层专门的联机协调子系统
7. 底层优先复用现有 `CommonUser / CommonSession`
8. 首版范围必须继续砍小，先只做最小闭环

这份文档先收口到这里。  
它的作用不是代替后面的正式实施计划，而是给后面继续拆实施方案时，提供一条不容易跑偏的第一阶段主线。
