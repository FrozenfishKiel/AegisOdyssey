## 第一章 这份笔记现在要解决什么

这份笔记先不进入正式方案阶段，也不直接拆实施计划。

它现在只做一件事：把“我们刚刚聊清楚了什么”先收下来，避免后面再从一片空白重新开聊。

当前用户侧的真实诉求，不是“怎么在编辑器里模拟两个玩家”，也不是“怎么先随便做个局域网试玩”，而是：

**想理解 Unreal 里正式上线的多人联机到底是怎么回事，以及我们这个项目如果以后真要做这件事，应该从哪条路开始。**

这个目标很重要，因为它决定了当前讨论的重心，不应该放在零散 API、某个蓝图节点，或者某个 RPC 写法上。  
现在更需要先搭主干，把几件最容易混淆的事情拆开。

## 第二章 先把几件最容易混淆的事拆开

我们这次先明确了一个前提：**编辑器里的多人模拟，不等于正式联机。**

这句话看起来像常识，但如果一开始不把它说死，后面很容易一边聊专用服务器，一边脑子里想的还是 PIE 双开。

### 2.1 编辑器双开和正式联机不是一回事

在 Unreal 里，编辑器里开两个玩家、开多个窗口、用 PIE 模拟 Server / Client，这些都只是开发调试手段。

它解决的是下面这类问题：

1. 某个复制变量会不会同步
2. 某个 RPC 能不能发到服务端
3. 某个 UI 在客户端视角下会不会出错
4. 某条玩法链在本地多实例环境里能不能先跑通

但它不解决正式上线会遇到的那些问题：

1. 真正的服务器进程怎么独立运行
2. 客户端怎么在编辑器外连进来
3. 房间、会话、登录、匹配挂在哪个在线服务上
4. 服务器怎么部署、更新、监控和维护

所以这次已经先把一个误区排除了：  
**我们后面要讨论的，不是“PIE 怎么开成两个人”，而是“正式上线多人在线产品怎么搭”。**

### 2.2 局域网联机和正式上线联机也不是一回事

局域网联机已经比编辑器模拟更接近真实网络环境了，但它仍然不是最终目标。

局域网联机通常只是说明：

1. 两台机器之间真的通过网络在通信
2. 基本的 Host / Join 流程能跑
3. 当前项目的复制、同步、切图、会话流程已经能脱离单机本地调试

但它通常还不意味着：

1. 你已经有正式可用的在线平台
2. 你已经解决了公网连通、登录、匹配、邀请
3. 你已经具备正式上线后的部署和运维能力

所以局域网联机更像是一个中间台阶。  
它有价值，但它不是终局。

### 2.3 真正要讨论的是“正式上线联机”

我们这次真正关心的，是玩家下载安装到正式版本之后，怎样通过一套稳定的联网产品链进入多人游戏。

这件事在 Unreal 里通常不再只是“某个玩法系统要不要复制”，而是下面几层东西一起成立：

1. 有稳定的服务器架构
2. 有正式的会话和连接入口
3. 有服务端权威的玩法同步边界
4. 有部署、版本、运维和异常恢复能力

也就是说，**正式上线联机是产品级问题，不是单点代码技巧问题。**

## 第三章 这次先立住的主判断

这次最重要的收口，不是某个技术细节，而是一个方向判断：

**如果目标是正式上线，多人联机的主路线默认应该优先看 Dedicated Server，而不是把 Listen Server 或局域网方案当终局。**

这里先不展开平台选型，只把主干记住。

### 3.1 Listen Server 能做什么

Listen Server 的意思，是某个玩家客户端自己同时充当服务器。

这种模式的优点是：

1. 开发早期很方便
2. 小范围测试很快
3. 没有专门服务器也能先把多人玩法跑起来

但它的问题也很明显：

1. 主机玩家既是玩家又是服务器，天然有权威和体验不对称
2. 主机一退房，整局就跟着结束
3. 真正上线后，稳定性、可控性、运维性都很差

所以 Listen Server 更像是开发阶段或某些轻量产品的选择，不太适合拿来当我们现在这个项目的默认正式目标。

### 3.2 Dedicated Server 的意思是什么

Dedicated Server 的核心不是“多开一个程序”这么简单。

它真正代表的是：

1. 服务器进程独立存在
2. 服务器不承担本地玩家表现层
3. 游戏真相由服务端统一掌握
4. 客户端只负责输入、表现和消费同步结果

这条路更麻烦，但它更接近真正上线后的多人游戏结构。

也正因为如此，如果后面真的要做正式联机，很多现在在单机里还能“差不多”的写法，到 Dedicated Server 环境里就会暴露问题。

## 第四章 我们当前项目不是完全没联机基础，但离正式上线还差很远

这次聊下来，一个很关键的判断是：

**AegisOdyssey 现在不是完全没有联机土壤，但它目前拥有的主要是玩法层的联机思维，还不是完整的正式上线联机架构。**

这点必须说清楚，因为它决定了后面到底是“从零开始”，还是“已有基础上继续往上搭”。

### 4.1 当前项目已经有的基础

从工程结构看，项目已经启用了不少和联机产品有关的公共模块与插件，包括：

1. `OnlineFramework`
2. `CommonGame`
3. `CommonUI`
4. `CommonUser`
5. `Networking`
6. `NetCore`

相关入口可以先记住：

- `AegisOdyssey.uproject`
- `Source/AegisOdyssey/AegisOdyssey.Build.cs`
- `Plugins/CommonUser/Source/CommonUser/Private/CommonSessionSubsystem.cpp`

这说明项目并不是完全没有准备过联机相关基础设施。

更重要的是，项目当前很多玩法系统已经明显不是“纯单机脑回路”了。

比如交互系统知识库里已经明确把交互主链收成了：

`Interact Ability -> 交互对象 -> SessionComponent -> SessionModel -> 对象状态 / 库存 -> OwnerOnly Session Snapshot -> UI`

这其实已经是很明确的联机思维了。  
它背后的核心观念不是“UI 自己读对象”，而是“服务端真相层整理快照，再按权限给客户端消费”。

这类边界在正式多人联机里非常重要。

再比如制造系统最近已经实际踩到了 `Dedicated Server` 下客户端时间基准错位的问题，知识库里也已经把结论收出来了：

**客户端可以本地刷新显示，但正式进度计算必须建立在服务端真相和同一套服务端时间基准上。**

这说明项目虽然还没搭完整的联机产品层，但玩法层已经开始进入真正的多人同步语境。

### 4.2 当前还缺的关键东西

虽然上面这些基础都很有价值，但它们还不等于“已经具备正式上线联机”。

当前明确还缺的关键层，至少包括下面这些：

#### 第一，工程层还没有正式的 Server Target

目前工程里能看到的是：

1. `AegisOdyssey.Target.cs`
2. `AegisOdysseyEditor.Target.cs`

也就是说，现在只有 `Game` 和 `Editor`，还没有单独的 `Server` 构建目标。

这件事看起来只是少了一个文件，但它背后的含义其实很大。  
没有单独的 `Server Target`，就说明项目还没真正进入“我要单独产出服务器程序”的阶段。

#### 第二，在线平台后端还没有定下来

当前模块里虽然已经挂着 `CommonUser` 和 `CommonSessionSubsystem` 这一类基础能力，但项目自己的 `Build.cs` 里，`OnlineSubsystem` 还是注释状态。

这说明一件很现实的事：

**现在还没正式选定后面要挂哪一套在线服务。**

这里以后会直接影响：

1. 登录方式
2. 会话创建和搜索方式
3. 平台能力接法
4. 邀请、好友、Presence
5. 最终发行平台上的接线方式

#### 第三，部署和运维层几乎还没开始

这次讨论里其实还没进入下面这些问题：

1. 服务器部署到哪里
2. 一台服开多少局
3. 怎样发版和更新
4. 崩服怎么恢复
5. 客户端版本不一致怎么拒绝连接
6. 日志、监控、告警怎么做

这些东西不写玩法代码的时候很容易被忽略，但如果目标真的是“正式上线多人游戏”，它们迟早都要补上。

## 第五章 我们这次讨论出来的更合理主线

这次已经先把后续思路收成了一条比较稳的主线。

不是先去问“某个房间按钮怎么写”，而是先按下面这个顺序理解：

`正式上线联机 = Dedicated Server 架构 + Online Session / 平台后端 + 服务端权威玩法同步 + 部署运维`

这四层里，我们当前项目大致可以这样看：

1. **玩法同步层已经有一些基础**
2. **Dedicated Server 工程基线还没真正立起来**
3. **在线平台与会话后端还没正式定路线**
4. **部署运维层还没有开始系统规划**

这意味着后面的工作顺序也不该乱。

## 第六章 如果以后进入正式方案阶段，建议怎么拆

这部分还不是实施计划，只是把后续最自然的拆法先记下来。

### 6.1 第一阶段：先立 Dedicated Server 基线

这一步的目标不是上线，而是让项目脱离“编辑器双开”和“本地 Listen Server 调试”的舒适区。

这一步要解决的是真正的工程地基问题：

1. 服务器程序能不能单独构建
2. 服务器进程能不能独立启动
3. 客户端能不能在编辑器外连接它
4. 切图、进入游戏、断开连接这些基础流程能不能稳定跑

如果这一步都没立住，后面去做大厅、匹配、邀请，只会越来越飘。

### 6.2 第二阶段：再定正式会话层

Dedicated Server 基线立住以后，才轮到正式会话层。

这一步才开始真正回答：

1. 玩家怎么登录
2. 怎么建房
3. 怎么搜房
4. 怎么加入
5. 怎么切图
6. 怎么返回大厅

这时就必须正面决定到底走哪种在线平台路线。

### 6.3 第三阶段：再补部署和运维层

很多人会习惯先写一堆会话逻辑，最后才想服务器怎么部署。

但如果目标真是正式上线，这一步不能永远往后拖。  
因为 Dedicated Server 一旦不是只在本机跑，部署方式就会反过来影响很多产品设计和工程边界。

### 6.4 第四阶段：最后再做产品级联机功能

比如：

1. 好友邀请
2. 断线重连
3. 跨区
4. 匹配
5. 观战
6. 房间迁移

这些都很重要，但它们不应该排在服务器基线前面。

## 第七章 当前最值得记住的几个判断

这部分单独列出来，是为了以后开新会话时能快速回忆起我们这次到底先收住了什么。

### 7.1 现在不要把问题想成“会不会写 RPC”

这次已经明确了，真正难的地方通常不是“某个 RPC 会不会发”，而是：

1. 哪些是服务端真相
2. 哪些状态应该复制
3. 哪些状态只是本地显示
4. 客户端现在看到的东西，到底是不是正式会话里承认的那份事实源

这一点其实和项目现有知识库是统一的。

### 7.2 当前项目并不是纯单机项目

虽然还没到正式上线联机阶段，但项目很多玩法链已经按联机思维在收：

1. 服务端权威
2. 状态复制
3. `OwnerOnly` 会话快照
4. 客户端 UI 消费快照而不是反过来拼真相

这说明后面不是从零推翻，而是继续把架构往上搭。

### 7.3 正式上线联机的第一站不是大厅 UI

后面如果真的开始做，不应该一上来先做：

1. 建房界面
2. 搜房列表
3. 房间按钮
4. 大厅表现层

更稳的顺序是：

1. 先把 `Dedicated Server` 工程基线立住
2. 再把会话层接上
3. 再把大厅和产品层表现接上

## 第八章 当前还没有定下来的问题

这次讨论主要是在立主干，所以还有几件关键事没有决定。

后面如果要进入正式方案阶段，这几件事需要尽快明确。

### 8.1 首发平台到底是什么

这件事影响非常大。

如果首发明确是 Steam 上的 PC-only 联机，那后面很多在线接线、会话能力和产品范围都会更容易收敛。

如果一开始就希望保留更强的平台无关性，那路线就会不一样。

### 8.2 以后是自己运维服务器，还是尽量借平台能力

这件事会直接影响：

1. 服务器部署方式
2. 会话和匹配怎么挂
3. 账号和登录怎么做
4. 未来上线成本和维护复杂度

### 8.3 首发版本的联机 MVP 到底想做多大

现在只知道目标是“正式上线联机”，但还没收窄到首发最小范围。

如果这一步不尽快收，后面很容易把：

1. Dedicated Server
2. 会话系统
3. 好友邀请
4. 匹配
5. 跨区
6. 断线重连
7. 一堆大厅表现

一次性塞进第一版，最后整个项目会失控。

## 第九章 新补充的关键澄清：当前真正关心的不是 LAN 还是公网，而是谁来承载服务器

这一轮讨论里，用户又把一个很容易说混的话题重新说清楚了。

前面我们一度把重点放在了“局域网联机”和“正式在线联机”的区别上，这个区分本身没有错，但它还不是用户当前最想确认的主问题。

用户现在真正关心的重点，不是“网络连接范围怎么分”，而是：

**这套多人游戏以后更像《饥荒联机版》或者《我的世界》那样，既允许玩家自己开服，也允许玩家去连接一台单独部署出来的服务器。**

也就是说，当前最值得继续往下讲的主轴，不是单纯区分：

1. `LAN`
2. `Online`

而是区分：

1. **玩家自己承载这一局服务器**
2. **一台独立机器承载这一局服务器**

这两个概念，才更贴近用户脑子里真正想表达的“房主自己做服务器”和“买一台云服务器开服”。

### 9.1 这里真正要拆开的，其实是“网络范围”和“服务器承载方式”

前面已经确认过，局域网和互联网不是一回事。

但这条线只是在回答：**玩家之间隔着什么网络。**

它回答的是：

1. 同一局里的玩家是不是在同一个本地网络里
2. 玩家之间是本地互联，还是要跨公网连接

而用户现在更关心的另一条线是在回答：

1. 这一局游戏到底由谁来当服务器
2. 这个服务器是不是某个玩家自己开的
3. 这个服务器是不是一台单独跑在别处的机器

所以后面继续讨论时，不能再把“局域网”和“Dedicated Server”当成一组平级选项去比较。

更准确的理解应该是：  
**“LAN / Internet” 是网络范围维度，`Listen Server / Dedicated Server` 是服务器承载方式维度。**

### 9.2 用户当前真正想要的，是像《饥荒联机版》或《我的世界》那样的“多承载方式”

把用户这轮表达翻成更准确的产品语言，大致可以写成：

> 我想做的多人模式，更接近《饥荒联机版》或者《我的世界》这类结构。  
> 我关心的重点不是局域网和公网本身，而是同一套游戏能不能既支持玩家自己开一局服务器，也支持单独部署一台服务器供其他玩家进入。  
> 换句话说，我想讨论的是多人游戏的服务器承载方式，而不只是网络连接方式。

这段话很重要，因为它把后面的问题范围收窄了。

以后再提“创建房间”“加入房间”“加入服务器”时，首先要先问的就不再是：

1. 这是局域网还是互联网

而是：

1. 这一局是不是由玩家主机承载
2. 这一局是不是由独立服务器承载

### 9.3 如果按这个主轴去理解，当前最自然的两种形态其实是

#### 第一种：玩家自托管

这条线更接近：

1. 玩家自己点“创建世界”或“创建房间”
2. 这个玩家的游戏进程同时承担服务器职责
3. 朋友通过联机入口加入这位玩家开的那一局

这本质上更接近 `Listen Server` 语义，只是产品上未必一定直接叫这个名字。

对于很多生存建造类游戏来说，这种模式是非常常见的。  
它的吸引力在于门槛低，玩家自己就能马上开一局。

#### 第二种：独立服务器托管

这条线更接近：

1. 单独有一个服务器进程在运行
2. 这个服务器可以跑在玩家自己电脑、朋友电脑、实验室机器，或者云服务器上
3. 玩家只是去搜索、选择并加入它

这本质上才是更标准的 `Dedicated Server` 语义。

它的关键不是“服务器一定要很贵”，而是：  
**服务器和玩家客户端是分离的。**

所以即使用户现在没有预算去长期运营大规模官方服务器，也不妨碍项目在工程结构上支持“独立服务器开服”这件事。

### 9.4 这也解释了为什么《饥荒联机版》或《我的世界》的讨论里，“房间”和“服务器”常常会混在一起

这类游戏很容易让初学者产生一个错觉：  
好像大家都在说“联机”，其实说的是同一件事。

但实际上它们经常把两套东西同时做进产品里：

1. 玩家可以自己开一局，朋友直接加入
2. 玩家也可以去连接一台常驻运行的独立服务器

从玩家视角看，这两件事都叫“进入多人游戏”。  
但从工程视角看，它们背后的服务器承载方式不一样。

这正是当前讨论里最值得记住的新澄清。  
**用户现在最关心的，并不是“联机有没有局域网模式”，而是“这个项目以后能不能同时支持玩家自托管和独立服务器托管”。**

## 第十章 这一轮先收口到哪里

在这一轮新的讨论里，关于项目上线形态和多人游玩方式，其实又进一步收出了一个更贴近现实的阶段性结论。

### 10.1 当前版本的项目目标，可以先这样理解

如果把这轮讨论压缩成一句更完整的话，那么当前项目想推进出来的多人联机目标，可以先理解成：

**AegisOdyssey 未来希望成为一个发布在 Steam 上、以互联网联机为主、支持玩家自托管并预留独立服务器托管升级路径的多人游戏。**

这里面有几个关键词已经比较清楚了。

第一，首发语境是 `Steam PC`。  
这意味着我们现在讨论的不是主机跨平台联机，也不是先做一个完全平台无关的超大范围联机底座，而是先围绕 Steam 上的 PC 联机玩家场景去理解问题。

第二，主场景是 **互联网联机**。  
局域网模式依然有价值，但它更适合开发测试、线下演示、同网环境体验。真正面向大多数玩家时，核心场景仍然是不同网络下的联机。

第三，产品形态希望同时容纳两种服务器承载方式：

1. 玩家自己开一局，朋友加入
2. 单独部署一个服务器，玩家去连接它

这正是前面讨论《饥荒联机版》和《我的世界》时真正收出来的重点。

### 10.2 当前阶段的现实约束，也已经很明确

用户当前是学生身份，预算有限，不适合一开始就去承担高成本的大规模官方服务器运营。

这意味着项目首版的目标，不应该设成：

1. 一上来就做大型官方 Dedicated Server 集群
2. 一上来就做复杂的运营、扩容、跨区和高可用体系
3. 一上来就把商业化产品后期那一整套运维压力全背上

更合理的现实目标应该是：

1. 先把多人游戏完整链路做通
2. 先让多人入口、建局、入局、进图、游玩、退出这一整套流程成立
3. 先采用低成本但可演示、可验证的承载方式
4. 工程上保留以后升级到独立服务器和云服务器托管的空间

### 10.3 这里提到的 MVP 是什么意思

`MVP` 是 `Minimum Viable Product` 的缩写，常见中文说法是：  
**最小可行版本**。

它的意思不是“随便做个残缺版”，而是：

**先做出一个范围尽量小、但核心流程真正闭环、能够被验证的第一版。**

放到当前这个多人项目语境里，`联机 MVP` 真正关心的就不是“功能是不是堆得很多”，而是：

1. 玩家能不能从主界面进入多人模式
2. 能不能创建一局或进入一局
3. 能不能稳定进入游戏并完成基本游玩
4. 断开、退出、返回这些基础路径是不是成立

也就是说，`MVP` 的重点是 **完整性**，不是 **大而全**。

### 10.4 所以这一轮调研真正得出的结论是什么

如果只看这一轮新增讨论，那么当前最值得记住的阶段性结论可以收成下面这几条：

1. 项目多人联机的目标场景已经明确偏向 `Steam PC` 上的互联网联机
2. 局域网不是主目标，但仍然可以作为补充模式保留
3. 用户真正关心的不是网络范围本身，而是服务器由谁承载
4. 项目长期形态应当允许“玩家自托管”和“独立服务器托管”两种方式并存
5. 首发阶段不追求高成本官方服运营，而追求低成本但流程完整的联机 `MVP`

这部分结论非常重要，因为它已经开始把“想做联机”往“想做哪一种产品形态的联机”收窄了。

## 第十一章 联机 MVP 的玩家入口可以先怎么预写

这部分还不是正式 UI 设计稿，也不是正式交互文档。  
它现在的作用更像是：**先把后面一定会用到的玩家入口主干语言写出来。**

这样做的好处是，等后面真的开始搭多人流程、做菜单、做页面时，不需要从零再想：

1. 主界面到底怎么分
2. 多人模式下先给玩家看什么
3. 哪些按钮是首版必须有的
4. 哪些入口应该故意先不做

### 11.1 主界面第一层先不要写得太花，先把分流做清楚

对当前这个项目来说，主界面第一层最自然的结构，仍然应该是：

1. `单人游戏`
2. `多人游戏`
3. `设置`
4. `退出`

这里最重要的不是按钮数量，而是：  
**先让“单人”和“多人”在第一层就分开。**

因为后面一旦开始做联机，很多页面、流程、状态和返回路径都会和单人模式不一样。  
如果一开始主界面就不把它们分开，后面越做越容易缠在一起。

### 11.2 多人游戏页，首版建议先只承载“联机入口分流”

进入 `多人游戏` 后，当前阶段不建议一上来塞太多东西。

首版最稳的做法，是先把这个页面当成一个**联机入口分流页**，先回答玩家一句话：

**你这次是想自己开一局，还是去加入别人的一局。**

如果按这个思路去写，`多人游戏` 页当前最适合预写成下面这样：

1. `创建游戏`
2. `加入游戏`
3. `返回`

这三个入口非常朴素，但它们对 `MVP` 来说已经足够强了。

因为对首版联机闭环而言，最重要的不是分类很炫，而是：

1. 玩家能不能明确知道“我要自己开一局”
2. 玩家能不能明确知道“我要去加入别人的一局”
3. 玩家能不能顺利退出这条流程

### 11.3 “创建游戏”这个入口，当前更适合承载玩家自托管逻辑

在当前阶段，如果项目还没有正式铺开独立服务器列表和完整选服体系，那么 `创建游戏` 这个入口最自然的含义应该是：

**玩家自己创建一局，并由自己的游戏进程承载这局服务器。**

换句话说，这个入口在工程语义上更接近：

1. 玩家创建世界
2. 玩家成为房主
3. 其他玩家可以加入这局

这里先不用急着在界面上把它硬写成 `Listen Server`。  
对玩家来说，`创建游戏` 这种说法就够了。

后面如果要继续细分，这个页面内部还可以再长出更多选项，比如：

1. 世界名称
2. 是否公开
3. 最大玩家数
4. 是否允许好友加入
5. 地图 / 存档选择

但这些都是后续扩展，当前预研阶段只需要先记住：  
**首版的“创建游戏”入口，默认先服务于玩家自托管这一条线。**

### 11.4 “加入游戏”这个入口，后面其实可以容纳不止一种加入方式

`加入游戏` 这个入口比它表面看起来更重要。  
因为它后面其实可以同时容纳多种不同的承载方式，而不需要用户一开始就理解底层技术。

当前最容易想到的几种加入方式包括：

1. 加入好友正在进行的游戏
2. 通过房间列表加入玩家开的局
3. 通过服务器列表加入独立服务器
4. 通过 IP 或其他定向方式连接到一台服务器

但对 `MVP` 来说，这里不应该一上来全做。

更合理的预写方式是：  
先把 `加入游戏` 当成一个**可扩展的总入口**，后续根据首版实际范围再往里面拆。

也就是说，当前阶段我们先只需要记住：

**“加入游戏”是必需入口，但它内部的二级结构可以后定。**

### 11.5 如果后面要支持独立服务器托管，这个入口结构不会推翻重来

这也是现在提前预写入口的最大价值。

因为只要第一层先收成：

1. `创建游戏`
2. `加入游戏`

那么以后即使项目继续长出独立服务器托管模式，也不需要把整个主界面推翻。

后续最自然的扩展方式，通常会是下面这种：

`加入游戏` 下再继续拆出：

1. `好友游戏`
2. `房间列表`
3. `服务器列表`
4. `直接连接`

甚至 `创建游戏` 以后也可以继续长出：

1. `本地创建`
2. `创建专用服务器会话`
3. `加载已有存档`

但这些都应该建立在当前这个最小入口骨架之上，而不是一开始就把 UI 做得很重。

### 11.6 首版故意先不做哪些入口，反而更重要

在预写入口时，最容易犯的错不是“写少了”，而是“把未来所有可能都先写上去”。

对当前阶段来说，下面这些东西都可以明确先不进首版入口骨架：

1. 匹配
2. 跨区
3. 推荐服务器
4. 复杂筛选器
5. 大型大厅系统
6. 赛季或活动入口
7. 断线重连专页

这些功能以后都可能有价值，但它们不应该抢在 `创建游戏 / 加入游戏` 这对最基本入口前面。

### 11.7 所以当前最适合记住的入口草图是什么

如果把这一章压缩成一个当前最实用的文字草图，可以先记成：

`主界面`

1. 单人游戏
2. 多人游戏
3. 设置
4. 退出

`多人游戏`

1. 创建游戏
2. 加入游戏
3. 返回

这里的真实含义是：

1. `创建游戏` 首版默认服务于玩家自托管
2. `加入游戏` 保留为未来承载好友局、房间列表、服务器列表、直接连接等多种方式的总入口
3. 整个入口结构先追求流程清楚和可扩展，不追求一次把所有联机形态铺满

这套骨架虽然简单，但它已经足够支撑后面继续搭建联机 `MVP` 流程。

## 第十二章 这一轮先收口到哪里

这份笔记到这里先不继续往“正式方案”推进。

本轮真正完成的，不是技术实现，也不是方案定稿，而是先把认知主干搭起来了：

1. 编辑器模拟多人不等于正式联机
2. 局域网联机不等于正式上线联机
3. 如果目标是正式上线，主路线默认应该优先看 Dedicated Server
4. AegisOdyssey 当前已经有一些联机玩法基础，但还缺工程层、平台层和运维层
5. 后面最合理的推进顺序，是先立 Dedicated Server 基线，再谈正式会话，再谈上线部署和产品层功能

换句话说，这一轮最该记住的一句话是：

**我们现在不是在补“一个联机功能”，而是在为“把项目推进成正式上线的多人在线产品”搭认知地基。**
